# compact-plan: 鮮度低下した計画文書を圧縮する

計画文書は進捗・ピボット履歴・判断ログを追記し続けるうちに肥大化し、`/carryon` 時の cache を食う。決着済の経緯や、本文 + 判断ログの二重保持を畳む。

## 起動条件

- 「プランを圧縮して」「計画ダイエット」「plan をスリムに」「サイズ縮めて」
- 「/compact-plan」「/compact-plan <path>」

引数で path 指定があればそれを対象、なければ `docs/**/*.md` のうち最大のものを `wc -c` で 1 件選んで提案。

## やること

### 1. 計測

```bash
wc -l <path> && wc -c <path>
```

600 行 / 40 KB を超えていれば圧縮価値あり。下回るならユーザに「現状で十分小さい、本当に圧縮する?」と確認。

### 2. 構造把握

```bash
awk '/^##[^#]/ || /^### / {printf "%4d  %s\n", NR, $0}' <path>
```

節タイトル + 行番号一覧を取得。どの節がどの行範囲を占めているかを把握する。

### 3. 圧縮ルールで診断

各節を以下で分類し、削減候補行数を見積もる。**実物を Read して判断**する。

R1-R6 は行単位の削減、R7-R10 は **節の解体と書き換え**。前者だけだと -25〜30% で頭打ちになるので、50% 以上削りたいときは後者も併用する。

| ルール | 検知 | 置換 |
|---|---|---|
| **R1. 履歴重複の削除** | 同じ経緯が Context / 該当節冒頭 / 判断ログに 2〜3 重記述 | 判断ログを SoT、本文はリンクのみ |
| **R2. 決着済選択肢の畳み込み** | 「案 A vs 案 B」「trade-off 表」だが既に方針確定済 | 採用結論を 1〜2 行、選択肢列挙は削除 |
| **R3. 完了段階の status 圧縮** | `[x]` 済みの step が並ぶだけの節 | 「完了 (commit XXX)」+ 残 step のみ |
| **R4. 参照の commentary 削除** | 関連ファイル一覧の各 path 末尾に長い散文 | path のみ、必要なら 1〜3 語の prefix |
| **R5. 見積もり表の圧縮** | 予測値だけの多列表 | 結論の数字を各 1 段落散文に |
| **R6. 検証コマンドの統合** | 同じコマンド列を段階ごとに再掲 | 最終検証節に 1 回 verbatim、他は散文 |
| **R7. 未着手段階の anchor 化** | 未着手段階の詳細手順 / 内訳表 | 1 段落 anchor (対象 + 判断基準 + 撤退ラインのみ)。詳細は着手時に再取得 |
| **R8. 内訳表を合計行へ** | per-file / per-item の verbatim 表 | 合計行のみ。内訳は必要時に再取得 |
| **R9. 完了段階の解説段落圧縮** | 完了済の現状・採用根拠・改訂内容が多段落 | 1〜2 行 (commit hash + 結論 + 判断ログ参照) |
| **R10. 進行中節の熟考削除** | 「選択肢 A: … 選択肢 B: … default は A」 | default のみ記述 (選択肢は撤退ラインで代弁) |

### 4. 残す対象 (削らない判定リスト)

進行中タスクの anchor になっているものは保持する:

- **アクティブな段階の scope + Approach** (実行中の参照点)
- **撤退ライン / 判断基準** — 進行中に発火しうる分岐
- **仮説そのものと、それを否定する条件** — これが消えると計画が「やることリスト」に退化する
- **数字とその出所の対応** — 実測値・外挿・仮定のラベルと根拠ログへの参照は削らない (CLAUDE.md「計測の誠実性」)。数字だけ残してラベルを削るのは最悪の圧縮

「決着したロジック」は残し、「決着済の選択経緯」「未着手段階の予想 walkthrough」は畳む、と覚える。

### 5. ユーザに診断結果を提示 + 確認

```
## ブロート診断 (<path>、現在 N 行 / M KB)

| カテゴリ | 行数目安 | 内容 |
|---|---:|---|
| R1. 履歴重複 | ~XX | 該当節 + 重複先の節 |
| ... | | |
| 小計 | ~YY | (~ZZ%) |

残すもの: <アクティブ段階 / 撤退ライン / 数字の出所>

目標: N → ~K 行 (~Z% 削減)。進めて良い?
```

green light を待つ。「方針に修正があるか?」と聞いて redirect を許す。

### 6. 実行 (2-pass)

Edit ベースで節単位に削減。**1 つの大きな Edit ではなく、節ごとに小さな Edit を積む** — rollback と差分レビューが楽。

1st pass で R1-R6 を機械的に適用 (-25〜30% が typical)。`wc -l` で計測し、目標未達なら 2nd pass で R7-R10 を適用する。大きく書き換える節は 1 つずつ Read → 書き換え後の像を確認 → Edit。複数節を一度に書き換えると整合性が崩れる。

### 7. 検証 + コミット

```bash
wc -l <path> && git diff --stat <path>
```

before/after を比較し、autonomous commit + push。1st pass / 2nd pass は別 commit にする。

## 出力

ユーザーへの返答は短く: 削減後の行数 / 削減率、効いたカテゴリ 2〜3 行、残ったブロート 1 行。

## 気をつけること

- **凍結された段階番号 / 仮説名 / 撤退ライン slug は触らない** — 他文書から参照されている可能性。本文の説明だけ縮める
- **判断ログは決着済 entry を削除** — 採用確定 / 反証で却下 / commit 済の経緯は git が持つ。残すのは active な撤退ライン・判断軸・進行中の判断
- **`benchmarks/` は scope 外** — 計測レポートと生ログは圧縮対象にしない (再取得コストが高い)
- **`/carryon` が依存する `.claude/handoff.md` は touch しない**
