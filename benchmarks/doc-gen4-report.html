Benchmark report — 2026-08-09

doc-gen4 のどこで時間が消えるか

Mathlib に依存する Lean プロジェクトのドキュメント生成を計装して測った。 結果は明快で、コストの大半はドキュメントを作る仕事ではなく、 同じ依存ライブラリを何千回も読み直す仕事に消えている。

実ビルドでの姿

Mathlib 依存プロジェクトのドキュメント化では、8.9 億回の定数走査に対して 実際に処理されるのは 0.032% にすぎない。しかも「該当しない定数を素通りするだけ」の コスト (1,195 秒) が、本来の意味解析 (631 秒) の約 2 倍を占めていた。

さらに、計測して初めて見えた事実が 2 つある。

  • HTML 生成には増分性が一切ない。 DB も出力も無変更で 2 回続けて実行しても 46.25 秒 → 43.91 秒と変わらない。増分性はビルドシステムのマーカーファイル層にしかなく、 しかもそちらは逆に変更を取りこぼす。
  • 並列度はメモリで律速される。 8 並列時の RSS 合計は 21.7 GB (物理 16 GB) に達し、 スワップ 17.4 GB をほぼ使い切った。CPU コアを増やしても頭打ちになる。

計測したパイプライン

doc-gen4 は v4.31 で SQLite ベースに再設計されている。ビルドシステムの facet として次の順に走る。 赤いレールが、計測でボトルネックと判明した段。

bibPrepass
参考文献の前処理。1 回だけ。
genCore × 4
Init / Std / Lake / Lean の宣言を DB へ。最小ケースの wall 265 秒中 240 秒。
single × N
モジュール 1 個につき 1 プロセス。ここが 8,600 回繰り返される。
fromDb
DB から全対象モジュールの HTML と検索インデックスを生成。増分性なし。

コードを読んで分かった構造

計測前には見えない、コスト構造を決めている性質が 3 つあった。

  1. 環境の全定数を走査している。 1 モジュールを抽出する場合でも、 Mathlib 依存プロジェクトでは 49 万定数を舐めて数十件だけ処理する。
  2. タクティク収集がモジュールごとに全タクティクを列挙する。 単発では 10–40 ms に埋もれるが、バッチ化すると即座に最大項に浮上する。
  3. HTML 生成の後段はモジュール数に比例した固定コストを毎回払う。 検索インデックス生成・navbar 生成・backrefs 収集は、いずれもディスク上の 全モジュール分を毎回読み直している。

計測方法

doc-gen4 に計装を入れた。環境変数 DOCGEN_TIMING が設定されているときだけ、 各フェーズの実測時間を JSONL で追記する (無効時はゼロコスト)。 あわせて、複数モジュールを 1 プロセスで抽出する batch コマンドを追加した — これが方式 B の実証になる。

中心仮説の検証

1 プロセスにまとめると 23 倍速い

環境ロードは 85% から 28% に落ち、代わりにタクティク収集が最大項になった。

利得は 23 倍で頭打ちではない

新たに最大項になったタクティク収集は、モジュールごとに全タクティクを列挙している 二重ループが原因で、全体を 1 回列挙してモジュール別に振り分ければ消える。 つまりバッチ化した先に、まだ 3 分の 1 が残っている。

この構造は closure 分布から予測できる

ソースの import ヘッダを解析して、パッケージ内の推移的 closure サイズを求めた。 single 方式では、この closure 合計がそのまま「延べモジュールロード回数」になる。

レンダリングは犯人ではない

HTML 生成の実コストは DB からの読み出しであって、レンダリング (9.2%) ではない。 原因は、モジュールのメンバー一覧を取ったあと宣言ごとに引数・属性・宣言範囲・equation を 個別クエリで引く N+1 構造にある。テンプレートエンジンの高速化や別言語での書き直しは、 ここでは効果が薄い。

増分性がない

同じ生成を、DB も出力も一切変えずにもう一度実行した。

一方でビルドシステム側の増分性は正しく効いている。無変更なら doc-gen4 は 1 プロセスも起動しない。

増分性は両方向に壊れている

3 回目で HTML 生成が再実行されなかった点は、速度ではなく正しさの問題である。 マーカーファイルが空ファイルのため、内容が変わってもハッシュが変わらない。 変更が HTML に伝播しない可能性がある。 そして仮に正しく再実行されたとしても、それは全モジュールの再生成を意味する。 現行の増分性は「取りこぼすか、全部やり直すか」の二択になっている。

そのほかに分かったこと

並列度はメモリで律速される

プロセスのピーク RSS は closure に比例する (720 MB 〜 3.26 GB)。 ビルドシステムは既定で CPU 数だけプロセスを並列に走らせるため、Mathlib の深部で次の状態になった。

指標実測
同時実行プロセス8
その RSS 合計21.7 GB (物理 16 GB)
スワップ使用量16.2 GB / 17.4 GB

ビルドが進むにつれ 1 モジュールの環境ロードは 1.34 秒 → 6.88 秒へ悪化した。 ただし悪化の主因はスワップではない — 同区間で closure 平均も 1,042 → 4,602 と 4.4 倍に増えており、1 module-load あたりの単価は 1.27 ms → 1.45 ms (14% 増) にとどまる。 コストは closure に線形であり、メモリ圧はその上に 14% 乗るだけだった。

それでも実運用上の帰結は深刻で、並列度を半減させるとスワップが解放されないまま 処理レートが 34 → 7.3 モジュール/分まで落ちた。1 プロセスに環境を 1 つだけ持つ方式なら、 この制約自体が存在しない。

新設計への指針

効果の大きい順。

  1. 抽出は 1 プロセス 1 環境のバッチにする

    最大の一手。実測 23 倍。副次的にメモリ律速も消える。 → 中心仮説の検証

  2. 環境の全定数を走査しない

    走査コストが意味解析の約 2 倍。該当率 0.032%。対象モジュールの宣言だけを引くべきで、 これはバッチ化とは独立に効く。→ 抽出フェーズ

  3. 依存パッケージからは「宣言名 → モジュール → URL」だけを取る

    HTML 生成が実際に必要としているのはこの写像だけで、型も docstring も equation も要らない。 依存を外部参照にする構想はそのまま成立する。

  4. 中間表現の粒度はモジュール単位のブロブにする

    現行は宣言ごとに行を分割したため、レンダリング時に N+1 クエリで再構築しており、 そこに生成 CPU の 66–78% が消えている。読みも書きもモジュール単位なら、 モジュール 1 個 = 1 ブロブ + 索引が正しい粒度。

  5. 出力側の増分性を独立に設計する

    モジュール単位の内容ハッシュを持ち、変わったページだけ書き直す。 現行はキャッシュ無効化とページ再生成を 1 つのマーカーファイルに載せようとして両方失敗している。

  6. 全モジュール横断の後処理をインクリメンタルにする

    検索インデックス・navbar・backrefs はいずれも毎回全モジュール分を読み直している。 今回の規模では 1–2 秒だが、モジュール数に線形なので短い待ち時間でのプレビューには障害になる。

  7. タクティク収集を二重ループにしない

    バッチ化すると即座に最大項 (36%) に浮上する。全体を 1 回列挙して振り分ければ消える。

  8. equation 生成は切り替え可能にする

    定理中心のライブラリでは 7% しか効かないが、定義中心のコードでは非常に重い。 固定の判断をせず段階にする。

あえて優先しなくてよいもの

HTML のレンダリング自体は生成 CPU の 9.2% にすぎない。 テンプレートエンジンの高速化や別言語での書き直しは、ここでは効果が薄い。 「言語選択より責務分離と計測を優先する」という構想の判断は、この計測結果と整合する。

本計測の限界

  • フルビルドは完走させていない。 Mathlib + InformationTheory 8,600 モジュールのうち 3,590 モジュール (42%) を抽出した時点で打ち切った。既定の並列度では残り 2.5 時間、 並列度を落とすとスワップが解放されず 11 時間相当まで悪化したため。 抽出フェーズは 3,590 モジュールの実測、HTML 生成フェーズは DB に入った 6,072 モジュールでの 単独実測に分けている。全体の wall clock は測れていない。
  • equation 比較の 2 本はフルビルドと並行して測ったため絶対値が膨らんでいる。 同一条件下の相対比較としてのみ有効。
  • 方式 A は 432 モジュール中 112 モジュールの実測で、残りは平均値からの換算。
  • 単一マシン (M1 / 8 コア / 16 GB) の結果であり、特にメモリ律速は RAM 量に強く依存する。
