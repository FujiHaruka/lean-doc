## 0. cold の作り方 — purge ではなく「退避 + 検証」

`purge(8)` は sudo が要るので使えない (計画 §6 事前決定 #6)。代わりに
`olean-evict` が対象 34,304 ファイルを PROT_READ/MAP_SHARED で mmap し
`msync(MS_INVALIDATE)` でページキャッシュから落とす。所要 1.3 秒、sudo 不要。

これは purge より**弱いが厳密**: 機械全体を冷やすのではなく olean だけを冷やす。
Lean のバイナリ・dylib・ディレクトリのメタデータは warm のまま残るので、
測っているのは **olean のページイン費用だけ**に絞られる。そして何より
**冷えたことを R0 = 0 バイトで検証できる** — 「セッション最初だから cold のはず」という
仮定を置かなくてよい。cold が再現可能になるのが実務上いちばん効く。

自然な cold との突き合わせ (§4 の表): 退避 cold の importModules 15.27–15.56 秒に対し、
退避を一切使わない自然な cold (9 時間放置後のセッション最初の 1 run) は 17.87 秒。
自然な cold の方が 2.4 秒遅いのは、そちらは extract バイナリや dylib も冷えていたから。
**olean 部分については退避 cold は自然な cold の忠実な代理**と見てよい。

## 2. 2 つの量を分けて出す (混ぜると 6% ずれる)

`resident_bytes` = 常駐ページ数 × 16,384。ページ単位なので**ファイル末尾の半端が 1 ページに
切り上がる**。`.olean.server` は 11,046 個の平均 12 KB で 1 ページに満たないから、この量で
測ると常駐率が 100% を超える (実際 lean-core .olean.server で 162.6% が出た)。
そこで末尾ページを実長で数える `resident_file_bytes` を足した。

| 量 | 意味 | 比べる相手 |
|---|---|---|
| **bytes read** (`resident_file_bytes`) | 常駐ページが覆う**ファイルの**バイト数 | ファイルサイズ、ディスク読み出し |
| **cache bytes** (`resident_bytes`) | ページキャッシュが占めた**メモリ** | peak RSS (こちらもページ単位) |

## 3. 答え — R0 → R1 の差分

R0 は退避直後 (= 0 バイト)、R1 は cold な 1 回目 (E1) の直後。したがって差分 = R1。

| | バイト | MiB | GB (10^6) | GiB (2^30) |
|---|---:|---:|---:|---:|
| **R0 (退避後の基準)** | **0** | 0.00 | 0.000 | 0.000 |
| **R1 − R0 : cold が読んだ olean のバイト数** | **2,588,347,936** | **2,468.44** | **2.588** | **2.410** |
| R1 − R0 : cold が占めたページキャッシュ | 2,747,498,496 | 2,620.22 | 2.747 | 2.559 |

**これが「約 3 GB」の置換値。ラベルは実測。**

触ったファイルは 17,528 / 34,304。その 17,528 個の見かけサイズ合計は 4,178,202,360 B
(3,984.64 MiB) なので、**Lean は開いた olean の 61.9% のバイトしか読んでいない** —
demand paging が要らない部分を飛ばしている。「closure の olean を全部読む」ではない。

独立反復 (run A、同じ手順・末尾補正前の道具) のページキャッシュ量は 2,759,983,104 B。
run B の 2,747,498,496 B との差は 0.45%。触ったファイル集合は 17,528 個で**両 run 完全一致**。

### peak RSS との突き合わせ (別方式による検算)

macOS の `maximum resident set size` はファイル由来の常駐ページも含み、
`peak memory footprint` は匿名 + 圧縮分だけを数える。よって RSS − footprint ≒ ファイル由来。

| | バイト |
|---|---:|
| peak RSS (E1) | 3,250,470,912 |
| − peak memory footprint (E1) | 531,525,504 |
| = ファイル由来と推定される分 | 2,718,945,408 |
| mincore で測ったページキャッシュ量 | 2,747,498,496 |
| 一致度 | **99.0%** |

**まったく別の 2 方式が 1% 以内で一致した。** これで mincore 側の集計ミス
(16 KiB ページの取り違え・MiB/MB の混同) はほぼ排除できる。

### 「約 3 GB」は過大だった

| 分母 | 比 |
|---|---:|
| 実測 2,588,347,936 B ÷ 3 GB (3×10^9) | 0.863 → 主張は **1.16 倍の過大** |
| 実測 2,588,347,936 B ÷ 3 GiB (3×2^30) | 0.804 → 主張は **1.24 倍の過大** |
| 元になった peak RSS 3,268,263,936 B ÷ 実測 | 1.263 → **RSS は 26% 上振れする** |

上振れの正体は §3 の表の通り、匿名メモリ約 0.53 GB。
**「約 3 GB の olean」ではなく「約 2.6 GB の olean + 約 0.5 GB の匿名メモリ」だった。**

**warm 判定の根拠 (3 つ、すべて同じ向きを指す)**

1. **major fault が 132,343 → 215–1,522 に落ちる (2 桁半)。** これが直接の証拠。
   major fault はディスクから取ってきたページの数そのもの。
2. **minor + major の合計は cold も warm も約 253,000 でほぼ不変** (cold 252,924 /
   warm 250,880–253,697)。つまり**触るページ数は同じで、その内訳が
   「ディスクから」から「キャッシュから」へ移っただけ**。仕事量は変わっていない。
3. **壁時計 ≒ user+sys**: warm は 3.19 秒に対し user+sys 3.17 秒 (比 0.99)。
   cold は 16.26 秒に対し 4.55 秒 (比 0.28) — 残り 11.7 秒は CPU を使っていない待ち時間。
   CLAUDE.md の「壁時計 ≒ CPU 時間なら warm」がそのまま成立している。

cold / warm = 16.26 / 3.26 (warm の壁時計中央値) = **5.0 倍**。CLAUDE.md が警告する「olean は page cache の状態で
5 倍動く」がこの系列でも再現した。

R1 以降のスナップショット (常駐は 6 run 通して動かない):

warm の 5 回で増えるのは 76 ファイル分だけ**。減少は他プロセスとのメモリ競合による退避で、
R2–R6 の振れ幅 (2.19 MiB) の外側だが 1% 未満。R1 が cold の到達点として妥当。

## 6. 実効読み出しスループット

MB = 10^6 B。cold の importModules を分母に取る。

| 分子 / 分母 | MB/s |
|---|---:|
| 読んだバイト 2,588,347,936 ÷ cold importModules 15.266 s | **169.5** |
| ページキャッシュ量 2,747,498,496 ÷ 同 | 180.0 |
| 読んだバイト ÷ I/O 起因分 (15.266 − warm 中央値 2.538 = 12.728 s) | **203.4** |

major fault あたりに直すと: 12.728 s / 132,343 = **96.2 µs/fault**、
1 fault が運ぶバイトは 2,588,347,936 / 132,343 = **19,558 B** (16 KiB ページ 1.19 枚分)。

### これは M1 の NVMe として妥当か → **妥当ではない。帯域ではなく fault 遅延で律速している**

同じ 17,528 ファイルを、退避直後に `read(2)` で丸ごと読む対照実験
(`xargs -0 cat > /dev/null`、各回の直前に olean-evict。**各条件 1 回のみ (n=1)**、
`/usr/bin/time -l` の real):

| 読み方 | バイト | 秒 | MB/s |
|---|---:|---:|---:|
| demand paging (extract の cold) | 2,588,347,936 | 12.728 (I/O 起因分) | 203.4 |
| 逐次 read、全バイト | 4,178,202,360 | 6.15 | **679** |
| 8 並列 read、全バイト | 4,178,202,360 | 2.27 | **1,841** |

**1.61 倍のバイト数を、逐次で 0.48 倍・8 並列で 0.18 倍の時間で読めている。**
バイト毎秒に直すと逐次で 3.3 倍、8 並列で 9.1 倍。ディスクは詰まっていない。

96.2 µs/fault は NVMe のランダム読み + カーネル往復の実測レンジそのもので、
**cold の 12.7 秒は「132,343 回の同期 major fault の直列な待ち行列」**である。
8 並列の 1,841 MB/s が出るなら 2.59 GB は 1.4 秒で読める計算になる。

含意 (CI 軸の打ち手として):
- 先読み (closure の olean を madvise(MADV_WILLNEED) か並列 read で先に載せる) には
  **理論上 3〜9 倍の余地**がある。上の 2.27 秒がその床の実測値。
- 逆に「olean を小さくする」方向の効き目は薄い。読んでいるのは見かけの 32.9% であり、
  ファイルを削っても fault の回数は減らない。

## 8. この計測で分かっていないこと

- **`purge` を使った機械全体の cold は測っていない** (sudo が無い)。§0 の退避 cold は
  olean だけを冷やす。Lean バイナリ・dylib まで冷えた自然 cold は natural-cold の
  17.87 秒 1 点しかなく、n=1 なので分散が分からない。
- **どのページが読まれたかは分かるが、なぜ読まれたかは分からない。** mincore は
  ページ番号の集合しか返さないので、`.olean.private` の読まれた 31.3% が
  「どの宣言の本体か」は本計測では特定できない。
