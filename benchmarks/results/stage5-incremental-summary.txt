## 0. 何を偽装したか (先に書く)

**対象リポジトリは書き換えていない。** `.lake/build/doc` は段階 4 の正解データ、
`.lake/build` の olean は全計測の基盤なので、`.lean` を編集して `lake build` し直す
素直な増分実験はできない。したがって **「モジュール M が変更された」という事実だけ**を
ハッシュ台帳の M のエントリを無効化して注入している (`ledger.ts touch`)。
それ以外はすべて本物 — 抽出器は実際に M の import closure を読み直して M を解析し、
merge は実際に IR を書き換え、生成器は実際にページを書き直している。

したがって **この数字に `lake build` は含まれない。** `lake build` は lean-doc の外だが
実際の編集 → プレビューの臨界パス上にある。測るには対象リポジトリの複製が要るので、
**この増分では測らない**。

もう 1 つの帰結: 実際には何も変わっていないので、再抽出した IR はバイト一致し、
**正直な再生成対象は空集合になる**。パイプラインはそう報告している (`irChanged: 0`)。
時間を測るために `--mode` でページ集合を強制した。**再生成の秒数は実在のページ集合に
対する実測だが、その集合は導出ではなく選択である。**

## 2. 理論値 0.03s との食い違い — **理論値は否定された**

`approach.md` §6.5 は「常駐プロセス 0.03s」を**理論値**として置いていた。実測は:

| | 秒 | 理論値との比 |
|---|---:|---:|
| 理論値 (§6.5、常駐前提) | 0.03 | 1x |
| **増分の実測・最小 (hub)** | **3.3044** | **110x** |
| 増分の実測・最大 (mid) | 4.3893 | 146x |
| うち「変更に比例する仕事」だけ (leaf: analyze + writeIR + render) | 0.266 | 8.9x |

**0.03s は常駐プロセス (環境がメモリ上にある) を前提にした数字**なので、
使い捨てプロセスの実測と直接は比べられない。ただし比べられる部分を切り出しても
食い違う: 環境ロードを除いた「1 モジュール解析 + 1 ページ生成」相当は
leaf で analyze 0.042 + writeIR 0.004 + render 0.220 = **0.266 秒**で、
**理論値の 8.9 倍**。差の大半は render の 0.220 秒であり、そのうち 0.135 秒は
**IR を全部読み直して名前写像を作る**費用 (§4)。**0.03 秒は常駐を仮定しても届かない。**

## 3. 差分検出 — 「変更なし」の時間 = 増分の下限

432 モジュール / 432 olean ファイル / 237,909,832 B。Lean は起動しない。
warm 系列は 3 つを交互配置で 8 round、cold 系列はその**後**に単独で 8 run
(evict は次の warm を汚すので混ぜられない)。中央値 [min-max]、run 1 は捨てる。

| 系列 | 壁時計 | うち hash | major fault | 何を読むか |
|---|---:|---:|---:|---|
| `lake` (warm) | **0.0798** [0.0789-0.0838] | 0.0509 | 3 | Lake の `.olean.hash` 432 個 = 6.9 KB |
| `sha256-c8` (warm) | **0.1173** [0.1121-0.1455] | 0.0875 | 3 | olean 227 MB を 8 並列で SHA-256 |
| `sha256-c1` (warm) | **0.2493** [0.2424-0.2519] | 0.2184 | 3 | 同・逐次 |
| `lake-cold` | 0.0800 [0.0793-0.1377] | 0.0507 | 3 | 同上 (olean を evict しても**動かない**) |
| `sha256-cold` | 0.3819 [0.3773-0.3916] | 0.3506 | 3 | olean を evict した直後 |

- **無変更の検出は 0.080 秒 (lake) / 0.117 秒 (sha256 8 並列)。** これが増分の下限。
  deno の起動床 0.026 秒 (stage4c で実測) がこのうち約 1/3 を占める。
- **`.olean.hash` は Lake が既に計算した olean の内容ハッシュ** (`cacheFileHash` →
  `computeBinFileHash`、`Lake/Build/Common.lean`)。読むのは 6.9 KB なので
  **olean の page cache 状態に影響されない** (cold 0.0800 対 warm 0.0798)。
  ただし 64bit 非暗号ハッシュで、ビルドツールの内部仕様。
- SHA-256 のスループットは warm 1,090 MB/s (逐次) / 2,715 MB/s (8 並列) /
  cold 678 MB/s。
- **doc-gen4 の「無変更 2.33 秒」(報告書 §4.5) と直接は比べられない。** Lake の
  replay はビルドグラフ全体 (olean のトレースを含む) を検証しており、こちらの台帳は
  olean 432 個を比べるだけで「olean がソースに対して最新か」は見ていない
  (それは `lake build` の仕事で、§0 のとおり範囲外)。

## 4. 再抽出と再生成の分解

### 4a. 1 モジュールの再抽出 (Lean を起動する側)

系列は**交互配置していない**。最初に round-robin で試したところ全系列が cold のまま
だった (full の作業集合が 1 モジュール側のページを追い出す。6 round 回しても
major fault 72,000)。作業集合が 3 倍違う変種の交互配置は「どれも warm にならない」
ことを保証するだけなので、系列ごとに連続実行して各自の warm 定常に入れ、
**最後に小さい系列を取り直してドリフトを測った** (hub 1.9257 → 1.8438、
leaf 3.1613 → 3.0191 — どちらも**速くなっている**ので、full による悪化は無い)。

| 系列 | 宣言 | import closure | 壁時計 | プロセス内 total | importModules | analyze | writeIR |
|---|---:|---:|---:|---:|---:|---:|---:|
| hub (`…Meta.EntryPoint`) | 1 | 2,259 | **1.9257** | 0.8075 | 0.8024 | 0.0003 | 0.0007 |
| leaf (`…OmegaNoncomputable`) | 52 | 4,258 | **3.1613** | 1.9962 | 1.9421 | 0.0419 | 0.0037 |
| mid (`…ChannelCoding.Basic`) | 32 | 5,267 | **4.6490** | 3.0388 | 2.9635 | 0.0610 | 0.0044 |
| full (432 モジュール) | 4,750 | 6,021 | **16.1919** | 14.6152 | 2.7171 | 11.2839 | 0.5974 |

mid の散らばりは大きい (壁 3.998-5.863、major fault 715-22,682)。peak RSS 3.0 GB で
16 GB 機の余裕を使い切りかけているため。**mid の数字はこの散らばりごと読むこと。**

**壁時計とプロセス内の差 (1.1-1.6 秒) はほぼ `lake env`。** 単独で実測すると
`lake env /usr/bin/true` = **0.9618 秒** [0.9594-0.9626] (warm、6 run)。
残りは 171 MB の実行バイナリの exec とプロセスの後始末。
`approach.md` の 13.71s / 14.5s 系の数字は**プロセス内**の値なので、
`lake env` はそこに入っていない。**増分ではこの固定費が相対的に大きい** (leaf で 25%)。

### 4b. 影響ページ集合の再生成 (Lean を起動しない側)

6 系列を交互配置で 6 round。IR は同一。

| 系列 | ページ | 壁時計 | プロセス内 total | うち IR 読み出し |
|---|---:|---:|---:|---:|
| leaf-self | 1 | **0.1952** [0.1909-0.2327] | 0.1562 | 0.1345 |
| leaf-importers | 2 | 0.2044 | 0.1655 | 0.1371 |
| mid-referrers | 81 | **0.3494** [0.3458-0.3695] | 0.3098 | 0.1356 |
| mid-importers | 160 | 0.5113 | 0.4718 | 0.1308 |
| hub-importers | 415 | 0.8696 | 0.8287 | 0.1335 |
| **full** | 432 | **0.8796** [0.8552-0.9216] | 0.8403 | 0.1358 |

**1 ページの再生成は 432 ページの 4.5 分の 1 にしかならない。** 床は
IR 読み出し 0.135 秒 + 名前写像の構築 0.010 秒 + deno 起動 0.026 秒 ≒ 0.17 秒で、
これはページ数に依存しない。**「Lean の外側の全域索引」が増分の床を作っている** —
`approach.md` §5.5 の「全モジュール横断の後処理も差分から更新できる形にする」が
未実施であることの実測値がこれ。

正しさ: **部分再生成した 415/160/81/2/1 ページは、432 ページ全部を生成したときの
出力と全部バイト一致**した (`cmp`、差 0)。

## 5. 正しさ (時間より先に確認したこと)

| 検査 | 結果 |
|---|---|
| フル抽出の IR が別セッションで再現するか | **432 ファイル + index + deps が byte 一致** (前セッションの ir-tagged と `diff -r`) |
| 1 モジュールだけ再抽出した IR が、フル抽出の同じモジュールと一致するか | **byte 一致** (hub / leaf / mid の 3 モジュール) |
| 部分抽出を merge した 432 モジュールの IR が、フル抽出と一致するか | **module 432/432 byte 一致、index エントリ (bytes / declarations / contentHash) 一致、deps は写像として 533/533 一致** |
| 増分を 6 回回した後の IR とページが、フルビルドと一致するか | **3 変種すべてで IR 432/432 一致、ページ 432/432 byte 一致** |
| 出力側ハッシュが「変わっていない」と正しく言えるか | **`irChanged: 0`** — 再抽出した IR の contentHash が動かないことを検出できている |

deps だけは JSON のキー順が Lean の HashMap 由来で外から再現できないため、
**バイトではなく写像として**比較している (`merge-ir.ts --verify`)。

**部分抽出は `deps/*.json` を正しく作れない。** 抽出器は「defining module が
target list に無ければ依存」と判定するので、1 モジュールの target list だと
自パッケージの他モジュールが依存に化ける (leaf の 1 モジュール実行は
フル実行に存在しない `deps/InformationTheory.json` を書く)。これは増分の性質ではなく
**抽出器のインタフェース (target list が package list を兼ねている) の副作用**で、
merge 側で全モジュールから作り直して潰している (0.161 秒)。

## 6. 増分の律速

leaf (1 ページ、3.8339 秒) の内訳を「環境の取得」と「変更に比例する仕事」で割ると:

| | 秒 | 壁時計比 |
|---|---:|---:|
| `importModules` (Lean の環境ロード) | 1.942 | 50.7% |
| `lake env` (環境変数の解決とプロセス起動) | 0.962 | 25.1% |
| exec + 171 MB のバイナリのページイン + 後始末 | 0.160 | 4.2% |
| スクリプトの起動と段の境界の時刻取得 | 0.072 | 1.9% |
| **環境の取得と糊 小計** | **3.135** | **81.8%** |
| render (うち IR 全読み 0.135 + 名前写像 0.010) | 0.220 | 5.7% |
| merge (うち deps スライスの再計算) | 0.161 | 4.2% |
| impact (IR の refs/imports グラフを組み直す) | 0.158 | 4.1% |
| detect (432 olean のハッシュ照合) | 0.103 | 2.7% |
| analyze + writeIR + tactics (本来の仕事) | 0.053 | 1.4% |
| **変更に比例する仕事 小計** | **0.695** | **18.2%** |

**増分の律速は環境ロード。** `approach.md` §6.5 の「ほぼ全部が環境ロード」という
記述は向きとしては正しいが、数字は 2 つ外れている:

1. **床は 2.5 秒ではない。** 1 モジュールの import closure は 2,259〜5,267
   モジュールで、パッケージ全体の 6,021 より小さい。実測は
   **importModules 0.80〜2.96 秒**で、モジュールによって 3.7 倍違う。
2. **`lake env` の 0.96 秒が入っていなかった。** これは Lean の外だが増分の毎回に
   かかる。使い捨てプロセスの増分では 25% を占める。

「変更に比例する仕事」18.2% のうち、**本来の仕事 (analyze + writeIR + tactics) は
1.4% しかない。** 残りの大半は全域索引の再構築 — render の IR 全読み 0.135 +
名前写像 0.010 + merge の deps 再計算を含む 0.161 + impact のグラフ構築 0.158 で
**0.463 秒 = 12.1%**。**常駐化して環境ロードを消しても、この 0.46 秒は別に潰さないと残る。**

## 7. doc-gen4 との比較 (分母を明示する)

| | doc-gen4 (報告書 §4.5) | lean-doc (本計測) |
|---|---|---|
| 無変更 | 2.33s — Lake が全 job を replay、doc-gen4 は 1 プロセスも起動しない | **0.080s** (台帳照合のみ) |
| 1 モジュール変更 | 5.21s — ただし **HTML が再生成されていない** (stale)。`lake build` を含む | **3.30〜4.39s** — 1〜415 ページを実際に書き直す。**`lake build` を含まない** |

**この 2 列は同じ仕事ではない。**
doc-gen4 の 5.21 秒は `lake build` (olean の再ビルド) を含み、HTML は更新していない。
lean-doc の 3.30〜4.39 秒は `lake build` を含まず、HTML を更新している。
**倍率を書かないのはそのため。** 比較可能にするには対象リポジトリの複製を作って
`lake build` を測る必要がある (→ 未着手の検証項目)。

無変更側の 2.33 秒 対 0.080 秒も同様で、Lake の replay はビルドグラフ全体を検証し、
台帳は olean 432 個を比べるだけ。**29 倍という数字を単独で引用しないこと。**

## 8. 判断基準 (計測前に宣言) と結論

| # | 基準 | 結果 |
|---|---|---|
| 1 | 再抽出した IR がフル抽出と一致する | **満たした** (§5、byte 一致) |
| 2 | 増分の合計がフル生成より有意に速い | **満たした** — 3.30〜4.39s 対 17.07s (同一セッション、分布は重ならない)。ただし **3.9〜5.2 倍**であって 480 倍ではない |

## 9. この計測が答えていないこと

1. **`lake build` の時間** (§0)。実際の編集ループの臨界パス上にあるが範囲外。
2. **影響集合の閉包** (§8-3)。印字の経路と所有モジュールの経路。
3. **パッケージ横断の出力**。`render.ts` はモジュールページしか書かない。
   モジュール索引・検索索引 (`declaration-data-*.bmp`)・`backrefs-*` は未実装なので、
   「stale が無い」は 432 ファイルについての主張でしかない。
4. **削除**。消えたモジュールのページも台帳エントリも残る。何も消していない。
5. **cold 側の増分**。増分の cold は測っていない (差分検出だけ cold を取った)。
   1 モジュールの環境ロードが cold でいくらになるかは未測定。
