0. 先に結論
-----------
- **`selectionRange == range` は「生成された」ではない。B-0 §11 の書き方は誇大で、
  この計測が否定した** (§1)。単独で使うと計測対象で 197 件、Mathlib 標本で 779 件を
  「生成」と呼ぶことになるが、その大半は structure/class の射影と macro 定義の宣言である。
- **`@[ext]` に限れば、拡張への所属と `selectionRange == range` の合成が
  両標本で完全に一致した** (§2)。誤って親を名乗った宣言は **0**。
- **落としたものはある** — Mathlib 標本の ext 系 94 件のうち **7 件**は
  `to_additive` / `to_dual` が `@[ext]` を代理適用したもので、**何も出していない** (§3)。
  **間違った親を出したものは 0 件。**
- **3 版すべてで反証条件は成立したまま** (§4)。生成宣言が親より前に並ぶ件数は
  v4.31.0 / v4.32.2 / v4.33.0 で **0 / 0 / 0**。
- IR は **+0.96%** 太った (§5)。

1. `selectionRange == range` は「生成された」を意味しない 【実測】
-----------------------------------------------------------------
B-0 §11 は「`selectionRange` を足せば『範囲が属性トークンを指している』ことが
この側で判定できる」と書いた。**両方向とも成り立たない。**

Mathlib 標本 2,786 宣言:

  selectionRange == range              779
    範囲が `@[...]` / `attribute [...]` の内側から始まる     570
    範囲が行頭から始まる (class の field など)               37
    範囲が行の途中から始まる (射影・親射影)                 172
  selectionRange != range             2007  (2007 件すべて range に真に内包される)
    うち範囲が `@[...]` の内側から始まるもの                376

- **偽陽性**: `sel == range` の 779 件のうち **209 件 (26.8%)** は属性トークンではない。
  内訳は structure / class の field 射影、constructor、`library_note` や
  `notation` のように 1 つの syntax で位置を記録する macro 定義。
- **偽陰性**: 範囲が属性トークンを指しているのに `sel != range` になるものが **376 件**。
  Mathlib の `to_additive` は `range` に属性全体 (`to_additive (attr := ext)`) を、
  `selectionRange` に **著者が書いた加法版の名前**を入れる。名前を書いていない場合は
  `to_additive` トークン自体が入る。**どちらも `sel != range` になる。**

計測対象 4,584 宣言:

  selectionRange == range              197
    範囲が属性トークン (`ext`)                                2
    それ以外 (射影・constructor・`scoped notation`)          195
  selectionRange != range             4387

  → **計測対象では 197 件中 195 件 (99.0%) が「生成されていないのに sel == range」。**

**したがってこの等式は単独の判定には使えない。** 使えるのは「どの宣言を見ているか」を
既に知っている規則の**後半**としてだけである。Rust 側でこれを
`DeclNaming::{Unknown, Named, Unnamed}` と名付け、`Unnamed` を「生成」と読まないことを
型と doc に書いた (`crates/litedoc4-ir/src/model.rs`)。

2. `@[ext]` の判定 — 両標本で一致 【実測】
------------------------------------------
規則 (`extractor/Extract.lean` の `extOriginOf`、判断は 1 箇所):

  `P.ext`      : `isStructure P` かつ `P.ext ∈ extExtension` かつ `sel == range` → 由来 `P`
  `P.ext_iff`  : `P.ext` が環境に在り `∈ extExtension` かつ `sel == range` → 由来 `P.ext`
  それ以外     : **何も出さない**

名前の作り方は推測ではない。Lean core の `Lean/Elab/Tactic/Ext.lean:107` が
`extName := structName.mkStr "ext"`、同 142 行が `extIffName := extName ++ "_iff"` と
**構成している**。出すのは「実現の入力」を 1 段だけで、`P.ext_iff` は `P.ext` を指す
(連鎖は読み手が辿る)。

オラクル: **IR を見ずに原典を切り出し**、`range` が覆うテキストが括弧の内側の
`ext` トークンそのものかどうかを見る (B-0 §4 と同じ方法)。

  標本                        ext 形の宣言   IR が由来を出した   オラクルが是   一致   誤り
  --------------------------  ------------  -----------------  ------------  -----  ----
  Mathlib 10 モジュール              94                57            57       94     0
  計測対象 422 モジュール             3                 2             2        3     0
  e2e/micro (標本 3)                 10                 9             9       10     0

  **一致 = 94/94, 3/3, 10/10。誤って親を名乗ったものは 3 標本とも 0 件。**
  出した由来の妥当性も別に検査した (名前から `.ext` / `_iff` を剥がしたものと一致するか、
  親が structure か): **不整合 0 件**。

判定に効いた反例が両標本に実在する:

  - Mathlib 標本の **20 件**が `@[ext] theorem ext ⦃inst₁ inst₂ : Ring R⦄ …` の形の
    **手書き** ext 定理。**拡張には入っている**ので、拡張だけを見る規則はこれを
    生成物と呼ぶ。`sel != range` で落ちる。
  - 計測対象の `InformationTheory.Shannon.LZ78Phrase.ext_iff` は
    docstring 付きの**手書き**定理。同じく `sel != range` で落ちる。
  - `e2e/micro` の `Micro.Gen.Solo.ext` は同じ形をフィクスチャとして持たせたもの。
    **意図的に一度壊して確認した**: `sameRange` の条件を外すと GATE 9 が exit 1 で
    `GATE 9 FAIL  Micro.Gen.Solo.ext: generated is ["ext", "Micro.Gen.Solo"], expected null`
    と 1 行で名指しする。

3. 落としたもの — 出さないという選択 【実測】
---------------------------------------------
Mathlib 標本の ext 形 94 件の内訳:

  57  `@[ext]` / `attribute [ext]` が実現した              → 由来を出す
  20  手書きの `@[ext] theorem`                            → 出さない (正しい)
   5  `@[to_additive (attr := ext)]` を書いた手書きの乗法版 → 出さない (正しい)
   5  `to_additive` が代理適用した加法版の `.ext`          → **出さない (落とした)**
   2  `to_dual` が代理適用したもの                         → **出さない (落とした)**
   2  docstring 付きの手書き                               → 出さない (正しい)
   2  `@[deprecated …] alias ext := Cone.ext`              → 出さない (正しい)
   1  `@[ext, grind ext] theorem ext`                      → 出さない (正しい)

**落とした 7 件は `to_additive` / `to_dual` の拡張が Mathlib にあるため引けない。**
extractor を Mathlib に依存させれば引けるが、そうすると `e2e/micro` で建たなくなり
CI のゲートが 1 本消える (B-0 §11、計画 §4 B-3 の撤退ライン)。
**間違った親を出すより出さない方を採った** — 7/94 は「知らない」であって「無い」ではない。

計測対象で落としたものは **0 件** (`to_additive` の使用が 0 件のため)。

4. 反証条件 — 3 版で数えた 【実測】
-----------------------------------
B-0 §13.2: 「生成宣言が親より前に並ぶ = 0 件」は v4.31.0 の `declRange` が
docstring と属性を範囲に含むという実装依存の性質にすぎない。litedoc4 は 3 版を
建てると約束しているので、**3 版すべてで数えた**。

`e2e/micro` を scratch に複製し、`lean-toolchain` だけを差し替えて
`lake build` → extractor をビルド → 抽出 → 数える、を 3 回。

  版          extractor  宣言数  由来を出した  **親より前に並ぶ**  親より後  sel == range
  ----------  ---------  -----  -----------  -----------------  -------  ------------
  v4.31.0     建つ         88        9              **0**            9        42
  v4.32.2     建つ         88        9              **0**            9        42
  v4.33.0     建つ         88        9              **0**            9        42

  → **3 版で完全に同一。B-0 §6 / §13.2 は書き換えない。**
  ついでに **3 版すべてで extractor が建つ**ことも再確認された (U5 の修正が効いている)。

同じ数を GATE 9 が `e2e/micro` で常時見ている (v4.31.0 のみ)。
**3 版の形は自動では回らない** — CI に 3 toolchain を持たせていないため、
この表が手で回した記録である。

5. IR の増分 【実測、計測対象】
-------------------------------
  modules/*.json 合計 (B-2 時点)      15,093,293 B
  modules/*.json 合計 (B-3 後)        15,238,229 B
  差                                     +144,936 B
  IR 全体に対する増分                       +0.9603%

  内訳: `"selectionRange":[l,c,el,ec],` が 4,584 件、`"generated":["ext","…"],` が 2 件。

  数え方: 生成済み IR から新しい 2 キーの実バイト数を正規表現で数え、引いた。
  **引いた結果 15,093,293 B が `attrs-2026-08-21.txt` §1 の値と 1 バイト一致する**ので、
  この引き算は検算済み。

  `selectionRange` は tagged な IR に**常に**書く。「range と違うときだけ書く」規則にすると
  **キーの不在が 2 つの意味を持つ**ことになり、`sorry` をそう作らなかった理由と同じ形の
  欠陥になる。0.96% はその値段。

6. この計測が触っていないもの
-----------------------------
- **母数は 1 パッケージ + Mathlib 10 モジュール**。B-0 §13.5 と同じ限界で、
  「規則が当たる」という結論には 94 + 3 + 10 件で足りるが、**割合は一般化しない**。
- **`simps` / `mk_iff` / `alias` は測っていない** — 由来を出さないと決めた以上、
  出す/出さないの判定材料が要らないため。B-0 §4 の表が現況の記録として残る。
- **描画は 1 バイトも動かしていない** (束 B は抽出と IR だけ)。凍結フィクスチャは無傷。
