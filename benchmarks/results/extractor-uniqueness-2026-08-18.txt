X1 / X4(macOS) — `extract` は何に依存して決まるか
==================================================

問い (docs/plans/distribution.md §3 D1):
  extractor のプリビルドを配れるか。配れるのは「対象の toolchain だけ」で決まる場合。
  tools/ci-build.sh は「別パッケージで byte 一致」を実測済みだが、**2 つの依存セットが
  互いのコピー**だったと自分で注記している。その穴を塞ぐ。

計測条件【実測 2026-08-18】
  機材        Apple M1 / 16 GB / macOS (Darwin 25.6.0), arm64
  toolchain   leanprover/lean4:v4.31.0 (3 パッケージすべて同一)
  ページキャッシュ  warm (連続実行、1 本目のみ cold 寄り: 19.01s real / 10.10s user)
  手順        extractor/build.sh を TARGET_REPO だけ替えて 3 回。`lake build` は
              一度も走らせていない (Extract.lean は `import Lean` のみで、対象は
              環境を借りるためだけに要る)
  生ログ      /private/tmp/lean-doc-relay/dist/x1.out (作業領域、削除済み)

2. バイナリは可搬 — Lean ランタイムは静的リンクされている
--------------------------------------------------------------------------

  otool -L:
      /usr/lib/libc++.dylib
      /usr/lib/libSystem.B.dylib
  LC_RPATH:   無し
  埋め込まれた /Users/haruka のパス: **1 件のみ**
      /Users/haruka/.elan/toolchains/leanprover--lean4---v4.31.0/include/lean/lean.h
      (leanc に渡したヘッダのパス。実行時には参照されない)

  → libleanshared への動的リンクが無い。171 MB はデバッグシンボルではなく
    静的リンクされた Lean ランタイムの実体 (strip -S で 8 バイトしか減らない【実測】)。
    macOS では OS 標準ライブラリ 2 つだけあれば起動できる。

--------------------------------------------------------------------------
4. 可搬性 (X4 / X6) と不一致の壊れ方 (X5)
--------------------------------------------------------------------------

  X4  別 runner に artifact 経由で渡して e2e 完走【実測】。
      ただし runner はどれも $HOME=/home/runner なので、**これだけでは
      「17 件の埋め込みパスが実行時に使われないこと」の証拠にならない**。

  X6  **ELAN_HOME を /home/runner/work/_temp/alt/elan に置き、~/.elan が
      存在しないことを確認した上で実行 → exit 0、IR 1,269 B**【実測】。
      → **17 件の埋め込みパスは実行時に読まれていない。バイナリは真に可搬**。

  X5  v4.31.0 でビルドした extract を **v4.30.0** の環境で実行:

        exit code 1
        uncaught exception: failed to read file
          '.../v4.30.0/lib/lean/Init.olean', incompatible header
        書いた IR: 53 バイト (ヘッダのみ)

      → **静かには壊れない。** olean のヘッダで弾かれる。
      53 バイトの残骸は出るが、非ゼロ終了なので呼び出し側が検知できる。

  **この 3 つの検査自体が 2 回落ちている** — 1 回目の X5 は `e2e/micro` を単独コピー
  したために lake の package 解決で落ち、extract は起動すらしていないのに
  「REFUSED (= 不一致は拒否された)」と緑を返していた。いまは `lake env true` を
  先に走らせ、環境が作れなければ exit 2 (実験不成立) にしてある。

--------------------------------------------------------------------------
5. 判定 — 配れる。しかし配らない
--------------------------------------------------------------------------

  **技術的には配れる**: toolchain だけで決まり (X1/X3)、可搬で (X4/X6)、
  不一致は明確に落ちる (X5)。3 つとも配布の前提条件で、3 つとも満たしている。

  **それでも配らない**。理由は数字:

    ビルド            15〜16 s (Linux 15 s / macOS 10〜19 s)【実測】
    配布物のサイズ    Linux 226 MB / macOS 171 MB (gzip 45.9 MB)【実測】
    削れるか          **削れない** — strip -S で 8 バイト【実測】
    マトリクス        toolchain × OS。Lean が版を出すたびに増え、
                      追随しないところに穴が開く

  16 秒のビルドを 45〜70 MB のダウンロードに置き換えても勝たない。しかも
  CI ではキャッシュが効くので、この 16 秒は**キャッシュが外れた初回にしか出ない**。
  維持コスト (版ごとのリリース) が利得 (年に数回の 16 秒) を上回る。

  **将来やる場合の手順はもう揃っている** — X1/X3〜X6 が緑で、
  `.github/workflows/ci-extractor-portability.yml` がその 4 つを回す。
  release.yml に artifact を足し、action の取得順を「Release → ビルド」にするだけ。
  **前提が崩れるとしたら**: Lean が extract の中身を小さくしたとき (226 MB が
  10 MB になれば計算が変わる)、または Lean 環境のロードが重くなってビルドが
  16 秒で済まなくなったとき。

--------------------------------------------------------------------------
6. 主張の強さの限界 — ここから先はまだ測っていない
--------------------------------------------------------------------------

  * **1 機材・1 OS (macOS arm64)・1 toolchain (v4.31.0)**。
    Linux は leanc の既定が違う可能性があり、そこで静的リンクとは限らない → X3 / X4
  * **「起動できる」と「正しい IR を書く」は別**。ここで比べたのはバイナリの byte であって
    出力ではない。ただし byte が同一である以上、同じ入力に同じ出力を返す
  * **別 toolchain の環境で走らせたときの壊れ方は未検証** → X5。
    静かに壊れるなら、プリビルドを配る前に版検査が要る
  * 実行時に olean を読むので `LEAN_PATH` が要る。これは `lake env` が対象側で作るもので、
    バイナリには埋まっていない (埋まっていたら可搬ではなかった)
