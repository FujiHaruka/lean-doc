cold にならない**可能性がある (`docs/plans/three-axes.md` §5 打ち手 1)。ここではそれを潰す。

## 0. この機材の page cache headroom

`headroom` = (free + speculative + purgeable + inactive) × 16,384。
**新しいファイルページを受け入れられるメモリの上限**であって、実際に使える量ではない
(inactive の匿名ページは圧縮を経ないと空かない)。**実測、各ステップで記録している。**

| | GiB |
|---|---:|
| 物理メモリ | 16.00 |
| headroom (計測中の範囲、実測) | **3.11 – 5.48** |
| うち file-backed が実際に占めていた量 | 1.52 – 2.42 |
| **compressor が占有** | **6.38 – 7.11** |

**この機材は計測中つねにメモリ逼迫下にある。** compressor だけで 16 GiB の 4 割強を持っていく。
GitHub の `ubuntu-latest` は 4 vCPU / 16 GB でほぼ専有なので、**page cache の余裕はこちらより広い**。
この非対称性は §5 の結論で必ず併記すること。

## 1. 増分 A — payload を振って「書き込み直後の常駐率」を測る

手順 (1 点あたり 3 回、`measure-warmstart.sh sizes`):
前 payload を削除 → **source 34,304 ファイルを `olean-evict`** (前回の読みの残留を消す) →
`vm_stat` → `tar cf - -T list | tar xf - -C dest` → **直後に** `olean-residency` → `vm_stat` →
source の常駐も測る → payload 削除。dest のパス列は tar の変換規則から**事前に生成**していて、
「コピー完了」と「測定」の間に `find` を挟まない。

payload は olean のコピー。sorted list の先頭からの prefix なので 7.4 の点は全 34,304 ファイル。

### 曲線 (3 回の中央値 [min–max])

| payload GiB | ファイル | **dest 常駐 GiB** | **dest 常駐 %** | payload/headroom | source 常駐 GiB | source 常駐 % | copy 秒 | 書込 GiB/s |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 0.25 | 1,304 | 0.235 [0.233–0.236] | **94.0** | 0.07 | 0.24 | 96 | 1.44 | 0.174 |
| 0.50 | 2,636 | 0.226 [0.215–0.226] | **45.1** | 0.13 | 0.43 | 86 | 2.88 | 0.174 |
| 1.00 | 4,567 | 0.237 [0.229–0.244] | **23.7** | 0.26 | 0.81 | 81 | 5.14 | 0.195 |
| 2.00 | 8,203 | 0.233 [0.221–0.245] | **11.7** | 0.48 | 1.47 | 73 | 10.34 | 0.194 |
| 4.00 | 18,092 | 0.198 [0.188–0.202] | **5.0** | 0.96 | 1.48 | 37 | 22.15 | 0.181 |
| 7.34 | 34,304 | 0.193 [0.153–0.197] | **2.6** | 1.77 | 1.17 | 16 | 46.24 | 0.159 |

**曲線の形が「headroom で決まる」ではない。** 常駐した**絶対量**が payload に依らず
**0.15–0.24 GiB でほぼ一定**で、率はその割り算として落ちているだけ。
payload/headroom が 0.13 (headroom の 1/8 しか書いていない) の点ですでに 45% に落ちる。

**headroom は一度も律速していない。** 7.34 GiB を書いた直後でも headroom は 3.26–4.10 GiB 残っていた。
つまり「入る場所はあったのに、書いたページが置かれなかった」。

### 対照 1 — 同じ瞬間に「読んだ」ページは残っている

上表の source 列は**同じ `tar` の読み側**で、dest と同じ瞬間・同じメモリ状態で測っている。

| payload GiB | 読んだページの常駐 % | 書いたページの常駐 % | 比 |
|---:|---:|---:|---:|
| 1.00 | 81 | 23.7 | 3.4 |
| 2.00 | 73 | 11.7 | **6.3** |
| 4.00 | 37 | 5.0 | 7.4 |

**メモリ不足なら読み側も同じだけ落ちるはずだが、落ちていない。**
これは容量の問題ではなく、**読みと書きで保持方針が違う**ことの直接の証拠。
(読み側も 1.5 GiB 前後で頭打ちになる。headroom 3.9–4.2 GiB の全部は file cache に回らない。)

### 対照 2 — 「一定量」は時間の窓か、バイトの窓か

`cp` は 0.16–0.20 GiB/s しか出ないので、「直近 N 秒ぶんが残る」でも「直近 N バイトが残る」でも
同じ数字になる。`dd if=/dev/zero` で書込速度を **11〜16 倍**に上げて分離した
(`measure-warmstart.sh zeros`、1 ファイル、3 回の中央値):

| payload GiB | 常駐 GiB | 常駐 % | 壁時計 | 書込 GiB/s | 時間窓仮説の予測 (1.3 s × 速度) |
|---:|---:|---:|---:|---:|---:|
| 0.25 | 0.250 | **100.0** | 0.09 s | 2.78 | 3.6 GiB → 外れ (payload 全部が上限) |
| 1.00 | 0.309 [0.307–0.312] | **30.9** | 0.46 s | 2.17 | 2.8 GiB → **外れ** |
| 4.00 | 0.302 [0.291–0.305] | **7.5** | 3.34 s | 1.20 | 1.6 GiB → **外れ** |

**バイトの窓**が正しい。速度を 11 倍にしても残るのは 0.29–0.31 GiB で変わらない。
ファイル数 (1 個 vs 18,092 個) にも依らない。

### A の結論

> **この機材では、書き込み直後のファイルページは page cache に残らない。**
> 残るのは末尾 **0.15–0.31 GiB** だけで、payload サイズ・書込速度・ファイル数・
> headroom のいずれにも依存しない。**すべて実測** (6 サイズ × 3 回 + 対照 3 サイズ × 3 回)。

正体は macOS の逐次書き込みに対する drop-behind (書いたページをフラッシュ後に即解放する) と
考えるのが整合的だが、**カーネル内部は観測していないので機構の同定は推測**。
観測事実は「残らない」「読みは残る」「量が一定」の 3 つ。

## 2. 増分 B — 本物の `leantar` 展開直後の常駐率 (CI の実経路)

`cp` は書き込みのモデルにすぎない。CI の実経路は ltar の展開で、
**411 MiB の圧縮を読んで 6.12 GiB を書く**のでキャッシュ圧のかかり方が違う。

- 対象: `~/.cache/mathlib/*.ltar` のうち**現行 rev のクラスタ 8,516 個 / 430,651,726 B (410.70 MiB)**
  (mtime 2026-06-27、`lake-manifest.json` と一致)
- **`lake exe cache get` は実行していない。** `leantar -x -f -C <scratch>` を直接呼ぶ

  **直後に** `olean-residency` → `vm_stat`
- 展開されたもの: **110,708 ファイル / 6,574,088,297 B (6.123 GiB)**。
  うち olean 3 種は **25,548 ファイル / 5,547,865,944 B (5.167 GiB)**
  (`.olean` / `.olean.server` / `.olean.private`。残りは `.ilean` / `.trace` / `.hash` / `ir/*.c`)

**2 系列の差はファイル集合ではない。** 完全集合の snapshot を第 1 系列と同じ 24,507 ファイルに

## 3. 増分 C — 展開直後の `importModules` は速いか (秒で答える)

§1・§2 は「率」の答え。主張は秒なので、秒で測る。

**CI のモデルの作り方**: Mathlib だけを leantar の展開先から読ませる。
`lake env printenv LEAN_PATH` の 17 エントリのうち **mathlib の 1 つを scratch に差し替え**、
残り (Lean core・自プロジェクト・他 14 パッケージ) は対象リポジトリのまま。
3 変種はすべて同一セッション・同一手順で、**変えているのは Mathlib の暖機状態だけ**:

| 変種 | Mathlib | それ以外の closure |

| **warm** | 直前の run が読んだまま | 直前の run が読んだまま |

`/usr/bin/time -l`。**warm 判定は major page fault を主指標にする。**

### 読み方

1. **fresh は warm ではない。** 14.96 / 15.66 秒で、warm 2.49–2.59 秒の **5.9 倍**。
   major fault が 119,318 / 119,934 と cold と同じ桁で、warm の 190–412 とは 2 桁半違う。
2. **fresh は cold より速くもない。むしろ 1.1–1.7 秒遅い。** major fault は 2〜3% だけ少ない
   (119,318–119,934 対 121,386–122,974) ので、常駐していたぶんの効きは**あるが 3% 未満**。
   壁時計が逆転する理由の候補は 2 つ — (a) leantar の書き戻しがまだ流れていて読みと競合する、
   (b) `cold` 変種の木は直前の run が一度読んでいるのでファイルシステムのメタデータが暖まっている。
   **どちらかは切り分けていない。** ただし (a) は CI でも起きる。
3. **warm 側はこの harness でも 2.49–2.59 秒に収束**し、前増分の warm 中央値 2.538 秒と一致する。
   LEAN_PATH を差し替えた計測系そのものは健全。
4. **cold 13.86–14.00 秒を前増分の cold 15.27 秒と並べないこと。** 経路も退避範囲も違う。
   意味があるのは**この表の中の fresh / cold / warm の比較だけ**。
5. **§2 の常駐率 (最大 20.2%) と、ここで浮いた fault (2–3%) は釣り合っていない。**
   §2 の 1.04 GiB が読み出し集合と比例して重なるなら fault は 12% 前後浮くはずで、実測はその 1/4 以下。
   考えられる理由は、(i) 残るのは**最後に書かれた**ページで、importModules が読む順とは無関係、
   (ii) 展開終了から実際の読み出しまでの 1〜15 秒でさらに剥がれる、の 2 つ。
   **どちらも切り分けていない。** 向き (常駐が秒に化けない) は 3 変種の比較で確定しているので
   判定には影響しないが、**「20% 常駐していれば 20% 速くなる」は成り立たない**ことは記録しておく。

### C の限界 (結論に効く)

- **fresh になっているのは Mathlib だけ。** Mathlib は closure が実際に読む 2,468.44 MiB のうち
  1,395.87 MiB (**56.6%**、`ci-residency-summary.txt` §5) を占めるので支配的だが、全部ではない。
  Lean core (907.29 MiB) と自プロジェクト (80.86 MiB) は両変種で cold のまま。
- 7.33 GiB 全部を「直前に書かれた」状態にするのは、§1 の 7.34 GiB 点が示す通り
  **この機材では常駐 0.19 GiB (2.6%) にしかならない**ので、やっても結論は変わらない。

## 4. 判定

> **仮説「CI では olean を展開した直後なので page cache に載っている」は、
> この機材 (macOS / Apple M1 / 16 GiB) では偽。実測。**

根拠は 3 つとも同じ向き:

| | 実測値 |
|---|---|
| `cp` で 0.25–7.34 GiB 書いた直後の常駐 | 末尾 **0.15–0.24 GiB** のみ (率 94% → 2.6%) |
| `leantar` で 5.167 GiB の olean を展開した直後の常駐 | **4.7–20.2%** (0.24–1.04 GiB) |
| 展開直後の `importModules` | **14.96 / 15.66 秒** (warm 2.49–2.59 秒の 5.9 倍、cold と同じ桁) |

**そして原因は容量ではない。** headroom は一度も使い切られておらず (7.34 GiB を書いた直後でも
3.26–4.10 GiB 空き)、同じ瞬間に**読んだ**ページは 6.3 倍よく残っている。
**この機材の OS は、書いたページを読んだページと同じようには保持しない。**

## 5. CI 軸の前提はどう変わるか — **「常に cold」は覆っていないが、証明もされていない**

**この判定を CI にそのまま持ち込んではいけない。** 理由は 2 つあり、向きが逆:

**(a) 機材の非対称性 — この機材の方が不利。**
この機材は compressor が 6.38–7.11 GiB を占有し、実効 headroom は 3.1–5.5 GiB。
`ubuntu-latest` は 16 GB をほぼ専有する。**「この機材で載らなかった」は「CI で載らない」の証明にならない。**
逆向き (この機材で載ったなら、より広い CI でも載る) なら単調性で言えたが、載らなかったので使えない。

**(b) 退避ポリシーの違い — これが本質。**
macOS の UBC と Linux の page cache は、**「書いたページがいったんキャッシュに入る」点は共通だが、
その後の扱いが違う。** 本計測が捉えたのは「入った後すぐ解放される」挙動で、
これは容量ではなくポリシーの結果 (§4)。Linux の page cache は writeback 後もページを
clean なまま保持し、解放は reclaim (メモリ逼迫) まで待つ設計なので、
**同じ実験を Linux で回して同じ結果になるとは限らない。**
**この機材に Linux 環境が無い** (docker / colima / lima / podman / VM いずれも未インストール、
ネットワーク不使用は計画 §6 事前決定 #5) ため、**Linux 側は測れていない。**

したがって `approach.md` §3 の扱いは次のように変える。

| | 前 | 後 |
|---|---|---|
| 「CI は常に cold」 | **ラベル無しの断定** | **仮定** (ローカル macOS では**実測で cold**、Linux ランナーでは未検証) |
| 打ち手 1「展開直後なら warm」 | 未検証の期待 | **この機材では否定 (実測)。Linux では未検証** |

**容量の側からは、Linux CI で仮説が通る余地は残っている (外挿)。**
cold が実際に読むのは **2,588,347,936 B (2.59 GB、実測、`ci-residency-summary.txt` §3)** で、
`ubuntu-latest` の 16 GB に対して **16%**。展開が書く 6.12 GiB でも 38%。
**容量は制約にならない。** 残るのは退避ポリシーだけなので、**Linux で測れば決着する。**
→ 検証項目: 「GitHub Actions の `ubuntu-latest` で `cache get` 直後の
`/proc/<pid>/pagemap` か `mincore` で olean の常駐率を測る」。

## 6. この計測で分かっていないこと

- **Linux での挙動は 1 バイトも測っていない** (§5)。CI の結論はここが埋まるまで確定しない。
- **fresh が cold より 1.1–1.7 秒遅い理由を切り分けていない** (§3 の読み方 2)。
- **カーネル内部の機構は同定していない。** 「drop-behind」は観測 3 点に整合する説明であって、
  `vm_stat` の外側は見ていない。
- **`purge` を使った機械全体の cold は測っていない** (sudo を使わない方針)。
- **常駐率の測定には ~1 秒の遅れがある** (プロセス起動 + 25,548 ファイルの mincore 走査)。
  ただし走査時間が 26 倍違う 0.25 GiB (1,304 ファイル) と 7.34 GiB (34,304 ファイル) で
  常駐**量**が同じなので、この遅れが曲線を作っているのではない。
- **`leantar` は `lake exe cache get` そのものではない。** cache get は展開に加えて
  manifest の照合や `.trace` の検査を行う。展開の I/O は同じだが、前後の処理は含んでいない。
