## 0. 判断基準 (測る前に宣言したもの)

leg の指示で先に固定した 3 条件。**満たさなければ「打ち手として不成立」と書く**:

1. **overlapped の壁時計が cold baseline より有意に短い** — 5 回の分布が重ならないこと
2. **major fault が減っている** — 効いている機序の裏づけ
3. **読むバイト数の増加を払ってなお得か**

結果は §6。**3 条件とも満たした (この機材で)。**

## 2. 道具の検証 (本番の数字を出す前に通した)

**先読みが本当に page cache に載せているか**を mincore で確かめてから時間を測っている。
載っていない道具で時間だけ測ると「速い先読み」が「何もしない先読み」と区別できない。

| 検査 | 期待 | 結果 |
|---|---|---|
| 250 MiB (1,256 ファイル) を退避 | 0 | 0 バイト |
| → `-m read -j8` で先読み | 全部載る | **100.00%** (0.127 s / 2,058 MB/s) |
| → `-m madvise -j8` で先読み | 全部載る | **100.00%** (0.115 s / 2,273 MB/s) |
| → `-m touch -j8` で先読み | 全部載る | **100.00%** (0.210 s / 1,251 MB/s) |
| 34,304 ファイル全部を退避 | 0 | **0 バイト / 触ったファイル 0** |
| → closure 17,199 を `madvise -j16` | 載る | **2,556,988,152 B** (8,653 ファイル) |
| `madvise -j1` と `read -j1` の所要 | 同じなら同期的 | 4.28 s 対 4.19 s → **MADV_WILLNEED はこの OS では同期** |

最後の行が重要: **macOS の `madvise(MADV_WILLNEED)` は「投げっぱなし」ではなく戻り時点で
ページが入っている**。したがって madvise の経過時間は正味の I/O 時間として読んでよい。
(**Linux の MADV_WILLNEED は非同期**なので、同じ道具を移植したら再検証が要る。)

さらに、載っていることは**下流でも**確認できている — §5 の通り major fault が
121,386 → 26,329 に落ちるので、mincore の数字はアーティファクトではない。

読めること:

- **前増分の「床」を超えた。** 8 並列 `cat` の 1,841 MB/s に対し、この道具は
  **2,395 MB/s** (madvise j=16)。2.59 GB 相当なら 1.1 秒、oracle 全体 4.18 GB でも 1.75 秒。
- **並列度は 4 で頭打ち。** j=1 の 998 MB/s → j=4 で 2,120、j=8 で 2,272、j=16 で 2,351。

  後から読んだぶんが先に読んだぶんを追い出すので、必要なファイルの常駐が 32.8–50.4% に落ちる。
- **needed-set 常駐率は「載せた量」であって「役に立つ量」ではない。** ファイル単位で
  「cold が実際に読んだバイト」で頭打ちにした重なり (upper bound) は次の通り
  (`ci-prefetch-need-*.jsonl.gz` と `ci-residency-snap-R1.jsonl.gz` から再集計):

  | 条件 | 必要 2,588,347,936 B のうち常駐 |
  |---|---:|
  | oracle j=8 madvise | **90.7–93.5%** |
  | oracle j=16 madvise | 78.1–79.4% |
  | oracle j=1 read | 75.6–77.9% |
  | oracle j=16 read | 69.8–70.0% |
  | blind j=16 read | 59.0–62.0% |
  | blind j=8 madvise | 36.9–37.0% |

## 4. 3 変種 × 並列度 × 方式 — extract を含む本体

**同じブロック内でだけ比較すること。** この機材はメモリ状態が時間とともに動くので、
条件を交互配置していないブロック同士を並べてはいけない (→ §7)。
すべて 5 回、`/usr/bin/time -l`。`wall` は退避直後から extract 終了までの全体
(`lake env` の起動を含む)、`real` は extract バイナリだけ。

## 5. 判定 — **打ち手 2 は成立 (この機材で、実測)**

§0 で宣言した 3 条件に照らす。数字はブロック Y (交互配置)。

| 条件 | baseline | overlapped oracle madvise j=16 | 判定 |
|---|---|---|---|
| 1. 壁時計の分布が重ならない | 17.56–18.35 s | **9.52–11.15 s** | **満たす** (重なりゼロ、中央値 −42.1%) |
| 2. major fault が減る | 121,206–124,752 | **20,446–36,671** | **満たす** (中央値 −78.3%) |
| 3. バイト増を払って得か | — | oracle は **1.61 倍**のバイトで importModules −49.0% | **満たす** (blind = 3.04 倍は不可、下記) |

**ブロック Y で先読みしたのは oracle 集合** (観測して作った集合)。
**実装可能な closure 集合 (1.60 倍のバイト) は §6 の別ブロックで oracle と区別できない**ので、
同じ値になると読んでよい — ただし**これはブロックをまたぐ推論**であって、
closure を −49.0% の条件で直接測ったわけではない。

- `importModules` 13.573 → **6.923 秒 (−49.0%)**。
- 実効読み出しレートで見ると、demand paging は 2,588,347,936 B ÷ 11.115 s = **232.9 MB/s**、
  先読みは **2,352–2,395 MB/s** で **10.1 倍**。§1 の主張 (帯域ではなく fault 遅延が律速) の
  直接の裏づけ。
- **blind は「成立するが割に合わない」**: 3.04 倍のバイトを読んで importModules は
  13.573 → 11.369 (−16.2%) にしかならない。oracle/closure の −49.0% に対して 1/3。

## 6. ファイル集合の現実性 — **oracle は「実装不可能な上限」ではなかった**

leg の指示では oracle を「実装不可能な上限」として扱う想定だったが、**測ったら違った。**

`.lean` のヘッダを読んで import closure を作ると、**432 モジュールから 6,021 モジュール**が出る。
これは extract が報告する `loaded modules 6021` と**完全に一致**する。
そこから引いた olean は **17,199 ファイル / 4,140,727,992 B**:

| | ファイル | バイト | cold が必要とする 2,588,347,936 B のうち |
|---|---:|---:|---:|
| oracle (観測した集合) | 17,528 | 4,178,202,360 | 100% |
| **closure (計算できる集合)** | **17,199** | **4,140,727,992** | **2,557,182,568 = 98.80%** |
| closure ∩ oracle | 17,129 | 4,123,099,920 | |
| oracle のみ (closure に無い) | 399 | 55,102,440 | 31,165,368 = 1.20% |
| closure のみ (oracle に無い) | 70 | 17,628,072 | — |

**oracle にしか無い 399 ファイルは全部 toolchain (Lean core) のもの**で、
これは計測ハーネスの `lake env` 自身がロードする分。抽出器本体の closure ではない。

そして**実測で確かめた** (ブロック W、交互配置、5 回):

| 変種 | wall s | importModules s | extract real s | major fault |
|---|---:|---:|---:|---:|
| baseline | 22.00 [20.81–25.45] | 15.703 [15.377–17.975] | 17.91 [16.71–21.55] | 138,203 [129,674–170,480] |
| overlapped **oracle** madvise j=16 | 18.07 [15.98–20.50] | 12.039 [11.868–12.896] | 14.88 [12.85–17.27] | 95,273 [78,356–121,736] |
| overlapped **closure** madvise j=16 | 18.81 [17.81–21.41] | 12.808 [11.782–13.833] | 14.87 [12.87–17.41] | 93,270 [76,313–124,664] |

**closure と oracle は区別できない** (分布が完全に重なる)。
→ **「実装可能な中間」は存在するどころか、上限そのものに届いている。**

closure を作るコスト (`import-closure.py`、6,021 ファイル / 82,043,320 B の `.lean` ヘッダを読む):

| | 秒 |
|---|---:|
| warm (ソースが page cache にある、5 回) | 0.93–0.98 |
| **cold (`olean-evict` でソースを落としてから、3 回)** | **1.63–1.64** |

これは Python の逐次実装で、**先読みと直列に払った場合の上限**。
実装では「解決できたモジュールから順に先読みへ流す」ことができるので、
この 1.63 秒は先読みの 1.75 秒とほぼ完全に重なる。

**注意**: このブロック W は §7 の通りメモリ regime が悪化した後の系列で、
効果の大きさ (−23.3%) はブロック Y (−49.0%) より小さい。
**closure = oracle という結論はブロック内比較なので影響を受けないが、
このブロックの絶対値をブロック Y と並べてはいけない。**

## 7. 効果の大きさはメモリ regime に依存する (実測、これは限界でもある)

同じ「overlapped oracle madvise j=16」でも、ブロックによって効果が違う:

| ブロック | wired GiB | headroom GiB | baseline importModules | 先読みあり | 削減 |
|---|---:|---:|---:|---:|---:|
| **Y** | 1.82–2.18 | 4.81–6.09 | 13.573 | 6.923 | **−49.0%** |
| X | 1.83–2.09 | 4.79–5.00 | 13.283 | 6.943 (j=16) | −47.7% |
| **W** | 3.17–3.39 | 3.83–5.17 | 15.703 | 12.039 | **−23.3%** |

**wired メモリが 2.1 → 3.3 GiB に増えると、効果が半減する。**
先読みしたページを保持できる余地が減るため。**向きは変わらないが大きさは変わる。**

wired が増えた原因は特定できている: **stage4b (完全版の抽出器、peak RSS 3.33 GB) を
16 run 回した後、wired が 2.08 → 4.09 GiB に上がって戻らなかった** (§8)。

### 8.2 cold 側 (**外挿**)

cold の追加コストを stage1 抽出器で実測し (ブロック Y、同一セッションの warm と対比)、

- **足している 11.115 / 4.465 秒は stage1 抽出器で測った値**であって、stage4b で測った値ではない。
  前提は「cold の追加コストは importModules に集中し、後段の意味解析は page cache に鈍感」。

  **実際の cold ペナルティはこれより大きい側に外れうる**。

### 8.3 stage4b を直接測ろうとして失敗した (記録)

cold 合計を外挿ではなく実測で出すため、stage4b (`--equations --refs --tagged-code
--write-ir`) で baseline / overlapped を交互配置 5 対 + warm 6 run を測った。**分離できなかった。**

stage1 の warm (190–385 回) と 2 桁半違う。つまり **stage4b の作業集合
(peak RSS 3.33 GB) はこの機材の当日のメモリ状態に収まらず、

## 9. この計測で分かっていないこと

- **Linux では 1 バイトも測っていない。** 打ち手 1 と同じ穴。ただし**向きが逆**:
  打ち手 1 は「不利な機材で出た否定」で移送できなかったが、
  こちらは**不利な機材で出た肯定**なので、機構 (同期 major fault を並列読みで置き換える) が
  同じなら Linux でも成立する側に寄る — **これは外挿であって実測ではない**。
  加えて **`madvise(MADV_WILLNEED)` は Linux では非同期**なので、
  「read と madvise のどちらが良いか」は**移送できない**。Linux では測り直しが要る。
- **stage4b の cold 合計は実測できていない** (§8.3)。cold 合計は外挿。
- **sequential と overlapped を交互配置で比べていない。** §4 の差は同一ブロック内では
  read の 2 対だけ。
- **`purge` を使った機械全体の cold は測っていない** (sudo を使わない方針)。
  §2 の退避 cold は olean だけを冷やす。
- **先読みが最良の順序で読んでいるかは分からない。** 今の実装はパス名のソート順で読む。
  extract が読む順に合わせれば LRU がもっと味方をする可能性があるが、測っていない。
- **madvise が read より残る理由は同定していない。** 観測事実は
  「同じ所要時間で常駐が 61.8% 対 76.7–90.5%」「下流の fault も少ない」の 2 つだけ。
- **effect size はメモリ regime に依存する** (§7)。この機材の実測レンジは −23% 〜 −49%。
  より広い機材ではさらに大きくなりうるが、**測っていない**。
