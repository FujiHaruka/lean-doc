**何が分離できて、何ができないか:**

* **`j1` 対 `j2` 対 `j4` は分離できている** — 範囲が重ならない
  (j1 の最小 10.73 / j2 の最大 6.30 / j4 の最大 3.64)。
* **`j4` 対 `j8` 対 `j16` は分離できていない** — j4 3.19-3.64 と j8 3.44-3.67 は重なる。
  **言えるのは「2 → 4 で伸び、4 を超えると伸びない」まで**で、「4 が 8 より速い」とは
  言えない。
* `total` の spread は `importModules` の振れ (IR の書き込みが olean の mmap ページインに
  干渉する — CLAUDE.md) が全部担いでいる。**この節の主張は `analyze` の
  フェーズタイマーで立てている。**

### 頭打ちの理由は 2 つ、どちらも実測が示している

1. **M1 は 8 コアだが性能コアは 4 本** (`hw.perflevel0.logicalcpu = 4`)。5 本目以降は
   効率コアに載る。j4 → j8 で壁時計が伸びないのはこれと整合する。
2. **仕事が増えたのではなく、待ちが増えた** — instructions retired は
   139.7 G → 141.1 G (**+1.0%**) しか増えていないのに、cycles elapsed は
   44.5 G → 73.9 G (**+66%**) 増える。命令数がほぼ同じで cycle だけ増えるのは
   ストール (メモリ帯域 / 共有オブジェクトの参照カウント) であって、
   並列化のために余分な仕事をしているのではない。

### `--jobs > 1` の `ppUs` は壁時計ではない

`ppUs` / `eqUs` / `refUs` は**スレッドごとの経過時間の和**なので、j8 で 24.88 s、
j16 で 48.54 s になる。j16 の 48.54 s は user+sys 28.21 s を**超えている** —
16 本のスレッドが 8 コアを取り合って、時計が動いている間に降ろされているため。
**フェーズの `us` (= `analyze`) だけが壁時計である。**

### 並列化が成立する理由 (と、成立しない場合に何が壊れるか)

`run` は宣言ごとに `job.toIO coreCtx { env := env } {} {}` で**新しい `Core.State`** を
作り、その中で環境が変わっても (equation 生成は実際に環境へ定義を足す) **捨てる**。
つまり宣言間に共有される可変状態が無い。`importModules (leakEnv := true)` は環境
オブジェクトを persistent に印付けするので、8 スレッドで共有しても参照カウントの
更新が起きない。

**壊れるとしたら出力順**である。worker はストライドで候補を取り、各答えは候補の
添字を持って帰って `slots` に書き戻される。**§1 の `diff -r` がこれを検査している。**

## 7. まだ言えないこと

* **`--jobs 4` と `--jobs 8` の優劣は分離できていない** (§3)。最適な N は機材依存で、
  この対象・この機材で「4 以上に増やしても伸びない」ことだけが実測。
* **並列化は Linux / CI では測っていない。** M1 の 4P+4E という構成が頭打ちの一因なので、
  同種のコアが並ぶ機材では別の形になりうる (`approach.md` §3 の CI 側は未測定)。
* **`importModules` が新しい最大項になった** (`--jobs 4` で合計の 38.8%)。
