## 1. cold と warm (混ぜないこと)

| | 壁時計 | user+sys | (user+sys)/壁 | peak RSS | page faults | run |
|---|---:|---:|---:|---:|---:|---:|
| **cold** (セッション最初の 1 run) | **0.9331** | 1.1600 | 1.243 | 222 MB | 148 | 1 |
| **warm** (runs 2-6 の中央値 [min-max]) | **0.8239 [0.8229-0.8360]** | 1.1100 [1.0900-1.1200] | 1.347 | 219 MB | 3 | 5 |
| warm・20 run 系列 (runs 2-20) | 0.8368 [0.8176-0.9155] | 1.1300 [1.0800-1.2000] | | | 3 | 19 |

cold / warm = 1.13。**olean の mmap のような 5 倍の振れは無い。**
cold の中身: page fault 148 対 warm 3。IR (15.9 MB) と出力先ディレクトリはこのセッションで
初めて触った。ただし **deno のバイナリと transpile キャッシュは既に warm** だった
(直前に `deno check` を通しているため)。sudo を使わない方針 (計画 §6 事前決定 #6) なので、
`purge` によるページキャッシュ破棄はしていない。**この cold は「IR と出力先が cold」であって
「機械が cold」ではない。**

**warm 判定**: page faults が 148 → 3 に落ちて以降動かない。(user+sys)/壁 は 1.3 前後で
**1 を超える** — これは cold の印ではなく、V8 と tokio の補助スレッドが並行に走っている印。
`CLAUDE.md` の「壁時計 ≒ user+sys なら warm」は単一スレッド前提の判定なので、ここでは
**page fault と、cold/warm の壁時計差 13% の両方**で warm を判定している。

## 4. タイマーの健全性

### 4a. rope の罠 — 文字列生成が書き出しに沈んでいないか (対照実験)

`pageHtml` は `+=` で組み立てるので V8 は cons string を返す。実体化を強制しないと、
その費用は `writeTextFile` の中に落ちて「描画が速い」ように見える。

| | flatten | write | 壁時計 |
|---|---:|---:|---:|
| 既定 (実体化を描画側で強制) | 0.0484 [0.0480-0.0490] | 0.1341 [0.1311-0.1356] | 0.8239 [0.8229-0.8360] |
| `--no-flatten-probe` | 0.0000 [0.0000-0.0001] | 0.1827 [0.1781-0.1979] | 0.8374 [0.8268-0.9075] |
| 差 | -0.0484 | +0.0486 | +0.0134 |

**費用は消えずに移動する**: flatten が 0.0484 秒減ると write が 0.0486 秒増え、
壁時計は +0.0134 秒しか動かない (20 run 系列の中央値 0.8368 秒の散らばりの内側)。
**罠は実在し、既定の分解はそれを踏んでいない。**

## 5. IR の読み出しは既存値を再現するか

| | 秒 | 出所 |
|---|---:|---|
| schema 2 中央値 (増分 2、コミット済み) | 0.1004 | benchmarks/results/stage4b-readir-tag.txt |
| 同、別プロセス 1 read ずつ | 0.1042 | 同上 |
| **今回の再実行** (in-process runs 2-7) | **0.1014** | stage4c-readir-recheck.txt |
| **今回の再実行** (別プロセス runs 2-6) | **0.1049** | 同上 |
| render.ts の read-IR フェーズ | **0.1297** | この表 §2 |

**既存値は再現した** (0.1004 → 0.1014、0.1042 → 0.1049。どちらも記録済みの散らばりの内側)。
render.ts が 0.130 秒と高いのは cold でも計測ミスでもなく、**IR を保持するから**:
`read-ir.ts` は 1 モジュール数えたら捨てるが、レンダラは全部持ち続ける必要がある。
同一プロセス構成で保持の有無だけを変えた対照 (stage4c-read-retain.txt、各 7 run) で
0.0973 → 0.1167 秒 (+0.0194、+20%) となり、差はこれで説明し尽くされる。

## 7. 同一性 (この計測が生成物を変えていないこと)

計装 (フェーズタイマー / `--limit` / `--timings`) を入れた `render.ts` と、
計装前 (HEAD) の `render.ts` の突き合わせ。すべて PASS:

- A. `--pages` 432 ファイルが計装前と **byte 一致**
- B. 2 回の `--pages` が互いに一致 (決定的)
- C. 増分 3 の `--out` JSONL が計装前と byte 一致
- D. `--pages` の有無で `--out` JSONL が動かない
- E. `--stats` の `## decl_header path` ブロックが文字一致
- 出力の実サイズ 29,671,173 バイト / 432 ファイルは README (増分 4 前半) の独立計数と一致

docstring 用の内数タイマーを足す前後で warm 系列を測り直し、中央値の差は
wall +0.9% / readIr +0.9% / renderHeaders −0.0% / renderPage +0.6% / write +0.4%
(20 run 系列) — run 間の散らばりの内側。**cold の 1 run は内数タイマーを入れる前の
バイナリで取ったもの**だが、この差の範囲で warm 側と比較可能。
