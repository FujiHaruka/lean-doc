C2. what doc-gen4 itself does with the names the index does not hold

  doc-gen4's link renderer reads name2ModIdx = env.const2ModIdx (Analyze.lean:243),
  i.e. every constant in the environment, not the 258,760 it published.
  Searched /Users/haruka/dev/lean-projects/.lake/build/doc/InformationTheory for the 3 dependency-side misses:
    Eq.rec                     1 href(s)   anchor on target page: ABSENT -> dead link
    List.recOn                 2 href(s)   anchor on target page: ABSENT -> dead link

  So doc-gen4 already emits hrefs with no anchor to land on. A map-based
  resolver that links only names present in the index is strictly better here:
  those names render as <span class="fn"> instead of a dead link.

  Reading of the shapes:
  - `docLink` repeats the module path for every declaration of that module and then
    repeats the declaration's own name after the `#`. Both are derivable, so
    `name -> module` is the same information with the duplication removed.
  - Interning the module into an index pays off at Mathlib scale (raw halves again)
    but not on a 530-entry slice, where the module table costs more than it saves
    -- there, gzip on the string form is the smaller of the two.
  - Turning `module -> URL` back into a path is increment 3's job. Until that is
    implemented the `name -> module` rows are a measured size, not a working map.

F. is the `kind` column needed for links

  doc-gen4 renders a link in DocGen4/Output/Base.lean:338-381 (`renderedCodeToHtmlAux`,
  the `.const` case). It consults `name2ModIdx` and emits `<a href=...>` or
  `<span class="fn">`. `kind` is never read there, and `declNameToLink`
  (Base.lean:231) builds the href from the module name alone.
  The only reader of `kind` is static/declaration-data.js:177-191, which feeds
  the `allowedKinds` filter of the search page (static/search.js:111,181,
  `.kind_checkbox`). So `kind` is a search-UI column, not a link column.
  -> a link-resolution map needs 2 columns (name, module), not 3.
  The size table above measures the `docLink only` shape for exactly this reason.

H. what these numbers do NOT cover

  - Cold page cache is not measured. Every number in section E is warm. The
    stage 1 finding that cold/warm differ by 5x was about 3+ GB of olean read
    through mmap; a single 37 MB sequential read is a different shape, but that
    is an argument, not a measurement. Treat any cold figure as UNMEASURED.
  - Load time is `Deno.readTextFile` + `JSON.parse` on V8. It is a property of
    this runtime as much as of the file. The implementation language of the
    non-Lean side is not decided (approach.md 5.6), so this is one data point,
    not the number for whatever ships.
  - The demand side (533) is signature + equation + structure parents only.
    Docstring links go through a separate path in doc-gen4
    (DocGen4/Output/DocString.lean) and are increment 3's material. The lower
    bound can only grow when they are added.
  - 533 is *this* package's demand. Nothing here extrapolates it to another
    package, and the map a resident server must hold is not the per-package
    demand.
  - The .bmp is the artifact of a build that was stopped at 42%. That affects
    the own-package rows of the coverage table and the count of target modules
    that contributed declarations (366 of 432). The dependency side is not
    visibly affected: 5,716 dependency .html pages exist under
    .lake/build/doc (6,080 total, minus 348 InformationTheory, 15 top-level
    namespace pages and find/find.html), and all 530 dependency docLinks
    resolved to a file with the right anchor.
  - The blacklist classification in section B is by *name shape*. doc-gen4's
    `isBlackListed` (DocGen4/Process/DocInfo.lean:151) also asks the
    environment (isAuxRecursor / isRec / isMatcher / isProjFn), which cannot be
    reproduced from a name alone. The three dependency-side misses are all
    recursors, where the two agree; a name-shape rule is not proven equivalent
    in general.
