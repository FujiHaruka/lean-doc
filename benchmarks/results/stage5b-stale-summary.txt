## 3. E2 — S2「影響集合は実際に変わるページを全部含む」

docstring の autolink は「名前 → 定義モジュール」の**全域写像** (`render.ts` の `known`) を
引くので、import と無関係にページが変わりうる、という仮説を実測で決めた。

### 3a. 何を注入するかを決めるための候補の分布 (実測、選定より先)

無改造の `render.ts` に計装コピーを作り (`instrument-render.py`)、
**autolink が失敗しているトークンを全部数えた**。計装コピーが出力を変えていないことは
432 ページのバイト一致と `autolinkAttempts` / `autolinkResolved` の一致で確認済み。

| | distinct | occurrences |
|---|---:|---:|
| autolink の試行 (全体) | — | 122,403 |
| うち解決した | — | 5,080 |
| **失敗したトークン** | **8,965** | **117,323** |
| うち `render.ts` の `isNameLit` を通る | 4,241 | 47,547 |
| うち宣言名の形をしている (全ドット成分が識別子、3 文字以上) | 2,930 | 10,745 |
| **うち 2 ページ以上に出る** | **997** | **8,070** |

宣言名形の候補の出現ページ数: median 1 / p90 3 / **max 138**。

**選定規則を先に決めた: 宣言名形の候補を出現ページ数で並べ、最大のものを機械的に採る。**
→ **`log`** (138 ページ / 638 回)。次点は `volume` 44、`Measure.pi` 44、`μ.map` 39。
「たまたま効いたものを選んだ」を避けるため、(i) 規則は分布を見る前に決め、
(ii) §3d で 432 通りの N すべてと 1,095 候補すべてに広げて確かめている。

注入先 N は**増分 1 で選んだ 2 モジュールをそのまま使った** (今回の結果を見て選んでいない):

| | モジュール | 推移 importers |
|---|---|---:|
| leaf | `…Shannon.Kolmogorov.OmegaNoncomputable` | 1 |
| hub | `InformationTheory.Meta.EntryPoint` | 414 (パッケージの 95.8%) |

### 3b. 真の変更集合と機構の集合 (実測)

`ir-base` と `ir-after-*` からそれぞれ 432 ページをフル生成し、バイト比較した。
`autolinkResolved` は 5,080 → **5,730** (+650)。

| 注入先 N | 真の変更ページ | mode | 機構の集合 | **stale** | gratuitous |
|---|---:|---|---:|---:|---:|
| leaf | 142 | `self` | 1 | **141** | 0 |
| leaf | 142 | `referrers` | 1 | **141** | 0 |
| leaf | 142 | `importers` | 2 | **141** | 1 |
| hub | 142 | `self` | 1 | **141** | 0 |
| hub | 142 | `referrers` | 1 | **141** | 0 |
| hub | 142 | **`importers`** | 415 | **3** | **276** |

142 = 新たにリンクになる 141 ページ + N 自身のページ。
**`--mode importers` は「健全な上界」として増分 1 の README §4 が宣言したものだが、
hub でも 3 ページを取りこぼし、同時に 276 ページを無駄に書き直している。**

### 3c. stale なページの実物 (実測)

hub の `--mode importers` でも stale な 3 ページ:
`InformationTheory.Fano.BinaryJensen` / `…Shannon.EPI.G2.KLVariationalLower` /
`…Shannon.Kolmogorov.EntropyRateUpper` (いずれも `Meta.EntryPoint` を推移的に import しない)。

`Fano.BinaryJensen` の docstring:

    変更前: <code>m * negMulLog (x / m) = negMulLog x + x * log m</code>
    変更後: <code>m * negMulLog (x / m) = negMulLog x + x * <a href=
            "../.././InformationTheory/Meta/EntryPoint.html#log">log</a> m</code>

`x * log m` の `log` が、import していないモジュールのページへのリンクになる。
ページは 12,625 → 12,690 バイト。全文は `stage5b-e2-excerpt.txt`。

### 3d. 「たまたまか」を潰す — 全 N・全候補への外挿 (**導出**、実測 2 点で検証済み)

外挿のモデル: 名前 X をモジュール N に足すと、「X がトークンそのもの」または
「最後のドット以降が X」(= `autoLinkInline` の 2 回目の試行) として失敗していたページが
新たにリンクになる。**このモデルは上の 2 つの実測に対して EXACT に一致した**
(leaf 142 対 142、hub 142 対 142)。以降はそのモデルの計算値。

| | |
|---|---|
| `log` を 432 通りの N すべてに順に注入したときの `--mode importers` の stale | **min 3 / median 137 / max 141** |
| stale が 0 になる N | **0 / 432** |
| 候補 1,095 個 × N 432 通り = 473,040 組のうち stale ≥ 1 | **446,333 (94.4%)** |
| 候補ごとの「N を変えたときの stale の中央値」 | median 2 / p90 7 / max 137 |
| 最も都合の良い N を選べたとして stale 0 になる候補 | 1,035 / 1,095 (94.5%) |

最後の行は「N を選べるなら閉じることが多い」を意味するが、**N は編集する人が決めるので
選べない。** 実際に起きる組の 94.4% で取りこぼしが出る。

### 3e. 判定

**S2 は否定された。** 否定条件 (「どの mode でも stale が 1 ページ以上残る」) を、
2 つの注入先いずれでも満たしている。増分 1 の README §4 の

> **The sound bound is the reverse transitive import closure.**

は**elaboration については正しく、生成されるページについては偽**。
`render.ts` の `known` も doc-gen4 の `name2ModIdx` も import で閉じていない。

## 4. E4 — S4「消えたモジュールは何も残さない」

対象の olean は消していない。432 モジュールのシンボリックリンクツリーを作り、
そこから 1 本消した。生ログ: `stage5b-e4-deletion.txt`。

### 4a. 台帳側 (実測)

| 操作 | 結果 |
|---|---|
| リンクツリーで `check` (基準) | 0 changed |
| **olean を 1 個消して `check`** | **例外で落ちる。** `Error: no olean for InformationTheory.Fano under …` (`ledger.ts:121`)、**exit 1**、`--changed-out` は書かれない |
| 戻して、**新規モジュールのリンクを 1 本足して** `check` | ディスク上 433 個。**`check` は 432 モジュールを見て 0 changed。新規は不可視** |

`incremental.sh` は `set -euo pipefail` (36 行目) なので、削除ケースでは
**パイプライン全体がその場で停止する** (「deleted と報告する」でも「無視する」でもない)。
新規ケースが見えないのは、台帳のモジュール一覧が `build` 時の `--modules`
ファイルで凍結されるため (`ledger.ts:174`)。ディスクを走査する経路は無い。

### 4b. IR とページ側 (コード + 実測)

- 削除経路をコードで探すと、`Deno.remove` は `merge-ir.ts:208` の
  **`deps/*.json` の掃除 1 箇所だけ**。`render.ts` にも `ledger.ts` にも
  モジュールを消す経路は無い。`merge-ir.ts` の `order` は base の index から作られ、
  inc に無いモジュールは**そのまま残る**。
- 実測: IR から `InformationTheory.Fano` (22 宣言) を消して 431 モジュールを再生成した。

| | |
|---|---:|
| 再生成したページ | 431 |
| ディスク上のページ | **432 (減らない)** |
| 消えたモジュールのページ | **残る。削除前とバイト一致** (56,385 B) |
| そのページへリンクし続ける生きたページ | **4** |
| 残り 431 ページのうちバイトが変わったもの | **0** |

最後の 0 は事前の想定と違う: `render.ts` は `known` を `refs` からも埋めるので
(`render.ts:1357`)、他モジュールの `refs` が消えたモジュールを指し続ける限り
リンクは**生成され続ける**。つまり削除は「古いページが残る」だけでなく
**「生きているページが、消えたはずのページを指し続ける」**形で現れる。
リンク先のファイルも残っているので、この木の中では 404 にすらならない。

### 4c. 判定

**S4 は否定された。** 否定条件 3 つ (ページが残る / 台帳エントリが残る /
パイプラインが例外で落ちる) のすべてを満たしている。

## 6. 事前予測と食い違ったもの

行レベルでは 4/4 が予測どおり (すべて refuted)。中身で食い違ったのは 5 点。

1. **`--mode importers` は「取りこぼすか否か」ではなく「取りこぼしつつ無駄も出す」だった。**
   hub で stale 3・gratuitous 276。健全な上界のつもりだったものが、
   上界でもなければ精度も低い。
2. **削除で他のページは変わらない** (§4b)。`render.ts` が `refs` からも `known` を埋めるため、
   消えたモジュールを指すリンクは生成され続ける。「消えたページが残る」より
   「生きたページが消えたページを指す」ほうが実害が近い。
3. **`envChanged` は計算されているのに使われていないだけでなく、実パイプラインでは
   IR スキーマの 2 項目がそもそも比較されない** (`incremental.sh` が `--ir` を渡さない)。
   予測は「`--source-url` が `envKey` に無い」までしか言っていなかった。
4. **class b の成果物がこの doc ツリーに 1 つも無い** (per-module の `.bmp` と
   `backrefs-*.json`)。ソース上は存在するので、「0 個だから考えなくてよい」ではない。
5. **`log` は 432 通りの N すべてで stale ≥ 3。** 「N の選び方次第で閉じることがある」
   (候補全体では 94.5% が最良 N で stale 0) のに、最も影響の大きい候補では
   逃げ道が 1 つも無い。
