# 段 E — 核の githash を `lake env` 抜きで聞く (2026-08-17)

`resolve_external_links` は Lean core の revision を知るために
`lake env lean --githash` を叩いていた。これは **`build` 自身の clock の外**で走るので
`--timings` には出ないが、wall では **0.763 s**【実測 → `g3-attribution-2026-08-17.txt`】、
1 モジュール変更 5.33 s のうち環境ロードの床に次ぐ大きさだった。

**その 0.763 s はほぼ全部 Lake の起動**で、`--githash` は Lake が用意するもの
(`LEAN_PATH`、ビルド木、依存) を 1 つも使わない。使うのは toolchain の選択だけで、
**それは Lake ではなく elan の仕事** — elan の `lean` shim は `lake env lean` が最終的に
呼ぶのと同じ shim で、同じ `lean-toolchain` を作業ディレクトリから解決する。

## 前提の実測 — 2 つの綴りは同じ答えを返す

機材 M1 / Darwin 25.6.0。`/usr/bin/time -p`。

```
                          対象 (lean-projects)        第 2 の対象 (target2)
lake env lean --githash   68218e876d2a38b1...  0.84s  68218e876d2a38b1...  0.98s
lean --githash            68218e876d2a38b1...  0.03s  68218e876d2a38b1...  0.03s
                          ^^^^^^^^^^^^^^^^^^ 同一      ^^^^^^^^^^^^^^^^^^ 同一
```

**陽性対照** — shim が本当に作業ディレクトリを見ているか:

```
$ cd /private/tmp && lean --githash
error: no default toolchain configured. run `elan default stable` ...
```

**`lean-toolchain` の無いディレクトリでは答えが存在しない。** つまり上の一致は
「たまたま同じ既定を返した」ではなく、**同じ toolchain を同じ経路で解決している**こと。

## 危険と、それをどう扱ったか

- **間違った revision を返しても「エラー」にはならない** — Lean core への外部リンクが
  全部間違った commit を指すだけで、無診断。だから前提 (2 つの綴りが同じ答え) を
  **実装より先に、両方の対象で、陽性対照つきで測った。**
- 残る番人は 2 つ: `is_revision` (40 桁の 16 進でなければエラー) と、値が
  `renderKey.externalLinks` に入ること — 動けば**全ページ再描画という騒がしい形**で出る。
- `--lake <path>` を渡すと `lean` は**その兄弟**から取る。toolchain 局所の lake を
  名指しした呼び手は、その toolchain の lean を意味しているため (`PATH` の先頭ではなく)。

## 壁時計 — 対象 (422 モジュール)、1 モジュール変更の交互 A/B

各サイクルで 1 宣言を足して `lake build` し、両バイナリを**順番を入れ替えながら**回す
(2 番目に走る方が page cache で得をするので、固定順は片方に下駄を履かせる)。
`outside` = wall − `build … in X s` = **`resolve_external_links` (置き換えた呼び出し) + 引数処理**。

```
run              wall    inside   outside
A1  before      6.97s   6.1558s   0.814s
B1  after       4.38s   4.3418s   0.038s
B2  after       4.80s   4.7660s   0.034s
A2  before      4.73s   3.9694s   0.761s
A3  before      7.05s   6.2524s   0.798s
B3  after       4.35s   4.3152s   0.035s
B4  after       4.79s   4.7568s   0.033s
A4  before      4.95s   4.1939s   0.756s
```

| | before (段 D) | after (段 E) |
|---|---|---|
| **outside 中央値** | **0.780 s** | **0.0345 s** |
| wall 中央値 | 5.96 s | 4.59 s |
| inside 中央値 | 5.17 s | 4.55 s |

**取り分は outside の −0.745 s。** ここは**暖機の影響を受けない** — 同じ 1 つの子プロセスを
起こすかどうかの差で、両者とも毎 run 同じ仕事をする。実際 before の 4 回は
0.756〜0.814 s、after の 4 回は 0.033〜0.038 s に収まっている。

**wall の差 (1.37 s) をそのまま取り分として引用しない** — inside が before で
3.97〜6.25 s と散っており (page cache)、その散らばりが乗っている。
**取り分として主張できるのは outside の 0.745 s。**

## 途中で起きたこと — ディスク満杯【記録】

最初の A/B はディスク満杯で落ち、**中断された `lake build` が対象の olean を 1 つ
欠落させた**。ソースは `git checkout` で戻したがディスクが無くて `lake build` ができず、
**シェルコマンド自体が動かなくなった** (ハーネスが出力ファイルを作れない)。
空きを作ってから `lake build InformationTheory` で復旧
(`Build completed successfully (3769 jobs)`)、ソースツリー clean を確認してから測り直した。
→ 規則を CLAUDE.md「ベンチマーク」に追加した。
