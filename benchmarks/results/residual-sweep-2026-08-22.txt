## 1. R1 — prototype の 7 キーを 1 箇所に集めた

### 何が壊れていたか

`crates/litedoc4-global/tests/state_and_delta.rs` の
`the_state_file_is_the_prototypes_bytes` が、書かれた state ファイルの
1 モジュールぶんのキー列を **「prototype の 7 キー + `instancesFor` 1 個」** と
主張していた。feature-sweep C-2 が `ModuleFacts::refs` を足したので、HEAD では
**9 キー**。この assert は偽で、**誰も気づかなかった**。

気づけなかった理由は「凍結テストだから」だけではない。**同じ 7 キーの転写が 2 本あり、
形が違った**:

| | 形 | フィールドが増えたとき |
|---|---|---|
| `tests/global.rs::Facts` | **射影** — 7 キーだけを再直列化する | 見えない。壊れない |
| `tests/state_and_delta.rs` | **差分** — 「7 キー + 手書きの追加リスト」 | 腐る。しかも凍結なので黙って腐る |

CLAUDE.md「判断は 1 箇所に集める。同じ問いに答える経路が 2 本あると、片方だけ直る」の
実例で、実際に射影の側だけが生き残った。

### 直した形

1. `litedoc4_global::PROTOTYPE_FACT_KEYS` (7 キー) を置いた。転写 2 本はこれを参照する。
2. **構造の主張を機材ゼロ依存のテストへ移した** — `facts.rs` の
   `tests::the_prototypes_keys_come_first`。「直列化キー列は 7 キーで**始まる**」は
   `ModuleFacts` の値 1 つで決まり、corpus も prototype state も要らない。
   **`#[ignore]` ではない。今日から走る。**
3. 凍結テスト側の手書き追加リストを消し、`starts_with` にした。**腐る場所が無くなった** —
   以後どのフィールドが増えても編集は要らない。
4. `tests/global.rs` に `the_shim_is_the_prototypes_keys` を足し、射影が単一の
   定義と一致していることを検査する。

### 落として通した【実測】

| 落とし方 | 出た結果 |
|---|---|
| `ModuleFacts` の `instances_for` を `module` の前に移す | `the_prototypes_keys_come_first` が FAILED。`left: ["instancesFor", "module", ...]` |
| `tests/global.rs::Facts` の `module` と `content_hash` を入れ替える | `the_shim_is_the_prototypes_keys` が FAILED。`left: ["contentHash", "module", ...]` |

**この 2 つはどちらも、直す前は何も落とさなかった失敗である。**

### 数の pin をやめた 1 件

`assert_eq!(got.len(), 861_999)` を消した。`got.len()` は **HEAD と
`LITEDOC4_IR` が指す corpus の積**で、裸の整数では落ちたときにどちらが動いたか
言えない。**そして片方は既に動いている** (C-2 の `refs`)。
数字は条件ごとコメントに残した:

- v1 ファイル **841,947 B**、`instancesFor` が **432 モジュール**で **20,052 B**、
  合計 **861,999 B**【実測 2026-08-16】
- `refs` は **422 モジュールの IR で 472,440 B**【実測 2026-08-22 →
  `usedby-2026-08-22.txt` §3】。**432 モジュールでの値は無い** — その corpus は
  この機材に無く、対象パッケージも 432 モジュールではない

残した assert は corpus が決めないもの: `got.len() == summary.state_bytes` /
`shim.len() == 841_947` / 各モジュールが 7 キーで始まり 7 キーとも一致すること。

### 緑

`cargo test --workspace` = **36 バイナリ / 435 passed / 0 failed / 21 ignored**。
`cargo fmt --check` / `cargo clippy --workspace --all-targets -- -D warnings` ともに緑。


## 2. R2 — NOTICE が closure を網羅していなかった

### 抜けていた件数【実測】

`docs/provenance.md` §8 が 2026-08-22 に起票した未検証項目。**実際に抜けていた。**

編集前の NOTICE に対して `tools/provenance-gate.sh` を回した結果 (exit 1):

    NO NOTICE     generic-array
    NO NOTICE     math-core
    NO NOTICE     math-core-renderer-internal
    NO NOTICE     memchr
    NO NOTICE     phf
    NO NOTICE     phf_generator
    NO NOTICE     phf_macros
    NO NOTICE     phf_shared
    NO NOTICE     sha2-asm
    NO NOTICE     strum
    NO NOTICE     strum_macros
    NO NOTICE     unicode-ident
    NO NOTICE     zmij

**13 件。起票時の見積り (`strum` / `strum_macros` / `phf` 系 /
`math-core-renderer-internal` = 6 件) は過小だった。** 見落としていたのは:

- **`generic-array` (MIT)** — `sha2` → `digest` → `block-buffer` 経由。**バイナリに入る**
- **`zmij` (MIT)** — `serde_json` 経由。**バイナリに入る**
- **`memchr` (`Unlicense OR MIT`)** — 「MIT 単独」ではないが Apache では払えない
- **`unicode-ident` (`(MIT OR Apache-2.0) AND Unicode-3.0`)** — 同上。`AND` が効く
- **`sha2-asm` (MIT)**
- **`math-core`** — 独立した節はあったが**導出セクションには居なかった**

**「MIT 単独」という言葉が判定として弱かった**のが見積りを外した原因で、
判定は「**Apache-2.0 単独では満たせないか**」に言い換えた (→ `provenance.md` §7)。

### 判定の形

対象は `release.yml` の matrix から読む (**`x86_64-unknown-linux-musl` と
`aarch64-apple-darwin` の 2 つ**)。2 つの closure の差は `libc`
(`MIT OR Apache-2.0`) 1 件だけだが、**片方だけ見て網羅を主張するのは
黙った狭め**なので両方取る。

covered の判定は `licence =~ /Apache-2\.0/ && licence !~ / AND /`。
**例外リストは持たない。**

### 落として通した【実測】

| 落とし方 | 出た結果 |
|---|---|
| 編集前の NOTICE (= 起票時の状態) | `NO NOTICE` × 13、exit 1 |
| 実在しない `not-a-crate` を足す | `STALE ENTRY not-a-crate ...`、exit 1 |
| `strum` の行を消す | `NO NOTICE strum ...`、exit 1 |

### 最初の落とし方でゲート自身の欠陥が出た【実測】

編集前の NOTICE に対する 1 回目、ゲートは **`files: ok (31 claims)` だけ印字して
黙って終了した**。原因は `grep` が 0 件で 1 を返し、`set -e` が
コマンド置換ごとスクリプトを殺していたこと。**終了コードは非ゼロなので CI は
赤くなるが、何が壊れたかは 1 行も出ない** — CLAUDE.md
「落ちたときに何が壊れたか 1 行で言えないゲートは足さない」に、
**ゲート自身が該当していた**。`|| true` を 2 箇所に付けて直し、理由をコメントに残した。

**この欠陥は「一度落とす」をやらなければ出なかった** — 緑の側では発火しない枝である。


## 3. R3 — ギュメ付きモジュールを持つ「版固定できる依存」

### 作り方 — 新しいパッケージもネットワークも要らなかった

未検証項目の本文は「**どれも『作れば測れる』もので、機材が無いのではない**」。
**額面どおりだった。** 既存の `e2e/micro-dep` (ギュメ付きの lib root `«Dep-Aux»` を持ち、
`e2e/micro` が path で require している) を**そのまま git リポジトリにして**、
require を差し替えるだけで版固定できる側に落ちる。

    e2e/micro-dep → git init (固定 author/committer/date) → 40 桁 rev
    e2e/micro の [[require]] を path から git + rev へ
    lake update → manifest entry が type: git になる

**モジュールも docstring も toolchain も同一で、動く変数は版固定可能性だけ。**
rev は `e2e/micro-dep` の内容の関数 (同じ手順を 2 回回して同一 —
`12d40c1a6c5921da6cdb29fbd57fdee273071ab4`)。ただしゲートは**この値を pin しない** —
自分で作った rev を manifest から読み戻して突き合わせる。

### ネットワーク無しで https の URL を manifest に載せる

`git` の `insteadOf` を `GIT_CONFIG_COUNT` 経由で渡す。Lake は
`https://example.invalid/micro-dep` を clone しているつもりで、実際には
`file://<work>/dep` から取る。**manifest に残るのは https の方**。

**最初は素直に `file://` を require に書いて、それで一度落ちた**【実測】:

    DEAD internal links : 5 (1 distinct destinations, 1 pages)
       5  Micro/file:/private/tmp/.../dep/blob/<rev>/Dep-Aux/Basic.lean

`site-gate.sh` が `file:` を外部スキームと認識せず、`Micro/` からの相対リンクとして
解決していた。**製品の欠陥と区別がつかない形の、ハーネスの欠陥。**
CLAUDE.md「両方向で同時に落ちる差分は、対象ではなく比較器を疑う」の変種で、
**疑うべきは自分が作った入力の方だった**。

### 測った結果【実測 2026-08-22】

対象: `e2e/micro` (10 モジュール / 92 宣言) + `«micro-dep»` (git, rev 40 桁)

| | 結果 |
|---|---|
| blob URL | `https://example.invalid/micro-dep/blob/<rev>/Dep-Aux/Basic.lean` |
| **ギュメの扱い** | **URL から落ちている** (`«Dep-Aux»` → `Dep-Aux/`)。href に `«` は 1 つも無い |
| dead internal links | **0** (internal 296 / external 225) |
| site-gate 全体 | **ok** (9 種すべて 0 failed) |
| `«Dep-Aux».Basic` (IR の綴り) | **リンクする** (2 箇所: import リストと docstring) |
| `Dep-Aux/Basic.lean` (source path) | **リンクする。同じ URL** |
| `Dep-Aux.Basic` (`.lidx` の綴り) | **リンクしない** |

**恐れていた壊れ方は無かった。** 版固定できる依存のギュメ付きモジュールへの
blob URL は正しく組める。

### 残ったのは欠陥ではなく仕様の判断 1 件

3 綴りのうち `.lidx` の綴りだけ解決しない。**これは「同じ問いに答える経路が 2 本ある」形**で、
`module_for_source_path` は escape してから引き、名前解決器は引かない。
どちらが正しいかは測定では決まらない (unescape は一般には曖昧 — `«A».«B»` の
unescape は実在しうる `A.B` と衝突する)。→ `docs/plans/residual-sweep.md` R3。

ゲートは**今の答えを pin している**ので、解決するようになったら落ちて、
判断とゲートを同じコミットで動かすことを要求する。

### 落として通した【実測】

| 落とし方 | 出た結果 |
|---|---|
| path require のまま (= 版固定できない側) | `lake update` が段 2 で落ちる (exit 1) |
| `lake update` 後に rev を `main` へ書き換える | `FAIL rev is 'main', not 40 hex digits` → **以降を実行せず終了** |
| 期待する blob URL を別ホストにする | `FAIL «Dep-Aux».Basic: links to [...], wanted ...` × 2 |

2 つ目の早期終了は意図的 — **shape が違えば以降の assert は「版固定できない側」を
検査して通ってしまう**ので、そこで止める (CLAUDE.md「『測った』の前に『測れる状態か』」)。

### 【外挿】RAM の小さいランナー — 算術で決まる

未検証項目が心配していたのは「同じジョブに置けば環境ロードは warm のまま
(1.08〜1.58 倍)」が小 RAM で崩れること。**崩れる。しかも大きいパッケージのせいではない。**

warm であるためには、**抽出プロセスの anonymous メモリと、Mathlib の olean が
page cache に載っている分が、同時に RAM に収まる**必要がある:

| | 抽出 peak RSS | + olean 5.7 GB | 15.6 GiB ランナー | 7 GB ランナー |
|---|---|---|---|---|
| 対象 422 モジュール | 約 3.3 GB | **9.0 GB** | 収まる (余裕 6.6 GB) | **収まらない** |
| Mathlib 8,169 モジュール | **5.70 GB** | **11.4 GB** | 収まる (余裕 4.2 GB) | **収まらない** |

**【外挿】7 GB のランナーでは、対象 422 モジュールですら warm を保てない。**
プロセス単体で 3.3 GB、olean が 5.7 GB で、合計が RAM を超える。
**大きいパッケージは余裕を 6.6 → 4.2 GB に削るが、境界を越えさせるのは RAM の方**。
cold 側の罰則は既存実測で **5.2〜11.9 倍**。

**この外挿の前提を明記する** (CLAUDE.md「理論値」):

1. **peak RSS は macOS/ARM の値**。Linux/x86 の同じワークロードでは違いうる
2. olean 5.7 GB が**全部**必要とは限らない。`importModules` は mmap で読むので、
   実際に触れるページだけが要る。**その割合はここでは測っていない**
   (`ci-olean-residency.yml` が Linux で 62.4% を測っている、n=1)
3. ランナーの RAM のうち OS と他プロセスが使う分を引いていない

**だから「7 GB で落ちる」ではなく「7 GB では warm を仮定できない」が結論。**
実際に小 RAM の Linux ランナーで回すのは**未検証のまま**
【決定 2026-08-22、ユーザー判断 — 手元の実測から外挿して書き、CI 往復はしない】。

### ハーネス側で 2 回踏んだ

1. **olean からモジュール一覧を作った** → 旧 Mathlib の残留 54 件が混ざり、
   `incompatible header` で落ちた。ソース木と突き合わせて解決。
2. **`--no-link-index` で描画した** → `Setoid.iseqv` に定義モジュールが無く、
   767 ページ目で停止。`.lidx` は**まさに「パッケージが宣言しない名前」の受け皿**で
   (2026-08-17 の batteries の件で入った)、そこを塞いだのは自分。
   link index 付きで **8,169 / 8,169 完走**。

**2 件とも「製品が落ちた」ように見えて、壊れていたのは入力の作り方。**
CLAUDE.md「両方向で同時に落ちる差分は、対象ではなく比較器を疑う」の、
比較器ではなく**自分が用意した入力**を疑う版。


## 5. R3 の判断 — `.lidx` の綴りを解決させた【決定 2026-08-22、ユーザー判断】

### 何が起きていたか — 写像に無かったのではない

§3 が出した非対称 (`Dep-Aux.Basic` だけリンクしない) の原因を追ったら、
**その文字列は引かれてすらいなかった**。`nameToLink` の 1 行目が
`is_name_lit(s)` で、`Dep-Aux.Basic` は **`-` が `isIdRest` でないので名前リテラルではない**。

    is_name_lit("«Dep-Aux».Basic")  = true   → branch 3 が答える
    is_name_lit("Dep-Aux.Basic")    = false  → 1 行目で None

`is_name_lit` は doc-gen4 の `isNameLit` の転写で、**あらゆる code span の入口**。
緩めれば何が名前かの定義が全体で動く。**緩めずに、弾かれた側に逆引きを足した。**

### 実装 — `NameIndex::module_for_unescaped`

非エスケープ綴り → モジュール名の写像。**クエリを escape する方式は取らない** —
unescape は単射でなく、`«Dep-Aux».Basic` と `«Dep-Aux.Basic»` は**どちらも**
`Dep-Aux.Basic` に潰れる。写像なら**衝突がビルド時に見えて項目を落とせる**

### 実装中に 1 回踏んだ — `known_modules` は綴りが混ざっている【実測】

最初の版は「実在モジュールが既にその綴りを持つなら写像に入れない」というガードを置いた
(`modules.contains(&spelling)`)。根拠は「その文字列は名前リテラルだから branch 3 が答える、
だからここは到達しない」。

**そのガードで、写像は書いた当のフィクスチャで空になった。**
デバッグ出力:

    DBG unescaped={} modules_with_quote=["«Dep-Aux».Basic"]

**`known_modules` は綴りの混合物**だった — IR が `«Dep-Aux».Basic` を入れ、
`.lidx` の `@` 節が**同じモジュールの** `Dep-Aux.Basic` を入れる。
**集合に居ることと、branch 3 で到達できることは別の問い**で、
バイトが動くかを決めるのは後者だけ。ガードは `is_name_lit(&spelling)` に直した。

**「到達可能性」を「集合の要素であること」で近似したのが誤り。**
CLAUDE.md「入力の同一性を『パス』で判定しない」と同型 —
**判定に使った性質が、主張したい性質とずれていた**。

**単体テストは最初から通っていた** (フィクスチャを `module_name` で直に与えるので
`.lidx` 由来の綴りが入らない)。**捕まえたのは実物のフィクスチャを通した実走だけ** —
§3 でゲートを作っておいたことがそのまま効いた。
