# stage 7g — 常駐の取り分は `--jobs 4` でも同じか / 常駐は 600 要求に耐えるか

段階 6a は常駐を `incremental.sh` に配線して **7.940 → 6.168 秒 (−22%)** を出したが、
そのときの抽出器は **stage4b (IR schema 3・`--jobs` 無し)** だった。段階 7d で抽出器は
**schema 4 + `--jobs N`** になり、意味解析は 3.23 倍になって**最大項が `importModules` に移った**。

常駐が取り除くのはまさにその `importModules` である。だからこの段階の問いは 2 つ:

1. **常駐の取り分は `--jobs 4` 前提でも同じか。**
2. **常駐は 600 要求に耐えるか** (`approach.md` §8 の「6 要求は 600 要求について何も言わない」)。

数字の SoT は `benchmarks/results/stage7g-{y0-gate,main,soak}.txt` と
`benchmarks/results/stage7g-{incremental,full-extract,soak}.jsonl`。
ここには**何をなぜ変えたか**と**命題・撤退ライン**を書く。

## 撤退ライン

* **Y0 が偽なら以降を止める。** 「常駐と並列は併用できない」が結論になり、本配線は
  **`--jobs 1` の常駐**か**`--jobs 4` の単発**かの二択に落ちる (どちらを取るかは Y2/Y3 の
  数字ではなく、その二択自体を測り直す別の段階になる)。
* **Y1 が偽なら速度の数字は全部無効。** 段階 5e/5f/6a と同じ規律で、判定オラクルは
  「from-scratch サイトとの byte 一致」であって、パイプライン自身の "0 stale" 報告ではない。
* **Y4(a) が偽なら常駐の寿命に上限が要る** (「N 要求ごとに立て直す」)。
  (b)(c) だけが偽なら上限は緩い — 数字が示す本数で切ればよい。

### `--serve auto` の設計上の選択

* **起動時間はパイプラインの壁時計の内側**。それが「1 パイプライン 1 台」の正直なコストで、
  外に出したら `fresh` との比較が成り立たない。停止も同じ理由で内側に入れてある
  (`serveStartSeconds` / `serveStopSeconds` として**内訳には出す**が、差し引かない)。
* **`--jobs` はサーバにも単発にも同じ値を渡す。** 比較が jobs で揃わなければ
  「常駐の取り分」ではなく「常駐と並列の取り分の混合」を測ることになる。
* **`--serve auto` は安全な形しか作れない。** サーバを立てるのはビルドの後に始まる run の
  中だけなので、段階 6a が誤答を出した「編集をまたいで生きたサーバ」は構成できない。
* `soak.sh` の要求ループだけは `serve-ctl.sh request` を使わず同じプロトコルを話す。
  あちらは 0.1 秒ポーリングで、1 要求 30〜90 ms のソークでは**量子化がそのまま計測になる**。
  起動と停止は `serve-ctl.sh` を通すので、trap のある部分の実装は 1 つのまま。

## 計測の規律 (この段階で守ったこと)

* 変種は**同一セッション内で回り持ち**、7 ラウンド (Y2) / 5 ラウンド (Y3) 回して
  1 ラウンド目を捨て、中央値と [min–max] を出す。
* **cold と warm を混ぜない。** すべて同一セッションの warm。cold 側は測っていないので
  この段階は cold について何も言わない。
* **サーバは 1 台ずつ。** 抽出器の peak RSS が 3.3 GB で 16 GB 機なので、
  2 台 + 単発は paging を招き、それが timings に乗る。
* `diff` は zsh で未インストールの `colordiff` に alias されているので、
  スクリプト内は**必ず `/usr/bin/diff`**。exit 127 を「差あり」と誤読した事故が過去にある。

## 段階 6a の数字と並べてよいか

**並べられない。** 抽出器が **stage4b (schema 3) → stage7d (schema 4)** に変わっていて、
レンダラも `stage4c/render.ts` → `stage7d/render.ts` に変わっている。
段階 6a の 7.940 / 6.168 秒は**別のワークロード**の数字である。
**この段階の `fresh-j1` が新しい基準**で、比較はその中で閉じている。

### Y0 — 門番は通った

対象 432 モジュールのうち **26 個** (17 個おきに拾って偏りを避けた) を
`serve --jobs 1` / `serve --jobs 4` / 単発 `--jobs 1` / 単発 `--jobs 4`、
および**同一サーバへの独立 2 要求**で抽出し、`/usr/bin/diff -r` で 5 組すべて**無差**。
`considered 505 / produced 265 / blacklisted 240 / equations 40 / refOccurrences 8,445 /
spans 22,972` も 5 構成で完全一致。

**サーバ起動時間は `--jobs` で動かない** (`--jobs` は `analyze` しか割らないので、
そうなるはず — 確認した)。この段階で取れた起動の全標本:
y0 **j1 3.514 / j4 3.584**、Y2 の run 内 **j1 3.705 [3.680–4.164] / j4 3.693 [3.685–3.714]**、
Y3 **j1 3.603 / j4 3.809**。**jobs による系統差は無く、分離もできていない**
(全体のばらつき 3.51〜4.16 秒のほうが大きい)。

**抽出器 (Lean 側) の改修は要らなかった。** `serve` は `run reqCfg (some env)` を
呼ぶだけで `cfg.jobs` をそのまま引き継ぐ (`Extract.lean:2722`)。
ただし**要求ごとの `--jobs` は無い** — 起動時の値が全要求に効く。

### Y1/Y2 — 2 ラウンドの増分ケース

| 変種 | 中央値 | [min–max] | うち extract | うちサーバ起動 | サイト |
|---|---:|---:|---:|---:|---|
| `fresh-j1` | **7.968** | [7.928–8.151] | 5.967 | — | 439/439 一致 |
| `fresh-j4` | **7.894** | [7.825–7.950] | 5.895 | — | 439/439 一致 |
| `res-j1` | **6.668** | [6.585–7.109] | 0.731 | 3.705 | 439/439 一致 |
| `res-j4` | **6.509** | [6.457–6.571] | 0.604 | 3.693 | 439/439 一致 |

* **常駐の取り分は `--jobs` でほぼ動かない**: `fresh-j1 → res-j1` **−1.300 秒 (−16.3%、分母 fresh-j1)**、
  `fresh-j4 → res-j4` **−1.385 秒 (−17.5%、分母 fresh-j4)**。**Y2 は当たった。**
* **`--jobs 4` はこのケースをほとんど動かさない**: fresh で **−0.074 秒 (−0.9%)**、
  resident で **−0.160 秒 (−2.4%)**。fresh 側は [min–max] が重なる (7.928–8.151 対 7.825–7.950) ので
  **総計だけでは分離できていない**。
* **ただし機構は分離できている。** 再抽出は round 1 が 5 モジュール・round 2 が 1 モジュールで、
  `analyze` は合計 **0.121 → 0.049 秒 (j1 → j4)**。差 **0.072 秒**は総計の差 **0.074 秒**と一致する。
  **`--jobs` が効く場所が小さいから効かないのであって、並列化が効かないのではない。**
* **支配項は `importModules`**: fresh は**ラウンドごとに** 1.819 + 1.766 = **3.585 秒**払う。
  extract 5.967 秒との差 **2.38 秒**は 2 回分のプロセス起動 (`lake env` + バイナリロード +
  `initSearchPath`)。**常駐が消すのはこの両方**で、代わりに起動 3.70 秒を 1 回だけ払う。

**注意 — 常駐側の 6.5 秒には計測ハーネスの分が乗っている。** `res-j4` の extract 0.604 秒のうち
`analyze` は 0.049 秒で、残る **≈0.55 秒 (2 要求ぶん)** は `serve-ctl.sh request` の
シェル + `python3` 起動 + 0.1 秒ポーリングである。ソークの python ドライバでは
同じ往復が **0.005 秒**なので、これはサーバのコストではない。
**製品実装なら `res-j4` は ≈5.96 秒まで下がりうる【外挿 — 実測の内訳から差し引いただけで、実装していない】。**
この段階の主張は実測の **6.509 秒**のほうで立てる。

### Y3 — フル 432 モジュールの再抽出

| 変種 | 中央値 (壁) | [min–max] | importModules | analyze | writeIR |
|---|---:|---:|---:|---:|---:|
| `fresh-j1` | **14.931** | [14.902–14.954] | 2.479 | 10.662 | 0.599 |
| `fresh-j4` | **7.507** | [7.468–7.544] | 2.485 | 3.215 | 0.611 |
| `res-j1` | **11.439** | [11.352–11.555] | — | 10.572 | 0.600 |
| `res-j4` | **4.257** | [4.172–4.429] | — | 3.395 | 0.606 |

IR は 4 変種すべて REFERENCE と byte 一致 (`/usr/bin/diff -r`)。

* **起動抜き** (既に立っているサーバに投げる): **j1 −3.491 秒 (−23.4%、分母 fresh-j1)、
  j4 −3.250 秒 (−43.3%、分母 fresh-j4)**。
  **絶対値はほぼ同じで、相対値だけが 2 倍近くになる** — 取り除いているのは
  `importModules` (+ プロセス起動) で、それは `--jobs` で並列化されないから。**Y3 は当たった。**
* **起動込み** (1 パイプライン 1 台): **j1 15.042 秒 = +0.7%、j4 8.066 秒 = +7.4%**。
  **フル抽出 1 回のためにサーバを立てても得はしない** — 環境ロードはどちらにせよ 1 回きりで、
  常駐にしても消えるものが無い (サーバ起動 3.6〜3.8 秒 ≒ 単発のプロセス起動 ≈1.0 秒 +
  `importModules` 2.48 秒)。**得になるのは抽出が 2 回以上あるときだけ**という
  段階 6a の結論は `--jobs 4` でも変わらない (分岐点そのものは測っていない)。
  なお j4 の +7.4% には `analyze` が resident 側で 3.215 → 3.395 秒と**遅く出た**分も
  混ざっている。**この差は分離できていない** (サーバの環境は 433 モジュールぶんで、
  単発のそれと同じではない)。
* **サーバの RSS は `ps` で 0.57〜0.62 GB**、5 回のフル抽出を挟んでも動かない。
  一方、単発パイプラインの peak RSS は `/usr/bin/time -l` で **2.30 GB**、
  フル抽出の peak RSS は検証ログで **3.27〜3.42 GB**。
  **矛盾ではない。測っているものが違う** — `ps` の値は**要求と要求の間**の resident set、
  `time -l` の値は**要求の最中を含む**ピークで、olean は mmap の clean ページなので
  触られなくなれば回収される。**要求中のサーバの RSS は測っていない。**
  言えるのは「**常駐 1 台が待機中に占める物理メモリは 3.3 GB ではなく 0.6 GB 程度**」まで。

### Y4 — 600 要求のソーク【`--jobs 4`、対象 432 モジュールを 1 回 import】

600 要求すべて成功 (`non-zero replies: 0`)、途中の応答なしもゼロ。

* **(a) 正しさ**: 同一の 5 モジュール要求を **#1 / #300 / #600** に投げ、
  `/usr/bin/diff -r` で **3 つとも byte 一致**。
* **(b) RSS**: 25 標本すべて **0.55 GB**、増加 **+0.00%**。**単調増加は無い。**
  標本は**要求が返った直後**に取っているので、これは待機中の resident set であって
  **要求中のピークではない** (そちらは測っていない)。
* **(c) 応答時間**: 前半 100 と後半 100 の中央値比較は **交絡している** —
  要求の歩き方が `start = (i×7) mod 432` なので前後で**別のモジュール**を訊いており、
  時間を決めるのは宣言数だから。**交絡の無い対照を 2 つ取った**:
  * **同一要求の反復** (歩きの周期は 432 なので要求 `i` と `i+432` は同じモジュール集合):
    **n=166、中央値 −0.0006 秒 (−1.9%)**、後のほうが遅かったのは **166 組中 48 組**。
  * **canary** (同一の 5 モジュール): **#1 0.0740 → #300 0.0652 → #600 0.0657 秒**。
    遅くなるどころか、**1 回目だけが遅い** (初回効果)。
* 参考: 要求あたり中央値は **1 モジュール 0.0209 / 2 モジュール 0.0280 / 3 モジュール 0.0366 秒**
  (サーバ自身の ns 時計)。

**§8 の「6 要求は 600 要求について何も言わない」は閉じた。**
ただし閉じたのは **600 要求 / 約 1 分 / 同一 olean 世代**の範囲であって、
**日をまたぐ寿命や、ビルドをまたぐ寿命については何も言っていない** (後者は段階 6a が
既に「使ってはいけない」で決着させている)。

### 段階 6a の 7.940 / 6.168 秒と並べられるか — **並べない**

抽出器が **stage4b (schema 3) → stage7d (schema 4)**、レンダラが
**`stage4c/render.ts` → `stage7d/render.ts`** に変わっている。仕事量そのものが違うので、
`fresh` 同士ですら同じものではない。**この段階の `fresh-j1` 7.968 秒が新しい基準**で、
比較はすべてこの表の中で閉じている。

参考までに: 段階 6a の `fresh2` 7.940 秒と今回の `fresh-j1` 7.968 秒は**たまたま近い**が、
**それを根拠に「schema 4 は速度中立」と言ってはいけない** — 同一セッションで
両方を測っていないので、条件が揃っている確認ができていない。

### 分離できなかったもの

* **`fresh-j1` 対 `fresh-j4`** (2 ラウンドの増分): 総計の [min–max] が重なる。
  言えるのは「機構 (`analyze` 0.072 秒) が総計の差 (0.074 秒) を説明する」まで。
* **常駐の分岐点が `--jobs 4` で何ラウンドに動くか**: 測っていない。
  Y3 が「1 回の抽出では損」、Y2 が「2 ラウンドでは得」を示すので、
  分岐点は依然として 1 と 2 の間にあるはずだが、**これは推論であって実測ではない**。
* **`res-j1` の [min–max] 上端 7.109 秒**は起動が 4.164 秒に伸びた 1 run による。
  起動時間の裾がどこまで伸びるかは 6 標本では分からない。

### 判断

1. **常駐と並列は併用できる。** `--jobs 4` のサーバは `--jobs 1` の単発と byte 一致の IR を返す (Y0)。
2. **本配線は成立した。** `--serve auto` で組んだパイプラインは 4 構成すべて
   from-scratch と **439/439 byte 一致** (Y1)。
3. **常駐の取り分は「何を任せるか」で決まり、`--jobs` ではほとんど決まらない。**
   増分 2 ラウンドなら **−16〜18%** (jobs 非依存)、フル抽出を**既に立っているサーバ**に
   任せるなら **−23%(j1) / −43%(j4)** で、ここだけ jobs が効く (分母が縮むから)。
4. **サーバを 1 台立てるコスト (3.7 秒) は、抽出 1 回ぶんの環境ロード + プロセス起動と同額。**
   だから「抽出が 1 回しかない仕事」に常駐を足しても得はしない。
5. **常駐は 600 要求で壊れない** (正しさ・メモリ・速度の 3 点とも)。
