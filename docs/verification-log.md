## 記録済みの結果

### 段階 1 — 前提の実測 (2026-08-09)

doc-gen4 に「複数モジュールを 1 プロセスで抽出する」コマンドを足して計測した。

- **実測**: 432 モジュールを 1 プロセスで 47.4 秒 (逐次プロセスは約 1,084 秒、23 倍)。
  ログ → `benchmarks/results/batch.jsonl`、レポート → `benchmarks/doc-gen4-report.md`

これは **doc-gen4 の機構での実測**であって、lean-doc 自身の抽出器での再現ではない。
段階 1 を満たすには (a) 自前の抽出器で同等の時間が出ること、
(b) カスタム構文・`Notation`・独自属性を持つプロジェクトでも壊れないこと、の 2 つが要る。

**この節の 47.4 秒 / 12.9 秒は下の「再現」で page cache のアーティファクトと判明した。**
数字は記録として残すが、床の議論には使わないこと。

### 段階 1 — 自前抽出器での再現 (2026-08-09)

**計測条件**: Apple M1 / 8 コア / 16 GB、Lean・Mathlib・doc-gen4 すべて v4.31.0
(mathlib `fabf563a7c` / doc-gen4 `0bc516c`)、`LEAN_NUM_THREADS` 未設定 (Lean 既定)、
olean ビルド済み、並列度 1 (単一プロセス)。

計測プログラムは `experiments/stage1/`。`import Lean` だけに依存する単一ファイルで、
432 モジュールを 1 回の `importModules` でロードし (import closure 6,021 モジュール)、
宣言を **索引方式** (`moduleData[i].constNames`) と **走査方式** (env 全定数) の
両方で列挙して**結果が一致することを検証**する。pretty print は一切しない。
ネイティブコンパイル済みバイナリで計測 (インタプリタ実行ではない)。

#### 結果

|---|---:|---:|
| `importModules` | 10.49s | **2.36–2.50s** |
| 索引方式の列挙 | 0.0022s | 0.0022s |

すべて**実測**。ログ → `benchmarks/results/stage1-extract*.jsonl`、
計測条件 → 同ディレクトリの `*-summary.txt`。

- **実測**: 宣言は 5,123 件。索引方式は 8,849 件を列挙、走査方式は 490,171 定数を走査して
  8,824 件が該当 (該当率 1.80%)。**両方式の宣言集合は完全一致** (`agree: true`)。
- **実測**: 索引方式 0.0022s vs 走査方式 0.62s = **286 倍**。ただしこれは

#### 判明したこと 1 — 「環境ロード 12.9 秒の床」は page cache のアーティファクト

warm 実行を 5 回連続で取ると `importModules` は 2.36–2.50 秒に収束し、
**壁時計 ≈ CPU 時間** (run7: 3.14s wall / 3.11s user+sys) になる。cold 寄りの実行では
壁時計 14.67s に対し CPU は 4.01s しかなく、**差はすべて olean の mmap ページイン待ち**。

これが lean-doc 側だけの現象でないことを確かめるため、**同じ warm 状態で doc-gen4 の
`batch` を測り直した** (2 回、再現性あり):

| phase | 初回計測 `batch.jsonl` | warm 再計測 `batch-rerun*.jsonl` |
|---|---:|---:|
| `load.importModules` | 12.910s | **2.601s / 2.518s** |
| `process.getAllModuleDocs` | 16.37s | 16.636s / 16.486s |
| `process.constantLoop` | 15.99s | 11.575s / 10.746s |
| └ うち `ofConstant` | 11.54s | 11.216s / 10.354s |
| `batch.updateModuleDb` | 0.639s | 0.676s / 0.660s |
| **`batch.total`** | **45.93s** | **31.50s / 30.43s** |

すべて**実測**。doc-gen4 の `importModules` も 2.6 秒に落ちた。
lean-doc の 2.44 秒とほぼ同じで、**同じ API を同じ引数で呼んでいる以上これは当然**。

したがって:

- **環境ロードの床は CPU で約 2.5 秒**であり、12.9 秒ではない。
  12.9 秒は「page cache に olean が乗っていない状態」の値。
- **cold と warm で 5 倍違う** (2.4s ↔ 12.3s、`stage1-extract-3th` が cold 側の実測)。
  計測条件に page cache 状態を書いていない数字は読めない。
- 初回起動には `stage1.total` の外側に **3.5 秒**ある (98 MB の静的リンクバイナリの
  ページイン)。2 回目以降は 0.07 秒。~~**CI は毎回この cold 側を払う。**~~
  (**後の訂正**: この断定は根拠が無く、後の「CI 軸 — cold の前提の検証」で**仮定**に格下げした。
  macOS では `cache get` 直後でも cold のままだと実測したが、**Linux ランナーは未測定**。)

上の再計測で方式B だけが warm になったので、**方式A (モジュールごと 1 プロセス) も
同じ warm 状態で 432 モジュール全数を測り直した** (以前は 112 モジュールの実測からの換算)。

#### 判明したこと 2 — 「走査 4.45 秒」も走査のコストではなかった

`approach.md` §6.1 の「走査 (該当外) 4.45s」は `constantLoop` 15.99s − `ofConstant` 11.54s の
**導出値**だった。warm 再計測では同じ差が **0.36 秒**になる。つまり 4.45 秒の大半は
走査そのものではなく cold cache のページインだった。

素の compiled IO で同じ 490,171 定数を舐めると 0.62 秒 (上表)。
**結論 (索引方式にすれば消える) は変わらない**が、行の名前と大きさは誤っていた。

#### 判明したこと 3 — 索引方式は宣言の「所有モジュール」を一意に決めない

索引方式の列挙数 8,849 と走査方式の該当数 8,824 に 25 件の差がある。
複数モジュールの olean に同名で焼かれる自動生成補題 (`Foo.eq_1`、`Foo.congr_simp`) で、
`const2ModIdx` は最初に定義したモジュールしか記録しないため走査は 1 回しか見ない。

- **実測**: 25 件、うち 5 件は内部名でない (`typeCount.congr_simp` 等)。
  帰属先はすべて対象パッケージ内で、依存側に漏れるものは無い。
- カバレッジではなく**ページ配置**の問題。索引方式は doc-gen4 が暗黙に持つ
  「最初に定義したモジュールが勝つ」規則を、明示的に決め直す必要がある (→ §8 の問い)。

#### 判断

**(a) は満たした。(b) は未検証。段階 2 に進んでよいが、段階 1 は閉じない。**

- (a) 自前の抽出器で同等の時間が出るか → **満たす**。同一 warm 条件で
  lean-doc 2.44s / doc-gen4 2.60s。走査数 490,171・該当数 8,824 も完全一致しており、
  両者が同じ環境・同じワークロードを見ていることが確認できた。
- (b) カスタム構文・`Notation`・独自属性で壊れないか → **未検証**。
  この最小抽出器は pretty print をしないので、カスタム構文が絡む経路を通っていない。
  `importModules (loadExts := true)` + `enableInitializersExecution` で
  環境拡張の初期化までは走っているが、それは (b) の一部でしかない。

  ただし**別の計測対象を用意する必要は無い**ことは確認した。現行の対象は
  Mathlib の `notation3` による scoped notation を持つ
  (`InformationTheory/Shannon/TypedRV.lean` の `H(μ; X)` / `I(μ; X ; Y)` / `D(μ; X ∥ Y)`、
  `InformationTheory/Asymptotic.lean` の `≐`)。**pretty print を入れた段階 2 が
  そのまま (b) の検証になる。**

`stage1.total` (3.1 秒) を `batch.total` (30.4 秒) と比べていない。
本抽出器は意味解析をしないので、比較できるのは `importModules` だけ。

#### 段階 1 (b) の決着 — カスタム構文は壊れない。ただし既定では**使われない**

生の出力は `benchmarks/results/stage2-notation-samples.txt` に残した。

```
                          既定 (doc-gen4 と同一)          --open 指定時
DotEq.refl              : DotEq a a                     a ≐ a
entropy_nonneg_rv       : 0 ≤ entropy μ X               0 ≤ H(μ; X)
mutualInfo_comm_rv      : mutualInfo μ X Y = ...        I(μ; X ; Y) = I(μ; Y ; X)
klDivRV_def             : klDivRV μ X Y = ...           D(μ; X ∥ Y) = ...
```

- **実測**: 既定モードの出力は doc-gen4 の HTML と**一字一句一致**。両モードとも
  例外・空署名は 0 件。**「壊れない」は確認できた。**
- **実測**: `scoped notation` の delaborator は `ScopedEnvExtension` にあり、
  import しただけでは**未活性**。`Core.Context.openDecls` に入れるだけでは効かず、
  **`Lean.activateScoped` で環境側を活性化する必要がある**。doc-gen4 はどちらも
  やっていないので、**パッケージ自身の記法が doc に一切出ていない**。
  lean-doc は出せる。コストは意味解析 +6% (8.15s → 8.67s)。4,750 件中 294 件が変わる。
- **実測**: `H(μ; X | Y)` は両モードとも出ない。notation が `Shannon.condEntropy`
  (`@[reducible]` な `MeasureFano.condEntropy` の別名) に対して定義されており、
  elaborate 後の項には `MeasureFano.condEntropy` しか残らないため delaborator が
  一致しない。該当 34 件。**対象プロジェクト側の宣言のしかたの性質で、抽出器の欠陥ではない。**

#### 計測で 1 回踏み外しかけた点 (記録)

doc-gen4 は `DocGen4/Load.lean` で pp オプション (`pp.tagAppFns` / `pp.funBinderTypes` /

(計画 §5.6 の境界と一致)。実測でプレフィクスは深さ 2〜6 まで行使されている

#### IR の形 (段階 3 の結論を反映)

```
<irDir>/index.json                   索引: モジュール一覧 + ハッシュ + ファイルパス + Lean/スキーマ版
<irDir>/modules/<Module.Name>.json   モジュール 1 個 = 1 ファイル (§5.4)
<irDir>/deps/<Package>.json          依存側の写像スライス (名前 → モジュール名の 2 列)
```

- **絶対識別子のみ**。参照は `(定義モジュール, 名前)` のペアで、**URL は相対も絶対も持たない**
  (相対化は出力時 = §5.6)
- 依存スライスは 2 列。`kind` は持たない (段階 3 増分 2 の結論)
- `schemaVersion` はモジュールファイルの本体に入っているので、**スキーマを上げると全ハッシュが変わる**
- ハッシュは Lean の `String.hash` の 16 桁 hex = **64 bit・非暗号学的**。
  Lean core v4.31.0 に digest が無いため。432 モジュールなら衝突確率 ~5e-15 で
  変更検出には十分だが、改竄検知には使えない (leg 7 で再検討)

#### 予測と食い違った点 / 踏み外しかけた点

**1. ハッシュのタイマーが最初 0 µs を返していた (記録)。**
`let h := hashHex text` の消費者はタイマーの外 (索引エントリ構築) にしかないので、
コンパイラが呼び出しをタイマーの後ろに沈め、**8.6 MB に対して 34 µs = 253 GB/s** と出た。
落とせない分岐 (`if h.length != 16 then throw …`) で強制して 2.3 ms になった。
段階 2 の `--tactics-probe`、段階 3 の `refUs` と同型で、**3 回とも低い側 = 都合の良い側に外れた。**
なお `writeIR` の**合計は両方とも正しかった** (0.192s → 0.194s)。
タイマーが飛ばした分を後段の `writeFile` が払っていたため、内訳だけが誤っていた。
検算の型: 直列化 + ハッシュ + 書き込みは「8.6 MB ÷ 妥当なバイト単価」に収まること。

**2. `stage4.total` の差から書き込みコストを読んではいけない。**

| 系列 | `importModules` | `total` |
|---|---:|---:|
| IR OFF (ブロック) | 2.597 [2.551–2.714] | 12.466 [12.411–12.700] |
| IR OFF (交互) | 2.628 [2.548–2.696] | 12.685 [12.472–12.769] |
| IR ON・毎回削除 (ブロック) | 3.169 [2.610–4.429] | 13.447 [12.790–14.677] |
| IR ON・毎回削除 (交互) | 3.230 [2.563–5.852] | 13.251 [12.536–15.963] |
| IR ON・上書き | 2.816 [2.659–3.712] | 12.888 [12.638–14.017] |

`total` は最大 1.0s 動くのに `writeIR` はどの系列でも 0.196〜0.198s。
超過分は **`importModules`、つまり書き込みが始まる前に終わるフェーズ**に出ている。
効いているのは実行の前後のファイル操作で、**436 ファイルの削除が最も高く**、
上書きだけの系列はベースラインの半分まで戻る。2.59 GB の olean を mmap で
ページインするワークロードの隣で数千回のファイル操作をすると見える、ということ
(バイト数は ci-residency 節の実測。以前ここに書いていた「3 GB」は peak RSS からの流用だった)。
→ **書き込みコストはフェーズタイマーの 0.198s。合計の差は書き込みに帰属できない。**

最初のブロック配置 (IR OFF を 6 回 → IR ON を 6 回) では
**`--write-ir` が触れないはずの `analyze` に +0.23s が出た**ので、交互配置で測り直した。
交互配置では逆向き (IR OFF 側が +0.17s) になり、run 間ノイズと確定。

**3. import が 432 件多い。** `ModuleOut.imports` は
`header.moduleData[i].imports` の生の値で、全モジュールで `Init` が 2 回入る。
IR の import は 3,935 件、doc-gen4 の `module_imports` は 3,503 件、差はちょうど 432。
段階 2 の突き合わせは集合ベースだったので影響なし。重複除去は出力側の仕事。

**4. 参照の「位置」は IR に入っていない (leg 5 への申し送り)。**
`refs` は宣言ごとの `(モジュール, 名前)` の**集合**で、印字された署名のどのオフセットに
現れたかは落としている。doc-gen4 は保持している (`name_info.type` が
`RenderedCode` のバイナリ blob)。署名中の `Real.log` をその位置で `<a>` にする
レンダラは位置を要求する。**leg 5 が「集合で足りるか」を判定する。**
足りなければ IR は太り、この計測はやり直しになる — その場合の再計測は退行ではない。

`experiments/stage4/README.md` が「leg 5 が集合で足りるかを判定する」と書いた分岐は、

**(1) 印字トークンと定数名に字面の関係が無いものが 44.0%**

### 段階 4 — 増分 4 / ページ全体の生成時間の実測【判断点 2 の結論】 (2026-08-10)

**問い**: IR (schema 2) から **432 モジュールぶんの HTML ページをディスクに書く**まで、
warm で何秒か。これが `approach.md` §6.2 の「N+1 解消後 **1.28s** = **仮定**」を
置き換える数字であり、3 軸の「初回生成」に残った最後の仮定

**計測条件**: Apple M1 / 8 コア / 16 GB (Darwin 25.6.0 arm64)、Deno 2.7.14 /

出力 = **432 ファイル / 29,671,173 バイト**を scratch に書く (計測対象リポジトリには書いていない)。

`/usr/bin/time -l` (macOS の `real` は 2 桁しか出ないので壁時計はこちらを使わない)。

**この 3.8 倍を「同じ仕事量で 3.8 倍」と書いてはいけない。**

#### 判断 — **【判断点 2】通過。仮定 1.28s は外れ、実測はその 0.64 倍**

| | 秒 | ラベル |
|---|---:|---|
| §6.2 の旧行「N+1 解消後」 | 1.28 | 仮定 |
| **実測 (warm)** | **0.8239** | 実測 |
| 実測 (cold) | 0.9331 | 実測 |

**仮定は 1.55 倍の過大見積もりだった。有利な向きに外れたので、根拠を 3 つ残す**:
(1) 出力は 432 ファイル / 29,671,173 バイトがディスク上に実在し、計装前の生成器と byte 一致。
(2) 壁時計はプロセスの外から測っており、フェーズの和 (0.784) との差 0.040 秒も

**ただしこの 0.82 秒は完成版の下限である。** ページのバイトの 36.4% がまだ byte 再現

この 3 倍という係数自体に根拠は無い — **「数秒に化けることは無さそうだ」以上の主張はしない。**
検索索引を作るのは未実装分の埋め合わせではなく**このフェーズに足す新しい仕事**なので、

### CI 軸 — cold の前提の検証 / 「展開直後なら warm」の否定 (2026-08-10)

**問い**: `approach.md` §3 の「**CI (常に cold)**」には**ラベルが無く、ログも無かった**。
CI では `lake exe cache get` が olean を展開した直後に doc 生成が走るので、
**展開直後なら page cache に載っていて cold にならない**かもしれない
(`plans/three-axes.md` §5 打ち手 1)。正なら CI 軸の前提そのものが変わる。

**計測条件**: Apple M1 / 8 コア / **16 GiB** (Darwin 25.6.0 arm64)、page size 16,384 B、
Lean・Mathlib v4.31.0、leantar 0.1.19 (`--jobs` 既定 = 8)、extract は 1 プロセス
(`LEAN_NUM_THREADS` unset)、ディスク空き 12 GiB 以上を各点の前に確認。
**対象リポジトリには 1 バイトも書いていない** — `lake exe cache get` / `lake update` は
実行せず、`leantar -x -C <scratch>` を直接呼んで scratch に展開した。
cold は `olean-evict` (msync MS_INVALIDATE、sudo 不要) で作る。
ログ → `benchmarks/results/ci-warmstart-*`、条件つきサマリ →
`benchmarks/results/ci-warmstart-summary.txt`。再現 → `benchmarks/tools/measure-warmstart.sh`。

**この機材の headroom** (= free + speculative + purgeable + inactive、実測、各ステップで記録):
計測中 **3.11–5.48 GiB**。compressor が **6.38–7.11 GiB** を占有している。
16 GiB のうち page cache に回せるのは 2〜3 割。

#### (a) 書き込み直後の常駐率 — payload を 0.25 → 7.34 GiB で振る (実測、6 点 × 3 回)

olean のコピーを `tar` で scratch に書き、**書き終わった直後に** `mincore(2)` で常駐を数える。

| payload GiB | **書いたページの常駐 %** | 常駐 GiB (中央値) | payload/headroom | **同じ瞬間の「読んだ」ページの常駐 %** |
|---:|---:|---:|---:|---:|
| 0.25 | 94.0 | 0.235 | 0.07 | 96 |
| 0.50 | 45.1 | 0.226 | 0.13 | 86 |
| 1.00 | 23.7 | 0.237 | 0.26 | 81 |
| 2.00 | 11.7 | 0.233 | 0.48 | 73 |
| 4.00 | 5.0 | 0.198 | 0.96 | 37 |
| 7.34 | 2.6 | 0.193 | 1.77 | 16 |

**曲線は headroom で決まっていない。** 常駐した**絶対量**が payload に依らず 0.15–0.24 GiB で
一定で、率はその割り算にすぎない。**headroom は一度も律速していない** —
7.34 GiB を書いた直後でも 3.26–4.10 GiB 空いていた。
そして**同じ瞬間に読んだページは 6.3 倍よく残っている** (2 GiB 点で 73% 対 11.7%)。
容量ではなく**読みと書きで保持方針が違う**。

対照 (`dd if=/dev/zero`、書込速度を 11〜16 倍にする、実測 3 点 × 3 回): 常駐は
0.250 / 0.309 / 0.302 GiB で**速度に依らない**。つまり残るのは「直近 N 秒」ではなく
**「末尾 N バイト」**。ファイル数 (1 個 vs 18,092 個) にも依らない。

#### (b) 本物の `leantar` 展開直後 (CI の実経路、実測 3 回 × 2 系列)

現行 rev の ltar クラスタ **8,516 個 / 410.70 MiB** を展開 → **110,708 ファイル / 6.123 GiB**、
うち olean 3 種 **25,548 ファイル / 5.167 GiB**。展開 12.78–13.65 秒。

| 系列 (展開前 headroom) | 展開直後の olean 常駐 |
|---|---|
| headroom 4.70–4.75 GiB | **17.23 / 19.46 / 20.19 %** (0.89–1.04 GiB) |
| headroom 3.34–3.72 GiB | **4.72 / 7.62 / 8.27 %** (0.24–0.41 GiB) |

2 系列の差はファイル集合ではない (同じ 24,507 ファイルに絞り直しても 17.4–20.1%)。
**残る量は headroom に応じて動くが、payload には比例しない。**

#### (c) 展開直後の `importModules` は速いか — 秒で答える (実測)

`LEAN_PATH` の 17 エントリのうち **mathlib の 1 つだけを scratch の展開先に差し替え**、
残りは対象リポジトリのまま。3 変種で変えているのは **Mathlib の暖機状態だけ**。
全 run で `declaration sets agree (5123 declarations)` — 仕事量は同一。

| 変種 | Mathlib の状態 | **importModules** | 壁時計 | **major fault** |
|---|---|---:|---:|---:|
| **fresh** | leantar が直前に書いた | **14.956 / 15.656** | 15.71 / 16.38 | 119,318 / 119,934 |
| **cold** | 同じ木を退避 | **13.862 / 13.999** | 14.60 / 14.73 | 122,974 / 121,386 |
| **warm** | 直前の run が読んだまま | **2.492–2.587** | 3.21–3.33 | 190–412 |

**fresh は warm ではない (5.9 倍)。cold より速くもない (1.1–1.7 秒遅い)。**
major fault が浮くのは 2–3% だけ。warm 判定は major fault で行っている
(190–412 対 119,318 以上、2 桁半の差)。warm 側が 2.49–2.59 秒に収束して
前増分の warm 中央値 2.538 秒と一致するので、LEAN_PATH を差し替えた計測系自体は健全。

なお **(b) の常駐 20% と (c) の fault 2–3% は釣り合っていない。**
比例して重なるなら 12% 前後浮くはず。理由の候補は「残るのは最後に書かれたページで
読み出し順と無関係」「展開終了から読み出しまでにさらに剥がれる」の 2 つで、**切り分けていない**。
**「20% 常駐していれば 20% 速くなる」は成り立たない**ことだけ記録する。

#### 判断 — **打ち手 1 はこの機材では否定。CI については未検証に格下げ**

- **仮説はこの機材では偽 (実測)。** 展開直後は page cache に載らない。
- **ただし「CI で載らない」の証明にはならない。** 理由は 2 つ、向きが逆:
  1. **機材の非対称性** — この機材は compressor が 6.4–7.1 GiB を占有し実効 headroom 3〜5 GiB。
     `ubuntu-latest` は 16 GB をほぼ専有する。**不利な側で否定が出ても移送できない**
     (逆に「載った」なら単調性で CI にも言えたが、載らなかったので使えない)。
  2. **退避ポリシーの違い** — macOS の UBC と Linux の page cache は
     **「書いたページがいったんキャッシュに入る」点は共通だが、その後が違う**。
     本計測が捉えたのは「入った後すぐ解放される」挙動で、容量ではなくポリシーの結果。
     Linux は writeback 後も clean なまま保持し、解放は reclaim まで待つ設計なので、
     同じ結果になるとは限らない。**この機材に Linux 環境が無く** (docker / colima / lima /
     podman / VM いずれも未インストール、ネットワーク不使用は計画 §6 事前決定 #5)、**測れていない。**
- **容量の側からは Linux CI で仮説が通る余地が残る (外挿)。** cold が実際に読むのは
  **2,588,347,936 B (2.59 GB、実測)** で `ubuntu-latest` の 16 GB の **16%**、
  展開が書く 6.12 GiB でも 38%。**容量は制約にならない。** 残るのはポリシーだけ。
- → **検証項目 (未着手)**: `ubuntu-latest` 上で `cache get` 直後の olean 常駐率を
  `mincore` / `/proc/<pid>/pagemap` で測る。**ここが埋まるまで CI 軸の床は確定しない。**

`approach.md` に反映した箇所:

- §3 の「**CI (常に cold)**」を **「CI: 未検証 (仮定)」**に格下げし、
  macOS 実測で「展開直後 = warm」が否定されたことと、Linux 未測定であることを明記
- §6.1 の「**CI は常に cold 側**」に同じ但し書き
- §7 の検証表に **CI 軸の行**を追加 (状態: 部分的に否定、Linux 未検証)
- §8 の「cold な環境ロードをどう扱うか」に、打ち手 1 が macOS では否定された事実を追記

### CI 軸 — 打ち手 2「先読み」の実測 / **成立** (2026-08-10)

**問い**: `plans/three-axes.md` §5 打ち手 2 —「抽出の開始と並行して olean を舐めて
page cache に載せる」。前増分で **cold の 12.7 秒は 132,343 回の同期 major fault の
直列な待ち行列**であり帯域律速ではないと分かっている (実測)。ならば先に並列で読めば
消せるはず、という仮説。打ち手 1 が否定されたので、**CI 軸に打ち手が入るかはここで決まる。**

**判断基準 (測る前に宣言)**: (1) overlapped の壁時計が cold baseline より短く、
5 回の分布が重ならない (2) major fault が減っている (3) 読むバイト数の増加を払って得か。
**満たさなければ「先読みは効かなかった」と書く**という条件で開始した。

**計測条件**: Apple M1 / 8 コア / **16 GiB** (Darwin 25.6.0 arm64)、page size 16,384 B、
Lean・Mathlib v4.31.0、extract は 1 プロセス (`LEAN_NUM_THREADS` unset)、
先読みの並列度は 1/4/8/16/32、ディスク空き 16 GiB 以上。
**対象リポジトリには 1 バイトも書いていない。** cold は `olean-evict` で作り、
**退避後に 34,304 ファイルの常駐が 0 バイトであることを毎回の系列で検証**している。
extract **162 run** (stage1 146 / stage4b 16) + 先読み単体 36 run。
stage1 の 146 run すべてで `declaration sets agree (5123 declarations)`、
stage4b の 16 run すべてで `produced 4750` — **仕事量は全 run 同一**。
ログ → `benchmarks/results/ci-prefetch-*`、条件つきサマリ →
`benchmarks/results/ci-prefetch-summary.txt`。再現 → `benchmarks/tools/measure-prefetch.sh` /
`olean-prefetch.c` / `import-closure.py` / `summarize-prefetch.py`。

#### (a) 道具の検証 — 「載っていない先読み」で時間を測らないための前提 (実測)

先読み器は 3 方式を持つ: `read(2)` / `madvise(MADV_WILLNEED)` / mmap して 1 ページ 1 バイト触る。
250 MiB の部分集合で **3 方式とも退避後 0% → 先読み後 100.00%** を mincore で確認。
34,304 ファイル全部でも退避後 **0 バイト**、closure 17,199 を先読みして **2,556,988,152 B**。
**`madvise -j1` の所要 4.28 秒は `read -j1` の 4.19 秒と同じ** → この OS の
`MADV_WILLNEED` は**同期**で、経過時間を正味の I/O 時間として読んでよい
(**Linux では非同期**なので移送不可)。

#### (b) 先読み単体 — 前増分の「床」を超えた (実測、3 回)

| oracle j=8 madvise | 1.772 | 2,358 | **90.7–93.5%** |

| oracle j=1 read | 4.186 | 998 | 75.6–77.9% |

前増分の「8 並列 `cat` で 1,841 MB/s」が床だったが、**2,395 MB/s まで出る**。
並列度は 4 で頭打ち (j=1 の 998 → j=4 の 2,120 → j=16 の 2,351)。

#### (g) 効果の大きさはメモリ regime に依存する (実測)

#### (a) 設計判断 — 何をハッシュするか

**入力側と出力側で別のハッシュを使う。** §5.5 の「モジュール単位ハッシュが単一の真実」は
*役割*の話で、役割は 2 つある。1 つの数字では両方を埋められない (問う時点が違う)。

| | 入力側 | 出力側 |
|---|---|---|
| 問い | どのモジュールを**再抽出**するか | どのページを**再生成**するか |
| ハッシュ対象 | モジュールの `.olean` | モジュールの IR JSON |
| 計算するもの | `stage5/ledger.ts` (Lean 不要) | 抽出器 (既に `index.json.contentHash` にある) |

**`.lean` ソースではなく olean を選んだ理由**: 抽出器がモジュールについて見られるのは
`importModules` が返すものだけで、その出所は olean しかない。ソースのハッシュは
両方向に外す — 証明中の空白のように olean に届かない変更を「変更」と報告し、
依存の再ビルドで olean に入った変更を見落とす。**IR のハッシュは遅すぎる** —
それを計算するには、台帳が省こうとしている抽出そのものが要る。

**3 分割 olean**: モジュールシステムで作られたモジュールは
`.olean` / `.olean.server` / `.olean.private` を持つ。**存在するものは全部ハッシュする**
(抽出器は declaration range と docstring = server 側、private 宣言 = private 側を読む)。
**この対象では自パッケージ 432 モジュールは `.olean` 1 個ずつ** (実測)。3 分割は
依存パッケージ側にだけあり、8,360 モジュール中 8,297 が 3 つ持つ (実測)。

**Lake が既に同じハッシュを計算している (実測)。** olean の隣の `<file>.olean.hash` は
`cacheFileHash` → `computeBinFileHash` (`Lake/Build/Common.lean`、v4.31.0 のソースを確認)
すなわち**その olean の内容ハッシュ**。読むのは 432 × 16 B = 6.9 KB。
ただし 64bit 非暗号ハッシュで、かつビルドツールの内部仕様。**SHA-256 を基準にし、
Lake のハッシュは「ただで手に入る代替」として両方測った。**

**台帳の置き場所は IR の `index.json` とは別ファイル。** index は Lean が IR の一部として
書き、台帳は Lean を起動しない側が読み書きするため。分けておくと差分検出が
15.8 MB の IR を parse せずに済み、index.json のバイト再現性 (15,867,059 B) も保てる。

#### (b) 設計判断 — 依存の伝播

**健全な上界は「M を推移的に import しているモジュール全部」。** M を推移的に import
しないモジュールは M が宣言したものを一切観測できない。Lean にそれ以上遠くへ届く経路はない。

**olean 台帳だけではこの上界に届かない。** M の型レベルの内容が変われば import 側も
再ビルドされて olean が動くので台帳が捕まえるが、**2 つの経路が抜ける**:

1. **印字の経路** — `notation` / `syntax` / `@[app_unexpander]` / `@[delab]` / `export` は
   M の環境拡張にあり、**N の olean を一切触らずに N の署名の印字を変えうる**。
2. **所有モジュールの経路** — IR は参照を `(定義モジュール, 名前)` の対で持つ。
   宣言を M から M′ に移すと N の `refs` が古くなる (リンク先が旧ページ) が、
   N の olean は変わらない。

**どちらも塞いでいない。** 1 の表面積だけは実測した (対象の `.lean` を読むだけ、
書き換えていない): **`notation` 宣言は 6 個・2 モジュールだけで全部 `scoped`**
(`InformationTheory.Asymptotic` と `…Shannon.TypedRV`)、
`syntax` / `macro` / `elab` / `declare_syntax_cat` / unexpander / delab / `export` は
**0 個**。抽出器は既定で `--open` を渡さない (計画 §6 事前決定 #4) ので、
**この対象・この構成では印字の経路は不活性**。ただしこれは**対象の性質であって定理ではない**。

**2 つの閉包の実サイズ (実測、`impact.ts` で IR のグラフから)**:

| | 中央値 | 平均 | p90 | 最大 | 0 のモジュール |
|---|---:|---:|---:|---:|---:|
| 推移的 import 元 (自パッケージ内) | 13 (3.0%) | 31.3 (**7.2%**) | 63 | 414 | 1 |
| 直接の参照元 (`refs` 由来) | 0 | 2.6 (**0.60%**) | 7 | 80 | 259 |

参照元 ⊆ import 元 (M の定数を書くには M を import する必要がある)。
健全な上界は平均でパッケージの 7.2%、参照ベースなら 0.60%。
ルートモジュール `InformationTheory` が他 430 個を import しているため、
import 元が 0 のモジュールは 1 個しかない (55 個はルートだけが import している)。

#### (h) 43 ページ混在の実例の機構が特定できた

`.lake/build/doc` に **git rev が 2 つ混在** (`573793b…` 305 ページ / `5e38aec…` 43 ページ)

- rev は `lakefile.lean:110-119` の `git rev-parse HEAD` から `srcUri` facet を経て

  `buildFileUnlessUpToDate'` の内側にあるので (`doc-gen4/lakefile.lean:277-283`)、

- マーカー `.lake/build/doc-data/<M>.doc` の mtime は 2 群に**完全に分離**していて
  (stale 43 群 17:03:14–17:25:26、他 305 群 17:26:47–17:38:33)、HTML は全 348 が同じ 3 秒窓。
  **ビルド中に commit が入った**ことによる時間的分割で、サブツリーの構造とは無関係。

**これは「ハッシュ差分では原理的に捕まらない stale」ではなく、「グローバル入力が

増分 2 の「この計測が答えていないこと」(j)-1 を潰した節。**対象リポジトリの複製で

判断基準は**計測前に commit した** (`04a5b2d`、`experiments/stage5c/README.md`)。
全数字の出所は `benchmarks/results/stage5c-olean-propagation-summary.txt`、

#### (a) 計測条件と、制約をどう外したか

Apple M1 / 16 GiB / macOS (Darwin 25.6.0) / Lean 4.31.0 / Mathlib v4.31.0 /
Lake 5.0.0-src+68218e8。並列度は Lake の既定。

CLAUDE.md の「対象リポジトリを書き換えない」を守ったまま `lake build` を回すために、
**APFS の clonefile (`cp -Rc`) で複製を作った**。COW なので実消費ディスクは 0
(12 GB の複製後も `df` の空きは 16 GiB のまま)、**原本は一切書き換わっていない**。
複製直後に `lake build --no-build` が `All targets up-to-date (3779 jobs)` を返すことを

対象: **A** = `Shannon.GaussianPDFVarianceDerivative`、
**C** = `Shannon.FisherDeBruijnGaussian` (A の `isHeatTimeDerivHyp_gaussian` を 2 か所で参照)。
A の直接 importer は C と root だけ。**root (`InformationTheory`) は 431 モジュールを

(パッケージ内 import グラフで葉は root ただ 1 つ、実測)。

#### (b) 判定 — P3 が偽なので **L3-1 は必須で確定**

| # | 命題 | 事前予測 | 結果 |
|---|---|---|---|
| P1 | olean の生成は決定的 | 真 | **真** (パスを固定すれば。再ビルド 4 回すべて byte 一致) |
| P2 | 未参照の宣言を A に足しても C の olean は不変 | 真 | **真** (C の sha256 完全一致。mtime は変わる = 再ビルドはされている) |
| **P3** | **宣言が A→X へ移動すると参照側 C の olean が変わる** | **偽** | **偽** (C は 1 byte も変わらない) |

P3 の実験: A の中身を丸ごと新モジュール X へ移し、A を `import X` だけの shim にした。
**C のソースは 1 byte も変えていない**。宣言の完全名は不変 (namespace はファイルパスと独立)。
`lake build` 後の olean 差分は **added 1 (X) / content changed 1 (A のみ)** で、
**C と root は「再ビルドされたが byte 一致」**。Lake の `<file>.olean.hash` と sha256 は
全ステップで完全に一致した (食い違い 0) ので、**ハッシュの精度の問題ではなく、
参照側モジュールに変化そのものが存在しない**という構造の問題。

- 宣言の**改名**は参照側の olean を変える (名前が式に埋まっている。P2 の対偶)
- 宣言の**移動**は参照側の olean を変えない

→ `approach.md` §5.5 の L3-1「所有権が変わった名前を参照するモジュールを再抽出集合に足す」を
**仮定から実測に裏づけられた必須項目へ格上げ**した。
同時に P2 が真だったので、**再抽出集合を import 閉包へ広げる必要は無い**ことも実測で確定した
(広げるべきは出力側 = ページであって入力側ではない。増分 2 の結論と一致)。

#### (d) 副次的に出た 2 つ (どちらも §5.5 の設計に直接効く)

1. **olean にソースの絶対パスが 429/432 モジュールで埋まっている**【実測】。
   原本 (パス 31 文字) と複製 (107 文字) で同じソースをビルドすると C の olean が
   5,968 → 6,048 B (+80 = 差 76 文字を 8 byte 境界に丸めた値) になり、sha256 も
   Lake のハッシュも変わる。正体は **Mathlib の style linter のログを持つ環境拡張
   `lintLogExt`** で、警告文 (`Copyright too short!` など) に絶対パスが入ったまま
   olean に保存されている。パスを含まない 3 件 (root / `Meta.EntryPoint` /
   `Shannon.WynerZiv.Operational`) は `lintLogExt` のエントリも持たず、**429 と 429 が
   完全一致**するので原因はこれで確定。Mathlib 自身の olean にはパス文字列が 0 個。
   fan-in 実験がこれを 124 モジュール規模で再確認した — 撤回して baseline と同一ソースに
   戻したのに 124 個が byte 不一致で、**サイズ差は +72 と +80 の 2 値しかない**
   (パス長差 76 を 8 byte 境界に丸めた値)。**P1 は破れていない。破れているのは
   「パスをまたいだ再現性」。**

   開発機と違うだけで 429/432 が「変更あり」になり IR キャッシュが全滅する。
   Lean の olean 形式の性質ではなく**警告を出したままにしていることの帰結**なので、
   L1 に「リンタ構成」を入れるだけでは足りず、**キャッシュの鍵をパス非依存にする**
   (または警告を消す) 必要がある。
2. **Lake は孤児 olean を消さない**【実測】。X のソースを消して `lake build` しても
   X の olean は残った。同じ理由で、現行ソースが 432 モジュールしかないのに `.lake` の
   olean は 1,090 個あり、**659 個が現行ソースに対応しない**。
   → §5.5 の L2 改善案「モジュール一覧をディスク走査で作る」は、走査先を `.lake/build` に
   すると幽霊を 659 個拾う。**列挙元は Lake のライブラリ target (ソースの glob)**。
   増分 2 の S4 (消えたモジュールがページを残す) は doc 側だけの問題ではなく、
   **Lake 自身が同じ構造を持っている**。

### 段階 5 — 増分生成 / 増分 4「L1 の鍵を 2 種類に分ける」 (2026-08-10)

増分 2 で否定された S1 の**残り半分**を潰した節。段階 5c は「`envChanged` を計算して
捨てていた」ほうを直したが、**鍵の中身には `--source-url` が最後まで入っていなかった**
(`envKey` は 5 項目で、どれも source-url ではない)。つまり S1 の否定はここまで生きていた。

判断基準は**計測前に commit した** (`0b68b7e`、`experiments/stage5d/README.md` の C1〜C7)。
全数字の出所は `benchmarks/results/stage5d-keysplit.txt` (生ログ `stage5d-keysplit.jsonl`) と
`stage5d-detect-cost.txt` (生ログ `stage5d-detect-cost.jsonl`)。

#### (a) なぜ「入れる / 入れない」の二択が両方まずいか

`--source-url` は 40 桁の git revision を含むので、**コミットのたびに変わる**。
増分ビルドが走るのもコミットのたびなので、この入力は「たまに変わる設定」ではなく
**毎回変わる入力**である。

- 鍵に**入れない** → `check` は 0 changed、しかし 432/432 ページが stale (= S1)。
- 単一の鍵に**入れる** → 毎コミットで 432 モジュール全再抽出。Lean が見ることすら
  できない入力 (IR に source URL は入っていない) のために Lean を起動する。

第 3 の答えが**血中半径の違う 2 つの鍵**。振り分けの基準は「出力を変えるか」ではなく
(両方変える)、「**IR を変えうるか** = 答えるのに Lean が要るか」。

| 鍵 | 中身 | 変わったとき |
|---|---|---|
| `extractKey` | toolchain / manifest / 抽出器 id / IR schema / IR generator | 432 全再抽出。どのページが stale かは従来どおり IR 差分が決める |
| `renderKey` | 生成器 id / `--source-url` | 再抽出**ゼロ**、再レンダリング**全部** |

#### (b) 判定 — C1〜C6 は予測どおり、C7 は真だが予測値が外れた

| # | 命題 | 事前予測 | 結果 |
|---|---|---|---|
| C1 | source-url だけ変えると `reExtract 0` + render-all 報告 | 真 | **真** (`renderKey:sourceUrl` 1 行) |
| C2 | その実行で Lean が起動しない | 真 | **真** (extract 0.033s = 分岐不通過、抽出器イベント無し) |
| C3 | 432/432 ページのバイトが実際に変わる | 真 | **真** (旧 rev を残すページ **0**、新 rev を持つページ **432**) |
| C4 | IR は前後で byte 一致 | 真 | **真** (`diff -r` が無出力) |
| C5 | extract 鍵の変更は 432 再抽出、render-all は空 | 真 | **真** |
| C6 | 分割の detect コストはドリフト以下 | 真 | **真** (**+0.3 ms** 対 ドリフト 6.8 ms) |
| C7 | 単一鍵より安い | 真, 25〜30 s 節約 | **真。ただし予測値は外れ — 実際は 17.05 s** |

#### (c) C7 — 分割前後の対照【実測】

「単一鍵だったら source-url 変更が何を要求したか」は**反実仮想を作って測った** —
extract 鍵を偽装 + `--mode all` = 「432 再抽出 + 432 再レンダリング」。
5 回ずつ**交互**実行、run 1 破棄、同一セッション・同一暖機状態。

| | split (source-url 変更) | onekey (単一鍵の反実仮想) |
|---|---:|---:|
| 壁時計 | **1.3414 [1.3359–1.5036]** | **18.3923 [17.2356–21.2470]** |
| user+sys | 1.5200 | 17.3300 |
| major fault | 190 | 19,565 [5,586–53,544] |
| peak RSS | 218.5 MB | 3,297 MB |
| extract | 0.0281 (不実行) | 16.7658 [15.5857–19.5784] |

**節約は 17.05 秒 / 13.7 倍。分母は「1 コミット = revision が変わる」1 回分。**

**予測 25〜30 s が外れた理由**: 27 秒は `extract-once.sh` 単独の既存値で、この系列の

直前に台帳を作り直すので 432 個の `.olean.hash` が暖まっている。**分割の真のコストは
C6 の +0.3 ms** — 同一ワークロードに対し 2 つの**版**を交互に当てて測った。

#### (d) 節約以外に確定したこと — 「影響集合の mode」は実運用でほぼ効かない

revision は**ページのバイトに 4,992 か所出る**ので、コミットのたびに 432 ページ全部が
無効になる。したがって:

1. `--mode self|referrers|importers` は、**実際のコミットの revision 成分に対しては
   常に `all`** に潰れる。mode が決めるのは「モジュール変更が追加で stale にするページ」
   だけで、**レンダリング量を決めるものではなくなった。**
2. ただしその量は元々小さい — **432 ページ全部で 0.87 秒**。
   分割が 13.7 倍になるのは、**高いのはレンダリングではなく抽出のほうだった**から。

**訂正 (2026-08-10)。** ここには当初「大半は IR 全読みの固定費」と書いていたが、**生ログと
合っていなかった**。`benchmarks/results/stage5d-keysplit.jsonl` の `stage5d-split` の段別
タイマー (run 2、中央値の run) は次のとおり:

| | 秒 | 割合 (プロセス内 total 0.7996 に対して) |
|---|---:|---:|
| 固定費 (preMain 0.002 + readIr 0.133 + indexBuild 0.009) | **0.144** | **18%** |
| ページ数に比例する分 (renderHeaders 0.2136 + renderPage 0.2508 + flatten 0.0492 + write 0.1398) | **0.653** | **82%** |
| deno 起動など (サブプロセス壁時計 0.8653 − プロセス内 0.7996) | 0.066 | — |

**固定費が大半を占めるのは 1 ページだけ再生成する場合** — §(g) の `leaf-self` が
壁時計 0.1952 秒中 床 0.17 秒 = 87%。**その記述が 432 ページのケースに横滑りしていた。**
効くのは下の 3 で、**0.87 秒のうち消えるのは 82% の側**なので取り分は小さくない。

#### (e) この計測が答えていないこと

1. **実コミットの合計は測っていない。** split の 1.34 秒は「source-url だけが変わった」
   場合で、実際のコミットは**モジュールも変わる**。合計 = 1.34 秒 + 変更モジュールの抽出
   (+ `lake build`、これが臨界パスの 74〜98% であることは増分 3 の実測)。
2. **`--source-url` 以外の renderKey 項目は空。** `--ws-heuristic` は approach.md が挙げて
   いるが `render.ts` には該当フラグが無い。今の renderKey は生成器 id と sourceUrl の 2 項目。
3. **rev をページのバイトに埋めない設計は検討も計測もしていない。** 相対リンク + 配信時
   注入なら、コミットで無効になるページは **0** になり 0.87 秒も消える。§5.6 の出力契約の
   変更であって台帳の話ではない (→ approach.md §8 の未解決の問い)。

### 段階 5 — 増分生成 / 増分 5「L3-1 を実装して本物の移動で検証する」 (2026-08-10)

#### (b) F5 の正体は削除ではなく L3-2 (全域写像)【実測】

食い違ったのは削除と無関係な `Shannon/LZ78/GreedyLongestPrefix.html`。
**増分側にだけリンクが余分にある**:

```
増分:       <code>bAbsorbed = <a href=".../Mathlib/Data/Nat/Find.html#Nat.find">Nat.find</a></code>
フルビルド: <code>bAbsorbed = Nat.find</code>
```

機構を端から端まで追った:

1. 削除したモジュールは、パッケージ内で `Nat.find` を印字署名で参照していた**唯一**の
   モジュールだった (3 か所)。
2. だから `Nat.find` はパッケージの**全域写像 (名前 → 定義モジュール)** に入っていた。
   削除でこれが落ち、他 5 名と合わせて写像は **533 → 527** に減った。
3. `GreedyLongestPrefix` の **docstring** には `` `Nat.find` `` がバッククォートで出てくる。
   autolink はバッククォートのトークンをこの全域写像で解決するので、削除前はリンクになり
   削除後はならない。
4. そのページは再生成されない。自分の IR は変わっていないし、どの規則も指していない。
   **古いリンクがそのまま残る。**

判断点 3 が示した L3-2 より**鋭い**実例になっている:

- **失敗が双方向**。判断点 3 は「リンクが増えるべきなのに増えない」ページだった。
  ここは「**リンクが消えるべきなのに残る**」— しかも指す先のアンカーはもうどこにも無い。
- **影響先が任意に遠い**。LZ78 は Kolmogorov を import しないし、されないし、参照も共有
  しない。**繋いでいるのは全域写像だけ** — これが「import で閉じない」の意味。
- **差分が小さく、計算できる**。写像から抜けたのは 6 名。影響しうるページは
  「その 6 名を docstring に含むページ」で、これは**走査であって推測ではない** (→ 増分 7)。

**計測前に宣言した撤退ラインが「これは削除ではなく出力契約についての発見」と言っていた
とおりのものが出た。** F1〜F4 が削除経路であり、そこは成立している。

#### (c) 制約 — 常駐環境は再読み込みできない

- **ラウンド 2 以降**は olean が動いていないモジュール (L2 が見逃したのはまさにそれが理由)

> **L3-1 が直そうとしたその誤りをそのまま再現する** — 実測で参照側 IR が 10,263 B
> 対 正解 10,267 B、所有者が `…Huffman.Length` (正解は `…Huffman.LengthCore`)、
> **439 ページ中 1 ページが誤り**。「それ以外には正しい」の「それ以外」は

> 安全なのは **`lake build` の後に立てた**サーバ。

### 段階 6d — プレビューは常駐の受け皿になるか (2026-08-10)

段階 6 の結論「the real fit is a long-lived preview mode」が段階 6a の W1 と両立するかを
確かめる節。**プロセスを 1 つも起動せず、時計も使わない** — 問いは「どのバイトが存在するか」で
あって速さではないので、段階 6a が作った木のバイト比較だけで答える。

| | |

| 事後の正解と一致 | **しない** |
| よって「正しく、かつ新しい」もの | **0 件** |

**編集前の環境は編集前の olean の関数**なので、そこから導けるものは前回すでに導かれている。
**プレビューの仕事は編集について何か言うこと**なので、常駐はその高速化にはならない。

#### (b) U2 — 1 回の編集の影響範囲【実測】

| | |
|---|---:|
| 編集が届いたモジュールページ | **433 中 6 = 1.39%** (変化 5 + 追加 1) |
| パイプラインの再生成集合 | **6 — 同一集合** |
| 変化した全域成果物 | 4 (`declaration-data.bmp` / `name-map.json` / `navbar.html` / `tactics.html`) |
| ディスク上で既に正しかったモジュールページ | **427** |

**全域成果物 4 件は L3-3 が毎回作り直す**ので、プレビューの意味では stale ではない。
モジュールページと混ぜると「プレビューが間違える割合」が 1.39% → 2.28% に膨らむので分けて数える。

#### (c) U3/U4 — 「未更新」表示の精度【実測】

- **stale は 1.39%** で、集合は**名指せる**。だから表示は**ページ単位**。
  サイト全体のバナーは**正しい 427 ページを無駄に警告する**。
- **ビルド完了前に 6 のうち 5 (83%) を正確に名指せる** — 台帳 (olean のハッシュ) だけで、
  Lean は要らない。残る 1 は L3-1 の参照側で、**原理的に事前には分からない**:
  自分の olean が変わらないからこそ stale なので、どんなハッシュも漏らさない。
- 保守的に補うなら「変更モジュールの宣言を IR で名指しているモジュールも印を付ける」
  = 参照側集合 (この変更で 4 モジュール)。IR にあるので Lean 不要。

#### 判断

**§8 のプレビューの選択肢が 3 つから 2 つに減った。** 常駐は落ちた。
残るのは (1) 構文ベースの近似 (未計測、コストは elaboration 無しの Lean パーサ) と
(2) 前回のページ + 未更新表示 (数字が付いた)。**(2) には数字があり (1) には無い。**

**直した文書**: `approach.md` §8「プレビューモードを持つか」/ §7 の段階 6 の総括。

(参照側 2 つを含む) を全部拾っていた。**では何が救ったか** — instance 一覧は**ページのバイトに
無い**。`render.ts:1142` は空の `<details class="instances-for-list">` を出し、ブラウザが
`declarations/declaration-data.bmp` から埋める。そのファイルは `global.ts` が**毎回**
作り直す (L3-3)。**3 層でいちばん安い層が、L3-1 の仕事だと思われていたものをやっていた。**

#### (c) N4 — abbrev は L3-1 が必須で、5e より難しいケースだった【実測】

| | `--l3-1 on` | `--l3-1 off` |
|---|---|---|
| 結果 | **439/439 byte 一致** | **誤り — 3 ページが相違** |
| ラウンド / 変更 / stale / ページ | 2 / 2 / **3** / 5 | 1 / 2 / 0 / 2 |
| 誤ったページ | — | `Fano/Core.html` `Fano/DPI.html` `Fano/Measure.html` |

段階 5e の移動は stale **1**・誤り **1 ページ**だった。こちらは **3 と 3** で、
**L3-1 が作られた元のケースより強く効かせて、なお完全一致。**
**reducible な定義でも `(モジュール, 名前)` の鍵は壊れない** — delaborator は展開形ではなく
abbrev 自身の名前を印字する (少なくともここでは)。

#### (d) N5/N6 — 2 ラウンドは構造的な上限【実測】

ラウンド 2 に到達したのは abbrev だけで、その ownership 報告は **`lostNames 0, gainedNames 0`**。
これは構造的な議論が予測するとおり: **ラウンド 2 以降のモジュールは olean が動いていない**
(だから L2 が見逃した) ので、**宣言集合も動かない** (集合はそのモジュール自身の olean の
`constNames` から来る)。だから `lost`/`gained` に何も足さず、ループは止まる。
**偶然ではなく理由があって止まっている。**

**それでも `--max-rounds` は残す。** 議論には穴が 1 つある — 宣言集合は `constNames` を
`isBlackListed` で濾したもので、この述語は環境を参照する (`isAuxRecursor env` /
`isNoConfusion env` / `getStructureInfo? env parent` / `findDeclarationRanges?`、
`Extract.lean:168-189`)。**それを反転させる変更があればラウンド 3 が出る。**
今回のどの変更も反転させなかったが、それは定理ではない。

#### (e) 強い witness での追試 — 影響範囲 30 倍でも完全一致【実測】

初回の census は `abbrev` の候補を**並べ替えていなかった**ので、最初に来たもの
(`InformationTheory.Fano`、abbrev 1 個・参照側 2 モジュール) を選んでいた。直して、
この対象で最も強い witness (`…BroadcastChannel.Basic`、abbrev 4 個・**参照側 33 モジュール**)
で再走した。生ログ `benchmarks/results/stage6c-l31-generality-abbrev-strong.txt`。

| | `--l3-1 on` | `--l3-1 off` |
|---|---|---|
| 結果 | **439/439 byte 一致** | **誤り — 30 ページが相違** |
| ラウンド / 変更 / stale / globalStale / ページ | 2 / 5 / **30** / 1 / 36 | 1 / 5 / 0 / 1 / 6 |
| ラウンド 2 の ownership | `lostNames 0, gainedNames 0` | — |

**L3-1 が拾った 30 モジュールはすべて意味があった** — 無しにするとちょうどその 30 ページが誤る。
段階 5e の「stale 1 / 誤り 1 ページ」に対し **30 倍の影響範囲でなお完全一致**。
弱い witness に無かった 2 点: **L3-2 も発火した** (`globalStale 1`) ので L3-1 単独ではなく
**L3-1 と L3-2 の合成**を測っており、それでも byte 一致。そして **2 ラウンド上限が
ラウンド 2 に 30 モジュール入っても崩れない** — `lost 0 / gained 0` は小さいラウンドの
偶然ではなく、上限が規模に依存するならここで反例が出ていた。

#### 判断

**L3-1 の一般性は「移動する名前が印字署名に出るかどうか」で決まる**と確定した。
出る種別 (定理・`abbrev`) には必須、出ない種別 (`instance`、この対象の `@[simp]`) には無関係で、
**そちらを救っているのは L3-3 (全域成果物を毎回作り直す)**。
**3 層の分担は偶然ではなく、いちばん安い層が最も広い網だった。**

**直した文書**: `approach.md` §5.5 の L3-1 (種別ごとの効き方 + ラウンド上限とその穴) と
L3-3 (正しさにも効いていること)。
