# 検索の再設計 — 索引形式 v2

**状態: P0 / P1 / P2 実装済み (2026-08-19)。結果は §15。** 設計時の実測も同日で、生ログは
`benchmarks/results/search-design-2026-08-19.txt`、計測ツールは
`benchmarks/tools/search-format-probe.ts`。**入力は公開サイトが実際に配っている
`search-index.json`** (`etag "6a814682-62f9a"` / 405,402 B)。

制約は**静的ファイルホスティングのみ**。サーバも索引エンジンも足さない。

## 2. どこに余地があり、どこに無いか

**測ってから設計を決めた。順に潰した結果、余地がある軸は 2 本しか残らなかった。**

- **速度には無い。** 走査 0.65 ms に対し debounce が 90 ms ある。バイト走査に書き直した
  試作は **0.67 ms** で、**現行と区別がつかない**【実測】。N=4,584 では計算量の改善が
  観測にならない。**「速くなる」と書かない。**
- **転送量にもほとんど無い。** gzip 済み JSON は既に良い。検索に要る部分だけを比べると
  **40,935 → 39,651 B (−3.1%)**【実測】。gzip は整列済みの名前が共有する接頭辞を
  自力で見つけている。**バイト形式にしたから小さくなる、ではない。**
- **メモリには 8〜16 倍ある。** 常駐 860 KiB → **105 KiB (8.2×)**、山 1,651 KiB →
  **105 KiB (15.7×)**【実測】。
- **重複に 12.8% ある。** `modules` 節は `modules.json` と**同じ配列に同じ順で添字を
  張っている**【実測: `artifacts.rs:186-198` が一つの `own_sorted` から両方を作る】。
  そして `modules.json` は `initTree()` が**全ページで取る**【`app.js:544`】。
  検索索引がもう 1 部持つ理由が無い。

さらに、**規模が変わると前提ごと変わる** — 全件ダウンロードと O(N) 走査は、いまの母数が
小さいから成立している。§10 に限界を書く。

## 3. アプローチ

**索引を「JS オブジェクトの山」から「1 本の連続したバイト列」に変え、照合を文字列 API から
バイト走査に落とす。検索の意味は 1 ミリも変えない** — 同じ 3 段の採点、同じ母数、同じ順位。

外すもの: (a) `JSON.parse`、(b) 打鍵ごとの文字列確保、(c) 他のファイルと重複した節。
足すもの: front-coding と、打鍵ごとの絞り込みキャッシュだけ。

**配信形態は変わらない** — 静的ファイルを 1 本 GET するだけで、Range も分割も要らない
(どちらも検討して却下した → §9)。

小さくできる根拠は 1 つ: **名前は整列済みで、隣り合う名前が平均 46.7 文字の接頭辞を
共有している**【実測】。front-coding はこれを直接使い、**285,148 B の名前を 93,497 B にする**
【実測】。

そして**意味を変えないことが、この設計の検査手段そのもの**になる — 現行の採点器を
オラクルに置いて、新旧が同じ答えを出すことを機械で確かめられる (§11)。

## 4. 形式 v2

1 ファイル、ヘッダ + 4 節。**順列も辞書も持たない** (どちらも実測で高くついた → §9)。

| 節 | 中身 | raw | gzip |
|---|---|---:|---:|
| 0 | ヘッダ — magic / version / 宣言数 / kind 名の表 / 各節の offset | ~100 | — |
| 1 | 名前。**front-coded**、16 件ごとに restart | **93,497** | 34,119 |
| 2 | restart の byte offset (u32 × ⌈N/16⌉) | 1,148 | 876 |
| 3 | kind (1 宣言 1 ニブル) | 2,292 | 727 |
| 4 | モジュール添字 (u16 × N) | 9,168 | 3,095 |
| | **合計** | **106,105** | **39,651** |
| | (参考) いまの `search-index.json` | 405,402 | 47,959 |

【すべて実測。gzip は Deno の `CompressionStream`。GitHub Pages が返す gzip は設定が違い、
同じファイルで 49,193 B になる — **比較は同じ圧縮器同士で読むこと**】

形式の細目:

- **1 件は `(共有接頭辞長 u8, 接尾辞長 u8, 接尾辞バイト列)`。** 16 件ごとに共有をリセットし、
  その位置を節 2 に持つ。これで**任意の 1 件を先頭から読まずに復元できる** (結果行の描画に要る)。
- **接尾辞が 254 バイトを超える名前は表現できない。encoder は切り詰めず拒否する。**
  実測コーパスの最長は 129 B だが、**「Lean の名前はそんなに長くならない」は仮定**なので
  拒否を実装に持たせる (→ §13-3)。
- **大文字小文字は元のまま持つ。** 照合は ASCII 折り畳み (A-Z のみ +32)。
  **このコーパスでは `toLowerCase()` と 0 件差**【実測】だが、**パッケージごとに encoder が
  検査し、差が出た名前だけ例外表に載せる**。`Γ`/`γ` を持つパッケージは実在しうる。
  **「ASCII だろう」で焼かない。**
- 節 4 が指すモジュール配列は `modules.json` のもの。**検索索引は名前もパスも持たない。**

## 5. 照合 — 1 パス、確保ゼロ

節 1 を頭から 1 回なめる。復元と折り畳みと採点を**同じ走査の中でやる**:

1. 使い回しのスクラッチ 2 本 (`orig` / `fold`、各 512 B) に接尾辞だけ書く。
   共有接頭辞は**前の名前がすでに置いてある**ので触らない。
2. 最後の `.` の位置は走査中に維持する (接尾辞に `.` が無ければ前の値を引き継ぐ)。
3. 3 段を現行と同じ順で当てる — 最終成分の前方一致 → 全体の前方一致 → 部分文字列。
4. 当たった件だけ、`(id, score, 長さ)` を確保済みの `Int32Array` に積む。

**採点は UTF-16 長で行う** — 現行が `last.length` / `lower.length` で採点しており、
バイト長にすると非 ASCII を含む名前の順位が変わるため。連続バイト (`b & 0xC0 == 0x80`)
を数えて換算する。**当たった件だけ**なのでコストは出ない。

**確保は走査中ゼロ**、最後の整列で候補数ぶんだけ。表示する 30 行の文字列は、
節 2 経由で**その 30 件だけ**復元する。

**等価性: 20 クエリで、当たり集合も先頭 30 件の順序も現行と完全一致**【実測】。
非 ASCII (`β` / `₁`)・ドットを跨ぐ検索 (`nat.` / `theory.f`)・0 件 (`zz`) を含む。

## 6. 打鍵ごとの絞り込み

3 段のどれで当たるにせよ「クエリを含む」が必要条件なので、**候補集合は打鍵で単調に縮む**
【実測: 部分集合であることを確認済み】。つまり 2 文字目以降は**前回の候補だけ**見ればよい。

代表的な 5 語を打ち切るまでの候補数は **146,688 → 70,633 (48.2%)**【実測】。

**効かない場合を明記する** — `information` は**このパッケージの全名前に含まれる**ので
絞り込みが 1 件も減らさない【実測: 4,584 → 4,572 で頭打ち】。名前空間が 1 本の
パッケージでは、その名前空間を打つ限り効かない。

**これは形式に依存しない。** v2 を採らなくても単体で入れられる (→ §8 P2)。

## 9. 却下した案 — すべて実測で

| 案 | 結果 |
|---|---|
| **HTTP Range で必要な範囲だけ取る** | **GitHub Pages では成立しない。** `Accept-Encoding: gzip` を付けると **Range が gzip 後のバイト列に掛かる** (`content-range: bytes 1000-1099/49193` — 分母が圧縮後の長さ)。返るのは gzip ストリームの断片で復号できない。`image/bmp` でも同じ (66,418,003 B のファイルに対し分母 5,655,790 B、先頭は `1f 8b 08`)。**`fetch()` は `Accept-Encoding` を設定できない** (forbidden header name) ので、ブラウザから identity は要求できない【実測 §0】 |
| **成分辞書化** (名前を `.` で割り、語彙 + id 列に) | **front-coding に負ける。** 辞書 gzip 31,083 + id 列 gzip 10,047 = **41,130** に対し front-coded は **34,119**【実測】。最終成分がほぼ全部一意 (4,584 中 4,431) なので語彙が縮まない |
| **整列順列を持つ** (小文字名順 / 最終成分順の 2 本) | **索引本体より高い。** ほぼ非圧縮で **+16 KB gzip**【実測】。二分探索で買える速度は §2 の通り観測にならない |
| **lowercase を前計算する** (打鍵ごとの `toLowerCase()` を潰す一番素直な手) | **常駐 860 → 1,457 KiB**【実測】。**CPU をメモリで買う方向で、目的と逆** |
| **doc-gen4 方式の fuzzy 化** | 別件。**今回は照合の意味を変えない** — 変えると §11 の等価性ゲートが張れなくなり、形式の入れ替えと検索品質の変更が同じコミットで混ざる |

## 10. 規模が変わったとき — 限界を先に書く

母数が増えたら (依存込み = doc-gen4 の 258,760 宣言相当)、全件ダウンロードが先に破れる。
分割の鍵は**最終成分の先頭 2 バイト**で、いまの母数だと **179 バケット / 最大 374 / 中央値 8**
【実測】。検索欄が 2 文字未満で走らないので、鍵は常に揃う。

**ただし、きれいに分割できるのは第 1 段だけ。** 第 2 段 (全体の前方一致) は
**接頭辞が全件に当たりうる** (`information` が実例【実測】)、第 3 段 (部分文字列) は
n-gram の転置索引が要る。**ここは設計しない。**「バケット分割で全部いける」と書かない。

## 11. ゲート

- **等価性 — 別経路が同じ答えを出すか。** encoder が吐いた `.bin` を decoder に食わせ、
  **現行の `score()` を無改変のオラクルとして**当たり集合と先頭 30 件を突き合わせる。
  決定的で、機材に依存しない。**オラクルを書き直さない** (書き直すと両方同じ間違いをする)。
- **決定的な整数で見る** — 節ごとのバイト長 / 打鍵あたりの候補数 / 復元した名前の本数。
  **壁時計はゲートに使わない。**
- **新しいゲートは必ず一度落としてから通す** — encoder を壊して赤が出ることを見る。
  「何をしても通るゲート」を過去に 2 件作っている。
- **母数を突き合わせる** — `.bin` の宣言数と `name-map.json` の母数が一致すること。
  「走った本数」を数えないゲートは嘘をつく。

## 12. 撤退ライン

- **ブラウザの実測でピークが 5 倍以上下がらなければ P1 は入れない。** 今回の数字は
  Deno の V8 で、ブラウザのヒープ会計は別物【→ §13-1】。P0 + P2 だけ入れて閉じる。
- **等価性が別コーパスで 1 件でも崩れたら止める。** 順位が変わる形式変更は、
  「速くなった」より高くつく。
- **P1 単体では体感が変わらないことを認めた上で入れる。** 効くのは規模が増えたときと、
  メモリが細い端末。**「速くなりました」と言わない。**

## 13. 未検証 — 「たぶん大丈夫」と読まない

1. **ブラウザでの常駐とピーク。** 今回は Deno 2.7.14 / V8 14.7 の `heapUsed` / `external`。
   Chrome / Firefox / Safari は**測っていない**。ArrayBuffer が external に載るのは V8 の
   会計であって、他エンジンの数字ではない。
2. **ASCII 折り畳みの例外。** このコーパスは 0 件だが、**0 件であることをこのコーパスでしか
   確かめていない**。`e2e/micro/` に非 ASCII の大文字を持つ宣言を足して確かめる。
3. **254 バイトを超える接尾辞。** 実測最長 129 B。長い名前を持つパッケージで encoder が
   実際に拒否するかは未検証。
4. **依存込み (258,760 宣言) での成立性。** §10 は設計を書いただけで、1 バイトも測っていない。

## 15. 実装の結果 — 2026-08-19

3 段とも入った。**設計から変えた点が 3 つあり、実装中に欠陥が 1 件出た。**

### 入ったもの

| | |
|---|---|
| **P0** | `search-index.json` から `modules` 節を落とし、`instances` / `instancesFor` を `instances.json` へ。成果物は 7 → 8 本 |
| **P1** | `search-index.bin` (形式 v2) と `app.js` のバイト走査。JSON の索引は無くなった |
| **P2** | 打鍵ごとの絞り込みキャッシュ (`NARROW_MAX = 512`) |

### 設計から変えた 3 点

1. **kind はニブルではなく 1 バイト。** `css_kind` は知らない kind を素通しするので**語彙が
   閉じていない** — ニブルは 16 種で破綻し、encoder が拒否する経路が要る。1 バイトにすると
   **その失敗経路ごと消える**。代償は宣言 1 件につき 0.5 バイト (実対象で +2,292 B raw)。
2. **接尾辞長に 255 のエスケープを付けた** (255 なら実長が u16 で続く)。実測コーパスの最長は
   129 B だが、**「Lean の名前はそんなに長くならない」は仮定**であって、切り詰める encoder は
   検索とページを黙って食い違わせる。共有接頭辞の方は 254 で頭打ちにしてある
   (圧縮が少し落ちるだけで、正しさは落ちない)。
3. **52 バイトのヘッダを置いた** (magic / version / 各節の offset)。計画の表には無かったが、
   version の無い形式は**読み手を差し替えられない**。

### 実装中に出た欠陥 — astral の長さ【実測】

**`utf16Length` が UTF-16 単位ではなく符号位置を数えていた。** 採点は `2000 - 長さ` なので、
長さが 1 ずれると順位が 1 つずれる。**ブラウザゲートが `Micro.script𝒜` を `Micro.usesDep` の
上に置いて落ちた** — どちらも接頭辞一致で、UTF-16 長は 14 と 13。

- **設計時の計測ツールも同じ間違いをしていて、気づけなかった** — 公開サイトのコーパス
  (4,584 宣言) に **BMP 外の名前が 1 つも無い**ため。`e2e/micro` が U+1D49C を持っているのは
  まさにこれのためで、**「対象が持たない宣言の形」を持つフィクスチャが 1 件回収した**。
- `benchmarks/tools/search-format-probe.ts` 側も直した。**直した理由を消さないこと。**

### ゲート

| ゲート | 見ているもの | 結果 |
|---|---|---|
| `cargo test --workspace` | 形式の往復 / restart 境界 / 254 バイト超 / fold 例外 / 空パッケージ | **緑** |
| `check-site-closure.py` | **Python の独立デコーダ**で索引 ↔ ページ ↔ `name-map.json` を突き合わせ | **緑** — micro で 42 宣言。`search-index == name-map` を新設 |
| `check-site-browser.ts` | **凍結した旧採点器**と、実ブラウザの実 UI の描画結果 | **緑** — 11 クエリ / 43 宣言、**うち 3 つは 1 文字ずつ打って**絞り込み経路を通す |

**どちらの新ゲートも一度落としてから通した**【実測】: 索引の module 添字を 99 に書き換えると
閉包検査が `1/42 failed` で落ち、`instances.json` を消すと `missing` で落ちる。絞り込みを
1 件落とすように壊すとブラウザゲートが **11 クエリ中 6 つ**で落ちる。

### サイズ — 実測は micro、実対象は外挿

- **実測**: `e2e/micro` の `search-index.bin` は **43 宣言で 606 B** (gzip 433 B)。
- **外挿**: 実対象 (4,584 宣言) は、設計時に測った試作形式 106,105 B に **kind の +2,292 B と
  ヘッダ 52 B と kind 名表 ~50 B** を足して **≈ 108,500 B**。**これは外挿であって実測ではない**
