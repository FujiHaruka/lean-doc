# 再抽出の回数を減らす — G2 の再定義

**状態**: 段 A・B は完了、**段 C は設計が実測で置き換わった** (leg 4、2026-08-17)。
実装はこれから — 入れるのは §6 の **C** と **D** の 2 つ。
**SoT**: 数字は `docs/verification-log.md`、アプローチは `docs/approach.md` §6.1 / §5.5。
この文書は**そのどちらでもない** — 「何を作るか決めるための調査の設計」を置く場所。

## 1. 出発点と、それが壊れたこと

leg 2 は G2 を **「宣言単位の再解析キャッシュ — 意味解析を*速く*するのではなく*回数*を
減らす」** と設定した。根拠は CI 実測で床が I/O から CPU に移ったこと:
ランナー上の `lean-doc build` は **11.5〜20.7 s** で、うち環境ロードは **1.6〜2.7 s** しかなく
**extract が 10.0〜18.2 s**【実測 2026-08-16、`benchmarks/results/ci-placement-5-summary.txt`
の same/split 腕】。`approach.md` §6.1 末尾が名指ししている「変更のない宣言を再解析しない」が
そのまま今の律速に当たる、という読み。

**この読みは母数を測ると壊れる。** 既存の実測ログ
(`benchmarks/results/stage7d-decl-profile.jsonl.gz`、4,750 宣言 / 406 モジュール) を
**モジュール単位に集計し直した**【実測の再集計、2026-08-17】:

| | 宣言数 | analyze 時間 |
|---|---:|---:|
| mean | 11.7 | 0.0263 s |
| median | 8 | 0.0178 s |
| p90 | 25 | 0.0562 s |
| p99 | 49 | 0.1240 s |
| max | 72 | 0.2033 s |

**1 モジュール変更で再解析される宣言は median 8 本、その analyze 時間は median 17.8 ms。**
最悪のモジュールでも 203 ms。増分ビルドの実測総時間は **11.739 s (fresh) / 18.096 s (resident)**
【段階 7h、→ approach.md §6.5】なので、**宣言単位のキャッシュが 100% 当たっても中央値で 0.15%、
最良でも 1.7% しか減らない。**

→ **増分シナリオでは、宣言単位のキャッシュは効かない。** これは仮説ではなく既存ログの再集計。

## 2. では 10〜18 s は誰のものか

CI の extract 10〜18 s は**増分ではなくフル抽出**の値である。432 モジュール / 4,750 宣言を
全部解析している。**キャッシュが無いのではなく、キャッシュを持ち越していない。**

`.github/workflows/ci-template.yml` (利用者に配る雛形) がキャッシュしているのは 3 つだけ:

- `~/.cache/mathlib` (Mathlib の olean、`lake exe cache get` 用)
- `lean-doc/extractor/build` (Lean 抽出器のバイナリ)
- `~/.cargo` + `lean-doc/target` (Rust ビルド)

**IR ディレクトリと台帳 (`ledger.json`) はキャッシュしていない。** 対象パッケージ自身の
`.lake/build` もキャッシュしていない。だから毎 run が初回ビルドで、L2 (モジュール単位ハッシュ)
は比較相手を持たない。増分機構は**実装済みなのに CI では一度も発火していない**。

→ **「回数を減らす」の正しい単位は、いまのところ宣言ではなくモジュールである。**

## 3. Approach

**やることは「新しいキャッシュ層を足す」ではなく「既にあるキャッシュ層を CI 跨ぎで発火させる」。**
そのうえで、発火しない条件が実測で見つかったときだけ、その条件に合う単位 (宣言単位を含む) を
検討する。順序は次の 3 段で、**各段の結果が次段の要否を決める**。

1. **段 A — 発火の可否を決める 1 つの実測**: 「**同じソースから再ビルドした olean は byte 一致するか**」。
   L2 の鍵は olean の内容ハッシュなので、ここが偽なら**モジュール単位のキャッシュは CI で
   原理的に当たらない** (毎 run 全モジュールが「変更あり」になる)。ここが真なら段 B に進む。
2. **段 B — 配線と実測**: `ci-template.yml` に IR + 台帳のキャッシュを足し、
   ワークフローを実走させて **extract 秒とプロセス起動数・再抽出モジュール数**を取る。
   ゲートに使うのは壁時計ではなく**決定的な整数** (再抽出モジュール数 / 再描画ページ数)。
3. **段 C — 残差を見てから単位を決める**: 段 B の後に残る再抽出が何に由来するかを数える。
   **そこで初めて「宣言単位」に意味があるかが決まる。**

**この順序を崩さない理由**: 宣言単位のキャッシュは、モジュール単位のキャッシュが**当たらない
とき**にだけ意味を持つ (当たるなら宣言は 0 本しか再解析されない)。だから先に段 A で
「当たるか」を決めないと、宣言単位の是非は原理的に判定できない。

### 分岐 (段 A の結果で決まる)

| 段 A の結果 | 意味 | 次にやること |
|---|---|---|
| **byte 一致する** | モジュール単位で足りる | 段 B。**宣言単位は不要** — G2 は否定として記録して閉じる |
| **byte 一致しない** | L2 の鍵が CI で無力 | 鍵を「olean のバイト」から**内容由来の別物**に変える必要がある。その単位の候補として初めて宣言単位が立つ |

**→ 段 A・段 B とも実行済み。結果は上段。** 数字の SoT は
`docs/verification-log.md`「IR キャッシュを CI 跨ぎで効かせた」(2026-08-17)。

### 撤退ライン

- 段 B を実走して **extract 秒が有意に減らない**なら、この方向を閉じて `verification-log.md` に
  否定として記録する。**「配線したから速いはず」で終わらせない。**
- 段 C で残差が **1 秒未満**なら、宣言単位は**作らない**。§1 の表がその根拠。

## 4. 段 A — 実行済み。**byte 一致する**【実測 2026-08-17】

計測器は `benchmarks/tools/olean-determinism.sh`、ログは
`benchmarks/results/olean-determinism-2026-08-17.txt` (小さい葉 5 本) と
`-large.txt` (大きい葉 4 本)。**母数 9 モジュール、olean 3,680 B 〜 1,231,808 B。**
対象は `/Users/haruka/dev/lean-projects` (`c4f6af29`)、機材は M1 (Darwin arm64)。

各モジュールで 4 点を取り、3 つの判定を出す:

| | 判定 | 結果 |
|---|---|---|
| h1 == h0 | DETERMINISTIC (消して再ビルドしても同じバイト) | **9/9 PASS** |
| h2 != h1 | SENSITIVE (宣言を 1 本足すとバイトが動く) — **陽性対照** | **9/9 PASS** |
| h3 == h1 | REPRODUCIBLE (編集を戻すと元に戻る) | **9/9 PASS** |

**sha256 (olean のバイト) と lake (`<file>.olean.hash`) の両方で同じ判定。** 台帳の既定は
sha256 なので、効くのは前者。陽性対照が全部通っているので「バイトが動かなかった」は
「再ビルドされていなかった」ではない。

→ 分岐表の上段。**モジュール単位のキャッシュで足りる。宣言単位は作らない。** 段 B へ。

**この実測が言っていないこと**: (a) Linux ランナー上での再現性、(b) 別マシン / 別 checkout
先での再現性 (olean には絶対パスが埋まっている → §4 の「未検証の前提」)、
(c) 葉でないモジュール。**(a) は段 B の実走がそのまま試験になる** — CI はキャッシュから
olean を復元せず毎 run ビルドし直すので、台帳が当たること自体が Linux 上の決定性の証拠になる。

**未検証の前提** (段 A が真でも残る):
- olean にはソースの**絶対パス**が 429/432 モジュールで埋まっている【実測 → approach.md §5.5】。
  GitHub Actions 内では checkout 先が run 間で一定なので run 跨ぎでは問題にならない、
  というのは**仮定**。段 B の実走で確かめる。
- `extractKey` は path 非依存である (`leanToolchain` / `manifestSha256` /
  `EXTRACTOR_ID` / IR schema・generator)【コードで確認、`crates/lean-doc-incr/src/ledger.rs`】。
  `EXTRACTOR_ID` は定数なので抽出器を再ビルドしても鍵は動かない。

## 5. 段 B — 実行済み。**無変更なら 31.6 倍、本番の押下は 1.35 倍**【実測 2026-08-17】

数字は `docs/verification-log.md` が SoT。ここには**次の判断に効く 3 点だけ**置く:

1. **配線は効いた** — `ci-template.yml` を同一 commit で 2 回回して cache-hit true、
   **再抽出 13 → 0 モジュール / 再描画 13 → 0 ページ / 抽出器プロセス 1 → 0**。
   run 2 でも `lake build` は実走しているので、**Linux ランナー上でも olean は byte 一致した**。
2. **無変更の増分は 31.6 倍** (422 モジュールの本番対象、同一セッション warm: 9.8848 → 0.313 s)。
   **1 モジュール変更は 1.35 倍しかない** (9.8848 → 7.3118 s)。**後者が本番の CI 押下の姿。**
3. **残った律速は宣言でも抽出でもない** — 1 モジュール変更 7.3118 s の内訳は
   環境ロード **3.329 s** + 依存写像の書き直し **1.461 s** + 意味解析 **0.0072 s** + 残り約 1.5 s。
   しかも依存写像の**全体ダイジェスト**が `renderKey` に入っているせいで **422 ページ全部**が
   再描画される (全域写像の差分 L3-2 は正しく 0 ページと答えている)。

→ **宣言単位のキャッシュはこれで 2 経路から否定された。閉じる。**

## 6. 段 C — 次の対象は「全環境成果物を毎回まるごと作り直していること」

1 モジュール変更で払っている 7.3 s のうち、**変更量に比例していないのは 2 つだけ**:

| 対象 | 秒 | 何が全環境なのか | 効きそうな筋 |
|---|---:|---|---|
| **依存写像 (`linkIndex`)** | **1.461** + 再描画 422 ページ | 490,287 定数を走査して 255,810 宣言 / 10.4 MB を毎回書く | (a) 差分で書く / (b) **鍵をファイル全体のダイジェストから「動いた名前の集合」に変える** — L3-2 が全域写像に対して既にやっている形 |
| **環境ロード (`ready`)** | **3.329** (cold なら 15.999) | 6,011 モジュールの import | 既知の床 (→ approach.md §3 / §5.1)。**常駐で 1 回に畳めるが、編集したモジュールの olean は resident では拾えない** (→ `extractor/Extract.lean` の `serve` の但し書き) |

**先にやるのは依存写像のほう。** 理由は 3 つ: 環境ロードは §3 で既に「床」と結論が出ていて
先読み以外の手が無いこと、依存写像は**過剰描画という正しさ寄りの症状**も同時に消せること、
そして L3-2 という**同じリポジトリ内の前例**があること。

### 母数 — 依存写像は 1 宣言追加で **267,504 行中 2 行**しか動かない【実測 2026-08-17】

`link-index.lidx` を 1 モジュール変更の前後で保存して差分を取った (`/usr/bin/diff`):

```
267,506 行 → 267,504 行、差分は 2 行 (0.0007%)
< InformationTheory.Shannon.SlepianWolf.FullRateRegion     ← モジュール見出し
< \tirCacheProbe2_\t13\t13                                  ← 増やした宣言 1 本
```

**残り 267,502 行は byte 一致。** それでも (a) 抽出器は 10,448,303 B を**まるごと書き直し**
(1.461 s、490,287 定数を走査)、(b) その**全体ダイジェスト**が動くので **422/422 ページが
再描画**される。**動いた名前は新設の 1 本で、それを参照しているページは 0**
(そのモジュール自身のページは既に変更集合に入っている)。

### 否定された設計 — 「安定な部分と動く部分に割って、動いた名前から再描画集合を導く」

leg 3 はこう設計した: **(C2)** 抽出器が自パッケージぶんと依存側を別ファイルに書き、
**(C1)** `renderKey` から `linkIndex` の全体ダイジェストを外して**動いた名前の集合**から
再描画集合を導く (L3-2 が全域写像に対してやっている形をなぞる)。

**この設計は必要ない。前提が実測で壊れた**【実測 2026-08-17 →
`benchmarks/results/lidx-own-half-2026-08-17.txt`】。

前提は「自パッケージぶんも描画の入力である」だった。**そうではない**:

| `.lidx` | サイト 429 ファイルとの byte 比較 |
|---|---|
| full (10,448,228 B) | — |
| **自パッケージの宣言群 396 / 4,584 行を除去** (10,098,730 B) | **差分 0 / 429** |
| **さらに `@` 節の自分ぶん 422 行も除去** (10,076,330 B) | **差分 0 / 429** |
| 自パッケージぶんだけ (371,905 B) — **陽性対照** | **差分 408 / 429** |

理由はコードにある: `NameIndex::module_of` は **IR 由来の `known` を先に見る**
(`crates/lean-doc-render/src/autolink.rs:258`)。`range_of` は全リンクで引かれるが
(`autolink.rs:332`)、出力に出るのは `ExternalLinks` が**依存パッケージの** URL を
解決したときだけ (`crates/lean-doc-render/src/external.rs:146-162`)。
自パッケージ内リンクでは引いた range は捨てられる。

**つまり `.lidx` の中で毎回動いている 3.6% は、そもそも誰も読んでいない。**
割って鍵を分けるのではなく、**書かなければよい**。

### 設計 — 段 C は「動く部分を地図に入れない」1 つの変更

- **(C) 抽出器は自パッケージのモジュールの宣言群を `.lidx` に書かない。**
  `@` 節は**全部そのまま残す** (`module_for_source_path` が `known_modules` を全走査して
  「一致が 2 つなら `None`」と答えるため、集合を縮めると答えが変わりうる —
  `autolink.rs:289-315`。上表の 3 行目はこの縮小をしても差 0 だったが、**縮めない方が
  主張が弱くならない**)。自パッケージのモジュール一覧は新しい入力として渡す
  (`serve` はリクエストごとに `modulesPath` を差し替えるので、**そこからは導けない**)。
  - **これで `.lidx` は 1 モジュール変更で 1 バイトも動かなくなる。**
    `renderKey.linkIndex` は**そのままでよい** — 動かなくなるので `Mode::All` に落ちない。
    C1 の delta 機構も台帳の schema bump も `ModuleFacts` の拡張も**要らない**。
  - 取り分: **再描画 422 → 変更集合ぶんだけ**、IR 全読み **4.00 → 約 2.00 pass**。
- **(D) 地図が既に正しいなら書き直さない。** C を入れても抽出器は毎回 490,287 定数を
  走査している (**1.23 s**)。地図の中身は (依存モジュール集合) × (その olean) で決まり、
  後者は `extractKey` (toolchain + manifest) が押さえている。so 抽出器が
  **依存モジュール名一覧のダイジェスト**を計算し、既存ファイルの `#` ヘッダ行
  (レンダラのパーサは `#` 行を無視する → 形式変更ゼロ) がそれと呼び手の渡す
  `extractKey` トークンに一致したら**走査ごと飛ばす**。
  - **`extractKey` だけでは不足**: 対象が `import Mathlib.NewThing` を足すと依存閉包が
    増えるのに manifest は動かない。依存モジュール名一覧のダイジェストがそこを閉じる。
  - 取り分: **1.23 s**。

**C と D は独立に入れられる** (C は描画側、D は抽出側)。順は C → D。

#### C は実装済み【実測 2026-08-17 → `benchmarks/results/g3-stage-c-2026-08-17.txt`】

`--link-index-omit <modules.txt>` を抽出器に足し、常駐サーバが起動時のモジュール一覧を
そのまま渡す (`crates/lean-doc/src/resident.rs`)。結果:

| | before | after |
|---|---:|---:|
| **再描画ページ数** | **422 / 422** | **1 / 422** |
| `link-index.lidx` の移動 | 2 行動く | **バイト不動** (sha256 同一) |
| オラクル (増分ツリー vs 同じ IR の全描画) | — | **差分 0** (陽性対照は 4 で差あり) |
| IR 全読み回数 | 4.00 pass | **4.00 pass — 動かない** |
| 壁時計 (warm 9 回の中央値) | 6.24 s | **6.23 s — 区別できない** |

**予測が 2 つ外れた。両方こちらが SoT。**

1. **IR 全読みは 4.00 pass のまま。** 4 pass は描画の枚数ではなく増分機構そのもの
   (ownership / merge / global) が読んでいる。**再描画を 1 枚にしても IR は 4 周読む。**
2. **壁時計は動かない。** 422 ページの描画はこの対象で約 0.3〜0.5 s しかなく、
   6.2 s の内訳は環境ロード 2.7〜3.4 s と依存写像の書き出し 1.2〜1.8 s。
   **段 C の取り分は決定的な整数と「地図が動かなくなったこと」で、秒ではない。**
   秒を動かすのは D。

#### D も実装済み【実測 2026-08-17 → `benchmarks/results/g3-stage-d-2026-08-17.txt`】

抽出器が `<地図>.key` の sidecar を持ち、**呼び手のトークン + `#lidx2` マーカー +
`@` 節が現環境と一致**したら 490,287 定数の走査ごと飛ばす (commit `c8c0fae`)。

| | baseline | 段 C | 段 D |
|---|---:|---:|---:|
| 抽出器が走査した定数 | 490,287 | 490,286 | **0** |
| 抽出器の `linkIndex` 位相 | 1.23 s | 1.53 s | **0.006 s** |
| 抽出要求の合計 | 2.09 s | 2.09 s | **0.022 s** |
| 1 モジュール変更 (warm 中央値、9 回) | 6.244 s | 6.228 s | **4.880 s** |

**baseline → 段 D で −1.364 s (−21.8%)。** 差は `linkIndex` 位相の減りとほぼ一致する。

**トークンの中身で 1 度誤った**: 最初は `extractKey` の 5 値すべてを入れていたが、
`irSchemaVersion` / `irGenerator` は **IR を説明する値で地図とは無関係**、
しかも後者は更新してはいけない値 (実装計画 §6)。副作用として初回ビルド直後に
1 回だけ理由なく地図を書き直していた。3 値 (`leanToolchain` / `manifestSha256` /
`extractor`) + omit 一覧のバイトに絞った。

**再利用の判定は 3 つ**で、3 つ目は後から足した: トークン / `@` 節 /
**`#lidx2` マーカー**。3 つ目が無いと、形式を変えても `EXTRACTOR_ID` の bump を
忘れれば旧形式の地図を再利用しうる。

**ゲート**: `tools/onemod-gate.sh` (e2e と CI が同じ 1 本を呼ぶ)。
baseline のログで exit 1 / 段 C のみのログでも exit 1 / 段 D のログで exit 0 を実走で確認。

**オラクル (実装前に決める、両方に共通)**: 変更後の site が**フル生成と byte 一致**すること。
過少描画は静かに壊れるので、**再描画ページ数だけを見て緑にしない**。
比較器は**必ず一度落としてから通す** — 上表の陽性対照 (408/429) がその形。

- **撤退ライン**: **壁時計では引かない** (page cache で 5 倍動く)。引くのは決定的な整数で、
  **C を入れて 1 モジュール変更の再描画が 422 のままなら C は失敗**、
  **D を入れて抽出器の `linkIndex` 位相が 1 s を超えたままなら D は失敗**。
  秒は結果として記録するが判定には使わない。
  - **leg 3 が置いた「6.5 s を切らなければ撤退」は破棄する。** このセッションの warm
    ベースラインが既に **5.90〜6.66 s (中央値 約 6.24 s)** で、閾値の下にいる
    【実測 2026-08-17 → `benchmarks/results/g3-baseline-onemod-2026-08-17.txt`】。
    **暖機状態が違う数字に閾値を置いたのが誤り**で、直すのは閾値の側。
