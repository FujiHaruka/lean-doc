## 2. Approach — 主張は、それを決めるものと同じ場所に置く

R1 は「432 モジュールの corpus が無いので測り直せない」問題**ではない**。
測り直せないのは pin のうち 2 つだけで、**残る 1 つは corpus を一切必要としない
HEAD の構造についての主張**であり、それが今 HEAD と食い違っている。

`state_and_delta.rs:1205-1213` は、書かれた state ファイルの 1 モジュールぶんのキー列を
**「prototype の 7 キー + `instancesFor` 1 個」**と主張する。C-2 が `ModuleFacts::refs` を
足したので HEAD では **9 キー**。この assert は偽で、**誰も気づかなかった**。

**なぜ気づけなかったか — ここが一般形**:
`ModuleFacts` の「prototype が持つ 7 キー」には**転写が 2 本ある**。

| | 形 | フィールド追加が起きたとき |
|---|---|---|
| `tests/global.rs::Facts` | **射影** — 7 キーだけを再直列化する | **見えない。壊れない** |
| `tests/state_and_delta.rs` の appended-key 列 | **差分** — 「7 キー + 手書きの追加リスト」 | **腐る。しかも凍結テストなので黙って腐る** |

CLAUDE.md 「**判断は 1 箇所に集める。同じ問いに答える経路が 2 本あると、片方だけ直る**」の
実例そのもの。実際に片方 (射影) だけが生き残った。

### 取る形

1. **prototype の 7 キーを 1 箇所で定義する。** `litedoc4-global` に `pub const` として置き、
   `ModuleFacts` のフィールド順に関する doc コメント (`facts.rs:46-51`) が主張していることを
   **機械が検査できる形にする**。転写 2 本はこれを参照する。
2. **構造の主張を、機材ゼロ依存のテストへ移す。** 「直列化したキー列は prototype の 7 キーで
   **始まる**」は `ModuleFacts` の値 1 つあれば決まり、corpus も prototype state も要らない。
   **これは `#[ignore]` にしない** — 今日から走り、以後どのフィールドが増えても自動で覆う。
   凍結テスト側は「7 キーで始まる」だけを言い、**その後に何が続くかは HEAD の話**として手放す。
   手書きの追加リストは消える。腐る場所そのものが無くなる。
3. **corpus × HEAD の同時性質である整数は、条件と一緒に置く。**
   `got.len() == 861_999` と `shim.len() == 841_947` は「HEAD がどうか」でも
   「corpus がどれか」でもなく**両者の積**で、裸の整数のままだと落ちたときに
   どちらが動いたのか 1 行で言えない (CLAUDE.md「落ちたときに何が壊れたか 1 行で言えない
   ゲートは足さない」)。**数字の SoT は `benchmarks/results/`** なので、テストには
   条件付きの主張として残し、`861_999` は復元者が測り直す対象であることを
   **assert の側から見える形**にする。
4. **オラクル本体 (`want == shim`) は触らない。** どの artifact も運ばない 818,331 B の
   facts に対する唯一のファイル型オラクルで、殺すと戻せない。frozen 分類のまま。

**この形を選ぶ理由は作業量ではない。** (a) corpus 復元は空きディスク 17 GB で
2026-08-17 の枯渇事故 (対象の olean 欠落) を再現しうるうえ、**復元しても
「差分の手書き」という腐り方は残る**。(b) byte 比較の廃止は腐り方を消すが、
オラクルも一緒に消す。**3 の形だけが、腐る構造そのものを消してオラクルを残す。**

### R2〜R5 に共通する形

R2 は `cargo deny` が**許可リストとの照合しかしない**ので抜けが緑で通る、という
「見ていないのに走っている」型 (CLAUDE.md「ゲートの被検査範囲を数字で確かめる」)。
R3〜R5 は「作れば測れる」。**どれも先に現況を確認してから着手する** —
CLAUDE.md「docs の『未』は腐る。項目を潰す前にまず現況を確認する」。

#### 残った判断 — `.lidx` の綴りを解決すべきか【ユーザー判断が要る】

docstring が同じ依存モジュールを 3 通りに綴ったとき、**2 つは解決し 1 つはしない**:

| 綴り | 出所 | 解決 |
|---|---|---|
| `«Dep-Aux».Basic` | IR / import リスト | **する** |
| `Dep-Aux/Basic.lean` | source path | **する** (`module_for_source_path` が escape してから引く) |
| `Dep-Aux.Basic` | `.lidx` | **しない** |

**版固定できない依存では 3 つとも「リンクしない」に落ちるので、この差は出力に出なかった。**
版固定できる依存で初めて出る。

これは CLAUDE.md「**判断は 1 箇所に集める。同じ問いに答える経路が 2 本あると、片方だけ直る**」の
形をしている — 「これはどのモジュールか」に答える経路が 2 本あり、**unescape するかどうかで
答えが違う**。ただし**どちらが正しいかは測定では決まらない**:

- **解決させない (現状)** の根拠: `Dep-Aux.Basic` は Lean の識別子として不正で、
  docstring の著者が書く綴りではない。unescape は一般に曖昧 —
  `«A».«B»` を unescape した `A.B` は実在しうる別モジュールと衝突する
- **解決させる** の根拠: `.lidx` は litedoc4 自身が公開する形式で、同じ入力に
  2 つの答えが出るのは非対称。`module_for_source_path` は既に片側で unescape している

**ゲートは現状 (解決しない) を pin している** ので、変えるならゲートと判断を
同じコミットで動かすことになる。

### R4 — より大きいパッケージ / RAM の小さいランナー — **大きい方は実測。小 RAM は外挿**

- [x] 現況確認 — **より大きいパッケージはこの機材に既に建っていた** (計測対象の
      `.lake/packages/mathlib`、olean 8,229 個 / 5.7 GB)。CI も新しい対象も要らなかった
- [x] Mathlib 全体 (**8,169 モジュール / 311,415 宣言**) を抽出 2 回 + 描画 1 回
- [x] 小 RAM 側は**手元の実測から外挿**【決定 2026-08-22、ユーザー判断】

**結果**: **壊れなかった** — 抽出失敗 0 / swap 0 / 描画は全モジュール完走。
そして**倍率の形が主張を変えた**: モジュール 19.4 倍・宣言 67.9 倍でも
**peak RSS は 1.7 倍** (3.3 → 5.70 GB)。メモリは宣言数ではなく**環境の大きさ**で決まり、
それは対象を測ったときから既にほぼ Mathlib 全体だった。
→ `benchmarks/results/residual-sweep-2026-08-22.txt` §4

**【外挿】小 RAM は算術で決まる**: warm でいるには「抽出プロセス + page cache の olean」が
同時に RAM に収まる必要がある。**7 GB のランナーでは対象 422 モジュールですら収まらない**
(3.3 + 5.7 = 9.0 GB)。**大きいパッケージは余裕を削るが、境界を越えさせるのは RAM の方**。
前提 3 つ (macOS/ARM の値 / olean 全部が要るとは限らない / OS の取り分未計上) は
レポートに明記した。

**実際に小 RAM Linux で回すのはやらない**【決定 2026-08-22、ユーザー判断】。
**外挿で結論が出ていて、実走しても動かない**というのが理由で、機材の話ではない。
**動くとしたら前提が外れたとき** — 特に前提 2 (olean 5.7 GB の全部が要るとは限らない)。
`ci-olean-residency.yml` が Linux で residency 62.4% を測っている (n=1) ので、
**もし 5.7 GB のうち 62% しか要らないなら 7 GB でも収まりうる** (3.3 + 3.5 = 6.8 GB)。
**これが再検討の入口**であって、ここを測らずに「7 GB で動く」とは書けない。

### R5 — 他人のリポジトリから `uses:` される — **保留のまま**【決定 2026-08-22、ユーザー判断】

**検証用の public リポジトリは作らない。** 潰すには `uses: FujiHaruka/litedoc4@<tag>` する
別リポジトリが要り、それは外向きで不可逆な作成にあたる。

**まず現況を確認したら、覆われている範囲は思っていたより広かった**
(CLAUDE.md「項目を潰す前にまず現況を確認する」):

| | |
|---|---|
| 覆われている | `ci-action.yml` の `published` job が **`uses: FujiHaruka/litedoc4@main`** を実行している。**GitHub が `_actions/` へ checkout する実チャネルそのもの**で、`uses: ./` では通らない経路。`released` job は tag 固定で release バイナリ経路も見ている |
| 覆われていない | **`GITHUB_WORKSPACE` が litedoc4 自身の checkout であること**。`published` は litedoc4 を checkout して `root: e2e/micro` を指す。だから `action.yml` の中で **litedoc4 のファイルが workspace に在ることに暗黙に依存している箇所**があっても通ってしまう (`hashFiles()` の glob、相対パス、`--lib` の見つけ方) |

**つまり残っているのは「別リポジトリを作ること」ではなく「workspace を他人の木にすること」。**
それは **既存の public な Lean パッケージを `actions/checkout` で workspace に入れる**だけで
作れる (`repository:` を指定する) — **新しいリポジトリの作成は要らない**。
`batteries` は Mathlib 非依存で、この木では既に第 2 対象として実走した実績がある
(`benchmarks/results/batteries-2026-08-17.txt`)。

**その安い道も取らない**【決定 2026-08-22、ユーザー判断】。**保留は「高いから」ではなく
保留である** — 安い道が見つかったことは判断を変えなかった。ここに書いてあるのは
**再検討するときに現況確認をやり直さないため**で、やることリストではない。

## 4. 撤退ライン

- **R1 の 3 で「凍結テストが走らないままなら検査していないのと同じ」なら、この計画は失敗**。
  そうならない根拠は、移した先の構造テストが**機材ゼロ依存で今日から走る**こと。
  移設して `cargo test --workspace` の本数が増えなかったら、移せていない。
- **R3〜R5 で「機材が無い」に着地したら、それは 2026-08-18 の
  「機材が無いのではなく持っている機材を使っていなかった」の再演を疑う。**
