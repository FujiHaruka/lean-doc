## 1. 何を作るか

Mathlib に依存する Lean パッケージが、**自分のモジュールだけを短時間でドキュメント化できる**
ドキュメント基盤。依存ライブラリは再生成せず、公開済みドキュメントへリンクする。主眼は
HTML を出すことではなく、**Lean の意味情報を再利用可能な形で抽出し、必要な部分だけを
高速に更新できること**に置く。速度以外の副産物として、lean-doc は doc-gen4 が
**出力できていないパッケージ自身の `scoped notation`** を出す (実測 → §10) — 読者が実際に
書く記法で署名が読めることは、生成が速いことと同じくらいドキュメントの価値に効く。

## 2. 背景 — 計測が示したこと

doc-gen4 を計装して、Mathlib 依存プロジェクト (432 モジュール) のドキュメント生成を実測した
(この節はすべて実測 → [`benchmarks/doc-gen4-report.md`](../benchmarks/doc-gen4-report.md))。
コストは 3 層に分かれ、どれも「ドキュメントを作る仕事」そのものではなかった。

| 層 | 支配率 | 実際に起きていること |
|---|---:|---|
| 環境ロード | **85.0%** | モジュールごとにプロセスを起動し、import closure 全体を読み直す |
| 意味解析 | 4.6% | 本来の仕事。宣言の型を pretty print し equation を生成する |
| 走査オーバーヘッド | 8.8% | 環境の全定数を舐めて、該当しないものを捨てる |

実ビルドでは **8.9 億回の定数走査に対して該当は 0.032%** で、走査して捨てるだけのコスト
(1,195 秒) が本来の意味解析 (631 秒) の約 2 倍あった。HTML 生成フェーズも同様で、
生成 CPU の **66〜78% が DB からの読み直し**、レンダリング自体は 9.2%。さらに
**増分性が一切ない** — 無変更で 2 回続けて実行しても 46.25 秒 → 43.91 秒と変わらない。

### 決定的だった 1 つの実験

doc-gen4 に「複数モジュールを 1 プロセスで抽出する」コマンドを足して、
同一の 432 モジュールを両方式で処理した (どちらも全数の実測で外挿なし、
同じ日・同じ warm な page cache 状態)。

| | warm 実測 (壁時計) | うち `importModules` |
|---|---:|---:|
| モジュールごとに 1 プロセス (現行) | **1,076 秒** | 908.6 秒 (88.8%) |
| 1 プロセスでまとめて | **31.9 秒** | 2.6 秒 |

**34 倍。分母は「同じ 432 モジュールを抽出する仕事」。** アルゴリズムの改良ではなく、
同じ依存ライブラリを 432 回読み直すのをやめただけで生じる。差の出どころは 1 行で言える —
**432 モジュールぶんの import closure をまとめて読んでも、1 モジュールぶん
(逐次時 2.10 秒) とほとんど変わらない** (closure が Mathlib に支配されているため)。

以前 23 倍としていたのは cold なバッチ計測と warm な逐次計測を比べていた誤り
(→ [検証ログ](verification-log.md) 段階 1)。**cold と warm を混ぜないこと。**

## 3. 仮説

> Lean の意味情報をパッケージ単位でまとめて抽出し、依存ライブラリを外部参照にすれば、
> downstream ライブラリのドキュメント生成時間を**依存ライブラリの規模から大きく切り離せる**。

計測はこの仮説を支持している。ただし完全には切り離せない — 自パッケージの型を正しく
pretty print するには Mathlib の `Environment` が要り、そのロードは残る。
**これが新設計の床**であり、それをどう扱うかが設計の中心的な論点になる。

床の大きさは **page cache の状態で 5 倍動く。warm で約 2.5 秒、cold で 10〜13 秒**
(実測 → [検証ログ](verification-log.md) 段階 1。以前 12.9 秒としていたのは cold を warm と
取り違えていたため)。warm では壁時計 ≒ CPU 時間で、差はすべて olean の mmap ページイン待ち。
したがって「床をどう扱うか」は最初から 2 つの別問題である。

| | 床 | 扱い |
|---|---|---|
| **ローカル (warm)** | 2.5 秒。1 モジュールだけの再抽出ならこれより小さい (`importModules` 0.80〜2.96 秒、実測・段階 5) が `lake env` の 0.96 秒が別にかかる (→ §6.5) | 常駐で消せるが、消さなくても致命的ではない |
| **CI** | 13 秒 + 実行バイナリのページイン 3.5 秒。cold を払う場合でも先読みで 13.6 → 6.9 秒 (実測、下記) | 常駐は効かない。**「CI は毎回 cold」は仮定であって実測ではない** (下記) |

**「CI は常に cold」の現状 (2026-08-10 の計測後)。** 「`lake exe cache get` が olean を展開した
直後なら page cache に載っていて cold にならない」という反論を、ローカル (macOS / M1 /
16 GiB) で潰した:

- **この機材では偽 (実測)。** 5.167 GiB の olean を `leantar` で展開した直後の常駐は
  **4.7–20.2%** だけで、その状態から走らせた `importModules` は **14.96 / 15.66 秒** —
  warm 2.49–2.59 秒の 5.9 倍で cold と同じ桁 (むしろ cold より 1.1–1.7 秒遅い)。原因は
  容量ではない: headroom は余っており、**同じ瞬間に「読んだ」ページは 6.3 倍よく残っている**。
  → [検証ログ](verification-log.md) 「CI 軸 — cold の前提の検証」
- **しかし CI (Linux) については未検証 (仮定)。** この機材は compressor が 6.4–7.1 GiB を
  占有していて `ubuntu-latest` より不利な側であり、かつ **macOS の UBC と Linux の page cache は
  退避ポリシーが違う**。**不利な側で出た否定は移送できない。** 容量の側からは余地が残る —
  cold が実際に読むのは 2.59 GB (実測) で 16 GB の 16% にすぎない。
- → **未着手の検証項目**: `ubuntu-latest` 上で `cache get` 直後の olean 常駐率を測る。
  **ここが埋まるまで CI 軸の床は確定しない。**

**cold を縮める打ち手は見つかった — 先読み (実測、2026-08-10)。** cold の 12.7 秒は
帯域律速ではなく **132,343 回の同期 major fault の直列な待ち行列**なので、
抽出と並行して olean を並列に読めば消せる。

- **importModules 13.573 → 6.923 秒 (−49.0%。分母は先読み無しの同一構成)、
  major fault 121,386 → 26,329 (−78.3%)**、壁時計 18.03 → 10.44 秒。5 回の分布は
  重ならない (交互配置、実測)。**cold 合計は 25.76 → 19.11 秒 (外挿、§6.3)。**
  → [検証ログ](verification-log.md) 「CI 軸 — 打ち手 2『先読み』の実測」
- 読ませる集合は **`.lean` のヘッダから作った import closure** で足りる (6,021 モジュール /
  17,199 ファイル、cold が必要とするバイトの **98.80%** を覆う。観測した集合との差は
  実測で区別できない)。先読み自体は 1.75 秒 / 2,395 MB/s、closure の計算は cold 1.63 秒。
- **効果の大きさはメモリの余裕に依存する** (実測レンジ −23% 〜 −49%)。向きは変わらない。
  **Linux では未測定**で、`MADV_WILLNEED` の同期・非同期が違うので方式の選択は移送できない。

## 4. Approach

> **Lean プロセスは「意味情報を吐く抽出器」に徹し、1 つの環境を長く使い回す。**
> 抽出したものはモジュール単位の中間表現 (IR) として永続化し、
> HTML・検索索引・その他の出力はすべて Lean の外側で IR から作る。
> 依存パッケージについては IR を作らず、「宣言名 → モジュール → URL」の写像だけを持つ。

現行との対比で言えば、変えるのは次の 3 つの境界である。
**どれも独立に効き、順に適用でき、1 つ失敗しても残りは成立する** (リスクが分散している)。

1. **プロセスの境界**: モジュールごと → パッケージごと (あるいは常駐)
2. **抽出の範囲**: 環境の全定数 → 自パッケージの宣言のみ
3. **Lean と出力の境界**: Lean が HTML まで作る → Lean は IR まで、出力は外側

## 5. 設計の柱

### 5.1 1 環境・長寿命プロセス

抽出は「モジュール 1 個 = プロセス 1 個」をやめ、対象パッケージを 1 度ロードしてまとめて
処理する。これが実測 34 倍 (§2) の正体で、単独で最大の効果を持つ。
さらに一歩進めて、**環境をロードしたまま常駐させる**選択肢がある。**段階 5 の増分の実測では、
常駐が消せる分は壁時計の 81.8%** だが、**残る 18% のうち本来の仕事は 1.4% しかなく、残りは
全域索引の再構築** (内訳は §6.5)。**常駐にしてもこの 0.46 秒は別に潰さないと残る** —
§5.5 L3-3 が未実施であることの値。**旧版の「常駐なら 0.03 秒」は否定された** (→ §6.5)。
常駐が持ち込む複雑さ (→ §8) に見合うかは、この 2 つの数字
(消える 3.1 秒 / 残る 0.46 秒) を見てから決める。

副次的な効果として、**メモリ律速が消える**。現行はプロセスごとに 2〜3 GB の環境を持つため
8 並列で RSS 21.7 GB (物理 16 GB) に達しスワップし (実測)、CPU コアを増やしても頭打ちに
なる構造だった。環境が 1 つなら、この制約自体が存在しない。

### 5.2 走査ではなく索引で宣言を引く

「環境の全定数を舐めて、対象モジュールのものだけ拾う」のをやめ、モジュールから宣言を引く
方向に変える。5.1 とは独立に効く — バッチ化しても走査は 1 回分残るため。
**実装と正しさは検証済み** (→ 検証ログ 段階 1): 索引方式 (`moduleData[i].constNames`) と
走査方式は同じ 5,123 宣言を返し、時間は 0.0022 秒 対 0.62 秒 (実測)。ただし**バッチ 1 回
あたりの走査コストは当初の見積もり (4.45 秒) より 1 桁小さい** — あの 4.45 秒は cold cache の
ページインを走査コストと取り違えた値で、warm では 0.36 秒。**この柱の価値は「時間が消える」
ことではなく、モジュール数に比例する走査を構造から無くすこと**に移った。

索引方式には走査方式に無い論点がある: 複数モジュールの olean に同名で焼かれる
自動生成補題があり、**宣言の所有モジュールが一意に決まらない** (実測 25 件)。
走査方式は「最初に定義したモジュールが勝つ」を暗黙に採用していた。明示的に決める (→ §8)。

同じ性質の問題がタクティク収集にもあり、**こちらの方が桁違いに大きかった**。現行はバッチ化
すると 16.7 秒 (全体の 54%) の最大項に浮上するが、全体を 1 回列挙して振り分ける実装で
**0.011 秒**になった (実測 → 検証ログ 段階 2)。**この 16.7 秒の正体は当初の見立てと違った。**
「モジュールごとに全タクティクを列挙し直す」分は 22% でしかなく、残り 78% は
`EnvironmentHeader.moduleNames` が**フィールドではなく `def`** で、呼ぶたびに import closure
と同じ長さ (6,021 要素) の配列を作り直していたこと。実際の計算量は
**O(対象モジュール数 × タクティク数 × import closure のモジュール数)** で、
第 3 の因子は呼び出し側のコードから見えない。したがってこの柱の一般形は、当初書いていた
「1 モジュールを処理するために全体を舐めるパターンを排除する」より一段強い:

> **1 モジュールの処理で、import closure のサイズに比例するものに触らない。**
> 走査でなくても、配列 1 本の構築でも、内側のループに入れば同じことになる。

この規則は §5.3 (依存は外部参照) と同じ形をしている。1 段下のレベルで同じ罠がある。

### 5.3 依存パッケージは外部参照にする

計測で分かったのは、HTML 生成が依存パッケージについて実際に必要としているのは**「宣言名 →
モジュール名 → URL」の写像だけ**だということ (型も docstring も equation も不要)。したがって
依存については IR を作らず、この写像だけを持ち、公開ドキュメントへリンクする。
これが「ゼロからサイトを構築する」ケースで桁違いの差を生む (→ §6.4(b))。

**検証段階 3 で実測に置き換わった** (348/432 モジュールの範囲、詳細は verification-log):

- **写像だけで doc-gen4 と同じ URL 文字列が出る** — 共通 39,298 ペアの **99.992%** が
  href 完全一致 (未一致 3 はリンクしてはいけない再帰子で、**写像はそれを出さない**)。
  **doc-gen4 が張ったリンクの取りこぼしは 0**
- 写像の実サイズは**下限 53 KB / 上限 34.3 MB** (この対象では 647 倍の開き)。必要な列は
  (名前, モジュール) の 2 列で、`kind` はリンクには要らない
- **blacklist は写像から復元できる** — 「写像に載っている名前だけリンクする」方式は
  doc-gen4 の dead link (実測 3 本) を出さない

URL 規則は `("../" × (ページのモジュール成分数 - 1)) + "./" + モジュールパス + ".html#" + 名前`。
**IR には絶対的な識別子 (モジュール名 + 宣言名) を持ち、相対化は出力時に行う** (→ §5.6 の境界)。
**残る欠落**: 自パッケージの `_private.` 名は素朴に URL を出すと dead になる (実測 8 名)。
除外するか親に落とす処理が要る — 依存側ではなく自分の IR 側の問題 (→ §8)。
なお、**リンク解決に必要なデータと、型を pretty print するために環境が必要なことは別問題**。
前者は外部参照で解決するが、後者 (§3 の床) は解決しない。混同しないこと。

### 5.4 中間表現の粒度はモジュール単位

現行 doc-gen4 は宣言ごとに DB の行を分割したため、レンダリング時に N+1 クエリで再構築する
羽目になり、生成 CPU の 66〜78% がそこに消えている。**読みも書きもモジュール単位なら、
モジュール 1 個 = 1 まとまり + 索引が正しい粒度。** 教訓は「規模が来たら SQLite」ではなく
**アクセスパターンに合わない粒度で分割すると逆効果**、ということ。格納形式
(JSON / SQLite / バイナリ) の選択より粒度の選択が先に来る。

IR にはスキーマバージョンを持たせ、キャッシュキーには少なくとも Lean バージョン・
抽出器バージョン・IR スキーマバージョン・olean ハッシュを含める (olean ハッシュだけでは
不足 — pretty printer の出力が Lean バージョンに依存するため)。**段階 5 で実装した形は
「モジュールごとの olean ハッシュ + パッケージ 1 つぶんの環境キー」** (前者以外は全モジュールを
同時に無効化するので 432 個複製せず 1 レコードにまとめた)。**この環境キーは判断点 3 で
不完全と分かった** (生成器の構成が入っておらず、そもそも変更集合に効いていない) → §5.5 の L1。

**この粒度は実測で成立した** (検証ログ)。**タグ無しの schema 1** (段階 4 準備) では
432 モジュール = 436 ファイル / 8.74 MB を書くのに **0.198 秒**、Lean を起動せずに全部
読み直すのに **0.056 秒** (床の 2.3%)。**現行の schema 2 (位置つきタグ) では 15.13 MiB /
書き込み 0.549 秒 / 読み出し 0.100 秒 (床の 4.0%)** — 結論は変わらないが、引用するときは
構成を揃えること (→ §6.1)。書き込みの 4 分の 3 は JSON の直列化で `write(2)` は 4 分の 1
(schema 1)。**モジュールごとの内容ハッシュは書き込みの 1.2%・実行全体の 0.02%** なので、
モジュール単位ハッシュを持つことに性能上の代償はない。

### 5.5 増分性を「入力側」と「出力側」で別々に設計する

現行はここが両方向に壊れていた。**取りこぼし**: モジュールを変更しても HTML が再生成されない
(マーカーファイルが空なので内容が変わってもハッシュが変わらない)。**無駄**: 再生成が走った
場合は変更の有無に関わらず全モジュールを作り直す。原因は、キャッシュ無効化とページ再生成
という別々の関心を 1 つの仕組みに載せたこと。当初の新設計は **IR のモジュール単位ハッシュ**を
単一の真実とし、再抽出集合と再生成集合を両方そこから導くものだった。

> **この「単一の真実」は否定された (判断点 3、2026-08-10)。** 5 つに分解した命題が
> **すべて実測で否定**され、`--source-url` を変えるだけで台帳が 0 changed のまま 432/432 ページが
> stale になる、宣言を 1 個足すと最も広い影響集合でも 3〜141 ページを取りこぼす、
> 削除でパイプラインが例外で止まる、といった穴が出た。
> → [検証ログ](verification-log.md) 段階 5 増分 2。**否定されたのは「モジュール単位ハッシュ
> だけで閉じる」という構造であって、増分生成そのものではない** (速度 3.30〜4.39s 対 17.07s は
> 生きている → §6.5)。以下は判断点 3 を受けた**見直し案**で、まだ実測で裏付けられていない。

**単一の真実は「役割が 1 つ」ではなく「役割ごとに 1 つ」だった** (段階 5 増分 1 の実測) —
問う時点が違うので、1 つの数字では両方を埋められない。

| | 入力側 = どのモジュールを**再抽出**するか | 出力側 = どのページを**再生成**するか |
|---|---|---|
| ハッシュ対象 | モジュールの `.olean` (3 分割なら 3 つとも) | モジュールの IR |
| 計算する時点 | 抽出の**前** (Lean 不要) | 抽出の**後** |

`.lean` ソースは早すぎ (証明中の空白のように olean に届かない変更を拾い、依存の再ビルドで
olean に入った変更を落とす)、IR は遅すぎる (計算するには省きたい抽出そのものが要る)。
**抽出器が見られるのは olean だけ**なので入力側は olean が正しい。**Lake が既に olean の
内容ハッシュを `<file>.olean.hash` に書いている**ので、入力側の台帳は 227 MB ではなく
6.9 KB を読めば済む (実測 0.080 秒)。

#### 見直し案 — 2 層ではなく 3 層 (判断点 3 を受けた設計、未検証)

判断点 3 が見つけた穴は**上の 2 層のどちらにも属さない依存**だった。層は 3 つ要る。

| 層 | 何を見るか | 何を決めるか | 変わったときの影響範囲 |
|---|---|---|---|
| **L1 グローバル鍵** | モジュールに属さない入力 | 全無効化するか | **全部** |
| **L2 モジュール単位ハッシュ** | 各モジュールの `.olean` | 再抽出集合の**核** | そのモジュール |
| **L3 導出の依存** | 名前の所有権 / 全域写像 / 全域索引 | L2 の核を**広げる** | import では閉じない |

**L1 に何を入れるか** (今の `envKey` は 5 項目しかなく、判断点 3 の S1 はここで否定された):
Lean toolchain / manifest / 抽出器 id と**その構成** (`--open` の名前空間) / IR schema /
**生成器 id とその構成** (`--source-url` の revision、`--ws-heuristic`)。判定は「入っているか」
ではなく「**出力のバイトに現れうるか**」で決める — `--source-url` は 1 ページあたり中央値
9 か所に現れる (実測)。**`envChanged` を計算して捨てていた穴は塞いだ** (実測でコストは +1〜2 ms = ドリフト以下)。
ただし今の実装は**鍵が変われば 432 モジュール全部を再抽出する**ので粗い。
`--source-url` の変更は再抽出ではなく**再レンダリングだけで足りる**はずで、
**L1 の鍵は「再抽出を要求するもの」と「再レンダリングだけを要求するもの」に分ける**。

**L2 の鍵は olean の内容ハッシュのままでよいが、そのままでは移送できない** — olean には
**ソースの絶対パスが 429/432 モジュールで埋まっている** (実測。Mathlib の style linter の
ログを持つ環境拡張 `lintLogExt` が、警告文にパスを入れたまま保存している)。
**チェックアウト先が違うだけでハッシュが全滅する**ので、CI と開発機で IR キャッシュを
共有するには鍵をパス非依存にする (または警告を消す) 必要がある。

**L2 に足りないもの**: モジュール一覧を台帳の構築時に凍結せず**ソースの glob で作る**
(今は消えると例外で止まり、増えても見えない)。**走査先を `.lake/build` にしてはいけない** —
Lake は孤児 olean を消さないので、現行 432 モジュールに対し olean は 1,090 個あり
**659 個が幽霊** (実測)。削除は台帳・IR・ページの **3 箇所**から消す経路が要る
(今は `deps/*.json` の掃除しか無い)。

**L3 が §5.5 に無かった穴で、3 つある**:

1. **名前の所有権** — 参照は `(定義モジュール, 名前)` で持つので、宣言が移動すると参照側の
   IR が腐る。**これは再生成ではなく再抽出の問題** — 影響集合をどれだけ広げても直らない
   (実測: `--mode referrers` は stale 0 でも 1 ページも直さない)。L2 の核から
   「**そのモジュールが定義していた名前の集合の差分**」を取り、その名前を `refs` に持つ
   モジュールを**再抽出集合に足す**。
   **この層が要ることは増分 3 で実測により確定した** — 宣言を別モジュールへ移しても
   (完全名は不変)、それを参照するモジュールの `.olean` は **1 byte も変わらない**。
   Lake の内容ハッシュも変わらないので、**L2 は移動を原理的に検出できない**。
   逆に**改名は検出できる** (名前が式に埋まっているため)。
   同じ実験で「**A を変えても importer の olean は変わらない**」も実測されたので、
   **再抽出集合を import 閉包へ広げる必要は無い** — 広げるべきは出力側だけ。
   → [検証ログ](verification-log.md) 段階 5 増分 3。
2. **全域写像** — docstring の autolink は名前 → 定義モジュールの全域写像を引くので
   **import で閉じない** (実測: 逆向きの推移的 import 閉包でも 3〜141 ページ取りこぼす)。
   閉じるには「**まだ解決していないトークン → それを含むページ**」の逆索引が要る
   (未解決トークンは 8,965 distinct / 117,323 出現、実測)。持たないなら
   **「autolink は増分では閉じない」を仕様として明示する**ほうが誠実。
3. **全モジュール横断の後処理** (検索索引・ナビゲーション・相互参照) — 毎回全モジュールを
   読み直すのではなく差分から更新できる形にする。**未実施の代価は実測された** — 1 ページ
   だけの再生成でも IR 全読み + 名前写像で 0.145 秒、増分の壁時計の 12.1% が全域索引の
   再構築に消える (→ §6.5)。**常駐化しても残る項はここだけ。** 判断点 3 でさらに、この
   後処理が**未実施どころか未実装**と確定した — doc-gen4 の非モジュール成果物 23 個のうち
   5 個 (38.6 MB) が全モジュールの関数で、こちらは 1 つも作っていない。
   **未検証項目ではなく必須項目に格上げする** (実装の形は doc-gen4 に前例がある)。

**「影響集合の mode」という枠組み自体が的を外していた**のが、判断点 3 のいちばん構造的な発見。
`self` / `referrers` / `importers` は**描画対象しか決めない**ので、再抽出が要る種類の
stale (L3-1) には原理的に効かない。**再抽出集合と再生成集合は別々に導く。**

### 5.6 出力は IR から作る (Lean の外側)

HTML・検索索引・JSON API・宣言グラフ・リンク切れ検査は、すべて IR を入力とする独立した消費者にする。
**HTML の再生成に Lean の起動が要らない**ことが、この分離が成立している証拠になる。
境界の入口までは実測で通った: Lean を起動しない別プロセスが 432 モジュール分の IR を
**0.100 秒**で読み切れる (15.13 MiB、環境ロードの床の 4.0% → 構成の違いは §5.4)。

**IR は参照定数を集合でなく位置つきで持つ必要がある** — 段階 4 増分 1 で判定済み。doc-gen4 の
署名内アンカー 72,421 件のうち **44.0% は印字トークンと定数名に字面の関係が無く**
(`ℕ`→`Nat`、`≤`→`LE.le`)、平文 + 集合からの再構成は上限でも recall 56%、実測 51.7% /
宣言単位の完全一致 4.0% にとどまる。ページのバイトの **71.1% が署名の描画**なので、ここを
落とすと「同じ仕事」ではなくなる。逆に**あて先の解決 (名前 → モジュール) は集合で足りている**
(取りこぼし 0.36%、全部 docstring 側 → [検証ログ](verification-log.md) 段階 4 増分 1)。
**ただしこの「集合」は全域写像で、増分では閉じない** — 初回生成の正しさに足りることと
差分から導けることは別で、判断点 3 が破れたのはまさにこの docstring 側 (§5.5 の L3-2)。

なお計測は、**レンダリング自体の最適化に価値が薄い**ことも示した (生成 CPU の 9.2%)。高速化や
Rust での書き直しをここに投資しても効果は限定的で、言語選択より責務分離が先。Rust を使うなら
理由は速度ではなく配布・常駐サーバ・並行性の扱いやすさであるべき。

## 6. 性能

**抽出・IR 永続化・HTML 生成・増分はすべて実測に置き換わった** (検証段階 1〜5)。
**残る非実測は 3 つだけ** — (1) cold 合計 25.76s / 19.11s は stage1 抽出器からの**外挿** (§6.3)、
(2)「CI が cold 側かどうか」は**仮定** (§3、Linux 未測定)、(3) 未実装分を足したときの
HTML 生成 1.2 秒前後は**外挿** (§6.6)。どの数字が実測 / 外挿 / 仮定かは行ごとに明示する。
**そしてこの節は速度の節である。** 増分の**正しさ**は判断点 3 で否定されており (→ §5.5)、
§6.5 の秒数は「正しい影響集合が導けている」という主張を含まない。

### 6.1 抽出フェーズ + IR 永続化 (自パッケージ 432 モジュール) — 実測済み

**基準は warm な page cache での実測** (旧版は cold を warm と取り違えていた → 検証ログ 段階 1)。

| 項目 | 現行 doc-gen4 (warm) | lean-doc | 根拠 |
|---|---:|---:|---|
| 環境ロード | 2.60s | **2.52s** | 実測。削減対象外 (§3 の床) |
| タクティク収集 + モジュール docs | 16.64s | **0.011s** | 実測。全体 1 回列挙 + closure 依存の排除 (§5.2) |
| 走査 (該当外) | 0.36s | **0.002s** | 実測。索引方式 |
| 意味解析 (equations + 参照定数 + 位置つきタグ) | 10.51s | **10.58s** | 実測。本来の仕事。差は未実装分 (下記) |
| 書き込み | 0.68s (SQLite) | **0.549s** (IR 15.13 MiB) | 実測。**仕事の範囲が違う** (下記) |
| **合計** | **31.50s** | **13.71s** | 実測。**両列ともプロセス内の計時合計** (`batch.total` / `total`) であって行の単純和ではない |

出所は doc-gen4 側が warm 再計測 `batch-rerun.jsonl` (壁時計 31.9s)、lean-doc 側が
2026-08-10 の同一セッション (段階 4 増分 2、交互配置 2 系列 × 6 run、runs 2–6 の中央値
→ [検証ログ](verification-log.md))。**意味解析の行だけは doc-gen4 3 run の中央値 10.51s**
なので列を足すと 30.79s になり合計と 0.7s ずれる。**行の和ではなく計時合計を合計とする。**
**この表は位置つきタグを入れた構成** (段階 4 増分 1 でタグは必須になった → §5.6)。

引用するときの注意が 5 つある。

- **同一セッションのタグ無し対照は合計 12.53s** (意味解析 9.70s / 書き込み 0.198s) で、
  **タグ付けの正味は +1.175s (+9.4%)** — 生成 +0.883s / 永続化 +0.351s と
  **生成が永続化の 2.5 倍**で、注目されていた書き込みの方が小さい半分。
- **セッションをまたいだ数字を並べないこと。** 同じタグ無し構成が別セッション
  (段階 4 準備) では 12.73s。0.2 秒はセッション間の差であって効果ではない。
- **書き込みの 0.549s と 0.68s を割り算しないこと。** doc-gen4 の 0.68 秒は
  `updateModuleDb` (SQLite への宣言の書き込み) で、lean-doc が書かない属性・instance 索引を
  書き、lean-doc が書くモジュールハッシュと依存写像は書かない。**同じ仕事ではない。**
  言えるのは「どちらも 1 秒未満で支配項ではない」まで (検証ログ 段階 4 準備 / 増分 2)。
- **13.71 秒を「完成品の値」として引用しないこと。** 属性収集・instance 索引・構造体メンバの
  binder が未実装。**抽出フェーズ単体の**目標 14.5 秒には収まっているが余裕は小さい
  (§6.3 の合計 14.53 秒とは別の数字。偶然近い)。
- **書き込みコストはフェーズタイマーで読む。** プロセス全体の壁時計はこの合計より広く振れ
  (段階 4 準備では系列中央値 12.47–12.89 秒、最大 15.96 秒)、振れは全部 `importModules`
  に出る — IR の書き込み・削除が olean の mmap ページインに干渉するため。

cold cache では環境ロードが 13.6 秒前後になり、合計はこれに 11.1 秒ほど上乗せされる
(実測: cold 13.573s / warm 2.458s、同一セッション)。**先読みを入れると上乗せは
4.5 秒に下がる** (実測 → §3)。**CI が cold 側かどうかは未検証 (仮定)** — §3 参照。

**内訳は当初の前提から反転した。** 旧見積もり (cold 基準) は環境ロード 51% / 意味解析 46%
だったが、実測 (warm、上表の 13.71s を分母に) では **18% / 77%**。残るコストの大半は
**本来の仕事**であり、環境ロードを避ける工夫 (常駐・遅延ロード) の取り分は小さい。
ここから先を縮めるなら狙うのは意味解析 — equation 生成を切る (寄与は 10% =
0.97 秒 / 863 本、実測)、変更のない宣言を再解析しない、といった方向。**自前実装でも
減らなかった** (同じ 4,750 宣言・同じ出力で lean-doc 9.26 秒 対 doc-gen4 10.51 秒。この
9.26 秒は段階 2 の構成で、段階 4 構成では上表の 10.58 秒。いずれも実測)。
**この行は「削減対象外」として正しい。** 一方、当初の最大の未検証項目だった
**タクティク収集は決着した** — 「0.04 秒に畳める」という**仮定**に対し実測 **0.011 秒**
(doc-gen4 の 1,500 分の 1)。ただし 16.7 秒の正体は当初の見立て (モジュールごとの再列挙)
ではなかった (→ §5.2)。**仮定は当たったが理由は外れていた。**

### 6.4 現行 doc-gen4 との比較

比較は 2 つの意味で成立し、桁が違うので分けて示す。

**(a) 同じ仕事量 — 自パッケージ 432 モジュールを抽出する**

| | 時間 | 倍率 |
|---|---:|---:|
| 現行 (モジュールごとに 1 プロセス) | 1,076s | — |
| lean-doc (warm、位置つきタグ込み) | 13.71s | **78×** |

どちらも 432 モジュール全数の warm 実測で、**外挿も仮定も含まない**。これが
「バッチ化 + 走査の排除」だけで得られる分で、**依存を外部参照にする効果はまだ入っていない**
(未実装の出力を足すとさらに下がる)。**倍率は出力の範囲と一緒に動く** — 段階 4 で
位置つきタグを足した時点で 85× から 78× に下がった。倍率だけを引用せず、
そのとき何を出していたかを併記すること。

**(b) ゼロからドキュメントサイトを構築する** — 現行 doc-gen4 は依存を外部参照にできないため、
Mathlib 8,169 モジュール分の抽出がすべて必要になる。

| | CPU 時間 | 倍率 |
|---|---:|---:|
| 現行 (Mathlib 全体の抽出を含む) | 約 32,600s = **9.1 時間** | — |
| lean-doc (依存は外部参照、warm) | 14.53s | **約 2,240×** |

現行の約 32,600 秒は**外挿**。**フルビルドは完走していない** — 8,600 モジュールのうち
3,590 (42%) を抽出した時点で打ち切っており、その 3,590 モジュールの実測 13,611 秒
(= 3.79 秒/モジュール) を 8,600 モジュールに伸ばした値である
(→ [`benchmarks/doc-gen4-report.md`](../benchmarks/doc-gen4-report.md) §4.6.1)。
8 並列が理想的に効けば壁時計で約 68 分だが、実測ではメモリ律速でこれを大きく超えた。
この方式の数字は **page cache 状態にほとんど左右されない** (§2 の逐次計測は別セッションの
1,084 秒に対し今回 1,076 秒) ので外挿値はそのまま使える。**前提「依存を外部参照にしても
同じリンクが張れる」は検証段階 3 で実測に置き換わった** (→ §5.3)。

**この 2,240 倍のほとんどは「やらなくてよい仕事をやめた」ことによる**もので、実装の巧拙では
ない。ここが本プロジェクトの存在理由である。**倍率だけを取り出して引用しないこと** —
(a) の 78 倍と (b) の 2,240 倍は別の主張で、後者の大半は作業範囲の差である。
**分母の 14.53s に仮定は残っていない** (13.71s + 0.82s、両方 warm 実測 → §6.1 / §6.2) が、
代わりに**出力範囲の差**が残る: この 14.53 秒が作るのは 432 モジュールのページだけで、
`declaration-data-*.bmp` / `backrefs-*.json` / `search.html` / 静的資産は入っておらず、
ページ自体も doc-gen4 の 63.6% のバイトしか byte 再現していない。**分子の約 32,600 秒は
打ち切りビルドからの外挿で、しかも抽出フェーズだけの値**である。ただし doc-gen4 の HTML
生成フェーズは 6,072 モジュールで 44.52 秒 (実測、§6.2) なので、検索索引・静的資産まで
全部作らせても分子はほとんど動かない — **差は分子ではなく分母 (lean-doc 側の出力範囲) に
ある。** 倍率には必ず併記する。なお同じ 432 モジュールのページ生成だけで比べた場合の倍率は
**3.8 倍** (doc-gen4 を 432 に比例縮小した 3.17s 対 実測 0.82s、→ §6.2) で、
これは (b) の 2,240 倍とは 3 桁違う別の主張である。

### 6.5 増分ビルド (1 モジュール変更) — 実測に置き換わった

**旧版の「使い捨て 2.5s / 常駐 0.03s」はどちらも理論値だった。段階 5 増分 1 で端から端まで
実測し、両方とも外れていた** (→ [検証ログ](verification-log.md) 段階 5、
`benchmarks/results/stage5-incremental-summary.txt`)。

| 変更するモジュール | 再生成ページ | 壁時計 | 根拠 |
|---|---:|---:|---|
| `…Meta.EntryPoint` (import 元 414、closure 2,259) | 415 | **3.30s** | **実測** |
| `…Kolmogorov.OmegaNoncomputable` (葉、closure 4,258) | 1 | **3.83s** | **実測** |
| `…ChannelCoding.Basic` (参照元 80、closure 5,267) | 81 | **4.39s** | **実測** |
| 同一セッションのフル生成 (抽出 16.19 + 生成 0.88) | 432 | 17.07s | **実測** |

**フル生成の 3.9〜5.2 分の 1 (分母は上表の同一セッションのフル生成 17.07s)。** 仕事量は
同じではない — フルは 432 ページ全部を作り、増分は 1〜415 ページを書き直して代わりに
差分検出と IR マージを払う。

> **この節は速度だけの節である。正しさは別で、判断点 3 で否定された** (→ §5.5)。
> ここの 3.30〜4.39 秒は「与えられたページ集合を作り直す時間」であって、
> 「作り直すべきページ集合を正しく導けている」という主張ではない。
> **実際の変更では stale が残る** (`--source-url` を変えると台帳 0 changed のまま
> 432/432 ページが stale、宣言 1 個の追加で 3〜141 ページ取りこぼし — いずれも実測)。
> **速度の数字だけを引用しないこと。**

**再生成ページ数は導出ではなく選択である。** 実際には何も変えていないので再抽出した IR は
バイト一致し、ハッシュ連鎖は「再生成すべきページは 0」と正しく答える。時間を測るために
ページ集合を強制した (1 = M のページだけ、81 = M を名前で参照するモジュールも、
415 = M を推移的に import するモジュール全部)。415 は増分 1 時点では**健全な上界**と
していたが、**判断点 3 で誤りと判明** — 印字と autolink の経路がこの上界の外に出る
(→ §5.5 / §8)。**秒数は実在のページ集合に対する実測。** 内訳 (葉、3.83s):

| | 秒 | 比 |
|---|---:|---:|
| `importModules` (環境ロード) | 1.94 | 50.7% |
| `lake env` (**実測 0.96s**。従来この表にも 13.71s にも入っていなかった) | 0.96 | 25.1% |
| exec + 171 MB のバイナリのページイン + 後始末 | 0.23 | 6.0% |
| HTML 再生成 / IR マージ / 影響集合 / 差分検出 (**全域索引の再構築が主**) | 0.64 | 16.8% |
| **本来の仕事 (解析 + IR 書き込み)** | **0.05** | **1.4%** |

**律速は環境の取得で 81.8%。** 向きは旧版の「ほぼ全部が環境ロード」と同じだが、数字は 2 つ
外れていた: 床は 2.5 秒固定ではなく **0.80〜2.96 秒** (1 モジュールの import closure は
パッケージ全体の 6,021 より小さく、モジュールで 3.7 倍違う)、そして `lake env` の 0.96 秒が
数えられていなかった。**理論値 0.03 秒は否定された** — 実測の最小は 3.30 秒 =
**110 倍 (分母は理論値 0.03 秒)**。常駐前提の数字なので直接は比べられないが、
**環境ロードを除いた分だけを取り出しても 0.266 秒 = 理論値の 8.9 倍**で、差の大半は生成側が
毎回 IR を全部読み直す 0.135 秒 (→ §5.5 L3-3)。**常駐にしても 0.03 秒には届かない。**

**差分検出 (無変更のときの時間) は 0.080 秒** (実測、432 モジュールの olean ハッシュ照合、
Lean 不使用)。**Lake が既に olean の内容ハッシュを `<file>.olean.hash` に書いている**ので、
227 MB を読み直さずに 6.9 KB で済む (自前 SHA-256 なら warm 0.117s / cold 0.382s)。

**現行との比較は倍率を書けない。** doc-gen4 の増分は 5.21 秒 (実測) だが**HTML を再生成して
いない** (stale) 上に `lake build` を含み、こちらは HTML を更新して `lake build` を含まない。
**同じ仕事ではない。** 無変更側 (doc-gen4 2.33 秒 対 lean-doc 0.080 秒) も、Lake の replay は
ビルドグラフ全体を検証しているので同様。**`lake build` は上表の数字に入っていない** —
増分 1 では「M が変更された」という事実だけを台帳に注入して測ったため。

#### `lake build` を足した端から端まで (増分 3 で実測)

`lake build` は lean-doc の外だが**編集 → プレビューの臨界パス上にある**。
対象リポジトリの複製 (APFS clonefile) を作って実測した
(→ [検証ログ](verification-log.md) 段階 5 増分 3、
`benchmarks/results/stage5c-olean-propagation-summary.txt`)。

| 変更 | 再ビルドされたモジュール | `lake build` | doc 側の増分 | `lake build` の割合 |
|---|---:|---:|---:|---:|
| 無変更 | 0 | **2.40s** | 0.080s | 96.8% |
| 直接 importer 2 (best case に近い) | 3 | **12.40〜12.73s** | 3.30〜4.39s | **74〜79%** |
| 直接 importer 54 / 推移 126 | 127 | **237〜243s** | 3.30〜4.39s | **98.2%** |

すべて**実測** (warm、n=5 / n=8 / n=1)。壁時計は page cache で 2.2 倍動くが CPU 時間は
安定していて、上の値は収束後の warm。再ビルド数は Lake の `Built` 行を数えたもので、
127 は import グラフの予測 (126 + 自分) と完全に一致する。
**doc 側をゼロにしても端から端は 12.4 秒より速くならず、fan-in が大きければ 4 分待つ** (n=2、237.24 / 242.72s)。

**この表は §6.5 の主張の分母を変える。** 3.30〜4.39 秒は「doc 生成だけを見たときの時間」で、
利用者が体感する時間ではない。**倍率を書くときはどちらの分母かを必ず明示する。**
また fan-in が大きいモジュールでは `lake build` が 98% を占めるので、
**そこでの高速化余地は doc 側にほとんど無い** — 効くのは常駐化ではなく、
Lean 側のビルドを待たずに古い IR でプレビューを出すような別の設計。

### 6.6 この見積もりが外れるとしたら

| 外れる筋 | 外れる向きと幅 |
|---|---|
| **page cache が warm でない** | 仮定ではなく**実測済みの変動要因**で、環境ロードが 2.5 秒から 13.6 秒に伸びる。先読みで 6.9 秒までは戻せる (実測) が **warm の 2.5 秒には戻らない**。**CI がどちら側かは未検証** (§3) だが、**warm の数字だけを出すのは誇大**なので両方を併記する |
| **意味解析 10.58 秒が減らせない** | 本来の仕事なので減らす前提を置いていない。逆に言えば**実測 13.71 秒の 77% は本質的なコスト**であり、ここが最終的な壁になる。当初の見積もりでは 46% だったので、**この壁は当初考えていたより手前にある** |
| **常駐プロセスが成立しない** | 環境の再利用が Lean の初期化まわりで安全にできない可能性がある (→ §8)。成立しなくても失うのは §6.5 の 3.1 秒 (環境の取得) で、**下限は 2.5 秒ではなく実測 3.30〜4.39 秒**。成立しても 0.46 秒 (全域索引) は残る |
| **HTML 生成の未実装分** | §6.2 の 0.82 秒は仮定ではなくなったが**下限**である。未実装のうち重いのは CommonMark と docstring の autolink 索引で、いま docstring 描画は 0.178 秒 = 壁時計の 21.6% (実測)。本物の CommonMark がこの項を 3 倍にしても +0.36 秒、合計 1.2 秒前後で**この範囲なら §6.3 の結論は動かない** (**外挿** — 根拠は現行の docstring 項の実測値のみで、md4c の実速度は測っていない)。逆に検索索引 (`declaration-data-*.bmp` 相当) は**このフェーズに足す新しい仕事**であって未実装分の埋め合わせではない |

## 7. 検証の順序

各段階は「次に進んでよいか」を判断する実験であり、機能の積み上げではない。
**仮説が否定されたらそこで設計を見直す** (逆をやらない)。

| # | 検証すること | 判断基準 |
|---|---|---|
| 1 ✅ | 1 プロセスで対象パッケージをまとめて抽出できる | 環境ロードが doc-gen4 と同等で再現し、カスタム構文を含むプロジェクトでも動く |
| 2 ✅ | 走査をやめ、モジュールから宣言を引ける | §6.1 の 14.5 秒 (warm) に到達する |
| 3 ✅ | 依存パッケージの IR なしで、リンクが解決できる | Mathlib へのリンクが正しく張れる。必要な写像の実サイズが分かる |
| 4 ✅ | IR から HTML を生成でき、再生成に Lean が要らない | Lean を起動せず HTML を作り直せる |
| CI ◐ | **CI の cold をどう扱うか** | (1) `cache get` の展開直後に載っているか → **macOS では否定 (実測)、Linux 未測定**。(2) 先読みで cold を縮められるか → **成立 (実測)**。importModules −49.0% / major fault −78.3%、cold 合計 25.76s → 19.11s (外挿) |
| 5 ✅◐ | 変更したモジュールだけ再処理できる | (1) 無変更で再実行してもほぼ即時 → **0.080 秒 (実測)**。(2) 1 モジュール変更 → **3.30〜4.39 秒 (実測)**、フルの 3.9〜5.2 分の 1、再抽出した IR はフル抽出と byte 一致 (**既定構成では**)。(3) stale ページが残らない → **否定 (実測)**。5 命題すべてが破れた (判断点 3) ので §5.5 を 3 層構造に見直した。**速度は残り、正しさが残らなかった** |
| 6 | 環境を常駐させて再抽出できる | **0.03 秒は否定された (§6.5)。** 常駐で消せるのは環境ロードの 81.8% までで、全域索引の再構築 0.46 秒が残る |

価値の核。5 は速度だけでなく**正しさ**の検証で、現行が失敗している箇所。**段階 6 (常駐) は
スコープ外として保留中** — 判断基準は上表、撤退ラインは「消える 3.1 秒に対し §8 の

## 8. 未解決の問い

| 問い | 分かっていること / 残っていること |
|---|---|
| **cold な環境ロード (13 秒) をどう扱うか** | warm の 2.5 秒は受け入れられるが、CI は毎回 cold を払う**らしい (仮定・未検証)**。**Lean の速度ではなく I/O の問題**なので打ち手も I/O 側 — 「展開直後だから warm」は macOS で否定 (実測)・Linux 未測定、「先読み」は成立 (実測) → §3。**残るのは「Linux で同じか」と「完全版の抽出器でも同じ差が出るか」の 2 つ** (後者は作業集合が 16 GiB に収まらず測れなかった)。**残る打ち手**: IR をキャッシュする (= 段階 5 と同じ機構)、実行バイナリのページイン 3.5 秒。**IR キャッシュには前提が 1 つ増えた** — olean の内容ハッシュは**チェックアウト先の絶対パスに依存する** (429/432 モジュール、実測 → §5.5)。CI と開発機でパスが違えば全滅するので、鍵をパス非依存にしない限り CI 側でのキャッシュヒットは 0 |
| **意味解析 (実測 10.58 秒) を減らせるか** | 最適化後の 77% がここになる以上、次に効くのはここしかない。equation 生成の切り替え、宣言単位のキャッシュ、出力に使わない情報の生成をやめる、あたりが候補 |
| **宣言の所有モジュールをどう決めるか** | 同名で複数の olean に焼かれる自動生成補題があり (実測 25 件)、索引方式では所有が一意に決まらない。「最初に定義したモジュールが勝つ」(現行 doc-gen4 の暗黙の規則) を踏襲するか否か。ページ配置とリンク先が変わる |
| **常駐プロセスの寿命と安全性** | 環境を使い回したとき、マクロ・属性・環境拡張の初期化が汚染されないか。**効き幅は実測で確定** (§6.5): 消えるのは 3.1 秒、残るのは 0.46 秒 |
| ~~**増分の影響集合をどう閉じるか**~~ | **段階 5 増分 2 (判断点 3) で決着 — 否定。** olean の内容ハッシュだけでは閉じない。抜けているのは当初挙げた 2 経路ではなく**5 つ**で、うち 3 つは import 閉包を上界としても塞がらない (実測) → §5.5 の見直し案。**「逆向きの推移的 import 閉包が健全な上界」という増分 1 の記述は誤りだった** — 印字の経路で 95 モジュール、docstring の autolink で 3〜141 ページが上界の外に出る。残った問いは 3 つのうち **(1) は増分 3 で決着**: **参照側の olean は変わらない (実測)** — 宣言を別モジュールへ移しても参照側は 1 byte も変わらず、Lake のハッシュも動かない。**L3-1 は必須で確定**。同時に「A を変えても importer の olean は変わらない」も実測され、**再抽出集合を import 閉包へ広げる必要は無い**ことも確定した。残るのは (2) **autolink の逆索引を持つか、増分では閉じないと明示するか** (未解決トークン 8,965 distinct / 117,323 出現 = 実測で、逆索引の規模はこちらで決まる)。(3) **全域索引 (38.6 MB / 5 ファイル) を差分更新できるか** (規模は実測、時間は未測定) |
| **依存パッケージの写像をどう配布するか** | 各パッケージが自分の「宣言名 → URL」写像を公開する形が理想。**doc-gen4 の出力からは導ける** — `declarations/declaration-data.bmp` がまさにその写像で、依存側需要 533 件のうち 530 件を満たし、組んだ URL は doc-gen4 の href と 99.992% 一致 (段階 3 増分 2・3、実測)。**未決なのは「上流の公開サイトに同じファイルがあるか / バージョン対応が取れるか」**。取れないなら生成側で作る |
| **`_private.` 名のリンクをどうするか** | 除外 / 親に落とす / モジュールページのどれを取るかは未決 (実測 8 名 → §5.3) |
| **docstring 内のリンクをどう解決するか** | doc-gen4 は別経路 (`Output/DocString.lean`) で処理していて署名のタグ付けを通らないので、別の仕組みになる可能性が高い。**規模は実測できた** (段階 4 増分 1): 348 ページの内部アンカー 80,743 件のうち IR の名前集合 (5,300 エントリ) で解決できないのは **293 件 / 188 種 = 0.36%** で、**その全部が docstring 内** (署名と equations の取りこぼしは 0)。要るのは「署名に出てこない名前も引ける索引」であって、写像の作り方の問題ではない |
| **Lean のバージョン差をどこで吸収するか** | IR スキーマとの対応付けの方針。未着手 |
| **プレビューモードを持つか** | 構文ベースの近似で即時表示する案は魅力的だが「不正確な情報を出す」代償がある。**「常駐なら 0.03 秒だから不要」という逃げ道は消えた** (§6.5)。常駐でも 0.46 秒 + 解析は残るので、この問いは生きている |

## 10. 補足 — 上流への還元

本プロジェクトを進めることと、知見を上流に投げることは排他ではない。3 つある。

| | 内容 |
|---|---|
| **バッチ化** | 計測で使った「複数モジュールを 1 プロセスで抽出する」コマンドは、doc-gen4 の内部 API が**既に複数モジュールを受け取れる**ため CLI の定義を変えるだけで実現できた。つまり §6.4(a) の 78 倍のうちバッチ化による分は、doc-gen4 本体への小さな変更としても成立しうる |
| **`scoped notation`** | doc-gen4 は**パッケージ自身の `scoped notation` を出力できていない** (段階 2 で実測)。delaborator が `ScopedEnvExtension` にあり import だけでは未活性なのに `Lean.activateScoped` を呼んでいないため、`H(μ; X)` や `≐` と書けるはずの署名が `entropy μ X` / `DotEq a a` と出る。**呼ぶだけで直り、コストは意味解析 +6% (実測)** |
| **`collectTactics` の 16.7 秒** | **1 行の直し方で消える** (→ §5.2) — `env.header.moduleNames` をループの外に括り出し、`allTacticDocs` を 1 回だけ呼ぶ。`moduleNames` が `def` であることは Lean core 側の API の形の問題なので、**同じ罠を踏んでいるコードは doc-gen4 以外にもありうる** |
