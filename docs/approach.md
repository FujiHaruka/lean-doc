## 1. 何を作るか

Mathlib に依存する Lean パッケージが、**自分のモジュールだけを短時間でドキュメント化できる**
ドキュメント基盤。依存ライブラリは再生成せず公開済みドキュメントへリンクする。主眼は HTML を
出すことではなく、**Lean の意味情報を再利用可能な形で抽出し、必要な部分だけを高速に更新できる
こと**。副産物として doc-gen4 が**出力できていないパッケージ自身の `scoped notation`** も出る
(実測 → §10) — 読者が実際に書く記法で署名が読めることは生成速度と同じくらい価値に効く。

## 2. 背景 — 計測が示したこと

doc-gen4 を計装して、Mathlib 依存プロジェクト (432 モジュール) のドキュメント生成を実測した
(この節はすべて実測 → [`benchmarks/doc-gen4-report.md`](../benchmarks/doc-gen4-report.md))。
コストは 3 層に分かれ、どれも「ドキュメントを作る仕事」そのものではなかった。

| 層 | 支配率 | 実際に起きていること |
|---|---:|---|
| 環境ロード | **85.0%** | モジュールごとにプロセスを起動し、import closure 全体を読み直す |
| 意味解析 | 4.6% | 本来の仕事。宣言の型を pretty print し equation を生成する |
| 走査オーバーヘッド | 8.8% | 環境の全定数を舐めて、該当しないものを捨てる |

実ビルドでは **8.9 億回の定数走査に対して該当は 0.032%** で、走査して捨てるだけのコスト
(1,195 秒) が本来の意味解析 (631 秒) の約 2 倍あった。HTML 生成フェーズも同様で生成 CPU の
**66〜78% が DB からの読み直し**、レンダリング自体は 9.2%。さらに**増分性が一切ない** —
無変更で 2 回続けて実行しても 46.25 秒 → 43.91 秒と変わらない。

### 決定的だった 1 つの実験

doc-gen4 に「複数モジュールを 1 プロセスで抽出する」コマンドを足して、
同一の 432 モジュールを両方式で処理した (どちらも全数の実測で外挿なし、
同じ日・同じ warm な page cache 状態)。

| | warm 実測 (壁時計) | うち `importModules` |
|---|---:|---:|
| モジュールごとに 1 プロセス (現行) | **1,076 秒** | 908.6 秒 (88.8%) |
| 1 プロセスでまとめて | **31.9 秒** | 2.6 秒 |

**34 倍。分母は「同じ 432 モジュールを抽出する仕事」。** アルゴリズムの改良ではなく、同じ依存
ライブラリを 432 回読み直すのをやめただけで生じる。差の出どころは 1 行で言える —
**432 モジュールぶんの import closure をまとめて読んでも 1 モジュールぶん (逐次時 2.10 秒) と
ほとんど変わらない** (closure が Mathlib に支配されているため)。**cold と warm を混ぜないこと。**

## 3. 仮説

> Lean の意味情報をパッケージ単位でまとめて抽出し、依存ライブラリを外部参照にすれば、
> downstream ライブラリのドキュメント生成時間を**依存ライブラリの規模から大きく切り離せる**。

計測はこの仮説を支持している。ただし完全には切り離せない — 自パッケージの型を正しく
pretty print するには Mathlib の `Environment` が要り、そのロードは残る。
**これが新設計の床**であり、それをどう扱うかが設計の中心的な論点になる。

床の大きさは **page cache の状態で 5 倍動く。warm で約 2.5 秒、cold で 10〜13 秒**
(実測 → 検証ログ 段階 1)。warm では壁時計 ≒ CPU 時間で、差はすべて olean の mmap ページイン待ち。
したがって「床をどう扱うか」は最初から 2 つの別問題である。

- **ローカル (warm)**: 2.5 秒。1 モジュールだけの再抽出ならこれより小さい (`importModules`
  0.80〜2.96 秒、実測・段階 5) が `lake env` の 0.96 秒が別にかかる (→ §6.5)。
  **常駐で消せるが、消さなくても致命的ではない。**
- **CI**: **配置で決まる。常駐は効かない** (下表)。

**「CI は常に cold」は否定された。効いていたのは `cache get` ではなく `lake build`**【Linux 実測、
2026-08-10】 — doc 生成が見るのは `cache get` 直後ではなく**ビルド後の page cache**。

| CI の組み方 (`ubuntu-latest` / 2 コア / 7.75 GiB) | `importModules` | major fault |
|---|---:|---:|
| doc 生成を `lake build` と**同じジョブ**に置く | **2.610 秒** (macOS warm と同じ) | **26** |
| 別ジョブでビルド済み olean を復元して doc だけ作る | **20.4〜89.2 秒** | 11,949〜30,424 |

**間は 8〜27 倍。設計上の推奨が出た — doc 生成はビルドと同じジョブに置く。**
効くのは**割合ではなく「どのページか」** (`lake build` が import の要るページを読む) —
常駐率は `cache get` 後 60.4% → ビルド後 **40.3%** と下がるのに fault はほぼ 0 で、
**`cache get` 直後の常駐率は代理指標ですらなかった** (n=2、容量律速)。**cold 側は
`ubuntu-latest` でも 2 実体に割れる** (readahead とストレージの差とみられる、未検証。**n=2**)。

**先読みは「効くこともある」打ち手** — **ランナー実体で答えが割れる**【実測】。
読ませる集合は **`.lean` ヘッダから作った import closure** (17,199 ファイル / 4.14 GB)。

| | baseline の `importModules` | 先読み後 | **壁時計** |
|---|---:|---:|---:|
| macOS / M1 | 13.573 s | 6.923 s (−49.0%) | 18.03 → 10.44 s |
| Linux **速い実体** (0.67 ms/fault) | 20.4 s | 5.0 s (−76%) | 46.3 → 44.5 s = **−4%** |
| Linux **遅い実体** (5.3 ms/fault) | 63.9 s | 12.4〜19.4 s | 97.3 → **56.0〜74.6 s = −23〜−44%** |

**遅い実体では直列な demand fault を 16 並列の読みに置き換える価値が大きく、速い実体では
closure 4.14 GB のうち要らない約 1.6 GB が節約を食い潰す** (ディスク 190〜220 MB/s = macOS の
1/11)。**実体は選べないので期待値としては効くが保証はない。「集合を絞れば効くか」は未検証**
(絞った版は必要分を取りこぼしていて検証になっていない)。**第一の打ち手は配置** (同じジョブ = 2.61 秒)。

## 4. Approach

> **Lean プロセスは「意味情報を吐く抽出器」に徹し、1 つの環境を長く使い回す。**
> 抽出したものはモジュール単位の中間表現 (IR) として永続化し、
> HTML・検索索引・その他の出力はすべて Lean の外側で IR から作る。
> 依存パッケージについては IR を作らず、「宣言名 → モジュール → URL」の写像だけを持つ。

変えるのは次の 3 つの境界。**どれも独立に効き、順に適用でき、1 つ失敗しても残りは成立する。**
(1) **プロセスの境界**: モジュールごと → パッケージごと (あるいは常駐)。(2) **抽出の範囲**:
環境の全定数 → 自パッケージの宣言のみ。(3) **Lean と出力の境界**: Lean が HTML まで作る →
Lean は IR まで、出力は外側。

## 5. 設計の柱

### 5.1 1 環境・長寿命プロセス

抽出は「モジュール 1 個 = プロセス 1 個」をやめ、対象パッケージを 1 度ロードしてまとめて
処理する。これが実測 34 倍 (§2) の正体で、単独で最大の効果を持つ。

**常駐は実装・実測して決着した** (`--serve`、段階 6 + 6a + 7g。要求あたりの数字は §7 の表)。
**寿命の上限は「自分が import した olean を書き換えるビルドまで」**【段階 6a、実測】 —
Lean には環境から 1 モジュールだけ差し替える手段が無く、プロセスは死なない
(`lake build` を生き延び 0.151 秒で応答した) が、**参照の所有者を環境から引く**ので
移動した名前に古い所有者を返す。**段階 6 の「ラウンド 2 以降なら安全」は誤り** —
ラウンド 2 はまさにその所有者列を直すためにあるので、編集前環境では 439 ページ中 1 ページが誤る。
**寿命の内側では持つ** — 600 要求で IR は byte 一致のまま、RSS 不動【段階 7g、実測 → §8】。

**正しい形は「`lake build` の後にサーバを 1 台立て、全ラウンドを任せ、終わったら落とす」**。
現行の抽出器 (schema 4 + `--jobs`) で自動起動・自動停止まで配線すると **439/439 byte 一致の
まま 7.968 → 6.668 秒 (−16.3%、`--jobs 1`) / 7.894 → 6.509 秒 (−17.5%、`--jobs 4`)**
【段階 7g、実測。起動・停止は計測の内側。**6a の 7.940 / 6.168 秒は抽出器もレンダラも別物なので
並べない**】。**取り分は `--jobs` でほぼ動かない** — 増分で再抽出するのは数モジュールで
`analyze` が小さく、常駐が消すのは**ラウンドごとの `importModules`** (1.819 + 1.766 秒) と
プロセス起動 2 回分だから。**jobs が効くのはフル再抽出**: 立っているサーバに任せると
**−23.4% (j1) → −43.3% (j4)** — 消える `importModules` は並列化されないので分母だけが縮む
【実測】。ラウンド 2 だけ任せるのは損で**分岐点は 2 ラウンド**【段階 6a】。臨界パスの
74〜98% は `lake build` なので、端から端で見た効き幅は小さいまま。

副次的な効果として、**メモリ律速が消える**。現行はプロセスごとに 2〜3 GB の環境を持つため 8 並列
で RSS 21.7 GB (物理 16 GB) に達しスワップし (実測)、CPU コアを増やしても頭打ちになる構造だった。
**この取り分は段階 7d で現金化した** — 1 環境の中で宣言を 4 スレッドに割ると意味解析が
**3.23 倍**になり **IR は byte 一致**、追加メモリはほぼ要らない (→ §6.1)。**同じ「4 並列」でも
プロセス並列とは意味が違う。**待機中の常駐 1 台は **0.55〜0.62 GB**【段階 7g、実測】 —
**3.27〜3.37 GB は要求処理中のピーク**で常時占有ではない。

### 5.2 走査ではなく索引で宣言を引く

「環境の全定数を舐めて、対象モジュールのものだけ拾う」のをやめ、モジュールから宣言を引く
方向に変える。5.1 とは独立に効く — バッチ化しても走査は 1 回分残るため。
**実装と正しさは検証済み** (→ 検証ログ 段階 1): 索引方式と走査方式は同じ 5,123 宣言を返し、
時間は 0.0022 秒 対 0.62 秒 (実測)。ただし**バッチ 1 回あたりの走査コストは当初の見積もり
4.45 秒より 1 桁小さい** (cold のページインを走査コストと取り違えた値。warm では 0.36 秒)。
**この柱の価値は「時間が消える」ことではなく、モジュール数に比例する走査を構造から無くすこと**に移った。

索引方式には走査方式に無い論点がある: 複数モジュールの olean に同名で焼かれる自動生成補題が
あり、**宣言の所有モジュールが一意に決まらない** (実測 25 件)。明示的に決める (→ §8)。
同じ性質の問題がタクティク収集にもあり、**バッチ化すると 16.7 秒 (全体の 54%) の最大項に
浮上するが、1 回列挙して振り分ける実装で 0.011 秒**【実測】。**正体は見立てと違った** —
78% は `EnvironmentHeader.moduleNames` が**フィールドではなく `def`** で、呼ぶたびに import
closure と同じ長さ (6,021 要素) の配列を作り直していたこと。
**第 3 の因子は呼び出し側から見えない。** ゆえにこの柱の一般形は一段強い:

> **1 モジュールの処理で、import closure のサイズに比例するものに触らない。**
> 走査でなくても、配列 1 本の構築でも、内側のループに入れば同じことになる。

### 5.3 依存パッケージは外部参照にする

HTML 生成が依存パッケージについて実際に必要としているのは**「宣言名 → モジュール名 → URL」の
写像だけ**だった (型も docstring も equation も不要)。したがって依存については IR を作らず、
この写像だけを持ち、公開ドキュメントへリンクする。これが「ゼロからサイトを構築する」ケースで
桁違いの差を生む (→ §6.4(b))。

**検証段階 3 で実測に置き換わった** (348/432 モジュールの範囲、詳細は verification-log):

- **写像だけで doc-gen4 と同じ URL 文字列が出る** — 共通 39,298 ペアの **99.992%** が href 完全
  一致 (未一致 3 はリンクしてはいけない再帰子で写像はそれを出さない)、**取りこぼしは 0**
- 写像の実サイズは **8.51 MB / gzip 1.33 MB**【段階 7c、実測】(旧: 下限 53 KB / 上限 34.3 MB の
  幅。作る 0.415 秒 / 読む 0.076 秒、宣言 258,760)。必要な列は (名前, モジュール)
  の 2 列で `kind` は要らない。**blacklist は写像から復元できる** — 「写像に載っている名前だけ
  リンクする」方式は doc-gen4 の dead link (実測 3 本) を出さない

URL 規則は `("../" × (ページのモジュール成分数 - 1)) + "./" + モジュールパス + ".html#" + 名前`。
**IR には絶対的な識別子を持ち、相対化は出力時に行う** (→ §5.6)。**残る欠落**: 自パッケージの
`_private.` 名は素朴に URL を出すと dead になる (実測 8 名 → §8)。なお**リンク解決に必要な
データと、型を pretty print するために環境が必要なことは別問題** — 後者 (§3 の床) は残る。

### 5.4 中間表現の粒度はモジュール単位

現行 doc-gen4 は宣言ごとに DB の行を分割したため、レンダリング時に N+1 クエリで再構築する
羽目になり、生成 CPU の 66〜78% がそこに消えている。**読みも書きもモジュール単位なら、
モジュール 1 個 = 1 まとまり + 索引が正しい粒度。** 教訓は「規模が来たら SQLite」ではなく
**アクセスパターンに合わない粒度で分割すると逆効果**、ということ。格納形式
(JSON / SQLite / バイナリ) の選択より粒度の選択が先に来る。

IR にはスキーマバージョンを持たせ、キャッシュキーには少なくとも Lean バージョン・抽出器
バージョン・IR スキーマバージョン・olean ハッシュを含める (olean ハッシュだけでは不足 —
pretty printer の出力が Lean バージョンに依存するため)。実装形は「**モジュールごとの olean
ハッシュ + パッケージ 1 つぶんの環境キー**」で、後者は判断点 3 で不完全と分かって 2 分割した
(→ §5.5 の L1)。

**この粒度は実測で成立した** (検証ログ)。**schema 2 (位置つきタグ) で 15.13 MiB / 書き込み
0.549 秒 / 読み出し 0.100 秒 (床の 4.0%)**、タグ無しの schema 1 なら 8.74 MB / 0.198 / 0.056、
**現行の schema 4 は schema 2 比で +0.97% / +13.5% / ±0**【実測】 — 結論は同じだが
**引用時は構成を揃えること** (→ §6.1)。内容ハッシュは書き込みの 1.2% で、持つ代償はない。

### 5.5 増分性を「入力側」と「出力側」で別々に設計する

現行はここが両方向に壊れていた — **取りこぼし** (マーカーファイルが空なので内容が変わっても
ハッシュが変わらず HTML が再生成されない) と **無駄** (走れば変更の有無に関わらず全モジュール)。
原因はキャッシュ無効化とページ再生成という別々の関心を 1 つの仕組みに載せたこと。

> **「IR のモジュール単位ハッシュを単一の真実にする」当初案は否定された (判断点 3)** —
> 5 命題すべてが実測で破れた (→ [検証ログ](verification-log.md) 段階 5 増分 2)。
> 否定されたのは**その構造**であって増分生成そのものではない。以下の 3 層が見直し案で、
> **増分 4〜7 で全層が実装され、本物の移動と本物の削除を `lake build` ごと回して
> フルビルドと byte 一致するところまで実測した。**

**単一の真実は「役割が 1 つ」ではなく「役割ごとに 1 つ」だった** — 問う時点が違う。

| | 入力側 = どのモジュールを**再抽出**するか | 出力側 = どのページを**再生成**するか |
|---|---|---|
| ハッシュ対象 | モジュールの `.olean` (3 分割なら 3 つとも) | モジュールの IR |
| 計算する時点 | 抽出の**前** (Lean 不要) | 抽出の**後** |

`.lean` ソースは早すぎ (証明中の空白のように olean に届かない変更を拾い、依存の再ビルドで
olean に入った変更を落とす)、IR は遅すぎる (計算するには省きたい抽出そのものが要る)。
**抽出器が見られるのは olean だけ**なので入力側は olean が正しい。**Lake が既に内容ハッシュを
`<file>.olean.hash` に書いている**ので、台帳は 227 MB ではなく 6.9 KB を読めば済む (0.080 秒)。

#### 3 層 (判断点 3 を受けた設計、増分 4〜7 で全層を実装・実測)

判断点 3 が見つけた穴は**上の 2 層のどちらにも属さない依存**だった。

| 層 | 何を見るか | 何を決めるか | 変わったときの影響範囲 |
|---|---|---|---|
| **L1 グローバル鍵** | モジュールに属さない入力 | 全無効化するか | **全部** |
| **L2 モジュール単位ハッシュ** | 各モジュールの `.olean` | 再抽出集合の**核** | そのモジュール |
| **L3 導出の依存** | 名前の所有権 / 全域写像 / 全域索引 | L2 の核を**広げる** | import では閉じない |

**L1 は 1 つの鍵ではなく 2 つ**【実測で確定、増分 4】。振り分けの基準は「出力のバイトを
変えるか」ではなく (両方変える)、「**IR を変えうるか** = 答えるのに Lean が要るか」。

| 鍵 | 中身 | 変わったとき |
|---|---|---|
| `extractKey` | toolchain / manifest / 抽出器 id とその構成 (`--open`) / IR schema / 生成器 id | 全再抽出。stale ページは従来どおり IR 差分が決める |
| `renderKey` | レンダラ id / `--source-url` | 再抽出**ゼロ**、再レンダリング**全部** |

分けないと二択が両方まずい: 入れなければ 432 ページが黙って stale、単一の鍵に入れれば
**`--source-url` の変化だけで 432 モジュール全再抽出**。
**分割の効果は 18.39 → 1.34 秒 = 13.7 倍**、追加コストは **+0.3 ms** でドリフト以下【実測】。
鍵の比較は**和集合**で行う — 片側にしか無い鍵も変化と数え、**黙って過少にレンダリングしない**。

**L2 の鍵は olean の内容ハッシュのままでよいが、そのままでは移送できない** — olean には
**ソースの絶対パスが 429/432 モジュールで埋まっている** (実測。Mathlib の style linter のログを
持つ環境拡張 `lintLogExt` がパス入りの警告文を保存している)。**チェックアウト先が違うだけで
ハッシュが全滅する**ので、CI と開発機で IR キャッシュを共有するには鍵をパス非依存にする必要が
ある。**モジュール一覧はソースの glob で作る** — **`.lake/build` を走査してはいけない**。
Lake は孤児 olean を消さないので 432 モジュールに対し olean は 1,090 個、**659 個が幽霊**
(実測)。**削除経路は実装済み** (台帳・IR・ページの 3 箇所、増分 6) — 台帳は作り直しで足り
(`build` は `check` と同コスト)、**ページは消す係が要る** (レンダラは書くだけ)。本物の削除 +
`lake build` でフルビルドと byte 一致まで実測した (複製上の落とし穴は `experiments/stage5e/README.md`)。

**L3 が §5.5 に無かった穴で、3 つある** (いずれも実装済み):

1. **名前の所有権** — 参照は `(定義モジュール, 名前)` で持つので、宣言が移動すると参照側の
   IR が腐る。**これは再生成ではなく再抽出の問題**で、影響集合をどれだけ広げても直らない。
   L2 の核から「**そのモジュールが定義していた名前の集合の差分**」を取り、その名前を `refs` に
   持つモジュールを**再抽出集合に足す**。**実装済み** — 本物の移動 + `lake build` で、無しは
   433 ページ中 1 ページが**リンク切れ**、有りは**フルビルドと 433/433 byte 一致**【実測】。
   **L2 が参照側を拾うかは当てにできない** (4 つのうち 1 つは olean が動かなかった) — 拾えるかは
   Lean の直列化の都合であって依存構造の性質ではない。**import 閉包へ広げる必要は無い。**
   **再抽出はラウンド構造になる** — 移動を知るには移動元の新しい IR が要るので「抽出 → 誰が
   腐ったか問う → それも抽出」の順。実測では **2 ラウンドで不動点**、これは**構造的な上限**
   【段階 6c】 (ラウンド 2 以降は olean が動いていないので宣言集合も動かない)。**穴は 1 つ**:
   その集合は `isBlackListed` で濾したもので述語が環境を参照するため、**反転させる変更があれば
   ラウンド 3 が出る**。`--max-rounds` は残す。**効く範囲は「移動する名前が印字署名に出るか」で
   決まる**【実測】 — `abbrev` は必須 (無しだと最大 30 ページ誤り)、`instance` や `@[simp]` には
   無関係で、そちらを救っているのは L3-3。
2. **全域写像** — docstring の autolink は名前 → 定義モジュールの全域写像を引くので
   **import で閉じない** (実測: 逆向きの推移的 import 閉包でも 3〜141 ページ取りこぼす)。
   **増分 6 で失敗が双方向だと確定** — モジュールを 1 つ削除すると全域写像が 533→527 に減り、
   **削除と無関係な LZ78 のページに、行き先の消えたリンクが残った**。繋いでいるのは全域写像
   だけ。**増分 7 で閉じた** — 規則は「**全域写像の差分に出た名前を docstring に含むページ**を
   再生成集合に足す」。走査であって推測ではなく、逆索引の常備も要らない。実測では 58 名の
   差分から**ちょうど 1 ページ**を名指しし (過剰近似なし)、削除ケースは **437/437 byte 一致**。
   **写像は自宣言だけでは足りない** — 効いたのは依存側の名前で、走査の単位も code span ではなく
   `autoLinkInline` と同じ空白分割。どちらも間違えると外からは「0 ページ」に見える。
3. **全モジュール横断の後処理** (検索索引・ナビゲーション・相互参照) — **実装済み、増分化済み**。
   IR から生成でき **合計 1.88 MB**【実測】(**doc-gen4 の 38.6 MB は依存木全体 258,760 宣言の
   値でこちらの数字ではない**)。`tactics.html` だけは自パッケージの関数ではない
   (tactic docstring は環境側にあり 432 モジュールで 0)。
   **この層は正しさにも効いている**【段階 6c】 — instance 一覧はページのバイトに無く
   `declaration-data.bmp` からブラウザが埋めるので、**instance の移動が正しく出るのは
   「全域成果物を作り直す」から**。3 層でいちばん安い層が最も広い網だった。
   **「増分化する価値なし」(増分 7) は段階 7h で否定された** — 消えるのは IR 全読み 1 回ではなく
   **`build` の全読み + `delta` の全走査 + プロセス 1 つ**。`contentHash` を鍵にした 842 KB の
   キャッシュで **0.4527 → 0.1257 秒 (fresh) / 0.4470 → 0.1461 秒 (resident)**、6 成果物も
   サイト 439 ファイルも byte 一致【実測】。**残る IR 全読みは 5 回** (ownership・merge ×2・
   impact・render) で、そちらのほうが大きい。

**「影響集合の mode」という枠組み自体が的を外していた**のが判断点 3 のいちばん構造的な発見 —
`self` / `referrers` / `importers` は**描画対象しか決めない**ので再抽出が要る種類の stale (L3-1)
には原理的に効かない。**再抽出集合と再生成集合は別々に導く。**
rev をバイトに焼く前提では「mode は常に `all` に潰れる」だったが、**§5.6 でその前提を外した**
ので `all` は立たず **0 ページ**になる (実測)。**高いのはレンダリングではなく抽出**
(rev を焼く構成でも 432 ページ全部で 0.87 秒)。

**空の再生成集合の落とし穴は、rev を外した今、常時通る経路になった** (段階 6b で発見・修正済み)。
`render.ts` は `--only` が無いと全モジュールを描くので、空集合から `--only` を 0 個渡すと
**433 ページ全部を再生成する**。rev を焼いていた間はコミットが必ず `all` を立てたので誰も
来なかった。**Rust へ移設するときここを再実装するので、同じ穴を空けないこと。**

### 5.6 出力は IR から作る (Lean の外側)

HTML・検索索引・JSON API・宣言グラフ・リンク切れ検査は、すべて IR を入力とする独立した消費者に
する。**HTML の再生成に Lean の起動が要らない**ことが、この分離が成立している証拠になる。
境界の入口までは実測で通った: Lean を起動しない別プロセスが 432 モジュール分の IR を
**0.100 秒**で読み切れる (15.13 MiB、環境ロードの床の 4.0% → 構成の違いは §5.4)。

**IR は参照定数を集合でなく位置つきで持つ必要がある** (段階 4 増分 1)。doc-gen4 の署名内アンカー
72,421 件のうち **44.0% は印字トークンと定数名に字面の関係が無く** (`ℕ`→`Nat`)、平文 + 集合から
の再構成は上限でも recall 56% / 実測 51.7%。ページのバイトの **71.1% が署名の描画**なので、
ここを落とすと「同じ仕事」ではなくなる。逆に**あて先の解決 (名前 → モジュール) は集合で足りて
いる** (取りこぼし 0.36%、全部 docstring 側)。**ただしこの「集合」は全域写像で増分では
閉じない** — 判断点 3 が破れたのはまさにこの docstring 側 (§5.5 L3-2)。

なお計測は**レンダリング自体の最適化に価値が薄い**ことも示した (生成 CPU の 9.2%)。
**外側の律速はレンダリングではなく IR の全読み** — 増分パイプラインは全読みを **5 回**残していて
(7h が 7 回から 2 回削った)、1 回のコストは **432 モジュールで 0.105 秒 / Mathlib 8,169 モジュール
(542 MB) で 3.18 秒**【実測】。**規模にほぼ線形**なので、大きなパッケージでは外側が支配的になる。
次に効くのは言語ではなく **7h と同じ `contentHash` キャッシュを残る 5 回に当てること** (未着手)。

#### 出力契約 — revision はページのバイトに入れない【決定】

rev を焼くとコミットのたびにページ内 4,992〜4,993 か所が変わり**全ページが無効**になる。
`{{SOURCE_URL}}` を焼いて**ブラウザ側で注入する**形を採る: 再生成 433 → **0 ページ**、
パイプライン合計 1.6227 → 0.6441 秒 (**−60.3%**)、ページは 399,440 B 小さくなる【段階 6b /
7e-rev、実測】。`--source-url` に定数トークンを渡すだけなので**実装コストはゼロ**で、renderKey
からも rev が外れる。

**代償「HTML 単体で完結しなくなる」は許容する** — このサイトは既に `declaration-data.bmp` を
ブラウザが読んで instance 一覧を埋めているので、**静的ファイル群で完結する形は元々の設計**。
ただし **注入が走らなければ 4,992 本のリンクが死に、死に方は無反応ではなく同一オリジンの 404**
【実測。ブラウザでも確認済み】。**採点は必ず注入後の木に対して回す** — プレースホルダのまま
採点すると **−3.1103 pt** ずれる (gh_link / nav_gh がきっかり 0.0% になる)【実測】。

**注入は 2 方式あり、どちらも成立する。製品は配信時 (ビルド時) 置換を採る**
【段階 8 で実測、決定 2026-08-11 → [実装計画](implementation-plan.md) §4 決定 3】。

| 方式 | コスト | 制約 |
|---|---|---|
| **配信時 (ビルド時) に文字列置換** | **0.1552 秒 / 432 ファイル** | **無い** — HTML が届く前に終わっている |
| **ブラウザで JS 注入** | **1 ページ最悪 0.80 ms** (p50 0.10 ms) | **順序制約がある** (下記) |

JS 注入版の制約は「注入が先」ではなく **`.gh_link a[href]` の書き換え完了が `jump-src.js` の
`DOMContentLoaded` ハンドラ実行より前**であること。満たし方は **3 通り**あり、外すのは
**「リスナ内で注入し、かつ登録が `jump-src.js` より後」のときだけ**【実測】。
**rev の供給元はページ外の共通 1 ファイルに限られる** — ページに埋めると rev がバイトに戻り
この決定の目的が消える。**配信側は鮮度ヘッダを付けること** — 付けないとブラウザは全ページで
その 1 ファイルを取りに来る (10 ナビゲーションで 10 回 → `max-age` で 1 回)【実測】。
壊れ方は `?jump=src` 付きのディープリンクに限られる。**Chrome 151 でのみ実測** (他エンジンは仮定)。
**採らない理由はこの制約 3 つ** — 置換版は 0.1552 秒で制約ゼロなので負う理由が無い。
数字は**選択肢の保存**として残す (静的ホスティングを使えない配信形態が出たら成立する形がある)。

#### 検索は組み込み・自パッケージのみ【決定】

doc-gen4 の組み込み検索は `declaration-data.bmp` を丸ごと落として全件を線形走査する。**依存を
含めない**と決めたので、この対象の索引は **4,750 宣言 / 406 モジュール / kind 6 種**、導出形式
(モジュールと kind を配列 + 整数 ID) で **361,466 B / gzip 45,780 B**【実測】。この規模なら
全件ダウンロードも線形走査も問題にならず、doc-gen4 が
[#133](https://github.com/leanprover/doc-gen4/issues/133) で切っている IndexedDB キャッシュも
要らない。**`docLink` は (モジュール, 名前) から 258,760/258,760 = 100% 復元できる**【実測】ので
索引に持たない。**落とし穴**: lean-doc の kind 語彙は doc-gen4 と違う (`definition`/`constructor`
対 `def`/`ctor`)。doc-gen4 の `search.html` を流用すると**種別フィルタが黙って全部外れる**
(静的資産は byte 再現率の母数外なので、この経路は誰も踏んでいない)。

#### 実装言語は Rust【決定】

抽出器は Lean、**その外側 (IR 消費・レンダリング・増分・検索索引) は Rust**。
**選定理由は速度ではない** — レンダリングは生成 CPU の 9.2% で、§6.4 の倍率は「やらなくてよい
仕事をやめた」ことによる。**速度の主張と言語を因果で結ばないこと。** 決め手は配布と、対外的に
「高速を謳うなら Rust」という期待に合わせる製品判断。**技術的な利得が 1 つ**: doc-gen4 の
CommonMark は **md4c (C)** で、TS にはバイト一致する実装が無く自前のサブセットを書いていた。
Rust なら md4c を FFI で直接リンクできる — **その C ソースは MD4Lean 経由で既に手元にある**が、
**FFI が消すのは自前サブセット 594 行だけで autolink 解決系 153 行は残る**【いずれも実測】。
**移設対象は約 4,250 行 + シェル約 1,100 行**、**完了条件は「Rust 版が 439/439 byte 一致」**
(オラクル `coverage.ts` は Deno のまま製品外)。**内訳・移設の順序・各ゲートは
[`implementation-plan.md`](implementation-plan.md) が持つ** — この文書は書かない。

## 6. 性能

**抽出・IR 永続化・HTML 生成・増分はすべて実測に置き換わった** (検証段階 1〜5。外れる筋は §6.6)。
**残る非実測は 2 つ** — (1) cold 合計は stage1 抽出器からの**外挿** (→ §6.3 の 26.22s / 19.57s)、
(2)「CI が cold 側かどうか」は**仮定** (→ §3、Linux 未測定)。どの数字が実測 / 外挿 / 仮定かは行ごとに明示する。
**そしてこの節は速度の節である。** 増分の**正しさ**は増分 4〜7 で閉じた (フルビルドと byte 一致、
→ §5.5) が、**§6.5 の秒数は正しさが閉じる前の構成のもの。**

### 6.1 抽出フェーズ + IR 永続化 (自パッケージ 432 モジュール) — 実測済み

**基準は warm な page cache での実測** (旧版は cold を warm と取り違えていた → 検証ログ 段階 1)。

| 項目 | 現行 doc-gen4 (warm) | lean-doc | 根拠 |
|---|---:|---:|---|
| 環境ロード | 2.60s | **2.52s** | 実測。削減対象外 (§3 の床) |
| タクティク収集 + モジュール docs | 16.64s | **0.011s** | 実測。全体 1 回列挙 + closure 依存の排除 (§5.2) |
| 走査 (該当外) | 0.36s | **0.002s** | 実測。索引方式 |
| 意味解析 (equations + 参照定数 + 位置つきタグ) | 10.51s | **10.79s** → **3.34s** (`--jobs 4`) | 実測。内訳は delaborate 55.3% / format 15.4% / タグ 12.7% (→ 検証ログ 7d) |
| 書き込み | 0.68s (SQLite) | **0.623s** (IR 15.28 MiB) | 実測。**仕事の範囲が揃った** (下記) |
| **合計** | **31.50s** | **14.08s** → **6.50s** (`--jobs 4`) | 実測。**両列ともプロセス内の計時合計**であって行の和ではない。**31.50s と並べてよいのは 14.08s のほう** (どちらも 1 スレッド) |

出所は doc-gen4 側が warm 再計測 `batch-rerun.jsonl`、lean-doc 側は **IR schema 4 (段階 7b)** の
同一セッション 6 run の中央値。**行の和ではなく計時合計を合計とする。** 引用の注意:

- **`--jobs 4` で意味解析は 3.23 倍、合計は 2.19 倍、IR は byte 一致**【段階 7d】。
  **減ったのは壁時計で CPU 時間ではない** (instructions +1.0%)。頭打ちは 4 スレッド。
- **セッション間の差が 0.3s 級ある** — schema 3 → 4 の正味は **+0.035s** で、13.71s → 14.08s の
  残りはセッション差。**分離できているのは phase timer とバイトだけ。**
- **書き込みコストはフェーズタイマーで読む** — 壁時計の振れは全部 `importModules` に出る
  (IR の書き込みが olean の mmap ページインに干渉する)。0.623s と 0.68s はいまは同じ仕事に近い
  (段階 7b で属性・instance 索引を実装した) が、lean-doc はモジュールハッシュと依存写像も書く。

cold cache では環境ロードが 13.6 秒前後になり合計に 11.1 秒ほど上乗せされ、**先読みを入れると
上乗せは 4.5 秒に下がる** (どちらも実測)。**CI がどれだけ cold 側かは §3。**

**内訳は当初の前提から反転した** — 旧見積もり (cold 基準) の環境ロード 51% / 意味解析 46% に
対し、実測 (warm、14.08s を分母に) は **18% / 75%**。残るコストの大半が**本来の仕事**なので
環境ロードを避ける工夫の取り分は小さく、**自前実装でも意味解析は減らなかった** (同じ 4,750
宣言・同じ出力で lean-doc 9.26 秒 対 doc-gen4 10.51 秒、いずれも実測)。次に狙うなら equation
生成を切る (寄与 10% = 0.97 秒 / 863 本、実測) か、変更のない宣言を再解析しない方向。
**タクティク収集は決着** (0.011 秒) だが 16.7 秒の正体は見立てと違った (→ §5.2)。

### 6.2 HTML 生成フェーズ (自パッケージ 432 モジュールのみ)

|---|---:|---|

| 同上・2 回目 (42.31s) | 3.01s | **外挿** (同じ 2 run の warm 側) |

### 6.3 初回ビルド

| | warm | cold・先読みなし | **cold・先読みあり** |
|---|---:|---:|---:|
| 抽出 + IR 書き込み (完成出力、1 スレッド) | **14.08s** 実測 (→ §6.1) | 25.20s **外挿** | 18.55s **外挿** |
| HTML 生成 (IR → 432 ページ) | **0.89s** 実測 (→ §6.2) | 1.02s **外挿** | 1.02s **外挿** |
| **合計** | **14.97s** (`--jobs 4` なら **7.39s**) | **26.22s** | **19.57s** |

先読みは import closure / madvise / 16 並列 / 抽出と並行 (→ §3)。
**cold の 2 列は外挿** — 足した追加コスト (+11.115s / **+4.465s**) は stage1 抽出器の実測値。
前提「cold の追加コストは `importModules` に集中する」は **Linux で実測になった**。
ただし**幅は移送できない** — 同じ cold でも Linux は 20〜89 秒で macOS の 1.3〜5.9 倍。
`lake env` の cold (+2.56s) はこの表に無い。**CI がこの cold 側に落ちるかは配置で決まる** (→ §3)。

### 6.4 現行 doc-gen4 との比較

比較は 2 つの意味で成立し、桁が違うので分けて示す。

**(a) 同じ仕事量 — 自パッケージ 432 モジュールを抽出する**

| | 時間 | 倍率 |
|---|---:|---:|
| 現行 (モジュールごとに 1 プロセス) | 1,076s | — |
| lean-doc (warm、schema 4 = 完成出力) | 14.08s | **76×** |

どちらも 432 モジュール全数の warm 実測で、**外挿も仮定も含まず、どちらも 1 スレッド**。これが
「バッチ化 + 走査の排除」だけで得られる分で、**依存を外部参照にする効果はまだ入っていない**。
**`--jobs 4` の 6.50s を 1,076s と割らないこと** — doc-gen4 側の並列壁時計を**測っていない**
(しかも向こうの並列はメモリ律速 → §5.1)。**倍率は出力の範囲とも一緒に動く** (位置つきタグで
85× → 78×、属性・instance 索引・メンバで 78× → 76×)。**必ず範囲を併記すること。**

**(b) ゼロからドキュメントサイトを構築する** — 現行 doc-gen4 は依存を外部参照にできないため、
Mathlib 8,169 モジュール分の抽出がすべて必要になる。

| | CPU 時間 | 倍率 |
|---|---:|---:|
| 現行 (Mathlib 全体の抽出を含む) | 約 32,600s = **9.1 時間** | — |
| lean-doc (依存は外部参照、warm) | 14.97s | **約 2,180×** |

現行の約 32,600 秒は**外挿**。**フルビルドは完走していない** — 8,600 モジュールのうち
3,590 (42%) を抽出した時点で打ち切り、その実測 13,611 秒 (= 3.79 秒/モジュール) を
8,600 に伸ばした値 (→ [`benchmarks/doc-gen4-report.md`](../benchmarks/doc-gen4-report.md) §4.6.1)。
8 並列が理想的に効けば壁時計で約 68 分だが、実測ではメモリ律速でこれを大きく超えた。
この方式の数字は page cache にほとんど左右されないので外挿値はそのまま使える。

**この倍率のほとんどは「やらなくてよい仕事をやめた」ことによる**もので実装の巧拙ではない。
ここが本プロジェクトの存在理由。**倍率だけを取り出して引用しないこと** — (a) の 76 倍、
(b) の 2,180 倍、同じ 432 ページの生成だけで比べた **3.6 倍** (→ §6.2)、Mathlib 自体を
対象にした CPU 時間の **約 30 倍** (→ 検証ログ) は、**分母が全部違う別々の主張**である。
**分子の約 32,600 秒は打ち切りビルドからの外挿で抽出フェーズだけの値**で、doc-gen4 の
HTML 生成 (6,072 モジュールで 44.52 秒、実測) は入っていない — **差は分子ではなく分母
(lean-doc 側の出力範囲) にある。** 分母側に残る差は**静的資産が母数の外**という一点だけ。

### 6.5 増分ビルド (1 モジュール変更) — 実測

旧版の「使い捨て 2.5s / 常駐 0.03s」はどちらも理論値で**両方外れていた**。
**現行構成 (7g 配線 + 7h) の段別内訳**【段階 7h、実測、中央値。生ログ `stage7h-main.txt`】:

| 段 | 担当 | fresh | resident |
|---|---|---:|---:|
| `serveStart` | Lean | 0.000 | 14.621 |
| `detect` (L2 台帳) | 外側 | 0.162 | 0.446 |
| `extract` | **Lean** | **9.485** | **0.707** |
| `ownership` / `merge` / `prune` (L3-1) | 外側 | 0.313 / 0.389 / 0.034 | 0.328 / 0.423 / 0.038 |
| `global` (L3-3) | 外側 | 0.126 | 0.146 |
| `impact` (L3-2) | 外側 | 0.207 | 0.213 |
| `render` | 外側 | 0.297 | 0.306 |
| **合計** | | **11.739** | **18.096** |

**外側の合計は 1.528s (fresh) / 1.900s (resident)。** サーバを立てて使い回す運用では Lean 側が
0.707s まで落ちるので**外側が 73% を占める**。そこでの律速は**レンダリング (0.30s) ではなく
増分ロジックの IR 全読み**で、7h の後も **5 回**残っている (→ §5.6)。**セッション間で構成が
動く** — この `serveStart` 14.6s は 7g の 3.71s より重い。**過去の総時間と並べない。**

旧構成 (L3-1 のラウンドが入る前) の値も残す: 1 モジュール変更で **3.30〜4.39 秒** = 同一
セッションのフル生成 17.07 秒の **3.9〜5.2 分の 1**、うち**環境の取得が 81.8%** で**本来の仕事は
0.05 秒 = 1.4%**【実測】。**差分検出 (無変更) は 0.080 秒** (Lean 不使用、台帳 6.9 KB)。
**理論値 0.03 秒は否定された** — 常駐でも届かない (要求あたり 0.035〜0.088 秒 → §5.1)。

**現行との比較は倍率を書けない。** doc-gen4 の増分 5.21 秒 (実測) は**HTML を再生成していない**
(stale) 上に `lake build` を含み、こちらは HTML を更新して `lake build` を含まない。**同じ仕事ではない。**

#### `lake build` を足した端から端まで (増分 3 で実測)

`lake build` は lean-doc の外だが**編集 → プレビューの臨界パス上にある**。対象リポジトリの複製
(APFS clonefile) を作って実測した (→ [検証ログ](verification-log.md) 段階 5 増分 3、
`benchmarks/results/stage5c-olean-propagation-summary.txt`)。

| 変更 | 再ビルドされたモジュール | `lake build` | doc 側の増分 | `lake build` の割合 |
|---|---:|---:|---:|---:|
| 無変更 | 0 | **2.40s** | 0.080s | 96.8% |
| 直接 importer 2 (best case に近い) | 3 | **12.40〜12.73s** | 3.30〜4.39s | **74〜79%** |
| 直接 importer 54 / 推移 126 | 127 | **237〜243s** | 3.30〜4.39s | **98.2%** |

すべて**実測** (warm、n=5 / n=8 / n=2)。壁時計は page cache で 2.2 倍動くが CPU 時間は安定。

**この表は §6.5 の主張の分母を変える** — 3.30〜4.39 秒は doc 生成だけの時間で、利用者の体感
ではない。**倍率を書くときはどちらの分母かを必ず明示する。doc 側をゼロにしても端から端は
12.4 秒より速くならず、fan-in が大きければ 4 分待つ。** 効くのは常駐化ではなく、Lean のビルドを
待たずに出す設計 (→ §8。段階 6d でその選択肢は 2 つに絞れた)。

### 6.6 この見積もりが外れるとしたら

**残る筋は 1 つだけ。** 他の 3 つ (意味解析が減らせない / 常駐が成立しない / HTML 生成の

|---|---|
| **page cache が warm でない** | 仮定ではなく**実測済みの変動要因**で、環境ロードが 2.5 秒から 13.6 秒に伸びる。先読みで 6.9 秒までは戻せる (実測) が **warm の 2.5 秒には戻らない**。**CI がどちら側に落ちるかは配置で決まる** (→ §3)。**warm の数字だけを出すのは誇大**なので両方を併記する |

## 8. 未解決の問い

**決着した問いはここから消して §5 / §7 / §9 に移した** — 常駐の寿命 → §5.1、増分の影響集合 →
§5.5、**revision をバイトに埋めるか → 外すと決定** (§5.5 + §5.6、段階 8 で注入の実装形まで実測)、
**プレビューモード → 持たないと決定** (§9)、**検索 → 自パッケージのみでスコープ内** (§5.6)。
経緯は git と [検証ログ](verification-log.md) が持つ。

| 問い | 分かっていること / 残っていること |
|---|---|
| **cold な環境ロード (13 秒) をどう扱うか** | **決着に近い (→ §3)。「CI は毎回 cold」は否定された**が、効いていたのは `cache get` の常駐率ではなく **`lake build` が import の hot set を読むこと**【Linux 実測】。**同じジョブなら 2.61 秒 / 別ジョブなら 20〜89 秒 = 8〜34 倍**なので、**第一の打ち手は配置** (doc 生成をビルドと同じジョブに置く)。**Lean の速度ではなく I/O の問題。残るのは 3 つ**: (a) **先読みの集合を「実際に読まれる分」まで絞れるか** (残留集合で絞った版は取りこぼして逆効果。読み取り追跡が要る → §3)、(b) 分割配置を強いられる場合の **IR キャッシュ** (= 段階 5 と同じ機構)、(c) 完全版の抽出器でも同じ差が出るか (作業集合が 16 GiB に収まらず macOS では測れなかった)。**IR キャッシュには前提が 1 つ増えた** — olean の内容ハッシュは**チェックアウト先の絶対パスに依存する** (429/432 モジュール、実測 → §5.5)。CI と開発機でパスが違えば全滅するので、鍵をパス非依存にしない限り CI 側でのキャッシュヒットは 0 |
| **意味解析 (実測 10.58 秒) を減らせるか** | **半分決着 (段階 7d)** — 筋は算法でも生成物の削減でもなく**並列化**だった。`--jobs 4` で **10.79 → 3.34 秒 (3.23×)、IR は byte 一致**。**内訳は delaborate 55.3% / format 15.4% / タグ 12.7%** で、分布はほぼ一様 (上位 1% で 6.97%) なので**外れ値を潰す筋は無い**。equation を切る筋は却下 (並列後は −3.4% しか効かず再現率が 2.4 pt 落ちる)。**残るのは CPU 時間そのもの** — instructions は +1.0% しか動いておらず、4 スレッドで頭打ち (M1 の性能コア 4 本 + cycles +66% のストール) |
| **宣言の所有モジュールをどう決めるか** | 同名で複数の olean に焼かれる自動生成補題があり (実測 25 件)、索引方式では所有が一意に決まらない。「最初に定義したモジュールが勝つ」(現行 doc-gen4 の暗黙の規則) を踏襲するか否か。ページ配置とリンク先が変わる |
| **依存パッケージの写像をどう配布するか** | **実装して数字が出た (段階 7c)** — `declaration-data.bmp` から導いた索引は **8.51 MB / gzip 1.33 MB、作る 0.415 秒 / 読む 0.076 秒**、宣言 258,760【実測】。これで docstring の autolink が **410,114 B ぶん byte 一致**し、過剰アンカーは 0。**残っていた 1 点は決着した (2026-08-11)** — 公開サイトに**ファイルはある** (`…/mathlib4_docs/declarations/declaration-data.bmp` が 200 / 66,418,003 B)【実測】が、**バージョン対応は取れない**: 公開サイトは **Lean 4.33.0 / mathlib `c3a9a08f`**、対象は **v4.31.0 / `fabf563a7c`** で **2 マイナー版ずれる**【実測】。バージョン別アーカイブは無い【仮定】。→ **生成側で作る。**「(名前, モジュール) の 2 列で足りる」は実測済みなので、抽出器が既にロードしている環境の走査 (490,171 定数 = 0.62 秒【実測】) で作れる**はず【未検証。実装計画 V1】** |
| **`_private.` 名のリンクをどうするか** | 除外 / 親に落とす / モジュールページのどれを取るかは未決 (実測 8 名 → §5.3) |
| **docstring 内のリンクをどう解決するか** | doc-gen4 は別経路 (`Output/DocString.lean`) で処理していて署名のタグ付けを通らないので、別の仕組みになる可能性が高い。**規模は実測できた** (段階 4 増分 1): 348 ページの内部アンカー 80,743 件のうち IR の名前集合 (5,300 エントリ) で解決できないのは **293 件 / 188 種 = 0.36%** で、**その全部が docstring 内** (署名と equations の取りこぼしは 0)。要るのは「署名に出てこない名前も引ける索引」であって、写像の作り方の問題ではない |
| **Lean のバージョン差をどこで吸収するか** | IR スキーマとの対応付けの方針。未着手 |

## 10. 補足 — 上流への還元

本プロジェクトを進めることと知見を上流に投げることは排他ではない。3 つある。

| | 内容 |
|---|---|
| **バッチ化** | 計測で使った「複数モジュールを 1 プロセスで抽出する」コマンドは、doc-gen4 の内部 API が**既に複数モジュールを受け取れる**ため CLI の定義を変えるだけで実現できた。つまり §6.4(a) の 76 倍のうちバッチ化による分は、doc-gen4 本体への小さな変更としても成立しうる |
| **`scoped notation`** | doc-gen4 は**パッケージ自身の `scoped notation` を出力できていない** (段階 2 で実測)。delaborator が `ScopedEnvExtension` にあり import だけでは未活性なのに `Lean.activateScoped` を呼んでいないため、`H(μ; X)` や `≐` と書けるはずの署名が `entropy μ X` / `DotEq a a` と出る。**呼ぶだけで直り、コストは意味解析 +6% (実測)** |
| **`collectTactics` の 16.7 秒** | **1 行の直し方で消える** (→ §5.2) — `env.header.moduleNames` をループの外に括り出し、`allTacticDocs` を 1 回だけ呼ぶ。`moduleNames` が `def` であることは Lean core 側の API の形の問題なので、**同じ罠を踏んでいるコードは doc-gen4 以外にもありうる** |
