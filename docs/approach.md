## 1. 何を作るか

Mathlib に依存する Lean パッケージが、**自分のモジュールだけを短時間でドキュメント化できる**
ドキュメント基盤。依存ライブラリは再生成せず公開済みドキュメントへリンクする。主眼は HTML を
出すことではなく、**Lean の意味情報を再利用可能な形で抽出し、必要な部分だけを高速に更新できる
こと**。副産物として doc-gen4 が**出力できていないパッケージ自身の `scoped notation`** も出る
(実測 → §10) — 読者が実際に書く記法で署名が読めることは生成速度と同じくらい価値に効く。

## 2. 背景 — 計測が示したこと

doc-gen4 を計装して Mathlib 依存プロジェクト (432 モジュール) の生成を実測した (**この節はすべて
実測** → [`benchmarks/doc-gen4-report.md`](../benchmarks/doc-gen4-report.md))。コストは 3 層に
分かれ、どれも「ドキュメントを作る仕事」そのものではなかった。

| 層 | 支配率 | 実際に起きていること |
|---|---:|---|
| 環境ロード | **85.0%** | モジュールごとにプロセスを起動し、import closure 全体を読み直す |
| 意味解析 | 4.6% | 本来の仕事。宣言の型を pretty print し equation を生成する |
| 走査オーバーヘッド | 8.8% | 環境の全定数を舐めて、該当しないものを捨てる |

実ビルドでは **8.9 億回の定数走査に対して該当は 0.032%**、走査して捨てるコスト (1,195 秒) が
本来の意味解析 (631 秒) の約 2 倍あった。HTML 生成も生成 CPU の **66〜78% が DB からの読み直し**で
レンダリング自体は 9.2%。**増分性は一切ない** (無変更の 2 回目も 46.25 秒 → 43.91 秒)。

### 決定的だった 1 つの実験

doc-gen4 に「複数モジュールを 1 プロセスで抽出する」コマンドを足し、同一の 432 モジュールを
両方式で処理した。**モジュールごとに 1 プロセス (現行) が 1,076 秒 (うち `importModules`
908.6 秒 = 88.8%)、1 プロセスでまとめて 31.9 秒 (同 2.6 秒) = 34 倍**【どちらも全数の warm 実測、
外挿なし、同じ日・同じ page cache 状態】。**分母は「同じ 432 モジュールを抽出する仕事」。**
アルゴリズムの改良ではなく、同じ依存ライブラリを 432 回読み直すのをやめただけで生じる —
**432 モジュールぶんの import closure をまとめて読んでも 1 モジュールぶん (逐次時 2.10 秒) と
ほとんど変わらない** (closure が Mathlib に支配されているため)。**cold と warm を混ぜないこと。**

## 3. 仮説

> Lean の意味情報をパッケージ単位でまとめて抽出し、依存ライブラリを外部参照にすれば、
> downstream ライブラリのドキュメント生成時間を**依存ライブラリの規模から大きく切り離せる**。

計測はこの仮説を支持している。ただし完全には切り離せない — 自パッケージの型を正しく
pretty print するには Mathlib の `Environment` が要り、そのロードは残る。
**これが新設計の床**であり、それをどう扱うかが設計の中心的な論点になる。

床の大きさは **page cache の状態で 5 倍動く。warm で約 2.5 秒、cold で 10〜13 秒**
(実測 → 検証ログ 段階 1)。warm では壁時計 ≒ CPU 時間で、差はすべて olean の mmap ページイン待ち。
したがって「床をどう扱うか」は最初から 2 つの別問題である。

- **ローカル (warm)**: 2.5 秒。1 モジュールだけの再抽出ならこれより小さい (`importModules`
  0.80〜2.96 秒、実測・段階 5) が `lake env` の 0.96 秒が別にかかる (→ §6.5)。
  **常駐で消せるが、消さなくても致命的ではない。**
- **CI**: **配置で決まる。常駐は効かない。**

**「CI は常に cold」は否定された。効いていたのは `cache get` ではなく `lake build`**【Linux 実測、
2026-08-10。`ubuntu-latest` / 2 コア / 7.75 GiB】 — doc 生成が見るのは `cache get` 直後ではなく
**ビルド後の page cache** で、**同じジョブに置けば `importModules` 2.610 秒 (macOS warm と同じ) /
major fault 26、別ジョブでビルド済み olean を復元すると 20.4〜89.2 秒 / fault 11,949〜30,424**。
**間は 8〜27 倍。設計上の推奨が出た — doc 生成はビルドと同じジョブに置く。**
効くのは**割合ではなく「どのページか」** (`lake build` が import の要るページを読む) —
常駐率は `cache get` 後 60.4% → ビルド後 **40.3%** と下がるのに fault はほぼ 0 で、
**`cache get` 直後の常駐率は代理指標ですらなかった** (n=2、容量律速)。**cold 側は
`ubuntu-latest` でも 2 実体に割れる** (readahead とストレージの差とみられる、未検証。**n=2**)。

**先読みは「効くこともある」打ち手** — **ランナー実体で答えが割れる**【すべて実測。実体別の内訳は
検証ログ】。読ませる集合は **`.lean` ヘッダから作った import closure** (17,199 ファイル / 4.14 GB)。
**macOS/M1 は壁時計 18.03 → 10.44 秒**だが、**Linux の速い実体では −4%、遅い実体では −23〜−44%**。
**遅い実体では直列な demand fault を 16 並列の読みに置き換える価値が大きく、速い実体では closure
4.14 GB のうち要らない約 1.6 GB が節約を食い潰す** (ディスク 190〜220 MB/s = macOS の 1/11)。
**実体は選べないので期待値としては効くが保証はない。「集合を絞れば効くか」は未検証** (絞った版は
必要分を取りこぼしていて検証になっていない)。**第一の打ち手は配置** (同じジョブ = 2.61 秒)。

## 4. Approach

> **Lean プロセスは「意味情報を吐く抽出器」に徹し、1 つの環境を長く使い回す。**
> 抽出したものはモジュール単位の中間表現 (IR) として永続化し、
> HTML・検索索引・その他の出力はすべて Lean の外側で IR から作る。
> 依存パッケージについては IR を作らず、「宣言名 → モジュール → URL」の写像だけを持つ。

変えるのは次の 3 つの境界。**どれも独立に効き、順に適用でき、1 つ失敗しても残りは成立する。**
(1) **プロセスの境界**: モジュールごと → パッケージごと (あるいは常駐)。(2) **抽出の範囲**:
環境の全定数 → 自パッケージの宣言のみ。(3) **Lean と出力の境界**: Lean が HTML まで作る →
Lean は IR まで、出力は外側。

## 5. 設計の柱

### 5.1 1 環境・長寿命プロセス

抽出は「モジュール 1 個 = プロセス 1 個」をやめ、対象パッケージを 1 度ロードしてまとめて
処理する。これが実測 34 倍 (§2) の正体で、単独で最大の効果を持つ。

**常駐は実装・実測して決着した** (`--serve`、段階 6 + 6a + 7g。要求あたりの数字は §6.5)。
**寿命の上限は「自分が import した olean を書き換えるビルドまで」**【段階 6a、実測】 — Lean には
環境から 1 モジュールだけ差し替える手段が無く、プロセスは死なない (`lake build` を生き延び
0.151 秒で応答した) が、**参照の所有者を環境から引く**ので移動した名前に古い所有者を返す。
**「ラウンド 2 以降なら安全」は誤り** — ラウンド 2 はまさにその所有者列を直すためにあり、編集前
環境では 439 ページ中 1 ページが誤る。**寿命の内側では持つ** (600 要求で IR は byte 一致のまま、
RSS 不動【段階 7g、実測】)。

**正しい形は「`lake build` の後にサーバを 1 台立て、全ラウンドを任せ、終わったら落とす」**。
自動起動・自動停止まで配線して **439/439 byte 一致のまま 7.968 → 6.668 秒 (−16.3%、`--jobs 1`) /
7.894 → 6.509 秒 (−17.5%、`--jobs 4`)**【段階 7g、実測。起動・停止は計測の内側。**6a の
7.940 / 6.168 秒は抽出器もレンダラも別物なので並べない**】。**取り分は `--jobs` でほぼ動かない**
— 常駐が消すのは**ラウンドごとの `importModules`** (1.819 + 1.766 秒) とプロセス起動 2 回分で、
増分の `analyze` は小さいから。**jobs が効くのはフル再抽出**で **−23.4% (j1) → −43.3% (j4)**
【実測。消える `importModules` は並列化されないので分母だけが縮む】。**分岐点は 2 ラウンド**
【段階 6a】。臨界パスの 74〜98% は `lake build` なので、端から端で見た効き幅は小さいまま。

副次的な効果として、**メモリ律速が消える**。現行はプロセスごとに 2〜3 GB の環境を持つため 8 並列
で RSS 21.7 GB (物理 16 GB) に達しスワップし【実測】、CPU コアを増やしても頭打ちになる構造だった。
**この取り分は段階 7d で現金化した** — 1 環境の中で宣言を 4 スレッドに割ると意味解析が **3.23 倍**
になり **IR は byte 一致**、追加メモリはほぼ要らない (→ §6.1)。**同じ「4 並列」でもプロセス並列とは
意味が違う。**待機中の常駐 1 台は **0.55〜0.62 GB**、**3.27〜3.37 GB は要求処理中のピーク**で
常時占有ではない【段階 7g、実測】。

### 5.2 走査ではなく索引で宣言を引く

「環境の全定数を舐めて、対象モジュールのものだけ拾う」のをやめ、モジュールから宣言を引く方向に
変える。5.1 とは独立に効く — バッチ化しても走査は 1 回分残るため。**実装と正しさは検証済み**
(→ 検証ログ 段階 1): 索引方式と走査方式は同じ 5,123 宣言を返し、時間は **0.0022 秒 対 0.62 秒**
【実測】。ただし**バッチ 1 回あたりの走査コストは当初の見積もり 4.45 秒より 1 桁小さい** (cold の
ページインを走査コストと取り違えた値。warm では 0.36 秒) ので、**この柱の価値は「時間が消える」
ことではなく、モジュール数に比例する走査を構造から無くすこと**に移った。

索引方式に固有の論点が 1 つ: 複数モジュールの olean に同名で焼かれる自動生成補題があり、
**宣言の所有モジュールが一意に決まらない** (実測 25 件)。明示的に決める (→ 実装計画 §4 決定 5)。同じ性質の問題が
タクティク収集にもあり、**バッチ化すると 16.7 秒 (全体の 54%) の最大項に浮上するが、1 回列挙して
振り分ける実装で 0.011 秒**【実測】。**正体は見立てと違った** — 78% は
`EnvironmentHeader.moduleNames` が**フィールドではなく `def`** で、呼ぶたびに import closure と
同じ長さ (6,021 要素) の配列を作り直していたこと。**第 3 の因子は呼び出し側から見えない。**
ゆえにこの柱の一般形は一段強い:

> **1 モジュールの処理で、import closure のサイズに比例するものに触らない。**
> 走査でなくても、配列 1 本の構築でも、内側のループに入れば同じことになる。

### 5.3 依存パッケージは外部参照にする

HTML 生成が依存パッケージについて実際に必要としているのは**「宣言名 → モジュール名 → URL」の
写像だけ**だった (型も docstring も equation も不要)。したがって依存については IR を作らず、
この写像だけを持ち、公開ドキュメントへリンクする。これが「ゼロからサイトを構築する」ケースで
桁違いの差を生む (→ §6.4(b))。**検証段階 3 で実測に置き換わった** (348/432 モジュールの範囲):

- **写像だけで doc-gen4 と同じ URL 文字列が出る** — 共通 39,298 ペアの **99.992%** が href 完全
  一致 (未一致 3 はリンクしてはいけない再帰子で写像はそれを出さない)、**取りこぼしは 0**
- 写像の実サイズは **8.51 MB / gzip 1.33 MB、作る 0.415 秒 / 読む 0.076 秒、宣言 258,760**
  【段階 7c、実測】。必要な列は (名前, モジュール) の 2 列で `kind` は要らない。**blacklist は
  写像から復元できる** — 「写像に載っている名前だけリンクする」方式は doc-gen4 の dead link
  (実測 3 本) を出さない

URL 規則は `("../" × (ページのモジュール成分数 - 1)) + "./" + モジュールパス + ".html#" + 名前`。
**IR には絶対的な識別子を持ち、相対化は出力時に行う** (→ §5.6)。**残る欠落**: 自パッケージの
`_private.` 名は素朴に URL を出すと dead になる (実測 8 名 → 実装計画 §4 決定 5)。なお**リンク解決に必要な
データと、型を pretty print するために環境が必要なことは別問題** — 後者 (§3 の床) は残る。

### 5.4 中間表現の粒度はモジュール単位

現行 doc-gen4 は宣言ごとに DB の行を分割したため、レンダリング時に N+1 クエリで再構築する羽目に
なり、生成 CPU の 66〜78% がそこに消えている。**読みも書きもモジュール単位なら、モジュール 1 個 =
1 まとまり + 索引が正しい粒度。** 教訓は「規模が来たら SQLite」ではなく**アクセスパターンに合わない
粒度で分割すると逆効果**、ということ。格納形式 (JSON / SQLite / バイナリ) の選択より粒度が先に来る。

IR にはスキーマバージョンを持たせ、キャッシュキーには少なくとも Lean バージョン・抽出器
バージョン・IR スキーマバージョン・olean ハッシュを含める (olean ハッシュだけでは不足 —
pretty printer の出力が Lean バージョンに依存するため)。実装形は「**モジュールごとの olean
ハッシュ + パッケージ 1 つぶんの環境キー**」で、後者は判断点 3 で不完全と分かって 2 分割した
(→ §5.5 の L1)。

**この粒度は実測で成立した** — **現行の schema 4 (位置つきタグ入り) で 15.28 MiB / 書き込み
0.623 秒 / 読み出し 0.100 秒 = 環境ロードの床の 4.0%**【実測 → §6.1】。内容ハッシュは書き込みの
1.2% で、持つ代償はない。**世代をまたいで引用するときは構成を揃えること** (タグの有無で容積も
書き込みも動く)。

### 5.5 増分性を「入力側」と「出力側」で別々に設計する

現行はここが両方向に壊れていた — **取りこぼし** (マーカーファイルが空なので内容が変わっても
ハッシュが変わらず HTML が再生成されない) と **無駄** (走れば変更の有無に関わらず全モジュール)。
原因はキャッシュ無効化とページ再生成という別々の関心を 1 つの仕組みに載せたこと。

> **「IR のモジュール単位ハッシュを単一の真実にする」当初案は否定された (判断点 3)** — 5 命題
> すべてが実測で破れた (→ [検証ログ](verification-log.md) 段階 5 増分 2)。否定されたのは**その
> 構造**であって増分生成そのものではない。以下の 3 層が見直し案で、**増分 4〜7 で全層が実装され、
> 本物の移動と本物の削除を `lake build` ごと回してフルビルドと byte 一致した。**

**単一の真実は「役割が 1 つ」ではなく「役割ごとに 1 つ」だった** — 問う時点が違う。**入力側**
(どのモジュールを**再抽出**するか) はモジュールの `.olean` (3 分割なら 3 つとも) を抽出の**前**に
(Lean 不要)、**出力側** (どのページを**再生成**するか) はモジュールの IR を抽出の**後**に見る。
`.lean` ソースは早すぎ (証明中の空白のように olean に届かない変更を拾い、依存の再ビルドで olean に
入った変更を落とす)、IR は遅すぎる (計算するには省きたい抽出そのものが要る)。**抽出器が見られる
のは olean だけ**なので入力側は olean が正しい。**Lake が既に内容ハッシュを `<file>.olean.hash` に
書いている**ので、台帳は 227 MB ではなく 6.9 KB を読めば済む (0.080 秒)。

#### 3 層 (判断点 3 を受けた設計、増分 4〜7 で全層を実装・実測)

| 層 | 何を見るか | 何を決めるか | 変わったときの影響範囲 |
|---|---|---|---|
| **L1 グローバル鍵** | モジュールに属さない入力 | 全無効化するか | **全部** |
| **L2 モジュール単位ハッシュ** | 各モジュールの `.olean` | 再抽出集合の**核** | そのモジュール |
| **L3 導出の依存** | 名前の所有権 / 全域写像 / 全域索引 | L2 の核を**広げる** | import では閉じない |

**L1 は 1 つの鍵ではなく 2 つ**【実測で確定、増分 4】。振り分けの基準は「出力のバイトを変えるか」
ではなく (両方変える)、「**IR を変えうるか** = 答えるのに Lean が要るか」。`extractKey` (toolchain /
manifest / 抽出器 id とその構成 (`--open`) / IR schema / 生成器 id) が変われば**全再抽出**、
`renderKey` (レンダラ id / `--source-url`) が変われば**再抽出ゼロ・再レンダリング全部**。分けないと
二択が両方まずい: 入れなければ 432 ページが黙って stale、単一の鍵に入れれば **`--source-url` の
変化だけで 432 モジュール全再抽出**。**分割の効果は 18.39 → 1.34 秒 = 13.7 倍**、追加コストは
**+0.3 ms** でドリフト以下【実測】。鍵の比較は**和集合**で行う — 片側にしか無い鍵も変化と数え、
**黙って過少にレンダリングしない**。

**L2 の鍵は olean の内容ハッシュのままでよいが、そのままでは移送できない** — olean には**ソースの
絶対パスが 429/432 モジュールで埋まっている**【実測。Mathlib の style linter のログを持つ環境拡張
`lintLogExt` がパス入りの警告文を保存している】。**チェックアウト先が違うだけでハッシュが全滅する**
ので、CI と開発機で IR キャッシュを共有するには鍵をパス非依存にする必要がある。**モジュール一覧は
ソースの glob で作る** — **`.lake/build` を走査してはいけない**。Lake は孤児 olean を消さないので
432 モジュールに対し olean は 1,090 個、**659 個が幽霊**【実測】。**削除経路は実装済み** (台帳・IR・
ページの 3 箇所、増分 6) — 台帳は作り直しで足り (`build` は `check` と同コスト)、**ページは消す係が
要る** (レンダラは書くだけ。複製上の落とし穴は `experiments/stage5e/README.md`)。

**L3 が §5.5 に無かった穴で、3 つある** (いずれも実装済み):

1. **名前の所有権** — 参照は `(定義モジュール, 名前)` で持つので、宣言が移動すると参照側の IR が
   腐る。**これは再生成ではなく再抽出の問題**で、影響集合をどれだけ広げても直らない。規則は
   「L2 の核から**そのモジュールが定義していた名前の集合の差分**を取り、その名前を `refs` に持つ
   モジュールを**再抽出集合に足す**」。本物の移動 + `lake build` で、無しは 433 ページ中 1 ページが
   **リンク切れ**、有りは**フルビルドと 433/433 byte 一致**【実測】。**L2 が参照側を拾うかは当てに
   できない** (4 つのうち 1 つは olean が動かなかった) — 拾えるかは Lean の直列化の都合であって
   依存構造の性質ではない。**import 閉包へ広げる必要は無い。再抽出はラウンド構造になる** (移動を
   知るには移動元の新しい IR が要る) が、**2 ラウンドで不動点**でこれは**構造的な上限**【段階 6c】
   (ラウンド 2 以降は olean が動いていないので宣言集合も動かない)。**穴は 1 つ**: その集合は
   `isBlackListed` で濾したもので述語が環境を参照するため、**反転させる変更があればラウンド 3 が
   出る**。`--max-rounds` は残す。**効く範囲は「移動する名前が印字署名に出るか」で決まる**【実測】 —
   `abbrev` は必須 (無しだと最大 30 ページ誤り)、`instance` や `@[simp]` には無関係 (救うのは L3-3)。
2. **全域写像** — docstring の autolink は名前 → 定義モジュールの全域写像を引くので**import で
   閉じない**【実測: 逆向きの推移的 import 閉包でも 3〜141 ページ取りこぼす】。**失敗は双方向** —
   モジュールを 1 つ削除すると全域写像が 533→527 に減り、**削除と無関係な LZ78 のページに、行き先の
   消えたリンクが残った** (繋いでいるのは全域写像だけ)。**増分 7 で閉じた** — 規則は「**全域写像の
   差分に出た名前を docstring に含むページ**を再生成集合に足す」で、走査であって推測ではなく逆索引の
   常備も要らない。実測では 58 名の差分から**ちょうど 1 ページ**を名指しし (過剰近似なし)、削除ケース
   は **437/437 byte 一致**。**写像は自宣言だけでは足りない** (効いたのは依存側の名前) し、走査の
   単位も code span ではなく `autoLinkInline` と同じ空白分割。**どちらも間違えると外からは「0 ページ」
   に見える。**
3. **全モジュール横断の後処理** (検索索引・ナビゲーション・相互参照) — IR から生成でき
   **合計 1.88 MB**【実測】(**doc-gen4 の 38.6 MB は依存木全体 258,760 宣言の値でこちらの数字
   ではない**)。`tactics.html` だけは自パッケージの関数ではない (tactic docstring は環境側にあり
   432 モジュールで 0)。**この層は正しさにも効いている**【段階 6c】 — instance 一覧はページの
   バイトに無く `declaration-data.bmp` からブラウザが埋めるので、**instance の移動が正しく出るのは
   「全域成果物を作り直す」から**。3 層でいちばん安い層が最も広い網だった。**「増分化する価値なし」
   (増分 7) は段階 7h で否定された** — 消えるのは IR 全読み 1 回ではなく **`build` の全読み +
   `delta` の全走査 + プロセス 1 つ**。`contentHash` を鍵にした 842 KB のキャッシュで
   **0.4527 → 0.1257 秒 (fresh) / 0.4470 → 0.1461 秒 (resident)**、6 成果物もサイト 439 ファイルも
   byte 一致【実測】。**残る IR 全読みは 5 回** (ownership・merge ×2・impact・render) で、そちらが大きい。

**「影響集合の mode」という枠組み自体が的を外していた**のが判断点 3 のいちばん構造的な発見 —
`self` / `referrers` / `importers` は**描画対象しか決めない**ので再抽出が要る種類の stale (L3-1) には
原理的に効かない。**再抽出集合と再生成集合は別々に導く。** rev をバイトに焼く前提では「mode は常に
`all` に潰れる」だったが、**§5.6 でその前提を外した**ので `all` は立たず **0 ページ**になる【実測】
(**高いのはレンダリングではなく抽出** — rev を焼く構成でも 432 ページ全部で 0.87 秒)。

**空の再生成集合の落とし穴は、rev を外した今、常時通る経路になった** (段階 6b で発見・修正済み) —
`render.ts` は `--only` が無いと全モジュールを描くので、空集合から `--only` を 0 個渡すと **433 ページ
全部を再生成する**。rev を焼いていた間はコミットが必ず `all` を立てたので誰も来なかった
(移設側の扱いは[実装計画](implementation-plan.md) §5)。

### 5.6 出力は IR から作る (Lean の外側)

HTML・検索索引・JSON API・宣言グラフ・リンク切れ検査は、すべて IR を入力とする独立した消費者に
する。**HTML の再生成に Lean の起動が要らない**ことが、この分離が成立している証拠になる。
Lean を起動しない別プロセスが 432 モジュール分の IR を **0.100 秒**で読み切れる
(15.28 MiB = 環境ロードの床の 4.0%)【実測。読み出しは schema 2 → 4 で ±0 → §5.4】。

**IR は参照定数を集合でなく位置つきで持つ必要がある** (段階 4 増分 1)。doc-gen4 の署名内アンカー
72,421 件のうち **44.0% は印字トークンと定数名に字面の関係が無く** (`ℕ`→`Nat`)、平文 + 集合からの
再構成は上限でも recall 56% / 実測 51.7%。ページのバイトの **71.1% が署名の描画**なので、ここを
落とすと「同じ仕事」ではなくなる。逆に**あて先の解決 (名前 → モジュール) は集合で足りている**
(取りこぼし 0.36%、全部 docstring 側)。**ただしこの「集合」は全域写像で増分では閉じない** —
判断点 3 が破れたのはまさにこの docstring 側 (§5.5 L3-2)。

**外側の律速はレンダリングではなく IR の全読み** (レンダリング自体は生成 CPU の 9.2%) —
増分パイプラインは全読みを **5 回**残していて (7h が 7 回から 2 回削った)、1 回のコストは
**432 モジュールで 0.105 秒 / Mathlib 8,169 モジュール (542 MB) で 3.18 秒**【実測】。
**規模にほぼ線形**なので大きなパッケージでは外側が支配的になる。次に効くのは言語ではなく
**7h と同じ `contentHash` キャッシュを残る 5 回に当てること** (未着手 → 実装計画 V2)。

#### 出力契約 — revision はページのバイトに入れない【決定】

rev を焼くとコミットのたびにページ内 4,992〜4,993 か所が変わり**全ページが無効**になる。
`{{SOURCE_URL}}` を焼いて**後から注入する**形を採る: 再生成 433 → **0 ページ**、パイプライン合計
1.6227 → 0.6441 秒 (**−60.3%**)、ページは 399,440 B 小さくなる【段階 6b / 7e-rev、実測】。
`--source-url` に定数トークンを渡すだけなので**実装コストはゼロ**で、renderKey からも rev が外れる。

**代償「HTML 単体で完結しなくなる」は許容する** — このサイトは既に `declaration-data.bmp` を
ブラウザが読んで instance 一覧を埋めているので、**静的ファイル群で完結する形は元々の設計**。
ただし **注入が走らなければ 4,992 本のリンクが死に、死に方は無反応ではなく同一オリジンの 404**。
**採点は必ず注入後の木に対して回す** — プレースホルダのまま採点すると **−3.1103 pt** ずれる
(gh_link / nav_gh がきっかり 0.0% になる)【いずれも実測。ブラウザでも確認済み】。

**注入は 2 方式あり、どちらも成立する。製品は配信時 (ビルド時) 置換を採る** — **0.1552 秒 /
432 ファイル・制約なし** (HTML が届く前に終わっている)。**ブラウザで JS 注入**は **1 ページ最悪
0.80 ms** (p50 0.10 ms) だが**制約を 3 つ負う**: (1) `.gh_link a[href]` の書き換えが `jump-src.js`
の `DOMContentLoaded` ハンドラより前という順序制約、(2) **rev の供給元がページ外の共通 1 ファイルに
限られ** (ページに埋めると rev がバイトに戻って目的が消える) **配信側に鮮度ヘッダが要る**、
(3) 壊れ方が `?jump=src` 付きのディープリンクに出る。しかも**実測は Chrome 151 のみ**で他エンジン
は仮定【段階 8 で実測、決定 2026-08-11 → [実装計画](implementation-plan.md) §4 決定 3】。
**0.1552 秒で制約ゼロの側を選ばない理由が無い。** 数字は**選択肢の保存**として検証ログに残す
(静的ホスティングを使えない配信形態が出たら成立する形がある)。

#### 検索は組み込み・自パッケージのみ【決定】

doc-gen4 の組み込み検索は `declaration-data.bmp` を丸ごと落として全件を線形走査する。**依存を
含めない**と決めたので、この対象の索引は **4,750 宣言 / 406 モジュール / kind 6 種**、導出形式
(モジュールと kind を配列 + 整数 ID) で **361,466 B / gzip 45,780 B**【実測】。この規模なら
全件ダウンロードも線形走査も問題にならず、doc-gen4 が
[#133](https://github.com/leanprover/doc-gen4/issues/133) で切っている IndexedDB キャッシュも
要らない。**`docLink` は (モジュール, 名前) から 258,760/258,760 = 100% 復元できる**【実測】ので
索引に持たない。**落とし穴**: lean-doc の kind 語彙は doc-gen4 と違う (`definition`/`constructor`
対 `def`/`ctor`) ので、doc-gen4 の `search.html` を流用すると**種別フィルタが黙って全部外れる**。

#### 実装言語は Rust【決定】

抽出器は Lean、**その外側 (IR 消費・レンダリング・増分・検索索引) は Rust**。
**選定理由は速度ではない** — レンダリングは生成 CPU の 9.2% で、§6.4 の倍率は「やらなくてよい
仕事をやめた」ことによる。**速度の主張と言語を因果で結ばないこと。** 決め手は配布と、対外的に
「高速を謳うなら Rust」という期待に合わせる製品判断。**技術的な利得が 1 つ**: doc-gen4 の
CommonMark は **md4c (C)** で、TS にはバイト一致する実装が無く自前のサブセットを書いていた。
Rust なら md4c を FFI で直接リンクできる — **その C ソースは MD4Lean 経由で既に手元にある**が、
**FFI が消すのは自前サブセット 594 行だけで autolink 解決系 153 行は残る**【いずれも実測】。
**移設対象は約 4,250 行 + シェル約 1,100 行**、**完了条件は「Rust 版が 439/439 byte 一致」**
(オラクル `coverage.ts` は Deno のまま製品外)。**内訳・移設の順序・各ゲートは
[`implementation-plan.md`](implementation-plan.md) が持つ** — この文書は書かない。

## 6. 性能

**抽出・IR 永続化・HTML 生成・増分はすべて実測に置き換わった** (検証段階 1〜5。外れる筋は §6.6)。
**残る非実測は 2 つ** — (1) cold 合計は stage1 抽出器からの**外挿** (→ §6.3)、(2)「CI が cold 側
かどうか」は**仮定** (→ §3、Linux 未測定)。**どの数字が実測 / 外挿 / 仮定かは行ごとに明示する。**
**そしてこの節は速度の節である** — 増分の**正しさ**は増分 4〜7 で閉じた (→ §5.5) が、
**§6.5 の秒数は正しさが閉じる前の構成のもの。**

### 6.1 抽出フェーズ + IR 永続化 (自パッケージ 432 モジュール) — 実測済み

**基準は warm な page cache での実測** (旧版は cold を warm と取り違えていた → 検証ログ 段階 1)。

| 項目 | 現行 doc-gen4 (warm) | lean-doc | 根拠 |
|---|---:|---:|---|
| 環境ロード | 2.60s | **2.52s** | 実測。削減対象外 (§3 の床) |
| タクティク収集 + モジュール docs | 16.64s | **0.011s** | 実測。全体 1 回列挙 + closure 依存の排除 (§5.2) |
| 走査 (該当外) | 0.36s | **0.002s** | 実測。索引方式 |
| 意味解析 (equations + 参照定数 + 位置つきタグ) | 10.51s | **10.79s** → **3.34s** (`--jobs 4`) | 実測。内訳は delaborate 55.3% / format 15.4% / タグ 12.7% (→ 検証ログ 7d) |
| 書き込み | 0.68s (SQLite) | **0.623s** (IR 15.28 MiB) | 実測。**仕事の範囲が揃った** (下記) |
| **合計** | **31.50s** | **14.08s** → **6.50s** (`--jobs 4`) | 実測。**両列ともプロセス内の計時合計**であって行の和ではない。**31.50s と並べてよいのは 14.08s のほう** (どちらも 1 スレッド) |

出所は doc-gen4 側が warm 再計測 `batch-rerun.jsonl`、lean-doc 側は **IR schema 4 (段階 7b)** の
同一セッション 6 run の中央値。**行の和ではなく計時合計を合計とする。** 引用の注意:

- **`--jobs 4` で意味解析は 3.23 倍、合計は 2.19 倍、IR は byte 一致**【段階 7d】。
  **減ったのは壁時計で CPU 時間ではない** (instructions +1.0%)。頭打ちは 4 スレッド。
- **セッション間の差が 0.3s 級ある** — schema 3 → 4 の正味は **+0.035s** で、13.71s → 14.08s の残りは
  セッション差。**分離できているのは phase timer とバイトだけ**なので、**書き込みコストは壁時計では
  なくフェーズタイマーで読む** (壁時計の振れは全部 `importModules` に出る — IR の書き込みが olean の
  mmap ページインに干渉する)。0.623s と 0.68s はいまは同じ仕事に近い (段階 7b で属性・instance 索引を
  実装した) が、lean-doc はモジュールハッシュと依存写像も書く。

cold cache では環境ロードが 13.6 秒前後になり合計に 11.1 秒ほど上乗せされ、**先読みを入れると
上乗せは 4.5 秒に下がる**【どちらも実測】。**CI がどれだけ cold 側かは §3。**

**内訳は当初の前提から反転した** — 旧見積もり (cold 基準) の環境ロード 51% / 意味解析 46% に対し、実測
(warm、14.08s を分母に) は **18% / 75%**。残るコストの大半が**本来の仕事**なので環境ロードを避ける工夫の
取り分は小さく、**自前実装でも意味解析は減らなかった** (同じ 4,750 宣言・同じ出力で lean-doc 9.26 秒 対
doc-gen4 10.51 秒、いずれも実測)。次に狙うなら equation 生成を切る (寄与 10% = 0.97 秒 / 863 本、実測) か、
変更のない宣言を再解析しない方向。

### 6.2 HTML 生成フェーズ (自パッケージ 432 モジュールのみ)

**lean-doc は IR から 432 ページを warm 0.885 秒 / cold 0.93 秒**【実測。段階 7c / 4c。warm の
うち autolink 索引の読み込み 0.076s】。**現行 doc-gen4 は 3.17 秒 (1 回目 44.52s) / 3.01 秒
(2 回目 42.31s)**【外挿。6,072 モジュールの実測をモジュール数で 432 に比例縮小】。

**byte 再現率は 63.6% → 99.506% (7a〜7c) = 到達上限**、完全一致ページ **34 → 304 / 348**【実測】。
**残る 0.494% は rev だけで、これはオラクル側の天井** (参照ツリー自身が 2 revision を持つ)。
**「出力範囲が違う」という留保は消えた** — 静的資産が母数の外にあることだけが残る。注意 2 つ:
**領域単位の全か無かの一致率**であって差分バイト比ではないこと、**オラクルは領域を宣言名で対応付ける
ので並べ替えを一致と数える**こと (rev を伏せても一致しないページが 2 枚ある — doc-gen4 の不安定 qsort)。

### 6.3 初回ビルド

合計 **warm 14.97s** (`--jobs 4` なら **7.39s**) = 抽出 + IR 書き込み **14.08s**【実測 → §6.1】
+ HTML 生成 **0.89s**【実測 → §6.2】。**cold は 26.22s、先読みありで 19.57s**【いずれも外挿】 —
足した追加コスト (+11.115s / **+4.465s**) は stage1 抽出器の実測値で、前提「cold の追加コストは
`importModules` に集中する」は **Linux で実測になった**。先読みは import closure / madvise /
16 並列 / 抽出と並行 (→ §3)。ただし**幅は移送できない** — 同じ cold でも Linux は 20〜89 秒で
macOS の 1.3〜5.9 倍。`lake env` の cold (+2.56s) はこの数字に無い。
**CI がこの cold 側に落ちるかは配置で決まる** (→ §3)。

### 6.4 現行 doc-gen4 との比較

比較は 2 つの意味で成立し、桁が違うので分けて示す。**(a) 同じ仕事量 — 自パッケージ 432 モジュールを抽出する。1,076s (現行、モジュールごとに
1 プロセス) 対 14.08s (lean-doc、warm・schema 4 = 完成出力) = 76×。**
どちらも 432 モジュール全数の warm 実測で、**外挿も仮定も含まず、どちらも 1 スレッド**。これが
「バッチ化 + 走査の排除」だけで得られる分で、**依存を外部参照にする効果はまだ入っていない**。
**`--jobs 4` の 6.50s を 1,076s と割らないこと** — doc-gen4 側の並列壁時計を**測っていない**
(しかも向こうの並列はメモリ律速 → §5.1)。**倍率は出力の範囲とも一緒に動く** (位置つきタグで
85× → 78×、属性・instance 索引・メンバで 78× → 76×)。**必ず範囲を併記すること。**

**(b) ゼロからドキュメントサイトを構築する。約 32,600s = 9.1 時間 (現行。依存を外部参照に
できないので Mathlib 8,169 モジュール分の抽出がすべて要る) 対 14.97s (lean-doc、warm) = 約 2,180×。**
**分子の約 32,600 秒は打ち切りビルドからの外挿で抽出フェーズだけの値** — 8,600 モジュールのうち
3,590 (42%) を抽出した時点で打ち切り、その実測 13,611 秒 (= 3.79 秒/モジュール) を 8,600 に伸ばした
(→ [`benchmarks/doc-gen4-report.md`](../benchmarks/doc-gen4-report.md) §4.6.1)。8 並列が理想的に効けば
壁時計で約 68 分だが実測ではメモリ律速でこれを大きく超えた。この方式の数字は page cache にほとんど
左右されないので外挿値はそのまま使える。doc-gen4 の HTML 生成 (6,072 モジュールで 44.52 秒、実測) は
分子に入っていない — **差は分子ではなく分母 (lean-doc 側の出力範囲) にあり**、分母側に残る差は
**静的資産が母数の外**という一点だけ。

**この倍率のほとんどは「やらなくてよい仕事をやめた」ことによる**もので実装の巧拙ではない。ここが
本プロジェクトの存在理由。**倍率だけを取り出して引用しないこと** — (a) の 76 倍、(b) の 2,180 倍、
同じ 432 ページの生成だけで比べた **3.6 倍** (→ §6.2)、Mathlib 自体を対象にした CPU 時間の
**約 30 倍** (→ 検証ログ) は、**分母が全部違う別々の主張**である。

### 6.5 増分ビルド (1 モジュール変更) — 実測

**現行構成 (7g 配線 + 7h) の段別内訳**【段階 7h、実測、中央値。生ログ `stage7h-main.txt`】:

段は fresh / resident の順で **`serveStart` (Lean) 0.000 / 14.621、`detect` (L2 台帳) 0.162 / 0.446、
`extract` (Lean) 9.485 / 0.707、`ownership`・`merge`・`prune` (L3-1) 0.313・0.389・0.034 /
0.328・0.423・0.038、`global` (L3-3) 0.126 / 0.146、`impact` (L3-2) 0.207 / 0.213、`render`
0.297 / 0.306、合計 11.739 / 18.096**。`extract` と `serveStart` 以外はすべて外側。

**外側の合計は 1.528s (fresh) / 1.900s (resident)。** サーバを立てて使い回す運用では Lean 側が
0.707s まで落ちるので**外側が 73% を占める**。そこでの律速は**レンダリング (0.30s) ではなく
増分ロジックの IR 全読み**で、7h の後も **5 回**残っている (→ §5.6)。**セッション間で構成が
動く** — この `serveStart` 14.6s は 7g の 3.71s より重い。**過去の総時間と並べない。**

旧構成 (L3-1 のラウンドが入る前) の値も残す: 1 モジュール変更で **3.30〜4.39 秒** = 同一セッションの
フル生成 17.07 秒の **3.9〜5.2 分の 1**、うち**環境の取得が 81.8%** で**本来の仕事は 0.05 秒 =
1.4%**、**差分検出 (無変更) は 0.080 秒** (Lean 不使用、台帳 6.9 KB)【いずれも実測】。**旧版の
理論値「使い捨て 2.5s / 常駐 0.03s」は両方外れた** (常駐でも要求あたり 0.035〜0.088 秒 → §5.1)。
**現行 doc-gen4 との比較は倍率を書けない** — doc-gen4 の増分 5.21 秒【実測】は**HTML を再生成
していない** (stale) 上に `lake build` を含み、こちらは HTML を更新して `lake build` を含まない。

#### `lake build` を足した端から端まで (増分 3 で実測)

`lake build` は lean-doc の外だが**編集 → プレビューの臨界パス上にある**。対象リポジトリの複製
(APFS clonefile) で実測した (→ [検証ログ](verification-log.md) 段階 5 増分 3、
`benchmarks/results/stage5c-olean-propagation-summary.txt`)。

**無変更** (再ビルド 0) は `lake build` **2.40s** / doc 側 0.080s = **96.8%**、**直接 importer 2**
(再ビルド 3、best case に近い) は **12.40〜12.73s** / 3.30〜4.39s = **74〜79%**、**直接 importer 54 /
推移 126** (再ビルド 127) は **237〜243s** / 3.30〜4.39s = **98.2%**。すべて**実測** (warm、
n=5 / n=8 / n=2)。壁時計は page cache で 2.2 倍動くが CPU 時間は安定。

**この数字は §6.5 の主張の分母を変える** — 3.30〜4.39 秒は doc 生成だけの時間で、利用者の体感
ではない。**倍率を書くときはどちらの分母かを必ず明示する。doc 側をゼロにしても端から端は
12.4 秒より速くならず、fan-in が大きければ 4 分待つ。** 効くのは常駐化ではなく、Lean のビルドを
待たずに出す設計 (→ §8。段階 6d でその選択肢は 2 つに絞れた)。

### 6.6 この見積もりが外れるとしたら

**残る筋は 1 つだけ — page cache が warm でないこと** (他の 3 つ、意味解析が減らせない / 常駐が
成立しない / HTML 生成の未実装分、は段階 6・7c・7d で決着 → §5.1 / §6.1 / §6.2、経緯は検証ログ)。
**仮定ではなく実測済みの変動要因**で、環境ロードが 2.5 秒から 13.6 秒に伸び、先読みで 6.9 秒までは
戻せる【実測】が **warm の 2.5 秒には戻らない**。**CI がどちら側に落ちるかは配置で決まる** (→ §3)。
**warm の数字だけを出すのは誇大**なので両方を併記する。**意味解析の壁に当たるのは 4 スレッド分先。**

## 7. 検証の順序

各段階は「次に進んでよいか」を判断する実験であり、機能の積み上げではない。
**仮説が否定されたらそこで設計を見直す** (逆をやらない)。**段階 1〜8 + CI 軸は全部完了した。**
**判断基準と結果の対応は [検証ログ](verification-log.md) 冒頭の状態表が SoT** —
設計に返ってきたものは各柱に畳んである: 1 (1 プロセスでまとめて抽出) → §5.1、2 (走査をやめ索引)
→ §5.2、3 (依存の IR なしでリンク解決) → §5.3、4 (IR から HTML、再生成に Lean 不要) → §5.6、
CI (cold をどう扱うか) → §3、5 (変更したモジュールだけ再処理) → §5.5、6 (環境の常駐) → §5.1、
7 (完成品の値) → §6.2、8 (rev をバイトから外す) → §5.6。

1 と 2 が本命だった。3 は「依存の規模から切り離す」価値の核。**5 は速度ではなく正しさの検証**で、
現行が失敗していた箇所 — ここが端から端で閉じたことが到達点。撤退ラインは 2 つとも発火せずに決着した:
段階 6 の「消える 3.1 秒が複雑さに見合うか」は**抽出ラウンドが 2 回以上あるときだけ得**、
「プレビューが常駐の受け皿」は**同じ機構で否定された** (→ §9)。

## 8. 未解決の問い

**決着した問いはここから消した** — 常駐の寿命 → §5.1、増分の影響集合 → §5.5、**revision をバイトに
埋めるか → 外すと決定** (§5.5 + §5.6、段階 8 で注入の実装形まで実測)、**プレビューモード → 持たない**
(§9)、**検索 → 自パッケージのみ** (§5.6)、**宣言の所有モジュール / `_private.` 名のリンク / Lean の
バージョン差 → v0.1 の範囲として [実装計画](implementation-plan.md) §4 決定 5 が引き取った**
(所有モジュールは同名で複数の olean に焼かれる自動生成補題 25 件、`_private.` は 8 名、いずれも実測)。
経緯は git と [検証ログ](verification-log.md) が持つ。

| 問い | 分かっていること / 残っていること |
|---|---|
| **cold な環境ロード (13 秒) をどう扱うか** | **決着に近い (→ §3)。「CI は毎回 cold」は否定された**が、効いていたのは `cache get` の常駐率ではなく **`lake build` が import の hot set を読むこと**【Linux 実測】。**同じジョブなら 2.61 秒 / 別ジョブなら 20〜89 秒 = 8〜34 倍**なので、**第一の打ち手は配置** (doc 生成をビルドと同じジョブに置く)。**Lean の速度ではなく I/O の問題。残るのは 3 つ**: (a) **先読みの集合を「実際に読まれる分」まで絞れるか** (残留集合で絞った版は取りこぼして逆効果。読み取り追跡が要る → §3)、(b) 分割配置を強いられる場合の **IR キャッシュ** (= 段階 5 と同じ機構)、(c) 完全版の抽出器でも同じ差が出るか (作業集合が 16 GiB に収まらず macOS では測れなかった)。**IR キャッシュには前提が 1 つ増えた** — olean の内容ハッシュは**チェックアウト先の絶対パスに依存する** (429/432 モジュール、実測 → §5.5)。CI と開発機でパスが違えば全滅するので、鍵をパス非依存にしない限り CI 側でのキャッシュヒットは 0 |
| **意味解析 (実測 10.58 秒) を減らせるか** | **半分決着 (段階 7d)** — 筋は算法でも生成物の削減でもなく**並列化**だった。`--jobs 4` で **10.79 → 3.34 秒 (3.23×)、IR は byte 一致**。**内訳は delaborate 55.3% / format 15.4% / タグ 12.7%** で、分布はほぼ一様 (上位 1% で 6.97%) なので**外れ値を潰す筋は無い**。equation を切る筋は却下 (並列後は −3.4% しか効かず再現率が 2.4 pt 落ちる)。**残るのは CPU 時間そのもの** — instructions は +1.0% しか動いておらず、4 スレッドで頭打ち (M1 の性能コア 4 本 + cycles +66% のストール) |
| **依存パッケージの写像をどう配布するか** | **実装して数字が出た (段階 7c)** — `declaration-data.bmp` から導いた索引は **8.51 MB / gzip 1.33 MB、作る 0.415 秒 / 読む 0.076 秒**、宣言 258,760【実測】。これで docstring の autolink が **410,114 B ぶん byte 一致**し、過剰アンカーは 0。**残っていた 1 点は決着した (2026-08-11)** — 公開サイトに**ファイルはある** (`…/mathlib4_docs/declarations/declaration-data.bmp` が 200 / 66,418,003 B)【実測】が、**バージョン対応は取れない**: 公開サイトは **Lean 4.33.0 / mathlib `c3a9a08f`**、対象は **v4.31.0 / `fabf563a7c`** で **2 マイナー版ずれる**【実測】。バージョン別アーカイブは無い【仮定】。→ **生成側で作る。**「(名前, モジュール) の 2 列で足りる」は実測済み。**2026-08-15 に実装して検証済み (V1 成立)** — 抽出器に `--link-index` を足して環境を走査すると、bmp 由来の写像と**共有 255,205 名すべてでモジュールが一致 (食い違い 0)**、同じ IR から作ったサイトが **438/438 バイト一致**【実測 → [結果ログ](milestone-log.md) M5-a】。**参照の 258,760 はこの対象の写像ではない** (`Lake.*` 3,523 名を含み、打ち切った doc 木は現行 432 モジュールに対し 348 ページしか持たない) ので、集合の総数を比較の分母に使わないこと |
| **docstring 内のリンクをどう解決するか** | doc-gen4 は別経路 (`Output/DocString.lean`) で処理していて署名のタグ付けを通らないので、別の仕組みになる可能性が高い。**規模は実測できた** (段階 4 増分 1): 348 ページの内部アンカー 80,743 件のうち IR の名前集合 (5,300 エントリ) で解決できないのは **293 件 / 188 種 = 0.36%** で、**その全部が docstring 内** (署名と equations の取りこぼしは 0)。要るのは「署名に出てこない名前も引ける索引」であって、写像の作り方の問題ではない |

## 10. 補足 — 上流への還元

本プロジェクトを進めることと知見を上流に投げることは排他ではない。3 つある。

| | 内容 |
|---|---|
| **バッチ化** | 計測で使った「複数モジュールを 1 プロセスで抽出する」コマンドは、doc-gen4 の内部 API が**既に複数モジュールを受け取れる**ため CLI の定義を変えるだけで実現できた。つまり §6.4(a) の 76 倍のうちバッチ化による分は、doc-gen4 本体への小さな変更としても成立しうる |
| **`scoped notation`** | doc-gen4 は**パッケージ自身の `scoped notation` を出力できていない** (段階 2 で実測)。delaborator が `ScopedEnvExtension` にあり import だけでは未活性なのに `Lean.activateScoped` を呼んでいないため、`H(μ; X)` や `≐` と書けるはずの署名が `entropy μ X` / `DotEq a a` と出る。**呼ぶだけで直り、コストは意味解析 +6% (実測)** |
| **`collectTactics` の 16.7 秒** | **1 行の直し方で消える** (→ §5.2) — `env.header.moduleNames` をループの外に括り出し、`allTacticDocs` を 1 回だけ呼ぶ。`moduleNames` が `def` であることは Lean core 側の API の形の問題なので、**同じ罠を踏んでいるコードは doc-gen4 以外にもありうる** |
