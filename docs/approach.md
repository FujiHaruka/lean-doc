## 1. 何を作るか

Mathlib に依存する Lean パッケージが、**自分のモジュールだけを短時間でドキュメント化できる**
ドキュメント基盤。依存ライブラリは再生成せず公開済みドキュメントへリンクする。主眼は HTML を
出すことではなく、**Lean の意味情報を再利用可能な形で抽出し、必要な部分だけを高速に更新できる
こと**。副産物として doc-gen4 が**出力できていないパッケージ自身の `scoped notation`** も出る
(実測 → §10) — 読者が実際に書く記法で署名が読めることは生成速度と同じくらい価値に効く。

## 2. 背景 — 計測が示したこと

doc-gen4 を計装して、Mathlib 依存プロジェクト (432 モジュール) のドキュメント生成を実測した
(この節はすべて実測 → [`benchmarks/doc-gen4-report.md`](../benchmarks/doc-gen4-report.md))。
コストは 3 層に分かれ、どれも「ドキュメントを作る仕事」そのものではなかった。

| 層 | 支配率 | 実際に起きていること |
|---|---:|---|
| 環境ロード | **85.0%** | モジュールごとにプロセスを起動し、import closure 全体を読み直す |
| 意味解析 | 4.6% | 本来の仕事。宣言の型を pretty print し equation を生成する |
| 走査オーバーヘッド | 8.8% | 環境の全定数を舐めて、該当しないものを捨てる |

実ビルドでは **8.9 億回の定数走査に対して該当は 0.032%** で、走査して捨てるだけのコスト
(1,195 秒) が本来の意味解析 (631 秒) の約 2 倍あった。HTML 生成フェーズも同様で生成 CPU の
**66〜78% が DB からの読み直し**、レンダリング自体は 9.2%。さらに**増分性が一切ない** —
無変更で 2 回続けて実行しても 46.25 秒 → 43.91 秒と変わらない。

### 決定的だった 1 つの実験

doc-gen4 に「複数モジュールを 1 プロセスで抽出する」コマンドを足して、
同一の 432 モジュールを両方式で処理した (どちらも全数の実測で外挿なし、
同じ日・同じ warm な page cache 状態)。

| | warm 実測 (壁時計) | うち `importModules` |
|---|---:|---:|
| モジュールごとに 1 プロセス (現行) | **1,076 秒** | 908.6 秒 (88.8%) |
| 1 プロセスでまとめて | **31.9 秒** | 2.6 秒 |

**34 倍。分母は「同じ 432 モジュールを抽出する仕事」。** アルゴリズムの改良ではなく、同じ依存
ライブラリを 432 回読み直すのをやめただけで生じる。差の出どころは 1 行で言える —
**432 モジュールぶんの import closure をまとめて読んでも 1 モジュールぶん (逐次時 2.10 秒) と
ほとんど変わらない** (closure が Mathlib に支配されているため)。**cold と warm を混ぜないこと。**

## 3. 仮説

> Lean の意味情報をパッケージ単位でまとめて抽出し、依存ライブラリを外部参照にすれば、
> downstream ライブラリのドキュメント生成時間を**依存ライブラリの規模から大きく切り離せる**。

計測はこの仮説を支持している。ただし完全には切り離せない — 自パッケージの型を正しく
pretty print するには Mathlib の `Environment` が要り、そのロードは残る。
**これが新設計の床**であり、それをどう扱うかが設計の中心的な論点になる。

床の大きさは **page cache の状態で 5 倍動く。warm で約 2.5 秒、cold で 10〜13 秒**
(実測 → [検証ログ](verification-log.md) 段階 1。以前 12.9 秒としていたのは cold を warm と
取り違えていたため)。warm では壁時計 ≒ CPU 時間で、差はすべて olean の mmap ページイン待ち。
したがって「床をどう扱うか」は最初から 2 つの別問題である。

| | 床 | 扱い |
|---|---|---|
| **ローカル (warm)** | 2.5 秒。1 モジュールだけの再抽出ならこれより小さい (`importModules` 0.80〜2.96 秒、実測・段階 5) が `lake env` の 0.96 秒が別にかかる (→ §6.5) | 常駐で消せるが、消さなくても致命的ではない |
| **CI** | **配置で決まる** — ビルドと同じジョブなら **2.61 秒**、別ジョブで cold なら **63〜71 秒** (どちらも Linux 実測、下記) | 常駐は効かない。**第一の打ち手は「同じジョブに置く」** |

**「CI は常に cold」は否定された。ただし効いていたのは `cache get` ではなく `lake build`
だった**【Linux 実測、2026-08-10】。**測るべき瞬間は `cache get` の直後ではない** — 実運用は
`cache get` → `lake build` → doc 生成 の順で、doc 生成が見るのはビルド後の page cache。

| CI の組み方 (`ubuntu-latest` / 2 コア / 7.75 GiB) | `importModules` | major fault |
|---|---:|---:|
| doc 生成を `lake build` と**同じジョブ**に置く | **2.610 秒** (macOS warm と同じ) | **26** |
| 別ジョブでビルド済み olean を復元して doc だけ作る | **63.4〜70.6 秒** | 11,949 |

**間は 24〜27 倍。設計上の推奨が出た — doc 生成はビルドと同じジョブに置く。**
**「どの N% か」も答えが出た**: 常駐率は `cache get` 後 60.4% → ビルド後 **40.3%** と下がるのに
fault はほぼ 0 — **割合ではなく「どのページか」が効く** (`lake build` が import の要るページを
読む)。**`cache get` 直後の常駐率はこの問いの代理指標ですらなかった** (60.4% は前回の 62.4% を
再現、n=2、どちらも容量律速。macOS は同じ時点で 4.7–20.2% / 14.96・15.66 秒と不利な側だった)。
**分けざるを得ない配置では Linux cold は macOS cold の 4.2〜4.7 倍**で先読みの価値は下がらない。

**cold を縮める打ち手は見つかった — 先読み (実測、2026-08-10)。** cold の 12.7 秒は帯域律速では
なく **132,343 回の同期 major fault の直列な待ち行列**なので、並行して読めば消せる。

- **importModules 13.573 → 6.923 秒 (−49.0%。分母は先読み無しの同一構成)、major fault
  121,386 → 26,329 (−78.3%)**、壁時計 18.03 → 10.44 秒。5 回の分布は重ならない (交互配置)。
  **cold 合計は 25.76 → 19.11 秒 (外挿、§6.3)。**
- 読ませる集合は **`.lean` のヘッダから作った import closure** で足りる (6,021 モジュール /
  17,199 ファイル、cold が必要とするバイトの **98.80%** を覆い、観測した集合と実測で区別
  できない)。先読み自体は 1.75 秒 / 2,395 MB/s、closure の計算は cold 1.63 秒。
- **効果の大きさはメモリの余裕に依存する** (実測レンジ −23% 〜 −49%)。向きは変わらない。**Linux
  では未測定**で、`MADV_WILLNEED` の同期・非同期が違うので方式の選択は移送できない。
  生ログ `benchmarks/results/ci-{warmstart,prefetch}-summary.txt`。

## 4. Approach

> **Lean プロセスは「意味情報を吐く抽出器」に徹し、1 つの環境を長く使い回す。**
> 抽出したものはモジュール単位の中間表現 (IR) として永続化し、
> HTML・検索索引・その他の出力はすべて Lean の外側で IR から作る。
> 依存パッケージについては IR を作らず、「宣言名 → モジュール → URL」の写像だけを持つ。

変えるのは次の 3 つの境界。**どれも独立に効き、順に適用でき、1 つ失敗しても残りは成立する。**
(1) **プロセスの境界**: モジュールごと → パッケージごと (あるいは常駐)。(2) **抽出の範囲**:
環境の全定数 → 自パッケージの宣言のみ。(3) **Lean と出力の境界**: Lean が HTML まで作る →
Lean は IR まで、出力は外側。

## 5. 設計の柱

### 5.1 1 環境・長寿命プロセス

抽出は「モジュール 1 個 = プロセス 1 個」をやめ、対象パッケージを 1 度ロードしてまとめて
処理する。これが実測 34 倍 (§2) の正体で、単独で最大の効果を持つ。

**常駐は実装・実測して決着した** (`--serve`、段階 6 + 6a)。要求あたり **0.035〜0.088 秒**
対 単発 1.72〜4.60 秒で、IR は単発と **byte 一致**、6 要求で汚染なし【実測】。
**寿命の上限は「自分が import した olean を書き換えるビルドまで」**【段階 6a、実測】 —
Lean には環境から 1 モジュールだけ差し替える手段が無い。プロセスは死なない
(`lake build` を生き延び 0.151 秒で応答した) が、**参照の所有者を環境から引く**ので
移動した名前に古い所有者を返す。**段階 6 の「ラウンド 2 以降なら安全」は誤り** —
ラウンド 2 はまさにその所有者列を直すためにあるので、編集前環境では 439 ページ中 1 ページが誤る。

**正しい形は「`lake build` の後にサーバを 1 台立て、全ラウンドを任せる」**:
**7.940 → 6.168 秒 (−22%)、byte 一致**【実測】。ラウンド 2 だけ任せるのは**損** (8.788 秒)
なので**分岐点は 2 ラウンド**。起動を払わない 2.682 秒はビルドを挟まない用途だけ。
臨界パスの 74〜98% は `lake build` なので、端から端で見た効き幅は小さいまま。

副次的な効果として、**メモリ律速が消える**。現行はプロセスごとに 2〜3 GB の環境を持つため 8 並列
で RSS 21.7 GB (物理 16 GB) に達しスワップし (実測)、CPU コアを増やしても頭打ちになる構造だった。

### 5.2 走査ではなく索引で宣言を引く

「環境の全定数を舐めて、対象モジュールのものだけ拾う」のをやめ、モジュールから宣言を引く
方向に変える。5.1 とは独立に効く — バッチ化しても走査は 1 回分残るため。
**実装と正しさは検証済み** (→ 検証ログ 段階 1): 索引方式 (`moduleData[i].constNames`) と走査
方式は同じ 5,123 宣言を返し、時間は 0.0022 秒 対 0.62 秒 (実測)。ただし**バッチ 1 回あたりの
走査コストは当初の見積もり 4.45 秒より 1 桁小さい** (あれは cold のページインを走査コストと
取り違えた値。warm では 0.36 秒)。**この柱の価値は「時間が消える」ことではなく、
モジュール数に比例する走査を構造から無くすこと**に移った。

索引方式には走査方式に無い論点がある: 複数モジュールの olean に同名で焼かれる自動生成補題が
あり、**宣言の所有モジュールが一意に決まらない** (実測 25 件)。明示的に決める (→ §8)。
同じ性質の問題がタクティク収集にもあり、**こちらの方が桁違いに大きかった** — バッチ化すると
16.7 秒 (全体の 54%) の最大項に浮上するが、全体を 1 回列挙して振り分ける実装で **0.011 秒**
(実測 → 検証ログ 段階 2)。**正体は当初の見立てと違った**: 「モジュールごとに全タクティクを
列挙し直す」分は 22% で、残り 78% は `EnvironmentHeader.moduleNames` が**フィールドではなく
`def`** で、呼ぶたびに import closure と同じ長さ (6,021 要素) の配列を作り直していたこと。
**第 3 の因子は呼び出し側から見えない。** ゆえにこの柱の一般形は一段強い:

> **1 モジュールの処理で、import closure のサイズに比例するものに触らない。**
> 走査でなくても、配列 1 本の構築でも、内側のループに入れば同じことになる。

### 5.3 依存パッケージは外部参照にする

HTML 生成が依存パッケージについて実際に必要としているのは**「宣言名 → モジュール名 → URL」の
写像だけ**だった (型も docstring も equation も不要)。したがって依存については IR を作らず、
この写像だけを持ち、公開ドキュメントへリンクする。これが「ゼロからサイトを構築する」ケースで
桁違いの差を生む (→ §6.4(b))。

**検証段階 3 で実測に置き換わった** (348/432 モジュールの範囲、詳細は verification-log):

- **写像だけで doc-gen4 と同じ URL 文字列が出る** — 共通 39,298 ペアの **99.992%** が href 完全
  一致 (未一致 3 はリンクしてはいけない再帰子で写像はそれを出さない)、**取りこぼしは 0**
- 写像の実サイズは**下限 53 KB / 上限 34.3 MB** (647 倍の開き)。必要な列は (名前, モジュール)
  の 2 列で `kind` は要らない。**blacklist は写像から復元できる** — 「写像に載っている名前だけ
  リンクする」方式は doc-gen4 の dead link (実測 3 本) を出さない

URL 規則は `("../" × (ページのモジュール成分数 - 1)) + "./" + モジュールパス + ".html#" + 名前`。
**IR には絶対的な識別子を持ち、相対化は出力時に行う** (→ §5.6)。**残る欠落**: 自パッケージの
`_private.` 名は素朴に URL を出すと dead になる (実測 8 名 → §8)。なお**リンク解決に必要な
データと、型を pretty print するために環境が必要なことは別問題** — 後者 (§3 の床) は残る。

### 5.4 中間表現の粒度はモジュール単位

現行 doc-gen4 は宣言ごとに DB の行を分割したため、レンダリング時に N+1 クエリで再構築する
羽目になり、生成 CPU の 66〜78% がそこに消えている。**読みも書きもモジュール単位なら、
モジュール 1 個 = 1 まとまり + 索引が正しい粒度。** 教訓は「規模が来たら SQLite」ではなく
**アクセスパターンに合わない粒度で分割すると逆効果**、ということ。格納形式
(JSON / SQLite / バイナリ) の選択より粒度の選択が先に来る。

IR にはスキーマバージョンを持たせ、キャッシュキーには少なくとも Lean バージョン・抽出器
バージョン・IR スキーマバージョン・olean ハッシュを含める (olean ハッシュだけでは不足 —
pretty printer の出力が Lean バージョンに依存するため)。実装形は「**モジュールごとの olean
ハッシュ + パッケージ 1 つぶんの環境キー**」で、後者は判断点 3 で不完全と分かって 2 分割した
(→ §5.5 の L1)。

**この粒度は実測で成立した** (検証ログ)。**schema 2 (位置つきタグ) で 15.13 MiB / 書き込み
0.549 秒 / 読み出し 0.100 秒 (床の 4.0%)**、タグ無しの schema 1 なら 8.74 MB / 0.198 / 0.056、
**現行の schema 3 (空白幅) は schema 2 比で +0.74% / +11.8% / ±0**【実測】 — 結論は同じだが
**引用時は構成を揃えること** (→ §6.1)。内容ハッシュは書き込みの 1.2% で、持つ代償はない。

### 5.5 増分性を「入力側」と「出力側」で別々に設計する

現行はここが両方向に壊れていた — **取りこぼし** (マーカーファイルが空なので内容が変わっても
ハッシュが変わらず HTML が再生成されない) と **無駄** (走れば変更の有無に関わらず全モジュール)。
原因はキャッシュ無効化とページ再生成という別々の関心を 1 つの仕組みに載せたこと。

> **「IR のモジュール単位ハッシュを単一の真実にする」当初案は否定された (判断点 3)** —
> 5 命題すべてが実測で破れた (→ [検証ログ](verification-log.md) 段階 5 増分 2)。
> 否定されたのは**その構造**であって増分生成そのものではない。以下の 3 層が見直し案で、
> **増分 4〜7 で全層が実装され、本物の移動と本物の削除を `lake build` ごと回して
> フルビルドと byte 一致するところまで実測した。**

**単一の真実は「役割が 1 つ」ではなく「役割ごとに 1 つ」だった** — 問う時点が違う。

| | 入力側 = どのモジュールを**再抽出**するか | 出力側 = どのページを**再生成**するか |
|---|---|---|
| ハッシュ対象 | モジュールの `.olean` (3 分割なら 3 つとも) | モジュールの IR |
| 計算する時点 | 抽出の**前** (Lean 不要) | 抽出の**後** |

`.lean` ソースは早すぎ (証明中の空白のように olean に届かない変更を拾い、依存の再ビルドで
olean に入った変更を落とす)、IR は遅すぎる (計算するには省きたい抽出そのものが要る)。
**抽出器が見られるのは olean だけ**なので入力側は olean が正しい。**Lake が既に内容ハッシュを
`<file>.olean.hash` に書いている**ので、台帳は 227 MB ではなく 6.9 KB を読めば済む (0.080 秒)。

#### 3 層 (判断点 3 を受けた設計、増分 4〜7 で全層を実装・実測)

判断点 3 が見つけた穴は**上の 2 層のどちらにも属さない依存**だった。

| 層 | 何を見るか | 何を決めるか | 変わったときの影響範囲 |
|---|---|---|---|
| **L1 グローバル鍵** | モジュールに属さない入力 | 全無効化するか | **全部** |
| **L2 モジュール単位ハッシュ** | 各モジュールの `.olean` | 再抽出集合の**核** | そのモジュール |
| **L3 導出の依存** | 名前の所有権 / 全域写像 / 全域索引 | L2 の核を**広げる** | import では閉じない |

**L1 は 1 つの鍵ではなく 2 つ**【実測で確定、増分 4】。振り分けの基準は「出力のバイトを
変えるか」ではなく (両方変える)、「**IR を変えうるか** = 答えるのに Lean が要るか」。

| 鍵 | 中身 | 変わったとき |
|---|---|---|
| `extractKey` | toolchain / manifest / 抽出器 id とその構成 (`--open`) / IR schema / 生成器 id | 全再抽出。stale ページは従来どおり IR 差分が決める |
| `renderKey` | レンダラ id / `--source-url` | 再抽出**ゼロ**、再レンダリング**全部** |

分けないと二択が両方まずい: 入れなければ 432 ページが黙って stale (= S1)、単一の鍵に入れれば
**`--source-url` は revision を含むので毎コミットで 432 モジュール全再抽出**。
**分割の効果は 18.39 → 1.34 秒 = 13.7 倍**、追加コストは **+0.3 ms** でドリフト以下【実測】。
鍵の比較は**和集合**で行う — 片側にしか無い鍵も変化と数え、**黙って過少にレンダリングしない**。

**L2 の鍵は olean の内容ハッシュのままでよいが、そのままでは移送できない** — olean には
**ソースの絶対パスが 429/432 モジュールで埋まっている** (実測。Mathlib の style linter のログを
持つ環境拡張 `lintLogExt` がパス入りの警告文を保存している)。**チェックアウト先が違うだけで
ハッシュが全滅する**ので、CI と開発機で IR キャッシュを共有するには鍵をパス非依存にする必要が
ある。**モジュール一覧はソースの glob で作る** — **`.lake/build` を走査してはいけない**。
Lake は孤児 olean を消さないので 432 モジュールに対し olean は 1,090 個、**659 個が幽霊**
(実測)。**削除経路は実装済み**
(台帳・IR・ページの 3 箇所、増分 6) — 台帳は作り直しで足り (`build` は `check` と同コスト)、
IR は `merge-ir --remove`、ページは `prune-pages.ts` (レンダラは書くだけなので消す係が要る)。
本物の削除 + `lake build` でフルビルドと byte 一致まで実測した。
(複製上で計測する際の落とし穴は `experiments/stage5e/README.md` に置いた。)

**L3 が §5.5 に無かった穴で、3 つある** (いずれも実装済み):

1. **名前の所有権** — 参照は `(定義モジュール, 名前)` で持つので、宣言が移動すると参照側の
   IR が腐る。**これは再生成ではなく再抽出の問題** — 影響集合をどれだけ広げても直らない
   (実測: `--mode referrers` は stale 0 でも 1 ページも直さない)。L2 の核から
   「**そのモジュールが定義していた名前の集合の差分**」を取り、その名前を `refs` に持つ
   モジュールを**再抽出集合に足す**。**実装済み** (`ownership.ts`)。
   **必須であることは増分 3 で、効くことは増分 5 で、どちらも実測で確定** — 本物の移動 +
   `lake build` で、L3-1 無しは 433 ページ中 1 ページが**リンク切れ**、有りは**フルビルドと
   433/433 byte 一致**。**L2 が参照側を拾うかどうかは当てにできない** — 4 つのうち 3 つは
   olean が動いて L2 が拾い、1 つは動かなかった。拾えるかは Lean の直列化の都合であって
   依存構造の性質ではない。同じ実験で**再抽出集合を import 閉包へ広げる必要は無い**ことも確定。
   **再抽出はラウンド構造になる** — 移動を知るには移動元の新しい IR が要るので、
   「抽出 → 誰が腐ったか問う → それも抽出」の順。実測では**2 ラウンドで不動点**、L3-1 自体は
   0.265 秒だが**2 ラウンド目が環境ロード約 3.1 秒を丸ごと払う** (4.17→7.78 秒。
   `lake build` 後のサーバに全ラウンドを任せれば 7.940→6.168 秒 — 段階 6a、実測)。
   **2 ラウンドは構造的な上限**【段階 6c】 — ラウンド 2 以降のモジュールは olean が動いて
   いないので宣言集合も動かない。**穴は 1 つ**: その集合は `constNames` を `isBlackListed` で
   濾したもので、述語が環境を参照する。**反転させる変更があればラウンド 3 が出る**ので
   `--max-rounds` は残す。**効く範囲は「移動する名前が印字署名に出るか」で決まる**
   【段階 6c、実測】 — 出る種別 (定理・**`abbrev` は必須**、無しだと最大 30 ページ誤り) には効き、
   出ない種別 (**`instance`** はこの対象に署名に出る例が 0、`@[simp]` も 70 宣言中 0) には
   無関係で、そちらを救っているのは L3-3。
2. **全域写像** — docstring の autolink は名前 → 定義モジュールの全域写像を引くので
   **import で閉じない** (実測: 逆向きの推移的 import 閉包でも 3〜141 ページ取りこぼす)。
   **増分 6 で失敗が双方向だと確定** — モジュールを 1 つ削除すると全域写像が 533→527 に減り、
   **削除と無関係な LZ78 のページに、行き先の消えたリンクが残った**。繋いでいるのは全域写像
   だけ。**増分 7 で閉じた** — 規則は「**全域写像の差分に出た名前を docstring に含むページ**を
   再生成集合に足す」。走査であって推測ではなく、逆索引の常備も要らない。実測では 58 名の
   差分から**ちょうど 1 ページ**を名指しし (過剰近似なし)、削除ケースは **437/437 byte 一致**。
   **写像は自宣言だけでは足りない** — 効いたのは依存側の名前で、走査の単位も code span ではなく
   `autoLinkInline` と同じ空白分割。どちらも間違えると外からは「0 ページ」に見える。
3. **全モジュール横断の後処理** (検索索引・ナビゲーション・相互参照) — **実装済み**
   (`global.ts`)。判断点 3 で「未実施どころか未実装」と確定した 5 成果物のうち、
   **`tactics.html` だけは自パッケージの関数ではない** (tactic docstring は環境側にあり、
   432 モジュールで 0)。残りは IR から生成でき、**合計 1.88 MB / 0.139 秒**【実測】。
   **「差分から更新できる形にする」は不要と実測で決着** — 増分化で消せるのは IR 全読みの
   0.119 秒だけで、増分実行の 1.5〜2.6%。台帳・依存スライスに続いて 3 度目の同じ答えで、
   共通の原因は **IR 全読みが 0.119 秒**であること (§5.4 の設計判断が効いている)。
   **doc-gen4 の 38.6 MB は依存木全体 258,760 宣言の値でこちらの数字ではない。**
   **この層は正しさにも効いている**【段階 6c】 — instance 一覧はページのバイトに無く
   `declaration-data.bmp` からブラウザが埋めるので、**instance の移動が正しく出るのは
   「全域成果物を毎回作り直す」から**。3 層でいちばん安い層が最も広い網だった。
   **rev をバイトから外すと、この層が rev-only コミットの最大項 (45.1%) になる**【段階 6b】。
   しかもパイプラインでの費用は 0.29 秒 — `global.ts` を `build` と `delta` で 2 回呼ぶため、
   増分 7 が測った 0.139 秒の 2 倍。**「増分化する価値なし」は別の分母での判断だった。**

**「影響集合の mode」という枠組み自体が的を外していた**のが判断点 3 のいちばん構造的な発見 —
`self` / `referrers` / `importers` は**描画対象しか決めない**ので再抽出が要る種類の stale (L3-1)
には原理的に効かない。**再抽出集合と再生成集合は別々に導く。**
増分 4 でさらに、**mode は実運用のコミットに対しては常に `all` に潰れる**ことが確定した
(revision がページのバイトに 4,992 か所出るため)。ただしその量は元々小さい —
**432 ページ全部で 0.87 秒**【実測】。**高いのはレンダリングではなく抽出のほうだった。**
その 0.87 秒の内訳は**ページ数に比例する分が 82%** (0.653 秒) で、
IR 全読みなどの固定費は **18%** (0.144 秒)【実測】。
固定費が大半を占めるのは **1 ページだけ再生成する場合** (0.195 秒中 0.17 秒) であって、
432 ページの場合ではない。**そして「常に `all`」は出力契約に依る** — rev をバイトから外せば
`all` は立たず **0 ページ**になる (段階 6b、実測 → §8)。**mode の枠組みが的を外していたのは
今も本当だが、「常に `all`」は前提付きの事実になった。**

**空の再生成集合には落とし穴があった** (段階 6b で発見・修正)。`render.ts` は `--only` が
無いと全モジュールを描くので、`incremental.sh` が空集合から `--only` を 0 個渡すと
**433 ページ全部を再生成していた**。rev がバイトにある限りコミットは必ず `all` を立てるので
この経路には誰も来なかった。**rev を外すと毎回ここに来る。**

### 5.6 出力は IR から作る (Lean の外側)

HTML・検索索引・JSON API・宣言グラフ・リンク切れ検査は、すべて IR を入力とする独立した消費者に
する。**HTML の再生成に Lean の起動が要らない**ことが、この分離が成立している証拠になる。
境界の入口までは実測で通った: Lean を起動しない別プロセスが 432 モジュール分の IR を
**0.100 秒**で読み切れる (15.13 MiB、環境ロードの床の 4.0% → 構成の違いは §5.4)。

**IR は参照定数を集合でなく位置つきで持つ必要がある** (段階 4 増分 1)。doc-gen4 の署名内アンカー
72,421 件のうち **44.0% は印字トークンと定数名に字面の関係が無く** (`ℕ`→`Nat`)、平文 + 集合から
の再構成は上限でも recall 56% / 実測 51.7%。ページのバイトの **71.1% が署名の描画**なので、
ここを落とすと「同じ仕事」ではなくなる。逆に**あて先の解決 (名前 → モジュール) は集合で足りて
いる** (取りこぼし 0.36%、全部 docstring 側)。**ただしこの「集合」は全域写像で増分では
閉じない** — 判断点 3 が破れたのはまさにこの docstring 側 (§5.5 L3-2)。

なお計測は**レンダリング自体の最適化に価値が薄い**ことも示した (生成 CPU の 9.2%)。
**言語選択より責務分離が先**で、Rust を使うなら理由は速度ではなく配布・常駐サーバ・
並行性の扱いやすさであるべき。

## 6. 性能

**抽出・IR 永続化・HTML 生成・増分はすべて実測に置き換わった** (検証段階 1〜5)。
**残る非実測は 3 つだけ** — (1) cold 合計 25.76s / 19.11s は stage1 抽出器からの**外挿** (§6.3)、
(2)「CI が cold 側かどうか」は**仮定** (§3、Linux 未測定)、(3) 未実装分を足したときの
HTML 生成 1.2 秒前後は**外挿** (§6.6)。どの数字が実測 / 外挿 / 仮定かは行ごとに明示する。
**そしてこの節は速度の節である。** 増分の**正しさ**は増分 4〜7 で閉じた (フルビルドと byte 一致、
→ §5.5) が、**§6.5 の秒数は正しさが閉じる前の構成のもの。**

### 6.1 抽出フェーズ + IR 永続化 (自パッケージ 432 モジュール) — 実測済み

cold cache では環境ロードが 13.6 秒前後になり合計に 11.1 秒ほど上乗せされ、**先読みを入れると
上乗せは 4.5 秒に下がる** (どちらも実測)。**CI がどれだけ cold 側かは §3。**

**内訳は当初の前提から反転した** — 旧見積もり (cold 基準) の環境ロード 51% / 意味解析 46% に
対し、実測 (warm、13.71s を分母に) は **18% / 77%**。残るコストの大半が**本来の仕事**なので
環境ロードを避ける工夫の取り分は小さく、**自前実装でも意味解析は減らなかった** (同じ 4,750
宣言・同じ出力で lean-doc 9.26 秒 対 doc-gen4 10.51 秒、いずれも実測)。次に狙うなら equation
生成を切る (寄与 10% = 0.97 秒 / 863 本、実測) か、変更のない宣言を再解析しない方向。
**タクティク収集は決着** (0.011 秒) だが 16.7 秒の正体は見立てと違った (→ §5.2)。

### 6.4 現行 doc-gen4 との比較

比較は 2 つの意味で成立し、桁が違うので分けて示す。

**(a) 同じ仕事量 — 自パッケージ 432 モジュールを抽出する**

| | 時間 | 倍率 |
|---|---:|---:|
| 現行 (モジュールごとに 1 プロセス) | 1,076s | — |
| lean-doc (warm、位置つきタグ込み) | 13.71s | **78×** |

どちらも 432 モジュール全数の warm 実測で、**外挿も仮定も含まない**。これが
「バッチ化 + 走査の排除」だけで得られる分で、**依存を外部参照にする効果はまだ入っていない**
(未実装の出力を足すとさらに下がる)。**倍率は出力の範囲と一緒に動く** — 段階 4 で位置つきタグを
足した時点で 85× から 78× に下がった。**そのとき何を出していたかを必ず併記すること。**

**(b) ゼロからドキュメントサイトを構築する** — 現行 doc-gen4 は依存を外部参照にできないため、
Mathlib 8,169 モジュール分の抽出がすべて必要になる。

| | CPU 時間 | 倍率 |
|---|---:|---:|
| 現行 (Mathlib 全体の抽出を含む) | 約 32,600s = **9.1 時間** | — |
| lean-doc (依存は外部参照、warm) | 14.53s | **約 2,240×** |

現行の約 32,600 秒は**外挿**。**フルビルドは完走していない** — 8,600 モジュールのうち
3,590 (42%) を抽出した時点で打ち切り、その実測 13,611 秒 (= 3.79 秒/モジュール) を
8,600 に伸ばした値 (→ [`benchmarks/doc-gen4-report.md`](../benchmarks/doc-gen4-report.md) §4.6.1)。
8 並列が理想的に効けば壁時計で約 68 分だが、実測ではメモリ律速でこれを大きく超えた。
この方式の数字は page cache にほとんど左右されないので外挿値はそのまま使える。
**前提「依存を外部参照にしても同じリンクが張れる」は検証段階 3 で実測に置き換わった** (→ §5.3)。

**この 2,240 倍のほとんどは「やらなくてよい仕事をやめた」ことによる**もので実装の巧拙ではない。
ここが本プロジェクトの存在理由。**倍率だけを取り出して引用しないこと** — (a) の
78 倍、(b) の 2,240 倍、同じ 432 ページの生成だけで比べた **3.8 倍** (3.17s 対 0.82s、→ §6.2)
は 3 桁にわたる別々の主張である。**分母の 14.53s に仮定は残っていない**が、代わりに
**出力範囲の差**が残る (静的資産なし、byte 再現率 63.6%)。**分子の約 32,600 秒は打ち切り
ビルドからの外挿で抽出フェーズだけの値** — doc-gen4 の HTML 生成は 6,072 モジュールで
44.52 秒 (実測) なので、**差は分子ではなく分母 (lean-doc 側の出力範囲) にある。**

### 6.5 増分ビルド (1 モジュール変更) — 実測

旧版の「使い捨て 2.5s / 常駐 0.03s」はどちらも理論値で、**両方外れていた**
(→ [検証ログ](verification-log.md) 段階 5、`benchmarks/results/stage5-incremental-summary.txt`)。

| 変更するモジュール | 再生成ページ | 壁時計 | 根拠 |
|---|---:|---:|---|
| `…Meta.EntryPoint` (import 元 414、closure 2,259) | 415 | **3.30s** | **実測** |
| `…Kolmogorov.OmegaNoncomputable` (葉、closure 4,258) | 1 | **3.83s** | **実測** |
| `…ChannelCoding.Basic` (参照元 80、closure 5,267) | 81 | **4.39s** | **実測** |
| 同一セッションのフル生成 (抽出 16.19 + 生成 0.88) | 432 | 17.07s | **実測** |

**フル生成の 3.9〜5.2 分の 1 (分母は上表の同一セッションのフル生成 17.07s)。** 仕事量は
同じではない — フルは 432 ページ全部を作り、増分は 1〜415 ページを書き直して代わりに
差分検出と IR マージを払う。

> **この表は速度だけの表で正しさを含んでいない。正しさ側は増分 5〜7 で閉じた** (本物の移動と
> 削除を複製上で `lake build` ごと回してフルビルドと byte 一致、→ §5.5)。**上の秒数は閉じる前の
> 構成のもの**で L3-1 のラウンドと全域索引が入っていない (入った値は 4.2〜8.0 秒 → 検証ログ)。

**上表の再生成ページ数は導出ではなく選択である** — 増分 1 では何も変えていないので再抽出した
IR はバイト一致し、時間を測るためにページ集合を強制した (1 / 81 / 415)。**秒数は実在のページ
集合に対する実測。**

**律速は環境の取得で 81.8%** (葉のケースで `importModules` 1.94s = 50.7% + `lake env` 0.96s =
25.1% + バイナリのページイン 0.23s。**本来の仕事は 0.05 秒 = 1.4%** — 段別内訳は検証ログ)。
床は 2.5 秒固定ではなく **0.80〜2.96 秒** (1 モジュールの closure はパッケージ全体の 6,021 より
小さく、モジュールで 3.7 倍違う)。
**理論値 0.03 秒は否定された** — 実測の最小 3.30 秒 = 110 倍 (分母は理論値)。環境ロードを
除いても 0.266 秒 = 8.9 倍で、差の大半は生成側の IR 全読み 0.135 秒。**常駐でも届かない**
(段階 6 実測: 要求あたり 0.035〜0.088 秒 → §5.1)。

**差分検出 (無変更のときの時間) は 0.080 秒** (実測、432 モジュールの olean ハッシュ照合、Lean
不使用)。**Lake が既に内容ハッシュを `<file>.olean.hash` に書いている**ので 227 MB ではなく
6.9 KB を読めば済む。

**現行との比較は倍率を書けない。** doc-gen4 の増分 5.21 秒 (実測) は**HTML を再生成していない**
(stale) 上に `lake build` を含み、こちらは HTML を更新して `lake build` を含まない。
**同じ仕事ではない。**

#### `lake build` を足した端から端まで (増分 3 で実測)

`lake build` は lean-doc の外だが**編集 → プレビューの臨界パス上にある**。対象リポジトリの複製
(APFS clonefile) を作って実測した (→ [検証ログ](verification-log.md) 段階 5 増分 3、
`benchmarks/results/stage5c-olean-propagation-summary.txt`)。

| 変更 | 再ビルドされたモジュール | `lake build` | doc 側の増分 | `lake build` の割合 |
|---|---:|---:|---:|---:|
| 無変更 | 0 | **2.40s** | 0.080s | 96.8% |
| 直接 importer 2 (best case に近い) | 3 | **12.40〜12.73s** | 3.30〜4.39s | **74〜79%** |
| 直接 importer 54 / 推移 126 | 127 | **237〜243s** | 3.30〜4.39s | **98.2%** |

すべて**実測** (warm、n=5 / n=8 / n=2)。壁時計は page cache で 2.2 倍動くが CPU 時間は安定。

**この表は §6.5 の主張の分母を変える** — 3.30〜4.39 秒は doc 生成だけの時間で、利用者の体感
ではない。**倍率を書くときはどちらの分母かを必ず明示する。doc 側をゼロにしても端から端は
12.4 秒より速くならず、fan-in が大きければ 4 分待つ。** 効くのは常駐化ではなく、Lean のビルドを
待たずに出す設計 (→ §8。段階 6d でその選択肢は 2 つに絞れた)。

## 7. 検証の順序

各段階は「次に進んでよいか」を判断する実験であり、機能の積み上げではない。
**仮説が否定されたらそこで設計を見直す** (逆をやらない)。

| # | 検証すること | 判断基準 |
|---|---|---|
| 1 ✅ | 1 プロセスで対象パッケージをまとめて抽出できる | 環境ロードが doc-gen4 と同等で再現し、カスタム構文を含むプロジェクトでも動く |
| 2 ✅ | 走査をやめ、モジュールから宣言を引ける | §6.1 の 14.5 秒 (warm) に到達する |
| 3 ✅ | 依存パッケージの IR なしで、リンクが解決できる | Mathlib へのリンクが正しく張れる。必要な写像の実サイズが分かる |
| 4 ✅ | IR から HTML を生成でき、再生成に Lean が要らない | Lean を起動せず HTML を作り直せる |
| CI ✅ | **CI の cold をどう扱うか** | **床は配置で決まる**【Linux 実測】— doc 生成を `lake build` と同じジョブに置けば `importModules` **2.61 秒** (major fault 26)、別ジョブなら **63〜71 秒**。**24〜27 倍。** 効いているのは `cache get` の常駐率ではなく「ビルドが hot set を読むこと」。先読みは macOS で成立 (−49.0%)、**Linux では未測定** |
| 5 ✅ | 変更したモジュールだけ再処理できる | (1) 無変更で再実行 → **0.080 秒 (実測)**。(2) 1 モジュール変更 → **3.30〜4.39 秒 (実測)**、フルの 3.9〜5.2 分の 1。(3) stale ページが残らない → 判断点 3 で**否定**、§5.5 を 3 層に見直したうえで**増分 5〜7 で閉じた** — 本物の移動と削除を `lake build` ごと回して**フルビルドと byte 一致** (実測) |
| 6 ✅ | 環境を常駐させて再抽出できる | **実装・実測済み** (`--serve`)。要求あたり **0.035〜0.088 秒** 対 単発 1.72〜4.60 秒、IR は単発と **byte 一致**、6 要求で汚染なし。**常駐環境は再読み込みできない**。段階 6a でパイプラインに組んで確定: **編集をまたいで生きたサーバは誤答する** (ラウンド 2 も含めて。所有者を環境から引くため) が、**`lake build` の後に立てて全ラウンドを任せると 7.940 → 6.168 秒 (−22%) で byte 一致** |
| 7 ◐ | **完成品の値を出す** — §6 から「出力範囲の差」と「外挿」の留保を外す | byte 再現率を上げ (準備で欠落を原因別に割った → §6.2。**最大項は §6.2 のリストに無かった `splitWhitespaces` 32.9 pt**)、意味解析 10.58 秒を割り、残る ◐ を閉じる |

1 と 2 が本命で、崩れたら仮説そのものを見直す。3 は「依存の規模から切り離す」価値の核。
5 は速度だけでなく**正しさ**の検証で、現行が失敗していた箇所 — **ここが端から端で閉じたことが
今の到達点**。段階 6 の撤退ライン「消える 3.1 秒が複雑さに見合うか」は段階 6a で決着:
**常駐の単位はパイプライン 1 回で、抽出ラウンドが 2 回以上あるときだけ得**。「プレビューが
常駐の受け皿」という段階 6 の結論は**同じ機構で否定された** (→ §8)。

## 8. 未解決の問い

| 問い | 分かっていること / 残っていること |
|---|---|
| **cold な環境ロード (13 秒) をどう扱うか** | **決着に近い (→ §3)。「CI は毎回 cold」は否定された**が、効いていたのは `cache get` の常駐率ではなく **`lake build` が import の hot set を読むこと**【Linux 実測】。**同じジョブなら 2.61 秒 / 別ジョブなら 63〜71 秒 = 24〜27 倍**なので、**第一の打ち手は配置** (doc 生成をビルドと同じジョブに置く)。**Lean の速度ではなく I/O の問題。残るのは 3 つ**: (a) **Linux での先読み** (macOS では −49.0%、`MADV_WILLNEED` の意味論が違うので移送できない)、(b) 分割配置を強いられる場合の **IR キャッシュ** (= 段階 5 と同じ機構)、(c) 完全版の抽出器でも同じ差が出るか (作業集合が 16 GiB に収まらず macOS では測れなかった)。**IR キャッシュには前提が 1 つ増えた** — olean の内容ハッシュは**チェックアウト先の絶対パスに依存する** (429/432 モジュール、実測 → §5.5)。CI と開発機でパスが違えば全滅するので、鍵をパス非依存にしない限り CI 側でのキャッシュヒットは 0 |
| **意味解析 (実測 10.58 秒) を減らせるか** | 最適化後の 77% がここになる以上、次に効くのはここしかない。equation 生成の切り替え、宣言単位のキャッシュ、出力に使わない情報の生成をやめる、あたりが候補 |
| **宣言の所有モジュールをどう決めるか** | 同名で複数の olean に焼かれる自動生成補題があり (実測 25 件)、索引方式では所有が一意に決まらない。「最初に定義したモジュールが勝つ」(現行 doc-gen4 の暗黙の規則) を踏襲するか否か。ページ配置とリンク先が変わる |
| ~~**常駐プロセスの寿命と安全性**~~ | **決着 (段階 6a)。寿命の上限は「自分が import した olean を書き換えるビルドまで」。** プロセスは死なず (`lake build` を生き延び 0.151 秒で応答、実測)、代わりに**答えが古くなる** — 参照の所有者を環境から引くため (`Extract.lean:1352`)、439 ページ中 1 ページが誤った【実測】。**死ぬより悪い失敗の仕方** (自信のある誤答)。安全なのは `lake build` の後に立てたサーバで、そのとき全ラウンドを任せられる。**残るのはソークテスト** (6 要求は 600 要求について何も言わない) |
| ~~**増分の影響集合をどう閉じるか**~~ | **決着。** 判断点 3 で「olean の内容ハッシュだけでは閉じない」が確定し (5 命題すべて否定)、§5.5 の 3 層に見直したうえで**増分 4〜7 で全層を実装、本物の移動と本物の削除でフルビルドと byte 一致まで実測**した。閉じ方は L3-1 (名前の所有権 → 再抽出のラウンド)、L3-2 (全域写像の差分 → 再生成集合)、L3-3 (全域成果物は毎回作り直す)。**逆索引の常備は不要だった** — 差分は小さく (削除 1 件で 58 名)、走査で足りる |
| **依存パッケージの写像をどう配布するか** | 各パッケージが自分の「宣言名 → URL」写像を公開する形が理想。**doc-gen4 の出力からは導ける** — `declarations/declaration-data.bmp` がまさにその写像で、依存側需要 533 件のうち 530 件を満たし、組んだ URL は doc-gen4 の href と 99.992% 一致 (段階 3 増分 2・3、実測)。**未決なのは「上流の公開サイトに同じファイルがあるか / バージョン対応が取れるか」**。取れないなら生成側で作る |
| **`_private.` 名のリンクをどうするか** | 除外 / 親に落とす / モジュールページのどれを取るかは未決 (実測 8 名 → §5.3) |
| **docstring 内のリンクをどう解決するか** | doc-gen4 は別経路 (`Output/DocString.lean`) で処理していて署名のタグ付けを通らないので、別の仕組みになる可能性が高い。**規模は実測できた** (段階 4 増分 1): 348 ページの内部アンカー 80,743 件のうち IR の名前集合 (5,300 エントリ) で解決できないのは **293 件 / 188 種 = 0.36%** で、**その全部が docstring 内** (署名と equations の取りこぼしは 0)。要るのは「署名に出てこない名前も引ける索引」であって、写像の作り方の問題ではない |
| **revision をページのバイトに埋めるか** | **計測済み (段階 6b)、決定は未。** 埋める限りコミットのたびに全ページ無効 (rev はページ内 4,992〜4,993 か所)。**プレースホルダ `{{SOURCE_URL}}` を埋めて配信時に注入する形なら、再生成は 433 → 0 ページ、パイプライン合計 1.6227 → 0.6441 秒 (−60.3%)、レンダリング段 0.9017 → 0.0256 秒、ページは 399,440 B 小さくなる**【すべて実測】。**実装コストはゼロ** — `--source-url` に定数トークンを渡すだけで renderKey からも rev が外れる。**代償は 3 つ、いずれも実測または特定済み**: (1) HTML 単体で完結しない (注入が走らなければリンク 4,993 本が死ぬ)、(2) 配信時に置換で注入する版は**丸ごと消えるわけではない** (0.1893 秒。JS 注入版なら消える)、(3) `jump-src.js` が実行時に `href` を読むので注入が先に走らないといけない (未検証) + `coverage.ts` の受け入れオラクルは注入後に回す必要がある (未検証)。**決めるのは「単体完結を失ってよいか」という製品判断**で、計測はその取り分を測っただけ |
| **Lean のバージョン差をどこで吸収するか** | IR スキーマとの対応付けの方針。未着手 |
| **プレビューモードを持つか** | 選択肢は **2 つに絞れた** (段階 6d)。**「常駐が受け皿」は否定** — 編集前の環境は編集前の olean の関数なので、**それが正しく出せるページは前回のビルドが既に書いたページと同一** (P が返した 1 モジュールは前回と byte 一致かつ誤り、実測)。残るのは (1) **構文ベースの近似** (未計測、コストは elaboration 無しの Lean パーサ) と (2) **前回のページを出して「未更新」と示す** — こちらは数字が付いた: **stale は 433 ページ中 6 = 1.39%**、うち **5 (83%) はビルド前に台帳だけで名指せる**【実測】。残る 1 は L3-1 の参照側で**原理的に事前に分からない** (自分の olean が変わらないから stale なので)。保守的に補うなら参照側集合 (この変更で 4 モジュール、IR にあり Lean 不要)。**表示はページ単位** — サイト全体のバナーは正しい 427 ページを無駄に警告する |

## 10. 補足 — 上流への還元

本プロジェクトを進めることと知見を上流に投げることは排他ではない。3 つある。

| | 内容 |
|---|---|
| **バッチ化** | 計測で使った「複数モジュールを 1 プロセスで抽出する」コマンドは、doc-gen4 の内部 API が**既に複数モジュールを受け取れる**ため CLI の定義を変えるだけで実現できた。つまり §6.4(a) の 78 倍のうちバッチ化による分は、doc-gen4 本体への小さな変更としても成立しうる |
| **`scoped notation`** | doc-gen4 は**パッケージ自身の `scoped notation` を出力できていない** (段階 2 で実測)。delaborator が `ScopedEnvExtension` にあり import だけでは未活性なのに `Lean.activateScoped` を呼んでいないため、`H(μ; X)` や `≐` と書けるはずの署名が `entropy μ X` / `DotEq a a` と出る。**呼ぶだけで直り、コストは意味解析 +6% (実測)** |
| **`collectTactics` の 16.7 秒** | **1 行の直し方で消える** (→ §5.2) — `env.header.moduleNames` をループの外に括り出し、`allTacticDocs` を 1 回だけ呼ぶ。`moduleNames` が `def` であることは Lean core 側の API の形の問題なので、**同じ罠を踏んでいるコードは doc-gen4 以外にもありうる** |
