## 1. 何を作るか

Mathlib に依存する Lean パッケージが、**自分のモジュールだけを短時間でドキュメント化できる**
ドキュメント基盤。依存ライブラリは再生成せず公開済みドキュメントへリンクする。主眼は HTML を
出すことではなく、**Lean の意味情報を再利用可能な形で抽出し、必要な部分だけを高速に更新できる
こと**。副産物として doc-gen4 が**出力できていないパッケージ自身の `scoped notation`** も出る
(実測 → §10) — 読者が実際に書く記法で署名が読めることは生成速度と同じくらい価値に効く。

## 2. 背景 — 計測が示したこと

doc-gen4 を計装して Mathlib 依存プロジェクト (432 モジュール) の生成を実測した (**この節はすべて
実測** → [`benchmarks/doc-gen4-report.md`](../benchmarks/doc-gen4-report.md))。コストは 3 層に
分かれ、どれも「ドキュメントを作る仕事」そのものではなかった。

| 層 | 支配率 | 実際に起きていること |
|---|---:|---|
| 環境ロード | **85.0%** | モジュールごとにプロセスを起動し、import closure 全体を読み直す |
| 意味解析 | 4.6% | 本来の仕事。宣言の型を pretty print し equation を生成する |
| 走査オーバーヘッド | 8.8% | 環境の全定数を舐めて、該当しないものを捨てる |

実ビルドでは **8.9 億回の定数走査に対して該当は 0.032%**、走査して捨てるコスト (1,195 秒) が
本来の意味解析 (631 秒) の約 2 倍あった。HTML 生成も生成 CPU の **66〜78% が DB からの読み直し**で
レンダリング自体は 9.2%。**増分性は一切ない** (無変更の 2 回目も 46.25 秒 → 43.91 秒)。

### 決定的だった 1 つの実験

doc-gen4 に「複数モジュールを 1 プロセスで抽出する」コマンドを足し、同一の 432 モジュールを
両方式で処理した。**モジュールごとに 1 プロセス (現行) が 1,076 秒 (うち `importModules`
908.6 秒 = 88.8%)、1 プロセスでまとめて 31.9 秒 (同 2.6 秒) = 34 倍**【どちらも全数の warm 実測、
外挿なし、同じ日・同じ page cache 状態】。**分母は「同じ 432 モジュールを抽出する仕事」。**
アルゴリズムの改良ではなく、同じ依存ライブラリを 432 回読み直すのをやめただけで生じる —
**432 モジュールぶんの import closure をまとめて読んでも 1 モジュールぶん (逐次時 2.10 秒) と
ほとんど変わらない** (closure が Mathlib に支配されているため)。**cold と warm を混ぜないこと。**

## 3. 仮説

> Lean の意味情報をパッケージ単位でまとめて抽出し、依存ライブラリを外部参照にすれば、
> downstream ライブラリのドキュメント生成時間を**依存ライブラリの規模から大きく切り離せる**。

計測はこの仮説を支持している。ただし完全には切り離せない — 自パッケージの型を正しく
pretty print するには Mathlib の `Environment` が要り、そのロードは残る。
**これが新設計の床**であり、それをどう扱うかが設計の中心的な論点になる。

床の大きさは **page cache の状態で 5 倍動く。warm で約 2.5 秒、cold で 10〜13 秒**
(実測 → 検証ログ 段階 1)。warm では壁時計 ≒ CPU 時間で、差はすべて olean の mmap ページイン待ち。
したがって「床をどう扱うか」は最初から 2 つの別問題である。

- **ローカル (warm)**: 2.5 秒。1 モジュールだけの再抽出ならこれより小さい (`importModules`
  0.80〜2.96 秒、実測・段階 5) が `lake env` の 0.96 秒が別にかかる (→ §6.5)。
  **常駐で消せるが、消さなくても致命的ではない。**
- **CI**: **page cache に olean が載っているかで決まる。常駐は効かない。**

**「CI は常に cold」は否定された。効いているのは olean が page cache にあるかどうかで、
それを決めるのは配置ではなくランナーのメモリだった。**2 段階で分かった:

**(1) 2026-08-10、`ubuntu-latest` / 2 コア / 7.75 GiB**【Linux 実測】 — doc 生成が見るのは
`cache get` 直後ではなく**ビルド後の page cache**で、**同じジョブなら `importModules` 2.610 秒
(macOS warm と同じ) / major fault 26、別ジョブでビルド済み olean を復元すると 20.4〜89.2 秒 /
fault 11,949〜30,424 = 8〜34 倍**。ここから「**第一の打ち手は配置**」を出した。
**この倍率の分母は n=1** (同じジョブ側は 1 つの run の 1 回だけ、別ジョブ側は 3 つの run に
またがる 7 回、**両側は別ワークフロー・別ランナー実体**)、測ったのは **`importModules` 単体**、
抽出器は凍結したプロトタイプ (IR schema 3)。

**(2) 2026-08-16、`ubuntu-latest` / 4 コア / 15.6 GiB、製品の `litedoc4 build` で n=5**【実測】 —
**8〜34 倍は再現しなかった。split/same は 1.08〜1.58 倍**、端から端では 0.83〜1.33 倍
(5 対中 3 対は split のほうが速い)。**機構は生きている** — 同じランナーで `drop_caches` した
陽性対照は **5.2〜11.9 倍** (fault 14,450〜37,240)。壊れたのは**「別ジョブは cold で始まる」
という前提**のほうで、別ジョブも `cache get` と artifact 展開で olean を**自分で書く**ので、
**RAM が足りればそのまま page cache に残る**。**メモリ 2 倍が、まさにあの倍率を決めていた変数だった。**

**したがって推奨は変わらないが、根拠が変わる** — 同じジョブに置くのは「別ジョブが遅いと
観測されたから」ではなく、「**cold の罰則が 5〜12 倍あり、別ジョブが cold になるかは
ランナーの RAM と作業集合の比で決まる**から」。配置はその比を**問わなくて済ませる**手。
測ったのは 1 ワークロード (422 モジュール / peak RSS 約 4.0 GB) なので、
**より大きいパッケージや RAM の小さいランナーでは (1) の側に戻りうる**。

効くのは**割合ではなく「どのページか」** (`lake build` が import の要るページを読む) —
常駐率は `cache get` 後 60.4% → ビルド後 **40.3%** と下がるのに fault はほぼ 0 で、
**`cache get` 直後の常駐率は代理指標ですらなかった** (n=2、容量律速)。

**先読みは「効くこともある」打ち手** — **ランナー実体で答えが割れる**【すべて実測。実体別の内訳は
検証ログ】。読ませる集合は **`.lean` ヘッダから作った import closure** (17,199 ファイル / 4.14 GB)。
**macOS/M1 は壁時計 18.03 → 10.44 秒**だが、**Linux の速い実体では −4%、遅い実体では −23〜−44%**
— 遅い実体では直列な demand fault を 16 並列の読みに置き換える価値が大きく、速い実体では closure
4.14 GB のうち要らない約 1.6 GB が節約を食い潰す。**実体は選べないので期待値としては効くが保証は
ない。「集合を絞れば効くか」は未検証** (絞った版は必要分を取りこぼしていて検証になっていない)。
**優先度は下がった** — 2026-08-16 のランナーでは `same` も `split` も major fault が 3 桁以下で
**先読みする相手がもう居ない** (効くのは cold の条件だけ)。**cold 側が `ubuntu-latest` でも
2 実体に割れる形は残っている** (readahead とストレージの差とみられる、未検証) が、単価差は
**5.3 ms ↔ 0.67 ms から 1.32 ms ↔ 0.38 ms に縮んだ** (n=5、検証ログ)。

## 4. Approach

> **Lean プロセスは「意味情報を吐く抽出器」に徹し、1 つの環境を長く使い回す。**
> 抽出したものはモジュール単位の中間表現 (IR) として永続化し、
> HTML・検索索引・その他の出力はすべて Lean の外側で IR から作る。
> 依存パッケージについては IR を作らず、「宣言名 → モジュール → URL」の写像だけを持つ。

変えるのは次の 3 つの境界。**どれも独立に効き、順に適用でき、1 つ失敗しても残りは成立する。**
(1) **プロセスの境界**: モジュールごと → パッケージごと (あるいは常駐)。(2) **抽出の範囲**:
環境の全定数 → 自パッケージの宣言のみ。(3) **Lean と出力の境界**: Lean が HTML まで作る →
Lean は IR まで、出力は外側。

設計に返ってきたものは各柱に畳んである: 1 (1 プロセスでまとめて抽出) → §5.1、2 (走査をやめ索引)
→ §5.2、3 (依存の IR なしでリンク解決) → §5.3、4 (IR から HTML、再生成に Lean 不要) → §5.6、

7 (完成品の値) → §6.2、8 (rev をバイトから外す) → §5.6。

## 8. 未解決の問い

**決着した問いはここから消した** — 常駐の寿命 → §5.1、増分の影響集合 → §5.5、**revision をバイトに
埋めるか → 外すと決定** (§5.5 + §5.6)、**プレビューモード → 持たない** (§9)、**検索 → 自パッケージ
のみ** (§5.6)、**宣言の所有モジュール / `_private.` 名のリンク / Lean のバージョン差 → v0.1 の範囲
として [実装計画](implementation-plan.md) §4 決定 5 が引き取った**、**外部リンクの版ズレ → 依存は
版固定 GitHub blob URL を指す** (§5.3、M7 で実装・実測)。経緯は git と
[検証ログ](verification-log.md) が持つ。

| 問い | 分かっていること / 残っていること |
|---|---|
| **cold な環境ロード (13 秒) をどう扱うか** | **決着した (→ §3)。「CI は毎回 cold」も「別ジョブは 8〜34 倍」も否定された** — 効いているのは olean が page cache にあるかどうかで、それを決めるのは配置ではなく**ランナーの RAM と作業集合の比**【製品の `litedoc4 build` 端から端で n=5 実測、2026-08-16】。**残るのは 2 つ、どちらも優先度が下がった**: (a) **先読みの集合を絞れるか** — 現ランナーでは `same` も `split` も major fault が 3 桁以下で**先読みする相手が居ない** (効くのは cold の条件だけ)、(b) 分割配置を強いられる場合の **IR キャッシュ** — 分割の罰則が 1.1 倍では割に合わない。**IR キャッシュには前提が 1 つ増えたままである** — olean の内容ハッシュは**チェックアウト先の絶対パスに依存する** (429/432 モジュール、実測 → §5.5)。CI と開発機でパスが違えば全滅するので、鍵をパス非依存にしない限り CI 側でのキャッシュヒットは 0 |
| **意味解析 (実測 10.58 秒) を減らせるか** | **半分決着 (段階 7d)** — 筋は算法でも生成物の削減でもなく**並列化**だった。`--jobs 4` で **10.79 → 3.34 秒 (3.23×)、IR は byte 一致**。**内訳は delaborate 55.3% / format 15.4% / タグ 12.7%** で、分布はほぼ一様 (上位 1% で 6.97%) なので**外れ値を潰す筋は無い**。equation を切る筋は却下 (並列後は −3.4% しか効かず再現率が 2.4 pt 落ちる)。**残るのは CPU 時間そのもの** — instructions は +1.0% しか動いておらず、4 スレッドで頭打ち (M1 の性能コア 4 本 + cycles +66% のストール) |
| **依存パッケージの写像をどう配布するか** | **決着した (→ §5.3)。生成側で作る** — 公開サイトの `declaration-data.bmp` は**ファイルはあるがバージョン対応が取れず** (公開は Lean 4.33.0 / mathlib `c3a9a08f`、対象は v4.31.0 / `fabf563a7c`)、**版別アーカイブも無い**【いずれも実測 → 検証ログ】。**2026-08-15 に実装して V1 成立** — 抽出器の `--link-index` が環境を走査して作る写像は bmp 由来のものと**共有 255,205 名すべてでモジュールが一致 (食い違い 0)**、同じ IR から作ったサイトが **438/438 バイト一致**【実測 → [結果ログ](milestone-log.md) M5-a】。索引は **8.51 MB / gzip 1.33 MB、作る 0.415 秒 / 読む 0.076 秒**、宣言 258,760、docstring の autolink が **410,114 B ぶん byte 一致**で過剰アンカー 0【段階 7c、実測】。**参照の 258,760 はこの対象の写像ではない** (`Lake.*` 3,523 名を含み、打ち切った doc 木は現行 432 モジュールに対し 348 ページしか持たない) ので、集合の総数を比較の分母に使わないこと |
| **docstring 内のリンクをどう解決するか** | doc-gen4 は別経路 (`Output/DocString.lean`) で処理していて署名のタグ付けを通らないので、別の仕組みになる可能性が高い。**規模は実測できた** (段階 4 増分 1): 348 ページの内部アンカー 80,743 件のうち IR の名前集合 (5,300 エントリ) で解決できないのは **293 件 / 188 種 = 0.36%** で、**その全部が docstring 内** (署名と equations の取りこぼしは 0)。要るのは「署名に出てこない名前も引ける索引」であって、写像の作り方の問題ではない |

## 9. 意図的にやらないこと

- **Lean フロントエンドの再実装** — 「パーサだけ持てば済む」は**実測で否定されている**。パーサは
  環境に依存し、`Init` だけの構成 (= パーサ相当) は **404 / 432 モジュールでパースエラー**、同じ
  バイト列から出る構文木のノード数が環境の厚さで **6.2 倍動く** (段階 7e)。`scoped notation` は
  import しても未活性で、`Lean.activateScoped` を呼ぶまで `H(μ; X)` も `≐` も出ない (段階 2 →
  §10)【いずれも実測。数字は [検証ログ](verification-log.md) 段階 7e (a) / 段階 2】
- doc-gen4 との表示互換 (**byte 再現率はオラクルであって製品目標ではない** → §6.2)
- **テーマシステム**、プラグイン機構 — サイトの見た目を**利用者が差し替える仕組み**は持たない。
  **明暗の切り替えは M8 で持った**が、それは仕組みではなく 1 枚の CSS の中の色の組で、
  差し替え口はどこにも開いていない (→ `plans/ui-redesign.md` 決定 1)
- レンダリングの高速化 (計測上、生成 CPU の 9.2% にすぎない)
- あらゆる Lean バージョンへの後方互換
- **プレビューモード** (ビルドを待たずに出す) — 段階 6d / 7e で両案を実測したうえで**持たない**と
  決めた。「常駐が受け皿」は否定され (編集前の環境が正しく出せるページは前回のビルドが既に書いた
  ページと同一)、構文近似は**プレビューではなくアウトライン** (宣言名 95.7% / 偽陽性 0 だが署名の
  byte 一致は 7.5%、**37.2% の宣言は型クラス仮定が `variable` にありソースに書かれていない**)、
  stale バナーは 433 ページ中 6 = 1.39% にしか効かない【いずれも実測。数字は検証ログ】。**編集 →
  表示の臨界パスは 74〜98% が `lake build`** なので、迂回しない限り体感は変わらない (→ §6.5)

## 10. 補足 — 上流への還元

本プロジェクトを進めることと知見を上流に投げることは排他ではない。3 つある。
